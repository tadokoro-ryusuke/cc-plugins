# Design Review — 視覚成果物の審査

**鉄則: このスキルは「生成」ではなく「審査」を担当する。**

- UI の実装・スタイル提案・スライド生成は、生成系スキル(ui-ux-pro-max / frontend-design 等)や通常の実装フローに任せる。
- 本スキルは、生成された UI・スライド・文書を **ルール化された基準で審査し、修正指示に変換する**。
- なぜ: AI が「それっぽい成果物」を数分で量産できる時代、品質の差は生成力ではなく **取捨選択と一貫性の担保** で決まるため。

## Step 0: 対象と前提の確認

審査を始める前に以下を揃える(足りなければユーザーに要求する):

1. **現物**: スクリーンショット、ライブ URL、HTML/CSS ソース、PDF のいずれか
2. **用途と読者**: 業務システムか LP か。対面プレゼン用か送付資料か。誰が1日何回使うか
3. **制約**: ブランドカラー指定、既存デザインシステム・テンプレートの有無

なぜ: 同じ画面でも読者と利用頻度で正解が逆転する(業務ユーザー向けは余白より情報密度が正義の場合がある)ため、基準の適用前に文脈を固定する。

## Step 1: 4原則(CRAP)チェック

すべての視覚成果物に適用する第一関門。「作る時」ではなく「見直す時」に使う。

| 原則 | チェック項目 | 判定基準 |
|---|---|---|
| **近接 (Proximity)** | 関連する要素は近く、無関係な要素は遠いか | **グループ内 : グループ間の余白 = 1 : 2〜3** で機械的に判定する |
| **整列 (Alignment)** | すべての要素が見えないグリッド線に揃っているか | **左揃えを基本**とし、中央揃えの乱用がないか。「なんとなくダサい」の原因第1候補 |
| **反復 (Repetition)** | 色・フォント・余白・装飾のパターンが全ページ/全画面で一貫しているか | ページごとにレイアウトが違う提案書、画面ごとにボタンの見た目が違う UI は反復違反 |
| **コントラスト (Contrast)** | 違うものは思い切り違うか | 強調は **明確な差(サイズ2倍・太字・濃度差)にするか、完全に同一にするか** の二択。中途半端な差が最悪 |

頻出違反として必ず疑うもの:

- 中央揃えの乱用(整列の弱体化)
- 余白を恐れた詰め込み(近接の破壊)。1ページの情報量を減らしページ数で稼ぐ方向を提案する
- 強調箇所の増やしすぎ=全部強調で無強調(コントラストの自殺)
- ページ/画面ごとの「工夫」によるレイアウト変更(反復違反)

なぜ: 4原則は素人っぽさの大半を説明でき、違反を言語化できるためクライアントへの修正説明にそのまま使えるため。

## Step 2: タイポグラフィ下限チェック

文字は成果物の面積の大半を占めるため、タイポグラフィの巧拙が「素人っぽさ」の最大要因になる。以下を **下限(交渉の余地がないライン)** として検査する:

- [ ] フォントは **1成果物に最大2ファミリー**、ウェイトは 2〜3種(Regular + Bold 基本)以内か
- [ ] 和文本文の `line-height` は **1.5〜1.9** か(見出しは 1.2〜1.4 に詰める)。1.2 のままは英文向け設定の放置を疑う
- [ ] 行長は **全角 35〜45 字**(欧文 45〜75 文字)に収まっているか
- [ ] **和欧混植スタック**になっているか: 英数字に専用の欧文フォントを当て、欧文を先に書く(例: `font-family: Inter, "Noto Sans JP", sans-serif`)。数字が多い見積書・ダッシュボードで効果大
- [ ] **全角英数字が使われていないか**(使用は一律 NG)
- [ ] MS Pゴシックが残っていないか。迷ったら Noto Sans JP、読みやすさ配慮が必要なら BIZ UD 系
- [ ] スライドの場合: 游ゴシック Light 等の細ウェイトを本文に使っていないか(プロジェクタでは Medium 以上)

なぜ: これらは好みではなく可読性の下限であり、機械的に検査・修正指示できるため。

## Step 3: 配色下限チェック

色は「量とルール」の問題として検査する。以下を下限とする:

- [ ] **60-30-10 ルール**: ベース(背景・余白)60% / メイン(ブランド色)30% / アクセント(CTA・強調)10% の面積配分か。アクセントは全体の1割までの上限として運用する
- [ ] **コントラスト比**: 通常テキスト **4.5:1 以上**、大きいテキスト(24px 以上または 18.5px 太字)と UI コンポーネント **3:1 以上**(WCAG AA)。美観ではなく品質基準として扱う
- [ ] **色のみの情報伝達禁止**: 赤/緑の対比だけで意味を伝えていないか。色+形状/ラベルの冗長符号化を要求する(日本人男性の約5%が P型・D型色覚)
- [ ] **高彩度色の広面積使用禁止**: 60% を占めるべきは低彩度。彩度の高い色が背景や大面積に使われていたら指摘する
- [ ] 白背景の薄グレー文字(`#999` 等)がコントラスト不足になっていないか。テキストは `#000` ではなく `#1a1a1a`〜`#333` 程度が目安

ブランド色がコントラスト下限を満たさない場合は「テキスト・ボタンには暗めの派生色、装飾面にオリジナル色」という役割分担で両立を提案する(採否の判断とクライアント説明は人間の仕事 → 分担線参照)。

なぜ: 配色の失敗は例外なく「配分オーバー」か「下限割れ」に還元でき、数値で判定できるため。

## Step 4: UX法則レビュー(挙動と構造の審査)

画面の挙動・構造は以下の観点表でスキャンし、違反には法則名を根拠として添える:

| 法則 | レビュー観点 |
|---|---|
| **ヤコブの法則** | ログイン・カート・検索など定番機能が他サイトの慣習から逸脱していないか。「独自 UI にしたい」への反論根拠 |
| **ヒックの法則** | 選択肢・メニュー項目が多すぎないか。フォームのステップ分割・選択肢の削減を提案する |
| **フィッツの法則** | タップターゲットは十分な大きさか(推奨 44×44pt、WCAG 2.2 の下限は 24×24px)。主要ボタンは届きやすい位置か |
| **ミラーの法則** | 一度に提示する情報が 7±2 チャンクを超えていないか。電話番号・カード番号は分割表示か。ナビは 5〜7 項目か |
| **ゲシュタルト原則** | 近接・類同・共通領域によるグルーピングが意味構造と一致しているか。同色ボタン=同種機能になっているか |
| **テスラーの法則** | 「シンプルにして」の結果、複雑さがユーザー側に押し付けられていないか。自動入力・賢いデフォルトで開発側が複雑さを引き受けているか |
| **ピークエンドの法則** | 完了画面・エラー時の体験が磨かれているか。体験の記憶はピークと終わりで決まるため、ここを優先的に指摘する |

注意: 法則を後付けの正当化に使わない。業務システムではヒックの法則より一覧性が正義のこともある(Step 0 の文脈判断に従う)。

なぜ: UX リサーチに工数を割けない体制では、法則群が「調査の代わりの事前知識」と「合意形成の説得材料」を兼ねるため。

## Step 5: AI生成UIの定番欠陥スキャン

AI が生成した UI・スライドをレビューする場合は、以下の既知の欠陥パターンを重点的に検査する:

1. **英文向け行間の放置**: 和文なのに `line-height` 1.2 前後のまま(和文は 1.7 前後が目安)
2. **ボーダー(罫線)過多**: 区切りを線に頼りすぎている。余白か背景色差での区切りに置き換えさせる
3. **全ボタン同強度**: primary 相当のボタンが画面に複数ある。primary は画面に1つ、他は secondary/ghost に落とす
4. **ARIA の過剰付与・誤用**: 不要な `role` の付与等。ネイティブ HTML 要素優先のルールで削らせる
5. **影の使いすぎ・不統一**: 影が 2〜3 段階のスケールに収まっていない
6. **「AI デフォルト見た目」の放置**: フォント・角丸・primary 色がテンプレートのままで既視感がある。この3点の変更を指示する
7. **エッジケースの未デザイン**: データ0件・長すぎる名前・ローディングの状態が設計されていない。素人 UI と業務品質 UI の差が最も出る箇所

なぜ: AI 生成 UI の欠陥は毎回ほぼ同じ箇所に出るため、パターンとして先回りスキャンする方が速く漏れがない。

## Step 6: アクセシビリティ(WCAG 2.2 AA)最低ライン+機械検証

実務の目標適合レベルは **AA** とする(AAA は部分適用のみ、全面 AAA を約束しない)。以下の 8 項目を最低ラインとして検査する:

1. 画像に適切な `alt`(装飾画像は空 alt)
2. コントラスト比: 本文 4.5:1 / UI・大きい文字 3:1(Step 3 と同一基準)
3. キーボードのみで全操作可能+フォーカスインジケータを消さない(`outline: none` は違反)
4. フォーム要素に `label` を関連付ける(プレースホルダをラベル代わりにしない)
5. 見出し階層(h1→h2→h3)とランドマークの正しい使用
6. 色だけで情報を伝えない
7. タップターゲット 24×24px 以上(推奨 44×44)
8. `lang="ja"` とページタイトルの設定

**機械検証を必ず実行する**(Web の場合):

- axe DevTools / Lighthouse を実行し、違反ゼロを確認して実行結果を証拠として提示する
- ただし自動テストで検出できるのは問題の 3〜4 割にすぎない。キーボード操作の手動確認、可能ならスクリーンリーダー(macOS VoiceOver)での主要フロー確認を重ねる
- 継続案件では CI への axe 組み込みを提案する(回帰防止)

法令面の注意(目安、2026年時点・最新動向は要確認): 日本では改正障害者差別解消法(2024年4月施行)により民間事業者にも合理的配慮の提供が義務化され、EU 向けには European Accessibility Act(2025年6月施行)がある。契約書に「WCAG 完全準拠を保証」と書くことは避け「準拠を目指す/試験実施」とするのが実務の型だが、**これは法的助言ではなく実務の型であり、契約上どこまで約束するかの最終判断は専門家(弁護士等)と自組織の契約レビュープロセスに委ねる**。

なぜ: アクセシビリティは基準が明文化された数少ない品質下限であり、機械検証の証拠がそのまま納品エビデンスになるため。

## Step 7: レビュー結果の報告と修正指示への変換

指摘は以下の優先度で並べて報告する:

- **Must**: 下限違反(コントラスト比、WCAG 8項目、全角英数字等)。数値基準を割っているもの
- **Should**: 4原則違反・UX法則違反。体験と信頼感を損なうもの
- **Consider**: トーン・好みに属する改善提案

各指摘は次のテンプレートで書く。クライアントにそのまま転送できる形にする:

```
【指摘】 (何がどう問題か、1文で)
【根拠】 (原則・法則・基準名を引用: 例「整列の原則」「フィッツの法則」「WCAG 2.2 AA コントラスト比 4.5:1」)
【修正指示】 (具体的な変更内容。可能な限り数値で: 「グループ間余白を 8px→24px に」)
【期待効果】 (クライアントに伝わる言葉で1文: 「視線が迷わず金額まで最短で届く」)
```

クライアント向け説明文の例: 「見出しと本文の整列が崩れているため視線が迷います。左端を1本のグリッド線に揃えることで、読み手が内容に集中できます(整列の原則)」

注意: 法則名の引用は1つの説明につき 1〜2 個まで。引用しすぎると衒学的になり説得力が落ちる。

なぜ: レビューの価値は指摘の数ではなく「相手が納得して直せること」で決まるため、根拠と数値を必ずセットにする。

## 分担線: AI がやること / 人間にしか決められないこと

**AI(このスキルを実行するエージェント)がやること:**

- スクリーンショット/ソースに対する 4原則・タイポグラフィ・配色・UX法則の違反検出
- コントラスト比の全数検証、axe / Lighthouse の実行と結果整理(決定的ロジックは機械検証に落とす)
- フォント監査(全角英数字・MS Pゴシック・行間の残存チェック)
- A案/B案の法則ベース比較、修正説明文(Step 7 テンプレート)の起草
- alt テキスト・ARIA の起案と「ネイティブ HTML 優先」ルールでの検証

**人間にしか決められないこと:**

- **どの情報グループを近接させるか**=情報の意味構造と序列の決定(クライアントの意思決定に効く序列はヒアリングした人間しか知らない)
- 書体・トーンの文化的判断(この業種にこのトーンは適切か。例: 金融に蛍光色は不可)
- ブランド色が下限を満たさないときの調整交渉と、その旨のクライアント説明
- 法則同士が衝突したときの優先順位(同じ画面でもユーザー熟練度で結論が逆転する)、クライアントの政治的事情との落とし所
- 契約でアクセシビリティをどこまで約束するかのリスク判断(専門家への相談を含む)
- alt テキストの「適切さ」の最終判断と、スクリーンリーダーでの体験品質評価

なぜ: AI は基準への適合は判定できるが、文脈上の意味・文化・交渉はレビュー対象の外側にあり、そこを誤ると基準適合でも成果物として失敗するため。

## 他スキルとの境界

重複する内容はここに書かない。以下へ1行で送る:

- コードの品質・セキュリティレビュー → dev-core:code-review / dev-core:verify 参照
- UI コンポーネントの実装パターン(状態管理・フォーム等) → dev-core:frontend-patterns 参照
- UI の生成・スタイル/パレット提案 → ui-ux-pro-max / frontend-design(本スキルは生成しない)
- 画面設計プロセス・外部設計書の作り方 → dev-core:external-design-deliverables 参照
- 提案書・スライドの論理構成と作成手順 → business-doc-design 参照(本スキルは出来上がった見た目の審査のみ)
- アクセシビリティ要件の合意・契約への落とし込み → delivery-core:client-alignment 参照+専門家判断
- デザイン対応の工数・金額の判断 → 自組織の見積・価格判断プロセスへ(本スキルでは扱わない)
