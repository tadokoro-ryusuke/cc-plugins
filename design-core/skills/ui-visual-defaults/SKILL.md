# UI Visual Defaults — 標準ビジュアル設定の確定とトークン化

**鉄則: プロジェクト冒頭に一度決めて固定し、以後は個別調整を禁止する。**

- なぜ: デザインはセンスではなくシステム(制約されたスケール)。事前に決めた段階から選ぶだけにすれば、誰がやっても一定品質になる。「決めて固定する」ことが品質と速度の両立手段。
- このスキルの成果物は **デザイントークン一式(CSS カスタムプロパティ / Tailwind 設定)+ コントラスト検証エビデンス**。UI の生成は生成系スキル(ui-ux-pro-max:ui-ux-pro-max 等)、生成物の審査は design-core:design-review に送る。
- コンポーネントの実装パターン(状態管理・フォーム・データフェッチ)→ dev-core:frontend-patterns 参照。
- 提案書・スライド・報告書のデザイン → design-core:business-doc-design 参照。

## Step 0: 前提の確認

決定を始める前に以下を確認する(足りなければユーザーに聞く):

1. **ブランドカラーの有無**: クライアントのロゴ色・ブランドガイドライン。ゼロから色を選ぶ場面はむしろ少ない
2. **案件種別**: 業務システム / ブランドサイト・LP / 社内ツール。フォントと情報密度の正解が変わる
3. **UD 配慮の要否**: 公共案件・幅広い年齢層向けか
4. **既存デザインシステムの有無**: あればそれが正本。このスキルは欠けている部分の補完のみ行う

なぜ: 同じ判断でも案件種別と利用者で結論が逆転するため、基準の適用前に文脈を固定する。

## Step 1: 標準スタックの決定

**既定: shadcn/ui + Tailwind CSS。** 理由を添えて確定する:

- Radix UI ベースでアクセシビリティが組み込み済み → **フォーカス管理・ARIA・キーボード操作系の要件をデフォルトで満たしやすい**(コントラスト・alt・見出し階層は別途担保が必要)
- コードを自分のリポジトリにコピーして所有する方式で、依存の陳腐化に強い
- Tailwind のユーティリティは「制約されたスケールから選ぶ」ことの強制装置になる

**3点変更で既視感を消す。** shadcn/ui デフォルトのままだと「AI っぽい見た目」になるため、必ず以下の3点だけ変更する:

1. **フォント** → Step 2 の決定木で選定
2. **角丸(radius)** → プロダクトのトーンに合わせ1値を選び全体に適用(シャープ=堅め、大きめ=フレンドリー)
3. **primary 色** → Step 4 でブランド色から生成

なぜ3点か: タイポグラフィと色が「素人っぽさ」の8割を決める。3点以外を触るとカスタム地獄に入り、既製システムを選んだ工数メリットが消える。

独自デザインへの投資は、ブランド性が本当に必要な LP・サービスサイトのみ。業務システムは既製一択。

## Step 2: フォント選定(決定木)

上から順に判定し、最初に該当したものを採用する:

1. **業務システム / 表示速度優先** → **システムフォントスタック**(Web フォント読み込みなし)。日本語 Web フォントはサブセット化しても重いため
2. **UD 配慮が必要(公共・幅広い年齢層)** → **BIZ UDゴシック / BIZ UD明朝**(Windows 標準搭載のモリサワ製 UD フォント)。Windows 以外の環境には **Web フォント配信で届ける**(Google Fonts で BIZ UDPGothic / BIZ UDMincho が配信されている)。配信しない場合は**フォールバック順を明示する**(例: `font-family: "BIZ UDPGothic", "Noto Sans JP", sans-serif;`)。なぜ: 指定するだけでは Windows 以外の利用者に UD フォントが届かず、UD 配慮という前提が崩れるため
3. **上記以外の一般 UI** → **Noto Sans JP(和文)+ Inter(欧文)**。デジタル庁デザインシステムも本文書体に採用しており、客先に「行政も使う無難で高品質な選択」と説明できる
4. **ブランドサイト・LP** → Noto Sans JP をサブセット配信。個性的なディスプレイ書体はヒーロー・見出しのみに限定し、本文は無難な書体で固定する

共通ルール(違反したら差し戻す):

- [ ] 1成果物にファミリーは **最大2つ**、ウェイトは **2〜3種**(Regular + Bold が基本)
- [ ] **MS Pゴシックは使わない**(Office 資料の書体選定は design-core:business-doc-design へ)
- [ ] 和欧混植: 英数字には専用の欧文フォントを当てる。**欧文を先に書く** — `font-family: Inter, "Noto Sans JP", sans-serif;` 数字が多い画面(ダッシュボード・帳票)で効果が大きい

なぜ決定木か: 書体選定を「センス」から「案件条件による分岐」に変換し、迷いと個人差を消すため。

## Step 3: タイプスケールとスペーシングの既定値

**任意の値を禁止し、以下のスケールからのみ選ぶ。**「17px か 18px か」という不毛な判断を消すため。

| トークン | 既定値 |
|---|---|
| タイプスケール(7段階) | **12 / 14 / 16 / 20 / 24 / 32 / 48px**(本文 16px 基準) |
| ジャンプ率(見出し/本文) | **150〜200%**。高い=元気・訴求的(LP)、低い=落ち着き(業務・報告) |
| スペーシング(4px 基準) | **4 / 8 / 12 / 16 / 24 / 32 / 48 / 64px** |
| 近接の余白比 | グループ内 : グループ間 = **1 : 2〜3** |
| 影・角丸 | それぞれ **2〜3段階**に固定(使いすぎ・不統一の防止) |

運用ルール:

- 余白は多めから始める。詰まった UI を広げるより、広い UI を詰める方が簡単。迷ったら倍にする
- 強調は「サイズ・太さ・色(濃度)」の3レバーで作る。ラベルを薄く値を濃く。中途半端な差は最悪 — 明確に差をつけるか完全に同一にするかの二択
- 区切りはボーダー(罫線)ではなく余白か背景色差を優先する

## Step 4: カラーパレット生成(ブランド色 → 明度スケール)

定型手順で機械的に生成する。**色数を増やすことは常に悪手側に倒す。**

1. **primary**: クライアントのブランド色(ロゴ色)を置く
2. **明度スケール生成**: HSL に分解し、同一色相で明度だけ変えた **50〜900 の9〜11段階**を作る(Tailwind CSS のカラースケールがこの実装例。そのまま借りてよい)
3. **色付きグレー**(Refactoring UI 流): 純粋な `#808080` 系ではなく、**ブランド色をわずかに混ぜたグレー**のスケールを作る。画面が安っぽくならない。テキストは真っ黒 `#000` ではなく `#1a1a1a`〜`#333` 程度
4. **セマンティックカラー**: success / warning / error の3色を追加して終わり
5. **配分ルール(60-30-10)**: ベース(背景・余白)60% / メイン(ブランド色)30% / アクセント(CTA・強調)10%。「アクセントは全体の1割まで」という上限として使う。60% を占める色は低彩度にする

- [ ] 彩度の高い色を広面積に使っていないか
- [ ] primary ボタンは1画面に1つか(全ボタン同強度は禁止)
- [ ] 赤と緑の対比だけで意味を伝えていないか — 日本人男性の約5%が P型・D型色覚。**色+形状/ラベルの冗長符号化**を原則にする

## Step 5: コントラスト比の機械検証とダークモード派生

### コントラスト検証(決定的ロジック — 目視で判定しない)

下限は美観ではなく品質基準であり、交渉の余地がない:

- 通常テキスト: **4.5 : 1 以上**(AA)
- 大きいテキスト(24px 以上 または 18.5px 太字)・UI コンポーネント・図形: **3 : 1 以上**

生成した全ペア(テキスト色 × 背景色、ボタン文字 × ボタン地)を機械検証する。WCAG 相対輝度の計算は決定的なのでスクリプトで行う:

```bash
# WCAG コントラスト比(前景 背景 の16進2色を渡す)
node -e '
const L=h=>{const c=[1,3,5].map(i=>parseInt(h.slice(i,i+2),16)/255)
  .map(v=>v<=0.03928?v/12.92:((v+0.055)/1.055)**2.4);
  return 0.2126*c[0]+0.7152*c[1]+0.0722*c[2]};
const [a,b]=process.argv.slice(1);
const [x,y]=[L(a),L(b)].sort((p,q)=>q-p);
console.log(((x+0.05)/(y+0.05)).toFixed(2));
' "#1a1a1a" "#ffffff"   # => 17.40 (合格)。"#999999" × 白 は 2.85 で不合格
```

補助ツール: WebAIM Contrast Checker / Chrome DevTools のコントラスト検査。検証結果は納品時のエビデンスとして保存する。

**ブランド色が下限を満たさない場合**(例: 薄いオレンジ): テキスト・ボタンには暗めに調整した派生色を使い、装飾面でオリジナル色を使う、と役割分担で両立させる(正本は design-core:design-review)。**この調整判断とクライアント説明は人間の仕事**(→分担線セクション参照)。

### ダークモード派生ルール

- **単純な色反転は禁止** — 必ず破綻する
- ライトモードの明度スケールを逆方向に再割当てし(明るい背景トークン←→暗い背景トークン)、**全ペアのコントラスト比を再検証**する。派生パレットの生成と全数検証は AI に任せられる
- 以下は一般的な目安(要確認): 背景は純黒 `#000` ではなく色付きダークグレーにする / 広面積の彩度をライトモードより下げる / 影ではなく明度差(surface の段階)で階層を作る

## Step 6: アクセシビリティ要件をトークンの前提条件として織り込む

**WCAG 2.2 AA 最低ラインセット・axe / Lighthouse による実地検証・法令面の注意は design-core:design-review(Step 6)が正本。** 本スキルは画面を生成しないため、ここでは**トークンで担保できるものだけ**を前提条件として織り込み、担保方法メモを残す。

トークン側で担保する前提(Step 3〜5 の決定に織り込む):

| トークン | 満たすべき前提 |
|---|---|
| テキスト色 × 背景色のペア | 本文 4.5 : 1 / 大きいテキスト・UI 3 : 1(Step 5 で機械検証済み) |
| フォーカスリング色(`--ring` 等) | 隣接背景に対し 3 : 1 以上。`outline: none` で消さない前提で定義する |
| タップターゲット寸法(ボタン・アイコンボタンの最小高さ) | **24×24px 以上(推奨 44×44)** — WCAG 2.2 新基準 |
| 本文の行間・行長(Step 7) | 和文行間 1.5 以上 |
| セマンティックカラー(Step 4) | 色だけで情報を伝えない前提(色+形状/ラベルの冗長符号化) |

**担保方法メモを残す**: 上記の各項目を「コンポーネント基盤(shadcn/ui)で担保 / トークンで担保 / 実装ルールで担保」のどれで満たすかを1行ずつ書く。
なぜ: トークンでは満たせない項目(`alt`・見出し階層・ランドマーク・`label` 関連付け・`lang="ja"`)を「担保済み」と誤認させないため。

- **実地検証(axe / Lighthouse・キーボード操作の手動確認・スクリーンリーダー)は design-core:design-review へ送る。** 本スキルでは実行しない。CI への組み込みは dev-core:verify の検証フローに載せる
- ARIA は過剰・誤用しがち(不要な `role` 付与等)。**ネイティブ HTML 要素優先**をトークン確定時の実装ルールに含める

## Step 7: 和文向け CSS 定数

AI コーディングエージェントはデフォルトで英文向けの詰まった行間を出しがち。以下を定数としてトークンに含め、生成品質を底上げする:

```css
:root {
  /* 和欧混植スタック(欧文を先に) */
  --font-sans: Inter, "Noto Sans JP", sans-serif;
  /* 和文行間: 本文 1.5〜1.9(WCAG も 1.5 以上を推奨)。1.7 前後を既定に */
  --leading-body: 1.7;
  --leading-heading: 1.3;   /* 見出しは 1.2〜1.4 に詰める */
  /* 行長: 和文 全角35〜45字(欧文 45〜75 文字) */
  --measure-body: 40rem;    /* 16px 基準で全角約40字。目安・案件で調整 */
}
```

- [ ] 本文 `line-height: 1.2` のまま放置していないか(和文には狭すぎる — AI 生成 UI の定番欠陥)
- [ ] 全角英数字が混入していないか
- [ ] スマホでは行長が自然に短くなるので行間をやや詰めてよい
- [ ] 約物の空き調整(`font-feature-settings: "palt"` 等)は Web ではやりすぎない

## 完成条件(Definition of Done)

以下がすべて揃ったらこのスキルの仕事は完了。以後の個別調整は禁止し、変更はトークンの改訂として行う:

- [ ] デザイントークン一式(CSS カスタムプロパティ or Tailwind 設定): フォントスタック / タイプスケール / スペーシング / 角丸・影 / カラースケール(primary 50〜900・色付きグレー・semantic)/ 和文定数
- [ ] ライト・ダーク両モードのコントラスト検証結果(スクリプト出力 or チェッカーのエビデンス)
- [ ] アクセシビリティ前提の担保方法メモ(コントラスト比・フォーカスリング色・ターゲット寸法トークンを、コンポーネント基盤で担保 / トークンで担保 / 実装ルールで担保のどれで満たすか。実地検証は design-core:design-review)
- [ ] 決定理由の1行サマリ(なぜこのフォント・この radius・この primary か — クライアント説明にそのまま使う)

完成したトークンでの UI 生成 → 生成系スキルへ。生成物の審査 → design-core:design-review へ。

## AI がやること / 人間にしか決められないこと

| AI に任せる | 人間にしか決められない |
|---|---|
| ロゴ色からの明度スケール・色付きグレー・ダークモード派生パレットの生成 | 書体の「声色」の最終選定(この客にこの書体はカジュアルすぎないか) |
| タイプスケール・スペーシングの CSS / Tailwind 設定への落とし込み | 業種とトーンの文化的判断(金融に蛍光色は不可、等) |
| コントラスト比の全数機械検証(全ペア・ライト/ダーク両方) | ブランド色がコントラスト下限を満たさないときの調整交渉とクライアント説明 |
| 既存コードのフォント監査(MS Pゴシック残存チェック等) | 「この画面は誰が1日何回使うか」に基づく情報密度の判断(業務システムは余白より密度が正義の場合がある) |
| 和文定数の一括適用、エッジケース(空状態・長い名前)の網羅生成 | 契約上どこまで約束するかのリスク判断(→専門家エスカレーション) |

なぜ分担線を引くか: AI は「平均的にきれいな設定」を量産できるが、案件固有の文脈(業種・利用者・契約)はヒアリングした人間しか知らないため。

## 報告フォーマット

トークン確定時は以下の構成で報告する。**実際に検証した証拠だけを書くこと**:

- 【スタック】採用基盤と3点変更の内容(フォント / 角丸 / primary)
- 【決定木の判定】フォント選定でどの分岐に該当したか
- 【トークン】ファイルパスと主要値(タイプスケール・スペーシング・カラースケール)
- 【検証】コントラスト比の実測値(全ペア、ライト/ダーク両方)とアクセシビリティ前提の担保方法メモ(実地検証は design-core:design-review へ)
- 【残課題】人間の判断待ち事項(書体の声色確認・ブランド色調整の要否 等)
