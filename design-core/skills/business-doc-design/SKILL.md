# Business Doc Design — ビジネス文書・スライドのデザイン

**鉄則: 情報量はページ数で稼ぐ。1枚に詰め込まない。**

受託開発では提案書・報告書が「営業担当者」そのものであり、文書デザインの品質が信頼に直結する。
本スキルの目的はデザイナーとして戦うことではなく、**「素人っぽさで信頼を失わない最低線」をテンプレートとルールで保証する**こと。

## Step 1: 文書種別を判定する

作り始める前に、必ずどちらの型かを決める。**最適解が種別で逆転する**ため、混ぜると両方失敗する。

| | プレゼン型 | ドキュメント型 |
|---|---|---|
| 用途 | 登壇・対面提案(話者が補足する) | 送付・回覧(単独で読まれる) |
| 情報密度 | 図中心・文字最少 | 文字多め・自立可読 |
| 1ページの役割 | 視覚補助(スライドは読ませない) | 完結した説明単位 |
| 典型例 | 提案プレゼン、キックオフ資料 | 送付用提案書、報告書、議事録 |

- 迷ったら確認する: 「この資料、その場で説明しますか? 先方に送って読んでもらいますか?」
- 送付もするプレゼン資料は、本文を削ぎ落とし、詳細を Appendix に逃がす(意思決定者は本文しか読まない)。

## Step 2: メッセージを設計する(アサーション・エビデンス構造)

レイアウトより先にメッセージを固める。**1スライド(1ページ)1メッセージ**を厳守する。

1. **タイトルに結論を書く**。「〜について」「現状分析」のような話題タイトルは禁止。
   - NG: 「保守費用について」
   - OK: 「現行システムの保守費は3年で回収可能」
2. 本文(ボディ)には**タイトルの主張を支える証拠だけ**を置く(図・表・データ)。
3. 1枚に主張が2つ以上あれば、ページを分割する。削るのではなく分ける。

なぜ: タイトルだけ拾い読みしても論旨が通る資料になり、読み手の認知負荷が最小になる。

## Step 3: 図解パターンを判定する

文章を先に書き、「この関係はどのパターンか」を判定してから図に変換する。**判定→変換の2段階にすると再現性が出る**。

| # | パターン | 判定基準(関係の種類) | 変換先 |
|---|---|---|---|
| 1 | **列挙** | 並列で順序なし(特徴・メニュー) | 箇条書き / アイコン格子(CSS グリッド)。Mermaid 不要 |
| 2 | **フロー** | 手順・時系列・状態遷移 | Mermaid `flowchart LR`(横)/ `TD`(縦)、`sequenceDiagram`、`gantt` |
| 3 | **比較** | A vs B、選択肢の評価 | 比較表(軸を列に)/ 2カラム vs レイアウト。マトリクスは表で |
| 4 | **階層** | 親子・包含的な分類・組織 | Mermaid `flowchart TD`(ツリー)/ ピラミッド図 |
| 5 | **循環** | 繰り返すサイクル(PDCA 等) | Mermaid `flowchart` を環状に結線 / 円環レイアウト |
| 6 | **包含** | 集合の重なり・入れ子(ベン図・同心円) | SVG / 手描き清書(Mermaid 不向き) |
| 7 | **相関** | 量的関係・因果ループ | 散布図・グラフ(チャート生成は dataviz 系の知見を使う)/ 因果は `flowchart` |

- 誤選択が最も多い失敗: 手順(フロー)なのにベン図、比較なのに列挙。判定基準は「要素間の関係」であって見た目の好みではない。
- Mermaid / PlantUML / draw.io で図をテキスト管理する。なぜ: バージョン管理でき、AI が生成・修正しやすい。
- 提案書の「顔」になる図(表紙直後の全体像など)だけは手で清書してよい。それ以外はコード生成で統一する。

## Step 4: 和文資料ルールを適用する

和文資料に特化した実務ルール(『伝わるデザインの基本』系の定石)。全ページに機械的に適用する。

- **箇条書きは2階層まで**。3階層必要になったら、ページ分割か図解への変換を検討する。
- **囲み(枠線)は最小限**。グルーピングは罫線ではなく**余白**で作る(グループ内:グループ間の余白 = 1:2〜3)。
- **整列**: 左揃えを基本にし、中央揃えの乱用を避ける。全要素を見えないグリッドに載せる。
- **表は横罫線のみ**。縦罫線は引かない。**数値は右揃え+桁区切り**、比較軸は列に置く。
- **フォント**: 和文は Noto Sans JP(または BIZ UDゴシック)、1成果物にファミリー最大2つ・ウェイト2〜3種。MS Pゴシックは使わない。細ウェイトをスライド本文に使わない(プロジェクタでは Medium 以上)。
- **和欧混植**: 英数字には欧文フォントを先に当てる(例: `Inter, "Noto Sans JP"` の順)。数字が主役の見積書・報告書で効果が最大。
- **行間**: 和文本文は 1.5〜1.9。見出しは 1.2〜1.4 に詰める。
- **強調はコントラストで**: 「少し大きく」ではなく「思い切り差をつけるか、同じにするか」。強調箇所を増やしすぎない(全部強調=無強調)。

なぜ: 和文の「素人っぽさ」の大半はフォント・行間・囲み過多・整列崩れで説明でき、全てルール化できる。

## Step 5: Marp テーマとスライドマスタを整備する

テンプレートは一度だけ本気で作り、**以後すべての資料をそこから生成する**(4原則の「反復」の実装)。案件ごとに作り直さない。

### 4マスタ構成

マスタは次の4種で足りる。増やさない。

| マスタ | 役割 | 要点 |
|---|---|---|
| **表紙** | タイトル・宛先・日付・自社名 | ロゴと配色はここで固定。個性を出すならここだけ |
| **中扉** | 章の区切り | 章番号+章タイトルのみ。情報を載せない |
| **本文** | アサーション+エビデンス | 上部にメッセージ行、下部にボディ領域 |
| **図解** | 図を主役にする | 余白広め。図+1行キャプションのみ |

### 生成手順

1. テーマ CSS を1ファイル作る(初回のみ)。マスタはクラスで切り替える:

```css
/* themes/company.css — 一度作って全案件で使い回す */
@import 'default';
section {
  font-family: 'Inter', 'Noto Sans JP', sans-serif; /* 和欧混植: 欧文が先 */
  line-height: 1.7;                                  /* 和文向け行間 */
}
section.cover   { /* 表紙: ロゴ・ブランド色 */ }
section.divider { /* 中扉: 章番号のみ */ }
section.diagram { /* 図解: 余白広め */ }
/* 無指定 = 本文マスタ。h1 をアサーション行として上部に固定する */
```

2. 資料本体は Markdown だけを書く。マスタは frontmatter とディレクティブで指定する:

```markdown
---
marp: true
theme: company
---
<!-- _class: cover -->
# ○○システム刷新のご提案

---
## 現行システムの保守費は3年で回収可能   <!-- タイトル=結論 -->
(エビデンス: 表・グラフ・Mermaid 図)
```

3. Marp CLI で出力する: `marp --theme ./themes/company.css deck.md -o deck.pdf`
4. 出力を Step 7 のセルフレビューにかけてから提出する。

なぜ: テーマを固定すれば、資料作成は「Markdown を書くだけ」になり、品質が安定したまま速度が出る。

## Step 6: スクリーンショットに統一注釈を付ける

スクリーンショットの無加工貼り付けは素人っぽさの筆頭。全スクショに**同一ルール**で加工する。

- **枠線**: 1〜2px の単色(テーマのグレーまたはブランド色)を全スクショに付ける。太さと色を混在させない。
- **影**: 付けるなら1段階に固定(例: `0 2px 8px rgba(0,0,0,.15)`)。ページごとに変えない。
- **番号**: 説明順を示す丸数字バッジ(色・サイズ統一)を振り、本文の説明と番号で対応させる。矢印・囲みも同じ色に統一する。

なぜ: 注釈スタイルの不統一は「反復」違反であり、1枚ごとの見栄えより資料全体の一貫性が信頼を作る。

## Step 7: セルフレビュー(4原則チェック)

提出前に必ず1周、以下で全ページを審査する。作る時ではなく**見直す時**に使う。

- [ ] **近接**: 関連要素は近く、無関係は遠いか(余白比 1:2〜3)
- [ ] **整列**: 全要素がグリッドに揃っているか。中央揃えを乱用していないか
- [ ] **反復**: 色・フォント・余白・注釈スタイルが全ページで同一か
- [ ] **コントラスト**: 見出しと本文、強調と地の差が「思い切り」ついているか
- [ ] タイトルは全ページ結論形か(「〜について」が残っていないか)
- [ ] 図解パターンの誤選択がないか(Step 3 の判定基準で再確認)
- [ ] 1ページ1メッセージを守れているか(詰め込みページはないか)

## 禁止リスト

以下を検出したら、提出前に必ず修正する。

1. **詰め込み** — 1枚に複数メッセージ・小さい文字の敷き詰め。→ ページ分割(情報量はページ数で稼ぐ)
2. **装飾過剰** — ワードアート的装飾、過剰なグラデーション、影の乱用、アイコンの過剰使用
3. **案件ごとのデザイン変更** — 提案のたびにテンプレートやレイアウトを変える(反復の破壊。工数と品質の両面で損)
4. 話題タイトル(「〜について」)
5. フォント3種以上の混在、全角英数字
6. 表の縦罫線・格子罫線、数値の左揃え
7. スクリーンショットの無加工貼り付け
8. 箇条書き3階層以上

## AI がやること / 人間にしか決められないこと

このスキルを実行するエージェントと人間の分担線。**AI はきれいな「平均的資料」を作れるが、勝てる資料の差分は人間のヒアリングから来る**。

| AI(このスキルの実行者)がやる | 人間にしか決められない |
|---|---|
| テンプレート・テーマ CSS の生成と適用 | メッセージ(何を主張するか)の最終決定 |
| 文章→図解パターン判定→Mermaid 生成 | 情報の取捨選択と序列(どれが決裁に効くか) |
| 和文資料ルール・4原則違反の検出と修正 | クライアント固有の文脈を踏まえた構成(誰が決裁者で何を気にするか) |
| 既存資料のトーン統一リライト・フォント監査 | 金額ページの見せ方と価格の判断(→ 自組織の見積・価格判断プロセスへ) |
| スクリーンショットへの統一注釈付け | 書体・トーンの「声色」判断(この客にこのトーンは適切か) |
| 表紙〜Appendix への情報再配置の提案 | 提出の最終承認 |

- 図解の視覚的グルーピングは AI が得意だが、**どの情報グループを近接させるか=意味構造の決定**はヒアリングした人間しか知らない。判断が必要な箇所は推測で埋めず、人間に確認する。

## 他スキルとの境界

- 金額・単価・値引きの判断は本スキルの対象外。本スキルは数値の**見せ方**(右揃え・和欧混植・表設計)のみ扱い、金額の決定は自組織の見積・価格判断プロセスに従う。
