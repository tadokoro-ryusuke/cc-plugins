# 原則集 — AIネイティブ開発運営の12原則

各原則は「原則 / 根拠 / 実務での現れ方」。相談への回答はここを起点にする。
根拠の出典は 2025-2026 時点の調査(DORA 2025、SRE Report 2026、Anthropic実践知)。
事実関係は変化しうるが、原則自体は安定している。

## 1. AIは増幅器であって解決策ではない
**根拠**: DORA 2025 — AIは既存のエンジニアリング環境を増幅する。成熟組織は生産性向上を
デリバリー性能に転換できるが、断片化した組織では技術的負債の生成を加速させる。
**実務**: AI導入の相談は基盤(VCS・テスト・観測性・プロセス)の成熟度診断から始める。
基盤が弱いのにエージェントの量だけ増やす提案には反対する。

## 2. 希少資源は人間の認知帯域。組織設計とはその配分設計
**根拠**: 生成コストはモデル改善で下がり続けるが、レビュー・判断の人間コストは下がらない。
インシデントでも拘束条件は観測データではなく人間の認知帯域。
**実務**: あらゆる設計案を「人間が判断に触れる回数と所要時間」で採点する。承認点は
数えられる状態(HOTLではCP1〜CP4の4点)に保つ。承認点が増殖し始めたら設計が腐っている。

## 3. 検証への投資 > 生成への投資
**根拠**: 無人で回せる作業量の上限は「機械的に検証できる範囲」で決まる。検証Skill・テスト・
evalの整備に1週間かける価値がある(Anthropic内部知見)。
**実務**: 「エージェントを増やしたい」という相談は「何で検証するか」に変換する。
検証手段のない自動化は承認しない。

## 4. 自律性は段階的にしか上げられない(RO → Advised → Approved → Autonomous)
**根拠**: 信頼構築サイクルはスキップできない。いきなり自律修復に行く組織はない(AI SRE実践)。
**実務**: 各自動化に現在の段階を明示させる。昇格には定量的な実績(decision-frameworks.md
の昇格基準)を要求する。降格をためらわない。

## 5. リスクで層別する。一律ゲートは速度も安全も殺す
**実務**: Tier 0(docs/依存patch)/ Tier 1(通常)/ Tier 2(認証・権限・migration・
秘匿境界・CI自体)。Tier 2 の定義はpaths-filterとCODEOWNERSの2箇所で機械的に強制し、
必ず同期させる。「全部厳しく」は必ず形骸化して「全部緩く」に転落する。

## 6. ゲートは comment-only → 較正 → 強制 の順。偽陽性は信頼を破壊する
**根拠**: 初日から強制すると、較正期間があれば解決した偽陽性にチームが反発し、ツールごと
剥がされる(AIコードレビュー導入の最頻失敗パターン)。
**実務**: 新ゲートの導入計画に較正期間(目安2週間)が含まれていなければ差し戻す。

## 7. プロンプト変更はコード変更と同じ重さの変更管理対象
**根拠**: エージェントのデプロイ単位は「モデル+プロンプト+ツール定義」の束(agent version)。
昇格はテスト合否ではなく評価結果で判定する。
**実務**: プロンプトを直接本番に反映できる経路があれば塞ぐ。eval-gate なしのプロンプト
改善は「テストなしのリファクタ」と同じ扱いにする。

## 8. 閾値は相対(baseline比)と絶対(下限)の二重にする
**根拠**: 相対のみだと劣化がじわじわ蓄積する(boiling frog)。絶対のみだと初期品質で満足する。
**実務**: eval・SLO・カバレッジ、どの閾値設計でもこの二重構造を要求する。

## 9. 平均で守れないものは must-pass で守る
**根拠**: MNPI境界・権限制御・injection耐性は「精度95%」に意味がない。1件の漏洩が
致命傷になる領域はスコア平均から分離し、100%必須+1件failでブロックにする。
**実務**: eval設計レビューでは最初に「must-passカテゴリは何か」を問う。

## 10. 監査証跡はワークフローの副産物として自動生成する
**根拠**: 後付けの証跡整備は必ず漏れる。PR承認ログ・eval レポート・デプロイ承認・
ロールバック記録が自動で不変ストレージに落ちる設計なら、監査対応は設定値の提示で済む。
**実務**: J-SOX関連は references/jsox-audit.md を参照。

## 11. 失敗は資産。24時間ルールで還流させる
**実務**: 本番の検索漏れ・誤回答は24時間以内に golden set 化。エージェントの同種ミス
2回で CLAUDE.md / スキルに1行追記。データセットと規範ファイルは「成長する資産」であり、
書いて終わりのドキュメントではない。

## 12. 買う前に、既存基盤+内製Read-Onlyで試す
**根拠**: AI SRE等のツール市場は乱立期で、少人数チームには過剰なものが多い。価値の大半は
「コンテキスト組み立ての自動化」にあり、それは既存のエージェント基盤で内製できることが多い。
**実務**: decision-frameworks.md の buy-vs-build 判定質問を通してから購買を検討する。
