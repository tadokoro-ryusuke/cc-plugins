# Eval 設計ガイド(一般化版)

エージェント・検索・生成系システムに評価ゲートを設計するときの手順。
具体実装は assets/evals/(run_evals.py, thresholds.json, judge_rubric.md)を雛形にする。

## 3層構造(コストとシグナルの分離)

1. **L1 決定的チェック**: retrieval メトリクス(recall@k, MRR)、禁止出力の正規表現、
   フォーマット検証、refusal 判定。毎回・全件・ほぼゼロコスト。L1 で落ちたケースに
   L2 を回さない
2. **L2 LLM-as-judge**: ルーブリック採点(正確性・忠実性・完全性の3軸、各1-5点)。
   temperature 0 + 3票中央値で分散を抑える。PR時は smoke サブセット、nightly で full
3. **L3 人間較正**: 月次30件を層化サンプリング(fail多め)して人間が同一ルーブリックで
   採点。±1点一致率 85% 未満なら judge プロンプトを改修。較正記録は監査証跡として保存

## golden set のカテゴリ設計(ここが設計の本体)

必ず含めるカテゴリ:
- **standard / hard**: 通常系と難問(表記ゆれ・複数ソース統合)
- **no-answer**: 正解が存在しないケース。「見つからない」と言えるか(幻覚検出)
- **境界系(must-pass)**: 権限境界・秘匿情報漏洩・prompt injection。
  ドメインごとに「1件漏れたら致命傷」の境界を特定して設計する(原則9)
- **freshness**: 更新されたデータの新版を返すか
- **format**: 指示形式の遵守

規模は 50件から始めて 100-150件へ。**本番の失敗報告は24時間以内に golden set 化**する
運用ルールとセットで初めて機能する(原則11)。

## ゲート条件の設計

- must-pass カテゴリ: 100%。1件 fail でブロック。平均に混ぜない
- 品質スコア: 相対(baseline − 許容幅)と絶対(下限)の**二重閾値**(原則8)
- baseline は「full suite を全通過した最後の main」の結果。nightly で自動更新
- smoke(PR時)は full より許容幅を広めに(ノイズでの誤ブロックを避ける)

## 実装上の要点

- 対象システムの呼び出しは1関数に隔離(call_target)し、API契約の違いを吸収する
- **権限テストはサーバー側の境界を叩く**(クライアントから権限リストを渡すテストは無意味)
- injection テスト用の罠文書を staging のインデックスに常設する
- 実データを含む golden set はリポジトリに置かず、アクセス制御されたストレージから
  CI 実行時に取得。リポジトリにはサニタイズ版サンプルのみ
- レポートは「人間が3分で読める」ことを要件にする(失敗ケース表 + baseline 差分)。
  これが CP4(昇格承認)のエビデンスになる
- judge モデルの変更・ルーブリックの変更自体も eval-gate の対象(メタ変更の統制)
