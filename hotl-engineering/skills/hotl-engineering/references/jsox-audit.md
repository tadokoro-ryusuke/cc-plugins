# J-SOX / IT全般統制・監査対応

IPO準備企業でAI・自動化を進めるときの統制設計と、監査人への説明論点。

## 統制マッピング(HOTLワークフローでの実装)

| 統制 | 実装 | 証跡 |
|---|---|---|
| 変更管理 | protected branch + PR必須 + CP2/CP3承認。本番反映の全経路がPRを通る | PRレビューログ、Environment承認ログ |
| 職務分掌 | 起票者(エージェント/開発者)≠ 承認者(人間)を ruleset で強制。Tier 2 は Code Owners レビュー必須 | ruleset 設定値、CODEOWNERS |
| アクセス管理 | 静的キー全廃(OIDC federated credentials)、最小権限ロール、production secrets は environment 単位 | IAM/Entra のフェデレーション設定 |
| 監査証跡 | eval レポート・デプロイ記録・レビュー結果を自動で不変ストレージ(Object Lock付きS3等)へ退避 | ストレージ内レポート(CIログは既定90日で消えることに注意) |
| プログラム開発 | テスト・eval の実施証跡が CI の副産物として残る | CI結果、evalレポート |

## 監査人への説明の組み立て方

- 「AIがコードを書くこと」自体は論点にならない。論点は**「承認されていない変更が本番に
  入る経路が存在しないこと」**。ruleset の設定値(bypass_actors 空、required checks、
  approval 必須)をそのまま提示できる状態にしておく
- AIレビュー・AI評価は「統制そのもの」ではなく「統制を補助するツール」と位置付ける。
  最終承認者は常に人間(CP2/CP3/CP4)である構造を図で示す
- LLM-as-judge の妥当性を問われたら: 人間較正の記録(月次一致率)を提示する。
  「AIがAIを評価している」への回答は較正プロセスの存在
- 緊急時対応(hotfix): bypass を常設せず、ruleset の一時無効化+その操作ログ自体を
  証跡とする運用を文書化しておく

## 少人数体制(2-4名)の職務分掌の限界と補完統制

起票と承認が同一人物になるケースは構造的に避けられない。監査対応としては:
1. 基本形を「エージェント起票 + 人間承認」にする(形式上の分離が常に成立)
2. Tier 2(認証・権限・migration・秘匿境界)は別の人間のレビューを必須にする
3. 月次で全マージの承認状況をサンプリングレビューし、記録を残す(発見的統制)
4. 上記を統制文書(規程・手順書)として明文化し、運用実績を積んでから監査に臨む

## AI固有の統制で先回りして整備しておくもの

- エージェントの権限一覧(どのワークフローが何のロールで何にアクセスできるか)の台帳
- プロンプト・モデル変更の変更管理(eval-gate + CP4)が「プログラム変更管理」に
  含まれることの明文化
- インシデント調査エージェントが Read-Only であることのロール設定の証跡
- 自動ロールバック・auto-merge など「人間承認なしで動く操作」の範囲と条件の一覧
