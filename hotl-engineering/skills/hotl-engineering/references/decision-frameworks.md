# 判断フレームワーク集

相談モードで使う判定表・基準・アンチパターン。原則(principles.md)を具体の判断に
落とすための道具。番号は原則の参照。

## F1. リスクティア判定(原則5)

| 質問 | Yes なら |
|---|---|
| 認証・認可・権限フィルタに触れるか | Tier 2 |
| DBスキーマ・migration に触れるか | Tier 2 |
| 秘匿情報境界(MNPI・個人情報)のデータフローに触れるか | Tier 2 |
| CI/CD・branch protection・ワークフロー定義自体を変えるか | Tier 2 |
| 上記いずれでもなく、docs・テスト追加・依存patchのみか | Tier 0 |
| それ以外 | Tier 1 |

迷ったら上のティアに倒す。ただし Tier 2 が全PRの3割を超えたらパス定義が広すぎる。

## F2. 自律性の昇格基準(原則4)

| 現在 → 次 | 昇格条件(目安) |
|---|---|
| Read-Only → Advised | 一次調査の結論が人間の結論と一致 ≥ 70%(直近10件) |
| Advised → Approved | 提案アクションを人間がそのまま採用 ≥ 80%(直近20件)+ 提案が有害だった事例 0 |
| Approved → Autonomous | 同一種別の承認済み実行が連続20回無事故 + 操作が可逆 + 影響範囲が定義済み |

昇格は操作種別ごと(「再起動は Autonomous、スケール変更は Approved」が正常な状態)。
1件でも重大事故があれば2段階降格し、原因を golden set / runbook に還流(原則11)。

## F3. buy vs build(原則12)— 特にAI SRE・監視・レビュー系SaaS

購買を検討する前に順に問う:
1. その製品の中核価値は何か。「コンテキスト組み立ての自動化」なら内製で足りる可能性が高い
2. 内製 Read-Only 版(既存エージェント基盤+read権限+定型プロンプト)を1週間で作って
   埋まらないギャップは何か。そのギャップに価格は見合うか
3. ベンダーの効果数値(MTTR◯%削減等)は自社規模での実測か。乱立市場のポジショントークを
   割り引いたか
4. データはどこに送られるか。秘匿要件(データレジデンシー)と両立するか
5. 剥がすコストはいくらか(ロックイン: 独自計装・独自データ形式)

「買う」が正解になりやすい領域: オンコール管理・通知配送のような信頼性が命の配管、
コモディティな脆弱性DB。「作る」が正解になりやすい領域: 自社データ・自社権限モデルに
密結合する判断ロジック。

## F4. 新モデル・新ツールへの切り替え判定(原則7,8)

1. 自社の eval set(golden set)で現行と新版を同条件比較する。ベンチマーク記事は参考値
2. must-pass カテゴリの結果を先に見る。平均が上がっても must-pass が落ちるなら不採用
3. コスト(トークン単価×実測消費)とレイテンシを同時に記録する
4. 切り替えは agent version として1つのPRで(モデルIDだけの変更でも eval-gate を通す)
5. ロールバック手順(旧バージョンのポインタ)を確認してから昇格

## F5. auto-merge 解禁の判定(原則3,5)

以下がすべて Yes になるまで解禁しない:
- Tier 0 の機械的判定(paths + 依存patch判定)が誤分類ゼロで4週間運用できた
- 全ゲート(5層)が required として安定稼働し、偽陽性が週1未満
- 事後監視: マージ後に自動 revert できる仕組み、または即時ロールバック可能なデプロイ
- 監査説明: 「auto-merge の範囲と条件」が文書化されている

解禁後も対象は Tier 0 のみ。Tier 1 への拡大は原則2(認知帯域)の観点で価値が薄い割に
リスクが跳ねるので、基本的に推奨しない。

## F6. 外注・新メンバーへの権限設計

- リポジトリ権限は Write まで。branch protection の bypass は誰にも与えない
- 外注の成果物も同じゲートを通す(人によってゲートを変えない。変えるのはティアだけ)
- CLAUDE.md / CODEOWNERS / スキルを「オンボーディング資料」として使う。初日から
  同じ規範・同じ道具で書けることが品質の分散を抑える
- 秘匿データを扱うリポジトリでは、外注にはサニタイズ済み環境(ダミーデータのstaging)のみ

## F7. 導入ロールアウトの順序原則(原則1,6)

新しい仕組みの導入は必ず: ①専任(1人でよい)が先行整備 → ②最初の利用者が初日から
生産的である状態を作る → ③観測期間 → ④強制化 → ⑤自律範囲の拡大。
①を飛ばした全社展開、③を飛ばした強制化は失敗パターン。

## アンチパターン集(見かけたら指摘する)

- **day-one enforcement**: 較正なしの初日強制 → 偽陽性でツールごと剥がされる(原則6)
- **boiling frog baseline**: 相対閾値のみで絶対下限がない eval(原則8)
- **spec の過剰形式化**: CRUD 1本に長大な仕様書。ティアに応じて仕様の深さを較正する
- **MCP・ツール定義の肥大**: CLIで足りるものをMCP化しコンテキストを圧迫。ツール定義の
  トークンコストを常に疑う
- **kitchen sink session**: 1セッションに無関係なタスクを混ぜてコンテキストを汚す
- **検証なき自動化**: 「動いたからOK」で Autonomous に上げる(原則3,4)
- **書いて終わりの規範**: 更新ルール(24時間ルール・2回ルール)のないCLAUDE.md/golden set(原則11)
- **平均への逃避**: must-pass にすべき境界(権限・injection)をスコア平均に混ぜる(原則9)
- **人間承認の形骸化**: CP2が「緑だから即Approve」の儀式になっている。エビデンス
  (レビュー観点サマリ)の提示品質を上げるか、そのティアを Tier 0 に落とすかの二択
