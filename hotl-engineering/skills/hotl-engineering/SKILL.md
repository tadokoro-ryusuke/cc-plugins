# HOTL Engineering — 設計・適用・相談

Human-on-the-Loop(HOTL)= 人間が各ステップの中にいるのではなく、少数の監督点で
エビデンスを見て承認/停止する開発運用モデル。このスキルは (A) プロジェクトへの
適用と (B) 日々のCTO判断相談の両方を扱う。

まずユーザーの依頼がどちらかを判定する:
- 対象リポジトリ/プロジェクトが特定でき、成果物(設定・ファイル・設計)を求めている → **モードA**
- 判断・方針・是非・説明の仕方を求めている → **モードB**
- 両方(「導入すべきか、やるならどう」)→ モードBで判断を先に固め、既に与えられた実装権限の範囲でモードA
- リポジトリの引き継ぎ・開発フローの立て直し(「引き継いだので開発が回るようにしたい」
  「運用を改善したい」)も**両方**型として扱う: モードAのアセスメント(Step 1)を先に実施し、
  その結果から比例した選択(何を導入し、何を導入しないか)をモードB様式で示してから、
  権限の範囲内でローカルの変更を準備する

どちらのモードでも、回答の土台として `references/principles.md` を最初に読むこと。

---

## モードA: プロジェクトへの適用

「全部入りを押し付けない」ことが最重要。ゲートはリポジトリの性質に比例させる。
過剰導入は速度を殺し、チームの信頼を失わせ、結局剥がされる。

### Step 1: 関連するデリバリーリスクのアセスメント

依頼された変更に関係する事実をリポジトリから調査する。既知の方針は再利用し、
結果を実質的に左右する未解決の判断だけを質問する。
デリバリーフロー全体の整備なら、以下を確認する:

1. スタックと既存CI(言語 / パッケージマネージャ / 既存workflow / テスト有無)
2. デプロイ先(Azure Container Apps / App Service / Vercel / その他)と現在のデプロイ方法
3. リポジトリの性格: 本番プロダクト / 社内ツール / エージェント系(プロンプト・検索を含む)/ 実験
4. リスクパス: 認証・権限・migration・秘匿情報境界に該当するディレクトリ
5. チーム構成(人数・外注の有無)と、監査要件(J-SOX対象か)

### Step 2: 適用計画と権限の確定

既存のユーザー承認は再利用する。実装を依頼されているなら、ローカルのテンプレートと
チェックを準備する。質問するのは、未解決の重要な方針か、その権限の外にある外部変更
だけにし、具体的にレビューできる成果物を準備してから尋ねる。アセスメントのみの
依頼なら計画の段階で止める。

性格別の推奨サブセット:

| リポジトリ性格 | 導入するもの | 導入しないもの |
|---|---|---|
| 実験・PoC | ci.yml の L1/L2 のみ | AIレビュー強制・deploy承認(速度優先) |
| 社内ツール | ci.yml 全層 + ai-review(comment-only)+ branch protection | eval(エージェント要素がなければ) |
| 本番プロダクト | 既存チェック + 実際のリリースリスクで正当化できるゲート | 使わない連携・重複する承認ゲート |
| エージェント系 | タスク固有の eval と選定したデリバリー統制。must-pass ケースを守る | 検索を伴わないシステムへの retrieval メトリクス |

新規の advisory/AI ゲートには、観測・較正・昇格の条件を計画に明記する。同梱の
CI workflow を採用する場合は、その `quality-gate` context を定義するが、既存の
required check を黙って置き換えない。人間の承認点は選んだスコープに必要なものを
特定し、限定的な変更に CP1〜CP4 のすべてを導入しない。

### Step 3: テンプレート適用

`assets/` からは必要なテンプレートだけを使い、`assets/ADJUST.md` の該当セクションに
沿って書き換える。該当する適合作業:

- パッケージマネージャ・コマンド(pnpm前提 → 実態に合わせる)
- ai-review.yml の Tier 2 paths-filter を Step 1 で特定したリスクパスに書き換え、
  CODEOWNERS と**必ず同期**させる
- Bedrock/Azure の例は任意のプロバイダアダプタとして扱う。選定済みの基盤は維持し、
  有効なモデル/プロファイルはその基盤の最新の公式ドキュメントから確定する。
  テンプレートが別のプロバイダを使っているという理由だけでプロバイダを置き換えない
- 本番デプロイを有効化する前に、capture/restore アダプタを実装してリハーサルする。
  revision の有効化だけでなく、実際のルーティングとヘルスまで復元する
- エージェント系なら `references/eval-design.md` を読み、golden set のカテゴリ
  設計から始める(テンプレの閾値をそのまま使わない)

### Step 4: 導入は必ず Phase 1 設定で

- 新規に入れるノイズの多い advisory/AI チェックは観測モードで導入する。既存の
  blocking な security チェック・branch protection・合意済みの must-pass 条件は維持する
- 昇格は、代表的な実行結果が文書化した信頼性・品質の基準を満たし、責任者と
  無効化手段(ロールバックスイッチ)が決まってから行う。経過週数だけは証拠にならない
- branch protection の変更は、明示的に与えられた外部変更権限の範囲でのみ適用する。
  先にポリシー差分を準備し、既存の保護を黙って弱めない

### Step 5: 検証と引き渡し

- workflow YAML は yaml.safe_load で構文検証、スクリプトは bash -n / py_compile
- artifact の欠落・不正形式、ジョブ失敗、対象 revision の不一致、recovery preflight の
  失敗をオフラインの fixture で実行確認する。構文検証は、ホスト上の workflow や
  クラウドでの復旧が動く証拠にはならない
- AIレビューの強制化を有効にする前に、`assets/scripts/check_review_verdicts.py` を
  `assets/ADJUST.md` で指定したプロジェクト側のパスに設置する。workflow を適用する前に、
  その信頼境界と適合の前提をレビューする
- 選んだゲートについて残っている昇格・セットアップ作業を、必要な証拠と権限要件つきで
  記録して引き渡す

## モードB: CTO相談

既に読んだ原則を使い、判断フレームが問いの解決に役立つときは
`references/decision-frameworks.md` を参照する。J-SOX・監査・統制の話題なら
`references/jsox-audit.md` も読む。eval・品質測定の話題なら `references/eval-design.md` も読む。

### 判断の内容

回答の形は判断に合わせる。短い推奨なら5項目すべての節を立てる必要はない。
関連する論拠を含める:

1. **原則**: 判断の説明に役立つとき、どの原則が支配するか(principles.md の番号で特定)
2. **文脈適用**: 相談者の状況(規模・リスク・段階)に当てはめる
3. **推奨**: 曖昧にせず立場を取る。「場合による」で終わらせない
4. **トレードオフ**: 推奨が捨てているものを明示する
5. **次の一歩**: 今日できる最小の行動1つ

### 振る舞いの規範

- 率直に。相手はきれいごとではなく判断材料を求めている。反対すべきときは反対する
- 規模感を常に問う。大企業向けプラクティスを少人数チームに持ち込む提案には
  「その規模で本当に必要か」を必ず検証する(decision-frameworks.md の buy-vs-build)
- **鮮度に注意**: モデル名・ツールの市況・価格・最新機能は変化が速い。これらが
  結論を左右する相談では、スキル内の記述を鵜呑みにせず web 検索で現況を確認
  してから答える。原則(principles.md)は安定、事実は要検証
- 判断を求められていないのに一般論の講釈をしない。聞かれたことに答える

## スキル自体の運用ルール(このスキルを腐らせないために)

- 相談・適用で原則の不足や誤りが2回露呈したら、references に1行追記する PR を提案する
- 四半期ごとに principles.md の根拠(DORA等)を最新版レポートで再検証する
- assets のテンプレートは実プロジェクトでの改良を還流させる(プロジェクト側で
  直した内容がテンプレに戻っていない状態を作らない)
