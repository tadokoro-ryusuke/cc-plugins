# AI Search Visibility（AI 検索での見え方）

プロダクトが AI の生成する回答に出る資格を持ち、正確に説明され、測れる形で現れている状態を作り、その見え方をユーザー獲得に結びつける。これは検索と流通（ディストリビューション）の仕事の一部として扱う。エンジンの運営者は、基本は検索と同じだと述べており、AI の回答の順位要因を公開しておらず、掲載を保証していない。したがって、ほかの誰も掲載を約束できない。

このプロダクトにとって AI の回答がチャネルとして追う価値があるかの判断と、その良し悪しを決める activation と定着の指標の定義には、利用できれば `indie-product-marketing:indie-product-marketing` を使う。ランディングページの設計と実装には、利用できれば `indie-product-marketing:global-landing-design` を使う。適格性の確認と、誰かの主張の監査は、どちらも先に済ませておく必要はない。

Claude Code で Web の証拠を集めるとき、プロンプトを実行して計測するとき、投稿・連絡・申請・デプロイなどの外部アクションに関わるとき、または実装を検証するときは、[references/claude-code-runtime.md](references/claude-code-runtime.md) を読む。

## 動作モードを選ぶ

依頼に合う、最も狭いモードを選ぶ。

1. **適格性の確認** — エンジンがページをクロールし、インデックスし、表示できるかを確かめる。
2. **基準の計測** — プロンプトセットを作り、エンジンごとの言及率と引用率を測る。
3. **ギャップと行動計画** — 買い手の問いを整理し、ギャップを振り分け、ページとソースごとに行動を 1 つ選ぶ。
4. **主張・業者の監査** — 手法、事例、提案を、証拠に照らして検証する。
5. **再計測** — 新しい snapshot を基準と比べ、続けるかどうかを決める。

手元の文脈からモードを推定する。不足している情報は、次の行動を変える場合にだけ尋ねる。そうでなければ前提を明示して進める。全体を通す場合は上の順に進めるが、どのモードも単独で実行できる。

`assets/` のファイルはテンプレートである。モードに必要なものをユーザーのプロジェクトのドキュメントにコピーするか、埋めた表を応答で返す。プロダクトのデータを、このスキル自身のファイルに書き込まない。

## 守る立場

当てはまるものは早い段階で伝える。ユーザーが何を期待すべきかが変わるためである。

- **見え方は需要ではない。** 引用されてもユーザーが増えないことがある。チャネルは、activation と定着で判断する。
- **知られていないプロダクトでは、ページの手直しだけで状況が変わることは少ない。** 観察データでは、ページの個々の特徴より、ドメインとブランドのほうがばらつきを多く説明する。これは相関であり、打ち手の順位を決めるものではない。最初の行動は、実際に観察したギャップから選ぶ。
- **書式の助言は、証拠として弱い。** FAQ ブロック、要約ボックス、schema、決まった語数、`llms.txt` が引用を引き起こすことは示されていない。構造は、読み手の助けになるから使う。
- **1 回の回答は計測ではない。** 回答は実行のたびに変わる。率には、反復と、その元になった件数と、何も変えていないときに率がどれだけ動くかを示す同日の繰り返しが要る。
- **他社の倍率は予測ではない。** 確立したブランドの報告された伸びは、別のプロダクトには移らない。ゼロに近い基準からの倍率は、ほとんど何も語らない。

重要な記述は、観察事実・報告された事実・推論・仮説・推奨のどれかに分ける。Web から得たものには、出典の URL と取得日を記録する。AI の引用を何が左右するかについての主張を繰り返す前に、[references/evidence-base.md](references/evidence-base.md) を読む。

## 適格性を確かめる

公開されているサイトについての作業なら、コンテンツやオフサイトの作業の前に確かめる。クローラが止められていると、そのエンジンの回答にプロダクト自身のページは使われない。ただし、ほかのサイトを元にプロダクトが言及されることはある。確認は、対象のエンジンとページに絞る。

1. `robots.txt` と、CDN やファイアウォールのルールを、各エンジンの検索用クローラについて読む。学習用のクローラは別の判断であり、検索への掲載を左右しない。例外が 1 つある。`Google-Extended` は Gemini アプリでの grounding も左右するので、Google のどの面が問題なのかを確かめる。
2. 優先するページがインデックスされ、クローラに本文を返し、canonical の URL を持つことを確かめる。
3. スニペット・キャッシュ・インデックスを制限するページの指定と、優先する URL ごとに、Google Search Console で実際に効いている生成 AI の設定を確かめる。
4. 見つけたことは、ページ、指定、どのエンジンにどう効くかを添えて報告する。ユーザーが開いていない管理画面のように確かめられなかったものは、不明として報告する。

クローラの名前、制御の手段、運営者の記述は、[references/engine-eligibility.md](references/engine-eligibility.md) を読む。これらは変わる。判断がその記述に依るときは、運営者のページを取り直す。

## 買い手の問いを整理する

市場は、プロダクト、顧客、記録された会話から定義する。検索ツールは、その一覧の確認と拡張に使い、起点にはしない。

買い手の意思決定ごとに、検索キーワードと、買い手が実際に入力するプロンプトを書く。プロンプトには、回答を左右する状況と制約（チームの規模、予算、プラットフォーム、既存のツール、地域）を含める。問いは、Search Console のクエリ、サポートへの問い合わせ、商談の記録、コミュニティのスレッドから取り、仮定で置いたものには印を付ける。課題、カテゴリ、比較、導入、乗り換えの問いを覆う。文面の精密さより、意図の幅が効く。

エンジンに送ったプロンプトは、ユーザーの手を離れる。顧客の言葉をプロンプトにする前に、買う意図は残したまま、氏名・会社を特定できる情報・秘密の内容を取り除く。使うのは、この目的で使うことにユーザーが同意したデータだけにする。

整理した結果は、`assets/question-map.md` のテンプレートで記録する。

## 基準を測る

何かを変える前に測る。あとの作業を判定できるようにするためである。

1. 問いの地図からプロンプトセットを作る。買い手の問い 1 つにつきプロンプトを 1 つにするか、言い換えを 1 つの問いにまとめる。各プロンプトに、ブランド名を含むかどうかの印を付ける。プロダクト名を含むプロンプトは、そのプロダクトを回答に引き込む。
2. 買い手が使うエンジンごとに、各プロンプトを複数回、きれいなセッションで、1 つの経路（surface）、1 つのロケール、1 つのモデルまたはモードで、ユーザーが認めた API の費用の範囲で実行する。失敗した実行と、AI の回答が出なかった実行も含めて、実行ごとに固有の ID を付けて記録する。
3. `scripts/visibility-stats.mjs` で集計する。script は記録を検証し、エンジン、経路、ブランド名を含むプロンプトを分けて、言及と引用について観察した件数と率を出す。信頼区間も判定も出さない。どちらも手で足さない。
4. 同じ日にセット全体をもう一度実行し、2 つの snapshot を比べる。その差が、何も変えていないときに率がどれだけ動くかの最初の目安になる。
5. 回答が引用したドメインと、プロダクトについての不正確な記述を記録する。
6. 次の snapshot の前に、判定ルール、その判断の根拠にする 1 つの比較、観察期間を書く。

基準がゼロか、それに近いとき（新しいプロダクトでは普通である）は、件数と初出で報告する。その基準からの変化率は報告しない。

数値が表すのは、これらの日付での、このプロンプトセットである。セットに無い問いについては何も言えない。引用するときは「このプロンプトセットでは」と書く。

指標の定義、プロンプトと反復の数、実行の手順、アナリティクスでの見え方、盲点は、[references/measurement.md](references/measurement.md) を読む。プロンプトセットと snapshot の記録には、`assets/prompt-set.md` のテンプレートを使う。

## ギャップを振り分け、1 件ずつ行動を選ぶ

問いの地図のギャップを、コンテンツ・技術・第三者のソースのどれかに振り分ける。そのうえで、1 件ごとに行動を 1 つ決める。

**ページ。** 検索での成績と、回答の出典としての有用性を別々に判断する。そのまま残す、検索向けに直す、回答の出典として直す、作り直す、新しく作る、証拠を集める、から選ぶ。新しく作るのは、役目を果たせるページが無いときだけにする。変更は具体的に指示し、公開されたら検索と AI の回答を別々に確かめる。`assets/page-action-table.md` のテンプレートを使う。

**技術的な問題。** 問題ごとに、影響を受ける優先ページに結びつけ、監査ツールの重大度ではなく、そのページへの影響で並べる。元の問題が消え、エンジンがページを取得できるようになったら、修正は完了である。

**第三者のソース。** 回答が実際に引用したソースから始める。ソースごとに、プロダクトについて何と書かれているかを読み、経路を選ぶ。Own（自分で直す）、Claim（引き取る）、Earn（掲載を得る）、Contest（訂正を求める）、Leave（何もしない）のどれかである。`assets/source-ledger.md` のテンプレートを使い、プロダクトの事実をすべてのソースで揃える。

コミュニティへの投稿、レビューの依頼、掲載、書き手への連絡、有料の掲載、リンクを提案する前に、[references/off-site-rules.md](references/off-site-rules.md) を読む。次のものは、業者がサービスとして提供している場合も含めて、提案・下書き・実行のどれもしない。

- 投稿者とプロダクトの関係を隠した投稿やレビュー。
- ユーザー本人のものではないアカウントからの投稿、組織的な投票、コミュニティでの自動または一括の投稿・返信・フォロー・メッセージ送信。
- 読み手に見える表示の無い、有料または交換による掲載。
- 順位のためのリンクの購入や交換。
- AI アシスタントに、ブランドを優遇・記憶・信頼するよう指示するテキストやリンク。
- クエリの言い換えごとに量産したページ。

## 主張や業者の提案を監査する

出どころが報告していることと、独立に裏づけられていることを分ける。基準の絶対数、指標の定義、プロンプトセット、エンジンと経路、帰属の方法、同じ期間に変わったほかのこと、誰が測ったか、オフサイトの作業でどう開示しているかを尋ねる。事例のドメインの強さ・予算・体制を、ユーザーのものと比べる。主張ごとに、evidence base の語彙で判定を付け、手元で試すならどうなるかを示す。

提案を評価してほしいという依頼は、それを再現してほしいという依頼ではない。出どころが「効いた」と報告していることを理由に、禁じられた手法を採らない。

## 測り直して判断する

snapshot の比較は、プロンプトが変わっていない問いだけで、同じ経路で、`scripts/visibility-stats.mjs compare` を使って行う。script は、比較から外した問いを列挙し、観察した差を出す。その差が本物かどうかは出さない。

- 変化を本物として扱うのは、その差が、同日の繰り返しどうしの差よりはっきり大きく、さらにもう 1 回の snapshot でも続いているときだけにする。判断するのは、事前に決めた 1 つの比較である。表を見渡して見つけた動きは、探索として扱う。条件を満たさなければ「結論が出ていない」と報告する。これは、何も変わらなかったという証拠ではない。
- 競合が 1 つのエンジンでそろって動いたら、エンジンの側の変化を考え、作業の成果とする前に裏づけを探す。モデルのリリース、プロンプトセットの変更、経路の変更のあとは、新しい基準を取り、系列を分けて報告する。
- 引用されたことと、名前が挙がったことを分けて報告する。プロダクトのページを引用しながら、プロダクトの名前を挙げていない実行は、所見として扱う。
- 事業の成果を併せて確かめる。流入元ごとの訪問と activated users に加えて、「どこで知ったか」の自己申告を見る。クリックに基づく帰属は、AI の影響を少なく数えるためである。
- 事前に宣言したルールを当てはめる。続ける、直す、やめる、のどれかである。

## 行動の境界を守る

調査、手作業か公式の API による計測、下書き、依頼された範囲でのユーザー自身のサイトの変更は、範囲の内である。承認された作業は、検証まで進める。

投稿、メッセージの送信、レビューの依頼、書き手への連絡、プロフィールの引き取り、掲載の申請、掲載への合意、公開とデプロイは、外部アクションである。ユーザーがその行動を頼んだときだけ行う。どの報告でも、計画した行動、実行した行動、観察した結果を分ける。

## 判断に使える成果物を出す

選んだモードに必要な、最小限のものを出す。

1. **診断** — 段階、最初の制約、このプロダクトが現実的に期待できること。
2. **適格性の所見** — ページ、指定、影響するエンジン、直し方。
3. **問いの地図** — 意思決定、キーワード、プロンプト、ギャップの種類。
4. **基準または比較** — 件数と率、プロンプトと実行の数、経路、日付、照らし合わせた同日の繰り返し。
5. **行動表** — ページとソースごとに 1 つの判断と、その検証。
6. **主張の監査** — 出典と取得日つきの判定。
7. **リスクと限界** — 規則の確認、計測の盲点、まだ分かっていないこと。

モードの作業が完了するのは、成果物が証拠で埋まり、すべての数値に定義と標本の大きさが付き、すべての外部アクションが「ユーザーの依頼で実行済み」か「未実行」として挙げられたときである。計測を含む作業では、次の計測日と判定ルールが書かれていることも要る。
