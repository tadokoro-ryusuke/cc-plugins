# Indie Product Marketing（個人開発プロダクトのマーケティング）

顧客の課題から、定着し利益を生む需要に至る道筋を、証拠に基づいて組み立てる。マーケティングを開発後に付け足す宣伝として扱わず、プロダクトのライフサイクル全体にわたる顧客理解と流通（ディストリビューション）の設計として扱う。

ユーザーに具体的な機会がない、アプリのアイデアを幅広く一覧で求めている、または解くべき課題を見つける必要がある場合は、利用できれば `indie-product-marketing:indie-idea-discovery` を使い、顧客課題の仮説かプロダクトコンセプトを確立する。すでに依頼されている検証やマーケティングの作業には、その文脈を引き継ぐ。

Claude Code で Web の証拠を集めるとき、出稿・投稿・メール送信・課金・デプロイなどの外部アクションに関わるとき、または検証結果を実装計画へ渡すときは、[references/claude-code-runtime.md](references/claude-code-runtime.md) を読む。

## 動作モードを選ぶ

依頼に合う、最も狭いモードを選ぶ。

1. **市場調査** — 顧客、課題、代替手段、競合、需要シグナル、到達できるチャネルを整理する。
2. **需要検証** — 最もリスクの高い前提を反証できる、最も安価で倫理的なテストを設計する。
3. **ローンチ計画** — ポジショニング、計測の仕込み、シードユーザー、素材、チャネルの順序、フォローアップを準備する。
4. **グロース診断** — リーチから紹介（リファラル）までのうち、最初に壊れている段階を特定し、修復の優先順位を付ける。
5. **チャネル実験** — オーディエンス・メッセージ・オファー・チャネルの組み合わせ1つを、予算と判定ルール付きでテストする。
6. **マーケティング監査** — 主張、指標、チャネルの適合、ポリシーの遵守、ユニットエコノミクスを検証する。

手元の文脈からモードを推定する。不足している情報は、次の行動を大きく変える場合にだけ尋ねる。そうでなければ前提を明示して進める。

## 証拠台帳から始める

重要な記述は、すべて次のいずれかのクラスに分ける。

- **観察事実（Observed fact）** — 提供されたアナリティクス、顧客記録、プロダクトの挙動、または直接検証した公開情報。
- **報告された事実（Reported fact）** — 創業者・動画・投稿・事例が報告しているが、独立した検証ができないもの。
- **推論（Inference）** — 明示した前提のもとで、事実から導いた結論。
- **仮説（Hypothesis）** — もっともらしいが、まだテストが必要な主張。
- **推奨（Recommendation）** — ここまでの証拠によって正当化される行動。

情報源は次の順に優先する。

1. プラットフォームの公式ドキュメント、法令、ファーストパーティのアナリティクス、ユーザーの生データ。
2. 査読済みの研究と、再現可能なデータセット。
3. 日付・分母・経済性が書かれた、詳細なファーストパーティの事例。
4. 方法論を開示した、実務家のヒューリスティクスとベンチマークレポート。
5. 逸話、文脈のないスクリーンショット、一般論の助言。

マーケティング上の主張、2本の元動画、ASO、SEO、AI による発見可能性（AI discoverability）、紹介、有料ソーシャル広告の助言を検証するときは、[references/evidence-base.md](references/evidence-base.md) を読む。1人の創業者の CPA、コンバージョン率、ローンチ結果を、普遍的なベンチマークへ一般化しない。

## プロダクト・マーケットの論旨を組み立てる

既存のプロダクト・マーケットの論旨（thesis）があれば再利用する。戦術を推奨する前に、依頼された判断に影響する部分を確立するか、明確にする。

- **顧客** — 絞り込んだ1つのセグメントと、行動のきっかけになる状況。
- **ジョブと課題** — 求めている進歩、現在の摩擦、緊急度、頻度。
- **代替手段** — 今使っているもの、今していること。何もしないことも含む。
- **約束（Promise）** — 具体的な成果、時間軸、信じる理由。
- **オファー** — プロダクト、価格、コミットメント、リスクの引き受け（リスクリバーサル）、主要な行動喚起（CTA）。
- **流通の前提** — 顧客がすでに注意を向けている場所、または意図を表明している場所。
- **定着の前提** — 顧客を繰り返し戻らせるはずの、継続的な価値。
- **経済の前提** — 収益モデル、粗貢献（gross contribution）、提供コスト、許容できる獲得コスト。
- **最もリスクの高い前提** — ビジネスを無効にする可能性が最も高い、ただ1つの思い込み。

広い戦略作業では、`assets/marketing-brief.md` のマーケティングブリーフを使い、再利用できる論旨を記録する。範囲の狭いチャネル診断や指標診断は、関係する前提だけに絞る。

## ライフサイクルに応じて進める

プロダクトの現在の段階と、依頼された範囲に合う指針を適用する。手元にある顧客の証拠を使う。範囲の限られた机上調査や実験設計の依頼に対して、インタビューや本格的なローンチプログラムを前提条件にしない。依頼された成果物を用意し、承認された作業は検証まで進める。計画したキャンペーン、提案した計測、観察した結果は、それぞれ別の証拠である。

### 構築前

1. 仮定の関心ではなく、最近の行動について顧客にインタビューする。
2. 検索クエリ、競合のレビュー、サポートのスレッド、コミュニティ、有料の代替手段を調べる。
3. 最もリスクの高い前提を、費用に見合う範囲で最も強いシグナルでテストする。
4. シグナルラダーを優先の目安にする: ページビュー < クリック < メールアドレス < 条件に合う相手との対話 < プロトタイプの利用 < デポジットまたは予約注文 < 繰り返しの利用 < 有料での定着。
5. ウェイトリストは学習を続けてよいという許可として扱い、プロダクト・マーケット・フィット（PMF）の証明としては扱わない。
6. 結果を集める前に、合格・修正・停止のしきい値を決める。

### ローンチ前

1. アクティベーションのイベントと、最初の価値に至る経路を定義する。
2. ローンチの判断に使う計測を定義する。流入元、ファネル、コホート、定着、収益、返金、サポートのうち、関係するシグナルを含める。実装が範囲に含まれるときは、計測を組み込む。
3. 小さく集中したシードコホートを集め、プロダクトを使う様子を観察する。
4. オンボーディング、信頼性、プライバシー、価値提供の深刻な不具合を直す。
5. 主要なチャネルを1つ選ぶ。オーディエンスへの到達手段と運用の余力が見合うときに、副次チャネルや自社所有のフォローアップチャネルを加える。
6. ローンチの施策とフォローアップ実験を、プロダクトのアクティベーションと自然な利用サイクルが見える期間で計画する。

### ローンチ後

最初の弱い環を、次の順に診断する。

`条件に合うリーチ(qualified reach) -> プロダクトページの訪問(product-page visit) -> 登録/インストール(signup/install) -> アクティベーション(activation) -> 定着(retention) -> 収益(revenue) -> 紹介(referral)`

トラフィックを買い増す前に、最も早い段階の重大な漏れを直す。下流の指標は、すべて獲得元（acquisition source）ごとに分けて見る。アクティベーションも定着もしない低コストのインストールは、効率的な成長ではない。

### 拡大前

次の証拠を求める。

- プロダクトの自然な利用間隔で見て、アクティベーションとコホートの定着が安定していること。
- 粗貢献がプラスになる収益化の道筋があること。または、そこへ至る道筋が範囲を区切られ、資金の手当てがあること。
- 定着した顧客の獲得コストが、経済モデルに収まるチャネルがあること。
- サポート、モデレーション、信頼性、ポリシー遵守を回せる運用能力があること。
- 一度きりのバイラルな急増ではなく、再現できる実験があること。

ライフサイクル全体のワークフローと、プロダクト種別ごとの分岐は [references/field-playbook.md](references/field-playbook.md) を読む。

## 流行ではなく行動からチャネルを選ぶ

流通を5つの系統に分類する。

1. **既存の需要を捕まえる** — SEO、ASO、マーケットプレイス、ディレクトリ、比較ページ、意図に基づく検索広告。
2. **需要を生み出す** — 創業者主導のコンテンツ、ショート動画、教育、コミュニティ、イベント、公開デモ。
3. **信頼とオーディエンスを借りる** — パートナーシップ、アフィリエイト、クリエイター、ニュースレター、連携（インテグレーション）、アーンドメディア。
4. **注目を買う** — 有料ソーシャル広告、有料検索広告、スポンサーシップ、リターゲティング。
5. **プロダクト自身に広げさせる** — 招待、共同作業、ユーザーの制作物、紹介、埋め込み、テンプレート、帰属表示のバッジ。

候補チャネルを、オーディエンスの集中度、意図の強さ、メッセージと媒体の適合、速さ、複利的に効く可能性、計測のしやすさ、必要な現金、創業者との適合、ポリシーリスクで採点する。顧客が集中していて、プロダクトを自然に実演できるチャネル1つから始める。チャネルを増やすのは、最初のチャネルがなぜ機能したか、またはなぜ失敗したかを学んでからにする。

チャネル別の戦術、オーガニックコンテンツの計画、有料キャンペーン、ASO/SEO の計画、コールドスタート戦略を作る前に、[references/channel-strategy.md](references/channel-strategy.md) を読む。

## 範囲を区切った実験を設計する

実験は、すべて次の項目で書く。

- 顧客セグメントと、きっかけになる状況。
- `because / therefore / expected observation`（なぜなら / だから / 予想される観察）の形の仮説を1つ。
- 可能なら、対照群またはベースライン。
- 主要指標を1つと、ガードレール指標を2つまで。
- アトリビューションの方法と、コホートの定義。
- ローンチ前に決めた、最短期間またはサンプル数の要件。
- 支出の上限と、創業者の作業時間の上限。
- 合格・修正・停止・フォローアップのルール。
- 交絡要因、目新しさの効果、季節性、プラットフォームの学習についての注記。

ベースラインがないときは、でっち上げない。計測または実現可能性のパイロットを行い、事業上の判断で正当化できる絶対的な行動のしきい値を使い、結果を探索的と明記する。最初の信頼できるコホートを将来のベースラインとして使うのは、流入元、プロダクトのバージョン、計測の品質を確認してからにする。

コンバージョン数が少ないときに、1日のキャンペーンを決定的と呼ばない。オーディエンス、メッセージ、クリエイティブ、ランディングページ、オファーを同時に変えたうえで、何が結果の原因かわかったと主張しない。実験記録を残し、クリックやインストールだけでなく、定着した価値で比較する。

実験のポートフォリオには `assets/experiment-backlog.md` を使う。数式、計測の組み込み、レポーティング、統計上のガードレールは [references/metrics-and-experiments.md](references/metrics-and-experiments.md) を読む。

## プロダクトの成長をプロダクト設計として扱う

共有の仕組みは、ユーザーにとっての価値を中心に設計する。

- ユーザーが誇りに思う、または共有したくなる制作物を作る。
- 受け取った人がすぐに利点を理解できるよう、文脈を保つ。
- 送り手の利点、受け手の利点、プロダクトの利点を両立させる。
- 頼まれていない自動化より、ユーザーが自分で始める、個別化された共有を優先する。
- 共有率、受け手のコンバージョン、受け手のアクティベーション、定着した紹介を測る。
- 個人データを守り、共有される内容をユーザーが事前に確認できるようにする。

ネットワーク型のプロダクトでは、役に立つ最小の密なネットワークを特定する。実際のコンテンツを種まきし、新しい参加者を歓迎し、初期の投稿に反応し、可能ならユーザーが1人でも役に立つプロダクトにする。有料の獲得で流動性の種をまくことはできるが、空の、または価値の低いネットワークを直すことはできない。

## 成功を宣言する前に経済性を計算する

分母をそろえて使う。

- `CPL = 獲得費用 / 条件に合うリード数`
- `CAC = 帰属できる営業・マーケティング費用 / 新規の有料顧客数`
- `CPI = 獲得費用 / 増分インストール数`
- `アクティベーション率 = アクティベートした新規ユーザー数 / 対象となる新規ユーザー数`
- `定着率 = 期間 N の時点でアクティブなコホートのユーザー数 / 対象となるコホートのユーザー数`
- `粗貢献 = 収益 - プラットフォーム手数料 - 変動インフラ費 - サポート・提供のコスト`
- `回収期間 = CAC / 顧客1人あたりの月次粗貢献`

顧客生涯価値（LTV）を見積もるのは、解約率と粗利率がそれを支えられるほど安定しているときだけにする。初期段階では、精密な LTV ではなく感度の幅を示す。「良い CPA は ¥100–¥300」のような普遍的な言明は退ける。許容できる獲得コストは、アクティベーション、定着、収益化、利益率、回収期間、資金の制約によって決まる。

## コンプライアンスと信頼のゲートを通す

キャンペーンを推奨または実行する前に、次を満たす。

- 有償またはインセンティブ付きの推奨（エンドースメント）は、明確に開示する。
- ウェイトリストの目的と、集めた連絡先データの利用目的を示す。
- ユーザー、ランキング、レビュー、推薦の声、緊急性、プロダクトの機能を捏造しない。
- 自動化、一括返信、いいね、フォロー、メッセージ送信は、プラットフォームのルールに従う。
- 必要なトラッキングの同意を取り、プラットフォームのプライバシー要件を守る。
- フェイクドアテストは、コミットする時点で透明にし、明確な次のステップか返金を用意する。
- コミュニティ型のプロダクトでは、UGC のモデレーション、著作権、商標、年齢、安全、通報の義務を確認する。

日本向けとプラットフォーム別のガードレールは [references/ethics-and-compliance.md](references/ethics-and-compliance.md) を読む。法的な不確実性は明示し、重要な場合は有資格の専門家への相談を勧める。

## 判断に使える成果物を出す

選んだモードに必要な、最小限の組み合わせを渡す。

1. **エグゼクティブ診断** — 現在のライフサイクル段階と、最初の制約。
2. **証拠台帳** — 事実、報告された事実、推論、仮説と、その確度。
3. **顧客とポジショニングの論旨** — 焦点を絞ったオーディエンス・メッセージ・オファーの組み合わせ1つ。
4. **優先順位付きの施策** — 今・次・後に分け、それぞれ理由を付ける。
5. **実験カード** — 指標、ガードレール、予算、期間、判定ルール。
6. **計測計画** — イベント名、流入元のフィールド、コホート、レポートの頻度。
7. **リスクとコンプライアンスの確認** — 信頼、ポリシー、プライバシー、運用上の制約。
8. **学習課題** — まだわかっていないことと、それを学ぶ最も安価な方法。

ローンチの作業には `assets/launch-plan.md`、ローンチ後の診断には `assets/growth-scorecard.md` を使う。[references/case-studies.md](references/case-studies.md) は、類推や事例が推奨を実質的に良くするときだけ読む。写すのは仕組みであり、表面的な戦術や虚栄の指標ではない。
