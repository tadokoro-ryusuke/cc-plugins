# Claude Code での実行ノート（indie-idea-discovery）

このファイルは cc-plugins が所有する。SKILL.md は codex-plugins の正本からの翻案で、同じフォルダの他の references と assets は英語原文のコピー。判断規則と完了条件の正本はそちらにあり、ここには Claude Code のツールでそれをどう実行するかだけを書く。

## スキルの参照名

- 同じプラグインの他のスキルは、`indie-product-marketing:<skill>` の名前で参照する。
  - 需要検証・ローンチ・集客: `indie-product-marketing:indie-product-marketing`
  - LP の設計と構築: `indie-product-marketing:global-landing-design`
- 英語の references・assets にある "the indie-product-marketing skill" は、`indie-product-marketing:indie-product-marketing` を指す（`references/evaluation-and-handoff.md`、`references/evidence-and-video-audit.md`、`assets/validation-handoff.md`）。

## Web の証拠

- WebFetch は、小型モデルによるページの要約を返す。数値・引用・価格・規約の文言は、生のソース（ブラウザ MCP のページテキスト、curl で取得した本文など）で照合する。
- 照合できなければ、`assets/problem-evidence-ledger.md` の該当行の `Source or URL` 列に「要約経由・未照合」と併記する。照合するまでは、SKILL.md の「観察事実」（検証済みの公開された事実）として扱わない。
- WebSearch は US-only で動く。日本市場の調査では、既知の一次 URL（公式サイト、価格ページ、官公庁の資料、日本向けのアプリストアのページなど）を直接取得する。
- 取得したソースには、URL と取得日を記録する。
- ログイン済みのブラウザでコミュニティやレビューを読むときも、`references/discovery-methods.md` の 5 節のとおり、規約・プライバシー・同意・コミュニティの規範を守る。アクセスできるというだけで、機微な個人データを収集・転載しない。

## 文脈の隔離

SKILL.md のフェーズ3「独立したパスが終わってから統合する」とフェーズ5「生成が完了してから採点する」を、サブエージェントで実行する方法。

- **創業者の種パスは親が扱う。** 創業者が自力で挙げた課題とコンセプトは、ユーザーとの対話で集める。AI の候補を見せる前に集め、サブエージェントには任せない。
- **ほかのパスは別々のサブエージェントで走らせる。** 規模の大きい発見やコンセプトの展開では、証拠主導パス・構造化した組み合わせパス・地味な課題のパスを、それぞれ別の Agent ツール呼び出し（組み込みの `general-purpose`）にする。
  - 各サブエージェントには、そのパスの証拠・次元・目的だけを渡す。創業者の制約や探索範囲など、パスの前提になる文脈は渡してよい。
  - 他のパスの候補と、モデルによる評価は見せない。
  - 指示には、前提と欠けているソースに印を付けること、インタビューの引用・レビューの抜粋・顧客数・支払意思・競合の事実を作らないことを含める（`references/divergence-and-morphology.md` の 5 節）。
- **統合は親が行う。** すべてのパスが終わってから、フェーズ4 の正規化と重複の除去をする。
- **採点は新しい文脈で行う。** 採点するサブエージェントには、正規化したカード（`assets/opportunity-card.md`）と証拠台帳を渡す。ハードゲートと同点の決着に要るため、発見ブリーフ（`assets/idea-portfolio.md` の Decision context など）にある創業者の目的と制約も渡してよい。生成パスの会話やモックアップは渡さない。
- **同じモデルによる採点は、順位付けの補助であり、市場の事実の認定ではない。** 採点の結果を台帳の証拠として記録しない。
- **証拠の収集は並列にしてよい。** 種類の異なるソース（レビュー、コミュニティ、価格ページ、求人など）は、並列のサブエージェントで集めてよい。その場合も台帳の行の形で返させ、照合は「Web の証拠」の節に従う。
- **小さな依頼は親が直接処理する。** 1つのアイデアの監査、少数の候補の比較、一問一答などが該当する。サブエージェントを使うのは、独立性や文脈の隔離が調整のコストを上回るときだけにする。

## 外部への働きかけ

発見の作業にも、外部へ働きかける場面がある。インタビューの依頼、コミュニティへの投稿や質問、DM・リプライ・メール、関心を測るページの公開、広告などである。Claude Code ではブラウザ MCP や CLI でこれらを実行できてしまうため、次の境界を守る。

- 下書きや設計までは進めてよい。送信・投稿・公開・出稿・課金は、ユーザーの明示の指示があるときだけ行う。
- 一括・自動のエンゲージメント（自動のいいね、一括の DM など）は、指示があっても行わない。
- 候補の比較ボードなどを Artifact にした場合も、公開リンク化はユーザーの明示の指示があるときだけ行う。
- 検証の作業に進んだ後の境界は、`indie-product-marketing:indie-product-marketing` に従う。

## 隣接スキルとの棲み分け

- 法規の深い論点（個人情報、生成物の権利など）は、compliance-core のスキルに任せる（導入されている場合）。
- 受託案件の営業・見積には使わない。受託案件の業務設計やシステム化範囲の線引きは、delivery-core:business-service-design の担当（導入されている場合）。

## dev-core への接続

- 発見の段階の機会仮説を、そのまま実装計画にしない。SKILL.md のフェーズ6と引き継ぎの節のとおり、まず `indie-product-marketing:indie-product-marketing` で検証する。
- 検証を通ったコンセプトを MVP にするときは、`assets/validation-handoff.md` と検証で得た結果を `/dev-core:task` に渡して計画にする（dev-core が導入されている場合）。
- `/dev-core:task` はユーザーが起動するコマンドで、モデルからは呼び出さない設定になっている。そのため、ユーザーに実行を提案する。
