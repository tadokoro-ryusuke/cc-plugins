# OSS License Audit

**鉄則: 解釈で勝負しない。強コピーレフトを頒布物に入れない。**

コピーレフトの伝播範囲（派生物該当性）は解釈が割れる論点であり、受託納品では「議論に勝つ」より「議論になる依存を入れない」方が常に安い。

> 本スキルは法的助言ではなく実務の型である。グレー判定・訴訟リスクの最終判断は弁護士・弁理士に委ねること。標準・ツールの記載は目安（2026年時点）であり、採用前に最新状況を要確認。

## 実行タイミング（2回）

1. **依存追加時**: 新しいライブラリを package.json 等に足す前にライセンスを確認する（後から抜くコストは追加前確認の何倍にもなるため）。
2. **納品前監査**: 依存ツリー全量をスキャンし、SBOM と第三者ソフトウェア一覧を納品物に添付する（納品後の発覚は知財瑕疵として契約不適合責任に直結するため）。

## Step 0: 頒布形態を判定する

最初に「この納品物は頒布されるか」を確定する。コピーレフトの開示義務が発動するかどうかの分水嶺だからである。

| 納品形態 | 頒布に当たるか | GPL の開示義務 | AGPL の開示義務 |
|---------|--------------|---------------|----------------|
| サーバサイドのみ（SaaS/Web アプリのバックエンド） | 当たらない | 発動しない | **発動する**（ネットワーク越し利用で発動） |
| フロントエンドバンドル（ブラウザに配布される JS） | **当たる** | 発動する | 発動する |
| デスクトップ/モバイルアプリ、組込み、パッケージ販売 | 当たる | 発動する | 発動する |
| 顧客へのソースコード納品（顧客が再頒布しうる） | 顧客の利用形態に依存 | 顧客側で発動しうる | 顧客側で発動しうる |

- 「GPL をサーバサイドで使うだけなら開示義務は発動しないが、AGPL は SaaS でも発動する」——この差を顧客に説明できることが受託者の専門性になる。
- ソースコード納品の場合は自社で完結せず、顧客の再頒布計画を確認して判定する（判定を顧客に伝えた記録を残す）。

## Step 1: ライセンス類型マップで依存を分類する

| 類型 | 代表 | 義務の要点 | 受託納品での扱い |
|------|------|-----------|----------------|
| パーミッシブ | MIT / BSD-2/3 / ISC | 著作権表示・ライセンス文の同梱 | 表示一覧を添付すれば原則安全 |
| パーミッシブ+特許 | Apache-2.0 | 上記+ NOTICE ファイルの保持、特許条項 | **NOTICE の同梱漏れ**に注意 |
| 弱コピーレフト | LGPL-2.1/3.0, MPL-2.0 | 当該ライブラリ改変部分の開示。動的リンクなら本体非開示で可（LGPL） | 静的リンク・改変時に要精査 |
| 強コピーレフト | GPL-2.0/3.0 | 結合著作物全体のソース開示（頒布時） | 頒布形態の納品では原則回避 |
| ネットワークコピーレフト | AGPL-3.0 | ネットワーク越し利用でもソース開示 | SaaS でも発動。**最重要の検出対象** |
| ソース公開系・商用対抗 | SSPL, Elastic License 2.0, BSL | OSI 非認定。サービス提供形態に強い制約 | 「OSS のつもり」事故の頻発地帯。OSS 扱いしない |

## Step 2: ライセンスポリシーを定めて CI ゲート化する

判定を人の記憶に置かず、ポリシーファイルと CI に置く。AI が依存を高速に追加する開発では、レビュー時の目視は必ずすり抜けるからである。

**ポリシー標準（プロジェクト開始時に顧客と合意し、リポジトリにコミットする）:**

- **許可（自動パス）**: MIT / BSD-2/3 / ISC / Apache-2.0 / CC0 / Unlicense / Python-2.0 / Zlib
- **要相談（人間判定に回す）**: LGPL / MPL-2.0（リンク形態・改変有無を確認）、デュアルライセンス品、ライセンス表記なし・UNKNOWN
- **禁止（CI で fail）**: GPL-2.0/3.0（頒布物の場合）、AGPL-3.0（常に）、SSPL / Elastic License 2.0 / BSL、独自ライセンスで再頒布条件不明のもの

**CI ゲート設定手順:**

1. 上記リストをツールのポリシーファイルに書き起こす（cargo-deny の `deny.toml`、ORT のポリシーファイル、license-checker の `--failOn` 引数など）。
2. CI の依存インストール直後にスキャンステップを追加し、禁止ライセンス検出で **fail させる**（警告止まりは必ず無視されるため）。
3. 「要相談」検出時は fail させつつ、例外承認は許可リストへの明示的追記（レビュー付きコミット）でのみ通す。承認の履歴が Git に残る。

**scripts 化候補**: `scripts/license-gate.sh`（言語検出→該当スキャナ実行→ポリシー照合）、`scripts/generate-third-party-list.mjs`（スキャン結果→納品用一覧の Markdown 生成）。決定的なロジックはスキル本文でなくテスト済みスクリプトに置く。

## Step 3: 言語別スキャンを実行する

日常（依存追加時・CI）はマニフェスト走査で足りる。**必ず推移的依存（依存の依存）まで全量を対象にする**。

```bash
# Node.js（npm）
npx license-checker --production --summary
npx license-checker --production --failOn "GPL-2.0;GPL-2.0-only;GPL-2.0-or-later;GPL-3.0;GPL-3.0-only;GPL-3.0-or-later;AGPL-3.0;AGPL-3.0-only;AGPL-3.0-or-later"
# Node.js（pnpm）
pnpm licenses list --prod

# Python
pip-licenses --format=markdown --with-urls
pip-licenses --fail-on="GNU General Public License v3 (GPLv3);GNU Affero General Public License v3"

# Rust（deny.toml に allow/deny リストを定義して実行）
cargo deny check licenses

# Go
go-licenses report ./...
go-licenses check ./... --disallowed_types=forbidden,restricted
```

- **禁止リストは SPDX 変種を網羅する**。ツールの照合は文字列完全一致のため、まず `--summary` で実際に報告されるライセンス表記を確認してから failOn リストを作る（`GPL-3.0` と `GPL-3.0-only`、pip-licenses の長い正式名など、表記はツール・パッケージごとに揺れる）。
- 出力の UNKNOWN / Custom は「安全」ではなく「未判定」。1件ずつ実ライセンスファイルを確認して分類する。
- lockfile を基準にスキャンする（package.json の宣言ではなく実際に解決されたバージョンが義務の対象だから）。

## Step 4: 本格スキャナへの格上げを判断する

マニフェスト走査はパッケージメタデータの申告値しか見ない。以下に該当する案件だけ本格スキャナに格上げする2段階運用がコスト的に現実的である。

| 手段 | 使いどころ |
|------|-----------|
| マニフェスト走査（Step 3） | 通常の Web/業務システム案件。CI ゲートとセットで常用 |
| ScanCode Toolkit（OSS） | ファイル単位のライセンス検出が必要な場合（ベンダリングしたコード・コピーされたファイルの検出）。SPDX/CycloneDX 出力可 |
| ORT / FOSSology（OSS） | ポリシー評価〜監査ワークフローまで自動化したい継続案件 |
| 商用（FOSSA / Black Duck / Snyk / Mend） | スニペット検出・監査グレードの証跡が要る組込み・パッケージ販売系の納品 |

**格上げ基準**: 頒布形態の納品（アプリ配布・組込み・ソース販売）、顧客の調達審査で監査証跡を要求された場合、ベンダリング/コピー由来コードが多いリポジトリ。

## Step 5: SBOM を生成して納品に添付する

SBOM+ライセンス一覧の標準添付は、経産省「SBOM 導入に関する手引」が買い手側の共通言語になりつつある流れ（2026年時点・要確認）に乗る差別化になる。

```bash
# Syft（ディレクトリまたはコンテナイメージから生成）
syft dir:. -o spdx-json > sbom.spdx.json
syft dir:. -o cyclonedx-json > sbom.cdx.json

# Trivy
trivy fs --format spdx-json --output sbom.spdx.json .

# npm 標準機能
npm sbom --sbom-format spdx > sbom.spdx.json
```

- フォーマットは **SPDX**（ISO/IEC 5962 として国際標準化）または **CycloneDX**（ECMA 標準化）。顧客指定がなければ SPDX-JSON を既定とし、両方の生成コマンドを README に残す。
- 生成は CI のリリースジョブに組み込み、リリースタグと同じコミットから生成する（納品物と SBOM の対応が崩れると監査価値がなくなるため）。
- 納品様式: `deliverables/sbom/` に SBOM ファイル、`deliverables/THIRD-PARTY-NOTICES.md` に次節の一覧、`deliverables/licenses/` に各ライセンス全文と NOTICE を集約。

## Step 6: 納品用「第三者ソフトウェア一覧」を作成する

スキャン結果から機械生成し、目視で UNKNOWN を潰してから納品する。テンプレート:

```markdown
# 第三者ソフトウェア一覧（THIRD-PARTY-NOTICES）

本ソフトウェアには以下の第三者ソフトウェアが含まれます。
各ライセンスの全文は licenses/ ディレクトリを参照してください。

| # | 名称 | バージョン | ライセンス (SPDX ID) | 著作権表示 | NOTICE |
|---|------|-----------|---------------------|-----------|--------|
| 1 | example-lib | 2.4.1 | MIT | Copyright (c) 20XX Example Authors | - |
| 2 | example-http | 5.0.0 | Apache-2.0 | Copyright 20XX Example Project | licenses/NOTICE-example-http |

- 生成日: YYYY-MM-DD / 対象コミット: <hash> / 生成ツール: <tool name + version>
- Apache-2.0 の NOTICE ファイルは原文のまま licenses/ に集約して同梱する。
```

- 「名称・バージョン・ライセンス・表示文」の4点は最低限。バージョンを省略しない（バージョンによってライセンスが変わるライブラリがあるため）。
- 一覧の生成は scripts 化候補（Step 2 参照）。手作業の転記はバージョン更新のたびに乖離する。

## 落とし穴チェックリスト（納品前に全項目を確認する）

- [ ] **推移的依存の AGPL 混入**: 直接依存だけ見て見逃す事故の典型。頻出例は ghostscript 系・iText（5系以降は AGPL。4系以前は MPL/LGPL だが保守終了）・readline 系（GPL）。全量スキャンで検出する。
- [ ] **フロントエンドバンドル＝頒布**: ブラウザに配られる JS はサーバサイドと違い「頒布」に当たる。バンドルに含まれる依存を別途スキャンしたか。
- [ ] **Apache-2.0 の NOTICE 漏れ**: ライセンス文だけ同梱して NOTICE ファイルを落とすのが頻出ミス。NOTICE を持つ依存を列挙して集約したか。
- [ ] **デュアルライセンス**（Qt、MySQL Connector 等）: OSS 側ライセンス（GPL 等）の条件を満たせない場合、商用ライセンス購入という解決手段があることを顧客に提示したか（購入の費用判断は自組織の見積・価格判断プロセスへ）。
- [ ] **SSPL / Elastic License 2.0 / BSL を「OSS」扱いしていないか**: OSI 非認定。サービス提供形態への制約を個別に読む。
- [ ] **ライセンス表記なし（UNKNOWN）を放置していないか**: 表記なしは「自由に使える」ではなく「許諾がない」。作者への確認か除去で解消する。
- [ ] **コード断片（スニペット）の混入**: Stack Overflow や AI 出力経由のライセンス不明断片はマニフェスト走査では検出不能。→ genai-ip-clearance 参照（AI 生成コードの権利処理はそちらが正本）。

## グレー判定のエスカレーション基準

以下に1つでも該当したら、AI・エンジニア単独で結論を出さず人間の判断（必要なら弁護士・弁理士）に上げる。派生物該当性は解釈問題であり、事後に「エージェントが安全と判定した」は防御にならないからである。

1. **LGPL/GPL ライブラリとの結合形態が論点になる場合**: 静的リンク・改変・同一プロセスでの密結合など、「派生物か否か」の解釈が結論を左右するとき。
2. **禁止ライセンスの依存に代替が存在しない場合**: 例外承認（リスク受容）は経営判断であり、技術判断ではない。
3. **頒布/SaaS の判定が納品後の顧客の行動に依存する場合**: 顧客の再頒布・再販計画の確認と、判定根拠の書面化が必要。
4. **ライセンス原文が英語独自ライセンスで再頒布条件が読み切れない場合**。
5. **既に混入が発覚した場合**: 除去・置換・開示・商用ライセンス購入のどれを取るかは契約責任に関わるため、顧客への報告方針込みで人間が決める。

エスカレーション時は「対象ライブラリ・ライセンス・混入経路（依存パス）・利用形態・選択肢と各リスク」を1枚にまとめて渡す。判断材料の整理までが AI の仕事である。

## 分担線: AI がやること / 人間にしか決められないこと

**AI（このスキルを実行するエージェント）がやること:**

- 依存ツリーの全量スキャンと類型マップへの分類、義務の要約
- ポリシーファイル・CI ゲートの作成と保守、違反検出時の代替ライブラリ提案
- SBOM 生成、第三者ソフトウェア一覧・NOTICE 集約の自動生成
- UNKNOWN ライセンスの一次調査（リポジトリの LICENSE ファイル確認）
- エスカレーション用の判断材料整理（依存パス・選択肢・各リスクの一覧化）

**人間にしか決められないこと:**

- 「派生物か否か」のグレー判定と、その顧客への説明
- 禁止ライセンスの例外承認（リスク受容）と、デュアルライセンス購入等のビジネス判断
- 混入発覚時の顧客への報告方針・タイミング
- ポリシー標準そのものの改定（許可/禁止の線引きは契約責任と表裏一体）
