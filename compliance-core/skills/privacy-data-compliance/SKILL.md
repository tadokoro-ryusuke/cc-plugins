# Privacy & Data Compliance（個人情報保護法の実務）

**鉄則: これは法的助言ではなく「実務の型」である。最終判断は弁護士と個人情報保護委員会（PPC）の一次情報（ガイドライン・Q&A）に委ねること。**

本スキル中の期限・数値・改正動向はすべて **目安（2026年時点）・要確認** として扱い、適用前に PPC の最新の一次情報で検証する。

## 分担線: AI がやること / 人間にしか決められないこと

このスキルを実行するエージェントは、両者を混同してはならない。AI 側の作業はすべて「ドラフト」として提示し、人間側の判断を先取りしない。

| AI（このスキルを実行するエージェント）がやること | 人間にしか決められないこと |
|---|---|
| データ分類表のドラフト（スキーマ・フォーム定義から個人データ項目を抽出） | 「要配慮個人情報に当たるか」等のグレー区分の最終判定 |
| ガイドライン・Q&A との照合、条文・公表事項チェックリストとの突合 | 漏えい等を報告する/しないの最終判断（過少報告は行政リスク、過剰報告は顧客関係リスク） |
| 顧客提示の契約書と標準8条項との差分抽出 | クラウド例外該当性のグレー判断（迷ったら「委託扱い」に倒す保守判断） |
| タグ・SDK の棚卸し（静的解析・ネットワークログ）、外部送信一覧のドラフト | 第一報を出す判断と文面の最終確認（法的・営業的に最も重い一手） |
| 漏えい時のタイムライン整理・報告書ドラフト・PPC 様式への転記 | 弁護士・保険会社への連絡判断、謝罪と信頼回復のコミュニケーション |
| 改正法の差分要約・施行状況の確認タスク化 | リスクを取るかの経営判断、専門家に投げるかの見極め |

## Step 1: データ区分判定（最初に必ずやる）

扱うデータがどの区分かで発動する義務が変わるため、実装・契約より先に判定する。

| 区分 | 定義の要点 | 発動する主な義務 |
|------|-----------|----------------|
| 個人情報 | 生存する個人に関する情報で特定個人を識別できるもの（個人識別符号含む） | 利用目的の特定・通知公表、適正取得 |
| 個人データ | 個人情報データベース等を構成する個人情報 | 安全管理措置、第三者提供制限、漏えい等報告 |
| 保有個人データ | 開示・訂正等の権限を持つ個人データ | 開示請求等への対応、公表事項（法32条） |
| 要配慮個人情報 | 病歴・犯罪歴・人種等 | 取得に本人同意。漏えい時は**件数を問わず**報告対象 |
| 仮名加工情報 | 他の情報と照合しない限り識別不可に加工 | 開示請求等の適用除外・第三者提供原則禁止（社内分析用） |
| 匿名加工情報 | 復元不可能に加工 | 加工基準・公表義務を守れば本人同意なく第三者提供可 |
| 個人関連情報 | Cookie・広告ID等、上記いずれにも該当しないもの | 提供先で個人データになる場合の同意確認（法31条） |

判定の要点:

- 実務の分水嶺は「個人情報か否か」ではなく「**個人データ**か否か」。DB 化された時点でほぼ個人データになる。なぜなら、安全管理措置・漏えい等報告など重い義務は個人データで発動するため。
- 統計・改善目的の分析なら仮名加工情報に倒す選択肢を提示する。開示請求・漏えい報告の負荷が下がるため、データ分析基盤の受託で提案価値がある。
- 「個人情報は扱わない」案件でも、ログ・フォーム経由の流入時の扱いを必ず決める。口頭合意のまま流入して無防備に漏えいする事故が定番のため。

## Step 2: 案件開始時のデータ分類チェックリスト

要件定義〜設計段階で以下の5軸の分類表を作り、案件の正本として管理する。この表が安全管理措置・プライバシーポリシー・削除設計のすべての起点になるため。

```
| データ項目 | 区分（Step 1の7区分） | 保存先（DB/ログ/SaaS/AI API） | 保存期間・削除方法 | アクセス権（誰が・どの権限で） |
```

作成時のチェック:

- [ ] フォーム入力・API・ログ・分析タグの**全取得点**を列挙したか（コードとインフラ設定から逆引きする）
- [ ] 各項目の区分を判定し、要配慮個人情報の有無を明示したか（漏えい時の報告要否が変わるため）
- [ ] 保存先に SaaS・クラウド・生成AI API を含めたか（→ Step 4 のクラウド例外判定の入力になる）
- [ ] 保存期間と削除方法（物理削除/論理削除/バックアップ）を項目ごとに決めたか
- [ ] 検証環境への本番データコピーを禁止し、マスキング/合成データを標準にしたか（検証環境の漏えいも報告対象のため）
- [ ] 外国のサーバ・事業者が関与する場合、所在国を記録したか（「外的環境の把握」の根拠になる）
- [ ] 分類表を顧客（委託元）と合意し、技術的措置（アクセス制御・ログ・暗号化）を設計書に明記したか

## Step 3: 委託契約のデータ取扱条項レビュー（標準8条項）

受託者は個人データの「取扱いの委託」を受ける**委託先**であり、委託元は法25条により受託者を監督する義務を負う。自社ひな形にはこの8条項を最初から入れ、顧客ひな形を使う場合は欠落をレビューする。欠落は自社に不利ではなく「双方のリスク」であるため、指摘は双方の保護として提示する。

| # | 条項 | 要点 |
|---|------|------|
| 1 | 目的外利用の禁止 | 委託業務の遂行に必要な範囲に限定 |
| 2 | 安全管理措置 | 講ずべき措置の水準（暗号化・アクセス制御等）を具体化 |
| 3 | 再委託の制限 | 事前の書面承諾制+再委託先に同等義務をフローダウン |
| 4 | 漏えい時の通知 | 「知ってから24時間以内に第一報」等の期限と報告様式 |
| 5 | 返還・消去 | 契約終了時の返還/消去と消去証明書の交付 |
| 6 | 監査・報告 | 委託元の監査受入れ、定期報告（年次点検） |
| 7 | 従業者の監督 | 秘密保持誓約、アクセス権限の最小化 |
| 8 | 損害賠償・責任 | 賠償範囲と責任制限（契約本体の責任制限条項と整合させる） |

欠落レビューの観点:

- 8条項との差分を機械的に抽出し、欠落・上書き・矛盾（例: 本体の責任制限と特約の無限責任の衝突）を列挙する。
- **再委託の落とし穴**: 小規模受託では外注パートナー・クラウド・SaaS が実質的な再委託先になる。利用する SaaS/クラウドの一覧を契約時に開示して包括承諾を取る形に倒す。無断再委託は契約違反+委託元の監督義務違反を誘発するため。
- 委託先の監督は「①適切な選定 ②契約締結 ③取扱状況の把握」の3点セット（ガイドライン通則編）。③に応える定期報告テンプレを用意しておくと監査対応が軽くなる。
- 顧客のセキュリティチェックシートには実態と一致する回答のみを書く。虚偽回答は監査で発覚すると契約解除事由になるため、満たせない項目は代替統制（MFA・監査ログ・暗号化）で説明する。
- 契約全般の設計（準委任/請負・検収・責任制限の本体）は本スキルの範囲外。自組織の契約実務・弁護士レビューに送る。
- 2026年改正（未施行）の施行後は、条項1が法定義務（第30条の3）になり、条項4などが委託先の義務免除（第58条の2）の要件に関わる。複数年の契約やひな形を今作るときは、後述の「2026年改正の扱い」の確認項目を施行時に見直す前提で進める。

## Step 4: クラウド例外の該当性判定（PPC Q&A 7-53）

クラウド・SaaS・生成AI API に個人データを置く/入力する前に、必ずこのフローで判定する。判定結果は再委託の承諾範囲とプライバシーポリシーの記載に直結するため。

```
Q1. その事業者は個人データを「取り扱わないこととなっている」か?
    ①契約条項で取り扱わない旨が定められている AND
    ②適切なアクセス制御が行われている
 ├─ YES → クラウド例外に該当（第三者提供にも委託にも該当しない=事業者の監督義務なし）
 │        ただし「外的環境の把握」（サーバ所在国の制度把握）は自らの安全管理措置として必要。
 │        公表事項（プラポリ）への反映も必要。
 └─ NO / グレー → 「委託」として扱う（Step 3 の監督・契約対象に含める）
```

判定の注意:

- 「AWS だから何もしなくてよい」は誤り。2024年3月に PPC がクラウド例外の誤用へ注意喚起（行政指導事例）を出している（文書名・趣旨は PPC サイトで要確認）。運用サポート等で事業者が中身にアクセスできる設計なら委託に該当し監督が必要。
- **生成AI API への個人データ入力も同じ枠組みで整理する**: 学習に利用されない設定（API 既定・ZDR 等）なら「取り扱わない」構成に近づくが、該当性は契約（利用規約・DPA の条項）と技術的措置で個別判断する。コンシューマ向け無料プランは原則不可。
- グレーなら「委託扱い」に倒す（保守判断）。倒す判断自体は人間が行う（分担線参照）。
- 生成AIへの入力可否の合意設計・AI利用ポリシー全体は → genai-ip-clearance 参照。

## Step 5: 外部送信規律対応（改正電気通信事業法27条の12）

Cookie・タグ・SDK 経由でユーザー端末から外部へ情報を送信させる場合、送信される情報・送信先・利用目的の**通知または公表**（または同意/オプトアウト）が必要。個人情報保護法とは**別の法律・別の義務**である点を顧客に明示する（プラポリだけでは足りないため）。

棚卸し手順:

1. コードベース・タグマネージャ設定・ビルド成果物から、GA4・広告タグ・SNS ピクセル・チャット SDK 等の外部送信を静的解析で列挙する。
2. 実際のネットワークログ（開発者ツール/プロキシ）で送信先を突合する。実装と文書のずれ（書いていない SDK が送信している）が最大のリスクであり、これは開発者にしか検証できないため。
3. 「外部送信ツール一覧」を作成する: ツール名 × 送信される情報 × 送信先事業者 × 利用目的。
4. 一覧を元データとして「外部送信ポリシー」公表ページを実装する。
5. タグを1つ足すごとに公表ページの更新が必要になる運用コストを顧客に説明し、タグの棚卸しを年次運用に入れる。

プライバシーポリシー支援の注意:

- 弁護士でない者による法律文書の作成代行は非弁リスクがある。**「ひな形+設計支援+弁護士レビュー推奨」のスタンス**を守り、最終版は顧客名義・顧客側弁護士レビューで確定させる。
- プラポリは「書く」前に「データフロー図を描く」（取得点→保存→第三者提供・外部送信の全経路)。Step 2 の分類表から生成する。
- 利用目的の特定（法17条）は「事業活動に用いるため」では不可。プロファイリング的利用は**分析することまで含めて**特定する。
- 同意チェックボックスを設けたら同意ログの保存設計まで実装する。争いになったとき立証できないため。

## Step 6: 越境移転チェック（法28条・3ルート）

外国にある第三者へ個人データを提供する場合、以下のいずれかのルートに乗せる（目安・2026年時点。詳細は PPC ガイドライン外国第三者提供編で要確認）。

1. **本人の同意**（移転先国の制度等の情報提供を伴う）
2. **基準適合体制**の整備された事業者への提供（相当措置の継続的実施+本人への情報提供対応）
3. **十分性認定国**（EU・英国等、PPC 指定国）への提供

注意:

- クラウド例外に該当する場合は「提供」に当たらないため3ルートは不要だが、**外的環境の把握**（所在国の制度把握と公表）は残る。Step 4 と必ずセットで判定する。
- EU 居住者へのサービス提供・行動監視があるなら GDPR の域外適用も検討対象になり、二重設計になる。早期に弁護士エスカレーション（後述）へ。

## Step 7: 漏えいインシデント初動（委託先として）

### 報告対象4類型と期限（いずれも「おそれ」段階を含む。目安・2026年時点・要確認）

| 類型 | 例 |
|------|----|
| 1. 要配慮個人情報の漏えい等 | 病歴を含むDBの流出（件数問わず） |
| 2. 財産的被害が生じるおそれ | 決済情報・クレジットカード情報 |
| 3. 不正の目的をもって行われたおそれ | サイバー攻撃・内部不正。ランサムウェアやウェブスキミングは1件でも対象 |
| 4. 1,000人超の漏えい等 | 大規模流出 |

- **速報: 知った時から概ね3〜5日以内**、**確報: 30日以内（不正目的類型は60日以内）**に PPC へ報告。本人通知も原則必要。
- 委託先（=自社）は**委託元への通知により自らの PPC 報告義務を免れうる**（法26条1項ただし書。通知の方法は規則で定める）。だからこそ契約の第一報期限（Step 3 条項4）の遵守が最重要になる。
- 2026年改正（未施行）の施行後は、本人に通知しなくても権利利益の保護に欠けるおそれが少ない場合（規則で定める）に、本人通知を代替措置で済ませられる（第26条第2項）。施行後に要件を確認する（→ 後述の「2026年改正の扱い」）。

### 初動フロー

1. **検知・封じ込め**（即時）: 認証情報ローテーション、該当システムの隔離。証拠保全（ログ・タイムライン）を並行。
2. **委託元へ第一報**（契約期限内、なければ24時間以内目安）: **完全な情報が揃うのを待たない**。速報は「不明」を含んでよい設計になっているため、原因究明を優先して第一報を遅らせるのが最悪手。
3. **報告義務の整理**: 契約と事案に応じて委託元と共同で速報・確報を準備。
4. **本人通知・公表の要否判断**: 委託元主導。自社は事実関係・影響範囲の技術調査を提供する。
5. **再発防止と記録**: 原因分析は → dev-core:debug の4フェーズ参照。対応記録を保存し、契約・体制文書に反映する。

### 委託先としての第一報テンプレ

```
件名: 【第一報】個人データ漏えいのおそれに関するご報告（<案件名>）

1. 検知日時: <YYYY-MM-DD HH:MM>（検知手段: <監視アラート/顧客指摘/等>）
2. 現時点で判明している事実:
   - 対象システム / データ項目 / 件数（概数。不明なら「調査中」と明記)
   - 要配慮個人情報の該当有無: <あり/なし/調査中>
3. 現時点で不明な事項: <侵入経路 / 影響範囲 / 等>
4. 実施済みの封じ込め措置: <認証情報ローテーション / 隔離 / 等>
5. 次報予定: <YYYY-MM-DD HH:MM までに続報>
6. 連絡窓口: <氏名・連絡先>
```

## 2026年改正の扱い（成立と施行を区別する）

- 改正法は「個人情報の保護に関する法律等の一部を改正する法律」（令和8年法律第56号）。2026-07-10 に**成立**、07-17 に**公布**された。施行は「公布の日から起算して2年を超えない範囲内において政令で定める日」（附則第1条）で、具体日を決める政令はまだ無い。例外として、一部の罰則規定などは公布から6月を経過した日（2027-01-17）に先に施行される（附則第1条第3号）。課徴金は2年以内の本体に入る。
- 個人情報保護委員会は、政令・規則の「基本的な考え方」①〜③を 2026-09-16、10-01、10-14 に決めた段階で、規則・ガイドラインはまだ策定中。下の論点の細目は規則で変わりうる。
- 出典（確認日 2026-10-26）: PPC「令和８年 改正個人情報保護法について」 https://www.ppc.go.jp/personalinfo/legal/r8kaiseihogohou/ （条文・概要・基本的な考え方①〜③の PDF を掲載）。法律番号と施行日の区分は e-Gov 法令 API の改正履歴（https://laws.e-gov.go.jp/api/2/law_revisions/415AC0000000057 ）でも照合した。
- 顧客向け説明では「成立済み」と「施行済み」を必ず区別する。「課徴金がもう課される」と説明するのは誤りであり、逆に「まだ関係ない」と切り捨てるのも準備期間を失わせるため。
- 施行前のこの期間は、顧客向け改正対応の点検（データ分類表・委託契約・プラポリの再確認）を提案する好機として扱う。

### 受託開発に効く論点（未施行。細目は委員会規則待ち）

| 論点 | 条文 | 受託開発への影響 |
|------|------|----------------|
| 委託先の範囲外取扱いの禁止 | 第30条の3 | 委託を受けた業務に必要な範囲を超えて扱うことが、契約違反だけでなく法律違反になる（法令に基づく場合等を除く。再委託先も対象）。Step 3 の条項1が法定義務になる |
| 契約による委託先の義務の免除 | 第58条の2 | 委託契約に「取扱いの方法」と「漏えい等・範囲外取扱い・契約違反を知ったら委託元へ速やかに報告すること」などを定め、その定めのとおりに扱う間は、委託先の義務の多くが外れる。ただし安全管理措置・従業者の監督・委託先の監督・漏えい等報告（第23条〜第26条）と範囲外取扱いの禁止（第30条の3）は外れない。PPC はデータ入力のように委託元の指示どおり機械的に扱う委託を想定例に挙げており、設計判断を委託先がする開発・運用で使えるかは規則待ち |
| 漏えい時の本人通知の緩和 | 第26条第2項 | 本人に通知しなくても権利利益の保護に欠けるおそれが少ない場合（規則で定める）は、代替措置で足りる。PPC の検討例は、単体ではほぼ意味を持たない社内IDだけの漏えい |
| 統計作成等の同意不要の例外 | 第30条の2・第31条の3 | 統計作成等（統計作成等と整理できる AI 開発等を含む）にだけ使う第三者提供と、公開されている要配慮個人情報の取得に、本人同意が要らなくなる。条件は公表、提供元・提供先の書面合意、目的外利用・第三者提供の禁止など。作るのは「個人に関する情報」でない傾向・性質の情報（第2条第13項）なので、個人データを参照・出力する RAG や、特定の人の記録を生成AI API で処理させる用途はこの例外に乗らないと読むのが安全。API 入力は引き続き Step 4 で判定する |
| その他 | 第31条の2 ほか | 16歳未満の本人は法定代理人の関与が必要になる。顔特徴データ等は周知が義務になる。Cookie ID・メールアドレス等で特定の個人に連絡できる「連絡可能個人関連情報」は、不適正利用と不正取得が禁止される（Step 5 のタグ棚卸しと関係）。課徴金は、不適正利用・不正取得・違法な第三者提供・統計特例違反のうち、本人1,000人を基準とする大規模事案などに限られる |

- [ ] 取扱いの方法: PPC の検討案（基本的な考え方②、2026-10-01）は、対象データ・処理の内容・始期と終期・取扱う国や地域を書面で定める案。規則が出るまで要件ではない。

## 弁護士エスカレーション基準（グレー判定時）

以下に1つでも該当したら、自分で結論を出さず弁護士（または PPC の相談窓口）へ送る。誤検知のコストより見逃しのコストが圧倒的に大きいため。

- [ ] 要配慮個人情報への該当性が割れる（例: 健康関連のログ・推知情報）
- [ ] クラウド例外の該当性が契約・技術的措置の両面で確認できない（暫定は「委託扱い」に倒す）
- [ ] 漏えい等の報告要否・本人通知要否の判断（報告する/しないは経営判断+法的判断）
- [ ] GDPR 等の域外適用が絡む越境案件
- [ ] プライバシーポリシー・利用規約の最終版確定（非弁リスク。顧客側弁護士レビューへ）
- [ ] 業規制（金融・医療・薬機法等）が絡むデータ利用
- 法務レビュー費用の扱いは自組織の見積・価格判断プロセスで織り込み、「受託者は適法性を保証しない」責任分界を契約に明記する。
