# Human-in-the-Loop Design（人間の介在点設計）

**鉄則: ゲートの数を増やすのではなく、位置を賢く選ぶ。事前承認は不可逆操作の直前 1 点に絞る。**

HITL 設計には両側の失敗がある: 過剰な承認は人間が律速になり自動化 ROI を消し、形骸化した承認はオートメーションバイアス（何も見ずに承認）を生む。「どこに承認を置くか」と同じ重さで「どこに置かないか」を設計すること。

以下の Step 順に進める。途中の Step から相談された場合も、Step 1〜2 の格付けを先に確認してから答えること。なぜなら、リスク格付けなしに承認フローだけ設計すると、全操作に承認が付く「安全側に全振り」設計に必ず退化するため。

## Step 1: 操作の棚卸しとリスク格付け（4 軸）

エージェントが呼び得る全操作（ツール呼び出し）を列挙し、各操作を 4 軸で格付けする:

| 軸 | 問い | 高リスクの例 |
|---|---|---|
| **可逆性** | 実行後に元に戻せるか | 削除・送信済みメール・本番デプロイ・force push |
| **金銭影響** | 課金・支払・リソース購入が発生するか | クラウドリソース作成・広告出稿・決済 API |
| **対外性** | 組織外の人間・システムに届くか | 顧客へのメール送信・公開リポジトリへの push・SNS 投稿 |
| **データ機微度** | 個人データ・秘密情報に触れるか | 顧客 DB 読取・認証情報・人事情報 |

なぜ 4 軸か: 「危なそう」という感覚での格付けは人によってブレて運用で崩れる。軸を固定すれば、新しいツールを追加するたびに同じ基準で機械的に格付けできる。

- 読取専用か書込かの区別を先に付ける。書込系のみ 4 軸の詳細格付けに進めばよい
- データ機微度の具体判定（個人データの法規制・越境移転など）→ privacy-data-compliance 参照

## Step 2: 介在方式の決定 — HITL 3 類型

格付け結果を 3 類型に割り当てる:

| 類型 | 意味 | 割り当てる操作 |
|---|---|---|
| **human-in-the-loop** | 実行前に人間が承認 | 4 軸のいずれかが高い操作（不可逆・金銭・対外・機微データ） |
| **human-on-the-loop** | 自動実行を人間が監視し事後介入 | 可逆な書込操作。事後レビュー + ロールバック手段とセットで |
| **human-out-of-the-loop** | 完全自動 | 読取専用・可逆・影響小の操作 |

判定ルール: **「不可逆・金銭・対外・機微データ」だけ in、それ以外は on か out に落とす**。全部 in にすると自動化の意味がなくなるため、これが定石。例外は、信頼できない入力を読むセッションの書込・送信である（下の「セッション単位のチェック」）。

さらにリスクが許容できない操作（例: 本番 DB の破壊的変更）は「承認すれば実行できる」にせず**禁止**（そもそもツールを渡さない）にする。なぜなら、承認ゲートは疲労や慣れで突破されるが、渡していないツールは呼べないため。

**セッション単位のチェック**（4 軸は操作ごとの格付けなので、これとは別にセッションごとに 1 回問う）: このエージェントのセッションは、信頼できない入力（Web・メール・顧客文書・Issue/PR コメント・MCP ツールの応答など）を読むか。

- [ ] 読むなら、そのセッションに書込系・対外送信系の操作を持たせない
- [ ] 持たせる必要があるなら、4 軸の格付けが低くても、その操作を in-the-loop にするか、信頼できない入力を読む部分を別のセッション（書込・送信を持たない子）に分ける
- [ ] 機微データにも触れるセッションなら、信頼できない入力・機微データ・書込/送信の 3 つがそろう構成を自動実行にしない

なぜなら、注入された指示はセッション内のどの操作にも届くため、操作ごとの格付けだけでは防げないから。例: Web ページを読んだセッションで社内 DB に書き込む操作は、可逆で社内向けでも on-the-loop に落とさない（正本 → ai-system-design Step 7 の権限分離と Agents Rule of Two）。

権限・リスクマトリクス（成果物テンプレ参照）に落とし、**人間の承認を得る**。何を自動化してよいかは事業判断であり、AI が確定してはならない。

## Step 3: 承認ゲートの配置 — 不可逆操作の直前 1 点

in-the-loop に分類した操作について、ゲートの位置を決める:

- [ ] ゲートは**不可逆になる直前の 1 点**に置く（例: 計画立案・下書き・ステージングは自由にさせ、本番送信・削除実行・支払確定の直前だけ止める）
- [ ] 可逆な中間ステップにゲートを置かない。なぜなら、途中承認が多いほど 1 回あたりの注意力が下がり、肝心の最終ゲートが形骸化するため
- [ ] 可逆操作は on-the-loop（事後レビュー + ロールバック手段）で担保する。ロールバック手段（revert・バックアップ・取消 API）が存在することを確認してから on に落とすこと
- [ ] 承認の待ち時間がスループットを律速していないか運用開始後に実測する。ボトルネック化していたら、ゲートを増やした結果でないか・スコープ化（Step 4）で減らせないかを見直す

## Step 4: スコープド・パーミッション設計

都度承認の代わりに、**事前にスコープを与えて範囲内は自律・範囲超過のみ承認**とする設計（2025〜26 年の実務潮流。目安・要確認）。承認回数を減らしつつ統制を保てる。

スコープの 3 要素を明文化する:

| 要素 | 例 |
|---|---|
| **予算** | 「クラウド利用額は上限◯◯まで」「トークン予算◯◯まで」 |
| **範囲** | 「この顧客のリポジトリ内のみ」「この DB スキーマのみ」「宛先はこのドメインのみ」 |
| **時間帯** | 「営業時間内のみ」「人間が応答可能な時間帯のみ」 |

使い分けの現実解: **金銭・対外送信は都度承認、それ以外は事前スコープ**。なぜなら、都度承認は説明責任が明確だが形骸化しやすく、事前スコープは効率的だがスコープ設計ミスが事故に直結する——両者の弱点を金銭・対外だけ都度に残すことで相殺するため。

- [ ] スコープは狭く始め、運用実績を見て広げる。逆方向（広く始めて事故後に狭める）は取り返しがつかない
- [ ] 範囲超過時の挙動は「安全側で停止して承認を待つ」に固定する。「超過したが続行」を既定にしない
- [ ] Claude Code では permissions の allow/ask/deny ルール + hooks がこの思想のツール実装例。allow = スコープ内自律、ask = 超過時承認、deny = 禁止に対応させる

## Step 5: 承認応答の 4 型と実装対応

人間の応答は 4 型に整理する（LangGraph interrupt() パターンが参照実装）。approve/reject の 2 択で設計しないこと。なぜなら、「少し直せば通る」提案を reject しかできない UI は、人間に「面倒だから approve」を選ばせ形骸化を早めるため。

| 応答型 | 意味 | Claude Code での対応 | LangGraph での対応 |
|---|---|---|---|
| **approve** | 提案をそのまま実行 | permission プロンプトの許可 / allow ルール | interrupt() → 承認して再開 |
| **edit** | 提案を修正して実行 | plan mode での計画修正、diff の手直し | 人間が引数・内容を修正して再開 |
| **reject** | 却下 + フィードバック | 拒否 + 追加指示 | 却下理由を状態に戻して再計画させる |
| **respond** | ツールを実行せず人間が直接回答 | ユーザーが代わりに回答・手動実行 | 人間の回答をツール結果として返す |

実装の要点:

- 承認待ちの間、エージェントの状態を永続化する（LangGraph なら checkpointer）。なぜなら、人間の応答は数分〜数日かかり得るため、プロセス常駐前提の設計は破綻する
- 決定的に強制すべきゲート（特定コマンドの禁止など）は、プロンプト指示でなく hooks / permissions のような機械的ゲートで実装する。ガードレール 4 層の全体設計 → ai-system-design 参照

## Step 6: 承認 UI の要件 — 判断材料なき承認は形骸化する

「実行してよいですか? [Y/n]」だけの承認画面を作ってはならない。人間は判断材料がなければ判断できず、必ず形骸化する。承認リクエストには以下を必ず含める:

- [ ] **何を** — 実行しようとする操作・対象・引数
- [ ] **なぜ** — エージェントがこの操作を選んだ理由・文脈
- [ ] **影響範囲** — 成功時に何が変わるか、失敗時・誤りだった場合に何が起きるか、可逆か
- [ ] **差分** — 変更前後の diff、送信する本文そのもの（Claude Code の diff 表示・plan mode がこの実装例）

承認リクエストの整形は AI（エージェント自身）の仕事にする。人間の注意力は最希少資源であり、「読めば 30 秒で判断できる形」に整えるコストはエージェント側が払うべきため。

## Step 7: エスカレーションと運用者不在時の設計

**エスカレーションフロー** — エージェントが自力で進めてはならない条件と引き継ぎ先を定義する:

- [ ] 発動条件を列挙する: 確信度が低い・規定回数失敗した（3 回失敗で停止 → dev-core:debug の Three Strikes Rule と同思想）・要求がスコープ外・矛盾する指示を検出した
- [ ] 引き継ぎ先を**名指し**で決める（役割名 + 通知経路）。「管理者へ」では夜間に誰にも届かない
- [ ] エスカレーション時にエージェントが渡す情報を定型化する: 状況・試行履歴・推奨案・判断してほしい点

**運用者不在時・夜間自動実行の制約** — 運用者（一人運用なら自分）が不在の時間帯にエージェントが止まる条件を決めておかないと、夜間の自動実行が事故源になる:

- [ ] 不在時間帯は in-the-loop 操作を実行しない。承認待ちキューに積み、応答可能時間に人間へ提示する
- [ ] 不在時間帯の on-the-loop 操作は、ロールバック手段が確認済みのものだけに限定する
- [ ] 承認タイムアウトの挙動は「時間切れ = 実行しない（安全側）」に固定する。無応答を暗黙の承認にしない
- [ ] 緊急停止手段（実行中エージェントを止める操作）と、その手順が不在先からも実行できることを確認する
- [ ] 通知経路を用意する: 不在中に起きたエスカレーション・スコープ超過・停止を、復帰時に一覧で確認できること

## Step 8: 監査ログ仕様 — 後付けにしない

監査ログは最初から構造化ログとして設計に含める。なぜなら、事故後に「何が起きたか説明できること」が受託では契約上の防御線になり、後付けでは事故前の記録が存在しないため。

記録要件（承認イベントごと）:

- [ ] **誰が** — 承認者の特定（認証済み ID。共有アカウント経由の承認は承認者を特定できないため不可）
- [ ] **何を・いつ** — 承認/却下した操作・引数・対象・タイムスタンプ
- [ ] **どの情報で** — 承認時に人間へ提示した判断材料（Step 6 の内容）そのもの。なぜなら、「提示された情報が不十分だった」のか「見て承認した」のかを事後に区別できる必要があるため
- [ ] **承認と行動の紐付け** — どの承認がどのツール実行に対応するかを 1:1 で辿れること

記録要件（エージェント動作）:

- [ ] 全ツール呼び出しのトレース（入力・出力・エラー）を残す。属性名は OpenTelemetry の GenAI semantic conventions に寄せる。ただしこの規約は専用リポジトリ（open-telemetry/semantic-conventions-genai、2026-05 作成）へ移り、gen_ai.* と MCP の属性はすべて Development（実験段階）で、リリース（タグ）はまだなく、Schema URL も開発版だけである（2026-10-26 確認）。そこで計装ライブラリの版を固定し、属性名が変わっても Collector の transform で吸収できる構成にする。なぜなら、監査ログの検索やダッシュボードを今の属性名に直接結びつけると、名前が変わったときに壊れるため。MCP 経由の呼び出しは、`_meta` の `traceparent` でトレースをつなぐ（MCP 2026-07-28 リビジョン → ai-system-design Step 3）
- [ ] **改ざん困難性**: ログの保存先をエージェントの書込権限から分離する（エージェント自身がログを消せる構成にしない）。追記専用ストレージや外部ログ基盤への転送で担保する

## ガバナンス語彙の対応表

エンタープライズ顧客への説明では、以下の枠組みを語彙として使う（日本と EU の行は 2026-10-26 に一次ソースで確認した版。NIST・ISO の行は最新版を要確認。どれも改訂されるので、顧客に示す前に確かめる）。**これは法的助言ではなく実務の型であり、適用要否・解釈の最終判断は法務専門家に委ねる**こと。

| 枠組み | 位置づけ | このスキルの成果物との対応 |
|---|---|---|
| **NIST AI RMF 1.0** | 米国のリスク管理フレームワーク。Govern / Map / Measure / Manage の 4 機能 | リスク格付け（Step 1〜2）と権限マトリクスが Map/Manage の説明材料になる |
| **ISO/IEC 42001:2023** | AI マネジメントシステム（AIMS）の認証規格 | AI 利用ポリシー・運用規程の章立ての参照枠になる |
| **EU AI Act 第 14 条** | 高リスク AI への human oversight（人間による監視）義務。適用時期は表の下の注を参照 | 承認ゲート設計書と「人間の最終責任の所在」の明文化が対応の中核になる |
| **AI 法（AI 推進法）**（人工知能関連技術の研究開発及び活用の推進に関する法律、令和 7 年法律第 53 号。2025-09-01 全面施行） | 日本の AI に関する基本法。第 13 条に基づき「人工知能関連技術の研究開発及び活用の適正性確保に関する指針」（2025-12-19 人工知能戦略本部決定）が定められた | 国内顧客に「AI 法と国の指針への対応」を問われたときの参照枠。事業者に何を求めるかは指針の本文で確かめてから書く（本スキルでは中身を要約しない） |
| **AI 事業者ガイドライン 第 1.2 版**（総務省・経済産業省、2026-03-31。法的拘束力のないソフトロー） | AI の開発者・提供者・利用者が取り組む事項の指針。AI エージェントを「特定の目標を達成するために、環境を感知し自律的に行動する AI システム」と定義する | 説明材料としての対応づけ: 別添が挙げる「人間の意図しない商品の注文やファイル削除」のリスク → 承認ゲート（Step 3）。別添の「権限を業務遂行に必要な最小限に設定」→ 権限マトリクスとスコープ（Step 2・4）。本編の「人間の判断が自動化バイアスに左右されない対策」→ 承認 UI（Step 6） |

EU AI Act の適用時期（注）: 第 14 条を含む高リスク AI の義務（第 3 章第 1〜3 節）は、Regulation (EU) 2026/1744（Digital Omnibus on AI。2026-07-08 付、官報掲載 2026-07-24）で延期された。附属書 III の高リスク AI は 2027-12-02、附属書 I（製品安全法令の対象製品）の高リスク AI は 2028-08-02 から適用される。顧客に「高リスクの義務は 2026-08 から適用」と説明しない。一方、第 50 条の透明性義務は延期されておらず、2026-08-02 から適用される（2026-08-02 より前に市場に出した生成 AI の第 50 条第 2 項のマーキングだけ、2026-12-02 までの経過措置がある）。延期を一括りに説明しないこと。

## 成果物テンプレ

設計結果は以下 5 点に落とす。顧客納品用の体裁 → external-design-deliverables 参照。

**1. 権限・リスクマトリクス**

| 操作(ツール) | 可逆性 | 金銭影響 | 対外性 | データ機微度 | 介在方式(out/on/in/禁止) | スコープ条件 |
|---|---|---|---|---|---|---|

**2. 承認ゲート設計書**

```
- ゲート位置: どの操作の直前か(不可逆点との対応)
- 承認者: 誰が承認できるか(役割・代理者)
- 提示情報: 何を・なぜ・影響範囲・差分
- 応答型: approve / edit / reject / respond それぞれの後続動作
- タイムアウト: 無応答時の挙動(安全側で停止)
```

**3. エスカレーションフロー**

```
- 発動条件: 確信度低 / 規定回数失敗 / スコープ外要求 / 矛盾検出
- 引き継ぎ先: 役割名 + 通知経路(不在時の代替経路を含む)
- 引き継ぎ情報: 状況・試行履歴・推奨案・判断してほしい点
```

**4. 監査ログ仕様**（Step 8 の記録要件 + 保存先・保持期間・アクセス権限）

**5. AI 利用ポリシー / 運用規程**（顧客組織向け。人間の最終責任の所在の明文化、EU AI Act 型の human oversight 要件への対応を含む）

## 分担線: AI がやること / 人間にしか決められないこと

**AI（このスキルを実行するエージェント）がやること:**

- 操作の棚卸しと 4 軸リスク格付けの一次判定（人間の確認前提のドラフト）
- 権限マトリクス・承認ゲート設計書・エスカレーションフローのドラフト作成
- 承認リクエストの整形（何を・なぜ・影響範囲・差分を人間が 30 秒で判断できる形に）
- 監査ログの実装と、ログの要約・異常の一次報告
- permissions / hooks 等の機械的ゲートのコード化

**人間にしか決められないこと（AI は推奨まで。決定を求めること）:**

- **承認そのもの** — 特に不可逆・金銭・対外の操作。AI が自分への承認を代行してはならない
- **スコープの初期設定** — 予算・範囲・時間帯の上限はリスク許容度の表明であり事業判断
- **権限マトリクスの最終承認** — 何を自動化してよいかは発注側・運用側の判断
- **エスカレーション先の指名** — 誰が責任を引き受けるかは組織の意思決定
- **事故時の説明責任** — 監査ログは材料を提供するだけで、責任の所在は人間に残る

## 最終チェックリスト

設計完了を宣言する前に確認する:

- [ ] 全操作が 4 軸で格付けされ、in / on / out / 禁止 のいずれかに割り当てられている
- [ ] 信頼できない入力を読むセッションの書込・対外送信の操作が、in-the-loop かセッションの分割になっている（Step 2 のセッション単位のチェック）
- [ ] in の承認ゲートが不可逆操作の直前 1 点に置かれ、判断材料（何を・なぜ・影響範囲・差分）が提示される
- [ ] on の操作すべてにロールバック手段と事後レビューの経路がある
- [ ] スコープ（予算・範囲・時間帯）が明文化され、超過時の挙動が「安全側で停止」になっている
- [ ] 承認応答が approve / edit / reject / respond の 4 型で設計され、2 択になっていない
- [ ] 監査ログが構造化で最初から入っており、エージェント自身がログを消せない構成になっている
- [ ] 運用者不在時の停止条件・承認タイムアウト・緊急停止手段が決まっている
- [ ] エスカレーション先が名指し（役割 + 通知経路）で定義されている
- [ ] 人間の決定事項（マトリクス承認・スコープ設定）が未決のまま実装に進んでいない

エージェント構成・ツール設計・ガードレール 4 層の方式設計 → ai-system-design 参照。実装後の検証 → dev-core:verify 参照。承認フロー導入の顧客合意 → client-alignment 参照。
