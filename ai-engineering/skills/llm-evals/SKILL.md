# LLM Evals（LLM/エージェント機能の評価設計）

**鉄則: 汎用スコアから始めない。実トレースのエラー分析から始める。**
（出典: Hamel Husain & Shreya Shankar「LLM Evals FAQ」— evals 実務の事実上の標準）

非決定的な LLM/エージェントの品質を、感覚でなく再現可能な仕組みで測る。以下の Step 順に進める。途中の Step から相談された場合も、Step 1 のエラー分析を経ているかを先に確認すること。なぜなら、実際の失敗モードを観測せずに作ったメトリクスは、顧客の業務要件と無関係な数字になるため。

エージェント構成やガードレールの設計そのものは → ai-engineering:ai-system-design 参照。

## Step 1: エラー分析ファースト 🔍

評価設計は必ずここから始める。

1. **実トレースを集める**: 本番または試験運用の入出力ログを 30〜100 件集める（開発初期なら想定入力で生成する）
2. **open coding**: トレースを人間が1件ずつ読み、失敗と感じた点を自由記述で書き出す
3. **分類（axial coding）**: 書き出した失敗を似たもの同士でグルーピングし、失敗モードとして命名する
4. **メトリクス化**: 観測された失敗モードだけを、アプリ固有の評価項目に変換する
5. **エラー分析ノートに記録**: 分類結果と件数をノートとして残し、メトリクス選定の根拠にする

なぜなら、hallucination score のような汎用メトリクスは「自分のアプリで実際に何が壊れるか」を教えてくれず、改善がすべて感覚頼みになるため。

トレースの一次分類の下書きは AI に任せてよいが、「これは失敗か否か」の最終ラベルは人間が付ける（→「AI がやること / 人間にしか決められないこと」節）。

- [ ] 実トレース（または代表的な想定入力）を 30 件以上読んだ
- [ ] 失敗モードが名前付きで分類されている
- [ ] 各メトリクスに「根拠となった実際の失敗トレース」がある

## Step 2: 判定は二値（pass/fail）にする ⚖️

すべての評価項目を **pass/fail の二値** で定義する。1〜5 のリッカート尺度は使わない。

なぜなら、尺度の目盛り差（3と4の違い）は定義できず、集計しても意味のある数字にならないため。

- 「品質を5段階で採点」→ ✗
- 「引用元が本文に実在するか: pass/fail」→ ✓
- 「回答が規定フォーマットに従うか: pass/fail」→ ✓

複数の観点を測りたければ、1つの尺度に潰さず、二値の評価項目を観点の数だけ作る。

## Step 3: 3レベル評価スタックを組む 🏗️

評価は3レベルに分け、**下のレベルで判定できるものを上のレベルに持ち込まない**。

| レベル | 手段 | 対象 | 特性 |
|---|---|---|---|
| 1. コード assertion | JSON Schema 検証・正規表現・完全一致・必須要素チェック・Levenshtein | 決定的に判定できるもの | 高速・安価・CI 向き |
| 2. LLM-as-a-Judge | 別系統モデルによる二値判定 | 主観的な品質（トーン・忠実性・網羅性） | 柔軟だが遅い・高い・自身が揺れる |
| 3. 本番 A/B・実ユーザーフィードバック | 実験基盤・トレースのサンプリング評価 | オフラインで測れない実分布での品質 | 最終判定だが遅効 |

**鉄則: 決定的に判定できるものに LLM 判事を使わない。** なぜなら、構造チェックを第一線に置くことで CI の信頼性とコストが両立するため。

オフライン評価に通っても本番分布は変わる。トレース収集+サンプリング評価（レベル3）を納品構成に含めること。なぜなら、本番モニタリングの欠如は「納品後に静かに劣化する AI 機能」の主因のため。

## Step 4: LLM-as-a-Judge の運用規律 👨‍⚖️

LLM 判事を使う場合、以下を守らないと判定は無意味になる。

1. **人間ラベルとの整合を先に測る**: ジャッジを使い始める前に、人間ラベル 100 件以上と突き合わせ、一致率（TPR/TNR）を測定する。なぜなら、キャリブレーションされていないジャッジの pass 率は何の品質も保証しないため
2. **別系統モデルを使う**: アプリ本体とジャッジは別系統のモデルにする。なぜなら、同系統だと自己選好バイアス（self-enhancement bias）で甘い判定になるため
3. **G-Eval 型で基準を展開する**: 判定基準を CoT で展開してから採点させる G-Eval が代表的手法（DeepEval に実装あり）
4. **判定は二値**: Step 2 の原則はジャッジにも適用する
5. **作る対象を絞る**: ジャッジは週次メンテ・関係者調整の維持コストが高い。「繰り返し改善する問題」にだけ作る

- [ ] 人間ラベル 100 件以上との一致率を測定し、整合性レポートを残した
- [ ] ジャッジのモデルはアプリ本体と別系統
- [ ] ジャッジプロンプト自体をバージョン管理している

## Step 5: エージェントの評価は軌跡（trajectory）まで見る 🤖

エージェント（ツールを使って自律ループする構成）は、最終出力だけの評価では不十分。**軌跡**を評価する。

| 観点 | 何を見るか |
|---|---|
| ツール選択 | 各ステップで適切なツールを選んだか（誤選択はツール description 改善のシグナル → ai-engineering:ai-system-design） |
| ターン効率 | 無駄なターン・重複呼び出しがないか |
| 停止判断 | 完了すべき時に止まり、続けるべき時に続けたか |

運用パターン（Anthropic のマルチエージェント研究システムの実例）:

- ルーブリック（事実正確性・引用品質・網羅性・ソース品質・ツール効率）で LLM 判事に採点させ、人間評価との一致を確認してから運用する
- 出力のばらつき対策として **pass^k**（k 回実行して全部成功）を指標に使う。なぜなら、1回の pass は「たまたま成功」と区別がつかないため

## Step 6: golden set を検収基準として契約時に合意する 📋

AI 機能の受託では、「品質をどう検収するか」を作り始める前に顧客と合意する。手順:

1. **実データから代表入力を集める**: 顧客の実データ 30〜100 件で golden set を作る。なぜなら、30 件でも「無いより桁違いにマシ」であり、実データでなければ検収の意味がないため
2. **期待出力/合格基準を顧客とラベル付けする**: 「何が正解か」のラベル付けは顧客のドメイン判断であり、AI にも受託側にも代行できない
3. **合格率の閾値を検収基準として合意する**: 「golden set に対する合格率 X% 以上」の形で、契約・発注段階で文書化する。なぜなら、ベンダーの汎用スコアは顧客の業務要件と無関係で、後から検収基準を握ると必ず揉めるため
4. **変更時の再実行を回帰条件にする**: プロンプト・モデル変更時に同じ golden set を再実行することを運用条件として合意する

要件としての合意の進め方 → delivery-core:requirements-definition 参照。顧客との合意形成・期待値調整 → delivery-core:client-alignment 参照。検収条項を契約文言に落とす際は法務専門家に確認する（目安: 2026年時点の実務慣行・要確認）。評価工数を含む金額の判断は自組織の見積・価格判断プロセスへ。

- [ ] golden set が顧客の実データ由来で 30 件以上ある
- [ ] 合格基準のラベルを顧客自身が確認した
- [ ] 合格率の閾値が契約・発注文書に明記されている

## Step 7: ツール選定と CI 回帰ゲート組込 🔧

用途で選ぶ。全部入りを目指さない。

| ツール | 向いている用途 |
|---|---|
| promptfoo | CI 組込・設定ファイルベースの回帰テスト |
| Ragas | RAG 評価（faithfulness / context precision / context recall） |
| DeepEval | G-Eval 実装を含む LLM-as-a-Judge 構築 |
| Langfuse / LangSmith / Braintrust | トレーシング+評価+データセット管理（本番モニタリング含む） |

CI への組込:

1. golden set + レベル1 assertion を CI で毎回実行する（高速・決定的なため常時回せる）
2. プロンプト・モデル・RAG 設定の変更 PR は、評価スイートの通過を**デプロイ前回帰ゲート**にする。なぜなら、評価なしのプロンプト変更は「直したはずの問題の回帰」を検出できないため
3. プロンプトはコードと同様に Git 管理し、評価とセットで変更する（秘伝のタレ化の防止）
4. LLM 判事を含むスイートは実行コストが高いので、夜間バッチやリリース前に頻度を落として回す

CI の検証フロー全般・証拠ベースの完了判定 → dev-core:verify 参照。

## Step 8: メトリクスのライフサイクル ♻️

メトリクスは増やすものではなく、入れ替えるもの。

1. **観測された失敗モードのみ計測する**: Step 1 のエラー分析で実際に観測された失敗だけをメトリクス化する
2. **直ったら引退させる**: 失敗モードが解消され再発しなくなったメトリクスは、回帰用の最小 assertion だけ残して評価スイートから外す
3. **定期的に棚卸しする**: 本番トレースのサンプリング評価で新しい失敗モードを拾い、メトリクスを入れ替える

なぜなら、メトリクスを増やすほど安心感は出るが、管理不能になり誰も見なくなるため。「誰も見ないダッシュボード」は評価が存在しないのと同じ。

## AI がやること / 人間にしか決められないこと 🤝

| AI に任せる | 人間にしか決められない |
|---|---|
| 評価スクリプト・assertion の実装 | エラー分析での「これは失敗か否か」のラベル付け（ドメイン判断そのもの） |
| トレースの一次分類（open coding の下書き） | 分類の採否と失敗モードの命名の最終確定 |
| ジャッジプロンプトの下書き | ジャッジと人間ラベルの整合確認・ジャッジ採用の判断 |
| 評価レポート・ダッシュボードの生成 | 検収基準（合格率の閾値）の顧客合意 |
| golden set 候補データの抽出・整形 | 期待出力の正解ラベル（顧客・ドメイン側の判断） |
| メトリクス集計・劣化検知アラート | メトリクスの引退・入れ替えの判断 |

人間ラベル付けの時間（週1時間でも）を定常確保する。なぜなら、一人〜少人数の受託では人間ラベルが評価系全体のキャリブレーション源であり、これが涸れると LLM 判事も golden set も静かに現実からずれるため。ラベル付け・承認をワークフローのどこに置くかの設計 → ai-engineering:human-in-the-loop-design 参照。
