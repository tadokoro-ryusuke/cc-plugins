# Conventions as Guardrails — 規約の強制装置化

**鉄則: 強制可能な規約は全部ツールへ。文書に残すのは「ツール化できない意図」と「明示的NGリスト」だけ。**

なぜ: 自然言語の規約（CLAUDE.md / AGENTS.md）を AI エージェントは確率的にしか守らない。lint・型・テスト・フックの決定的チェックだけが 100% 再現する。

開発原則そのもの（TDD / SOLID / アーキテクチャ / セキュリティ）の正本は → dev-core:best-practices 参照。本スキルはそれらの原則を「破れない形」に翻訳する工程を担当する。

## 分担線: AI がやること / 人間にしか決められないこと

このスキルを実行するときは、まずこの分担線を確認し、右列の項目は必ず人間に確認してから確定する。

| AI（このスキルの実行者）がやる | 人間にしか決められない |
|---|---|
| 規約のツール設定への翻訳（リンタ・フォーマッタ・アーキテクチャテスト・フック設定の生成） | どのスタイルガイドを標準にするか（規約そのものの選定） |
| 既製スタイルガイドとの差分整理・設定ファイルのドラフト | ユビキタス言語の定義（顧客との合意事項） |
| 依存関係図の自動生成・依存ルールのテスト化 | レイヤ数・抽象化レベルの決定（案件規模・保守契約に依存する判断） |
| 命名規約表・ログ規約表のドラフト作成 | disable コメント追加の承認 |
| 違反の検出・機械的修正・CI への組み込み | ログ保持期間・監査要件の確定（契約・規制と結びつく） |

なぜ: 「業務判断（顧客と合意する値）」と「技術判断（定石の適用）」を分離し、後者だけを AI + 決定的チェックに委譲するのが規約設計の基本構図だから。

## Step 0: 規約の棚卸しと翻訳判定

既存規約（または作りたい規約）を1件ずつ、次の3分類に振り分ける:

1. **決定的に強制できる** → ツール設定へ（フォーマット・import 順・依存方向・命名パターン・型の厳格さ）
2. **意味的判断が要る** → LLM レビュー観点へ（命名の質・抽象度・パターン準拠）
3. **業務判断** → 人間承認ゲートへ（ユビキタス言語・公開 API の変更・アーキテクチャ変更）

なぜ: 決定的に強制できるルールはコストほぼゼロで厳しくできる。人間の判断が要るルールは数を絞る——ルールが多いほど1つあたりの遵守率が下がる。

判定基準: 「この規約の違反を、テキストのパターンまたは AST で機械的に検出できるか?」。できるなら分類1。**設定ファイルにできない規約は原則作らない。**

## Step 1: スターターキットを敷く（案件初日）

新規リポジトリには以下の標準セットを初日に揃える。全案件共通のテンプレートとして整備しておき、案件開始日に展開する:

- [ ] **フォーマッタ**（Prettier / Biome / gofmt / Black / rustfmt）— 保存時 + コミット時（lefthook / husky + lint-staged）+ CI の三重適用
- [ ] **リンタ**（ESLint / Biome / RuboCop / golangci-lint / Ruff）— 既製スタイルガイド（Google Style Guides / PEP 8 / Airbnb / Effective Go）を採用し、逸脱したい点だけ差分を決める
- [ ] **型 strict**（TypeScript strict + `as any` 禁止 + no-floating-promises、mypy --strict 等）
- [ ] **アーキテクチャテスト**（→ Step 2）
- [ ] **CI ゲート**（format check / lint / typecheck / test / アーキテクチャテストで PR を落とす）
- [ ] **エージェントフック**（→ Step 4）

なぜ: フォーマッタは「設定した瞬間に議論終了」。規約文書は3ヶ月で形骸化するが、CI で落ちる設定は形骸化しない。

- ゼロから規約を作らない。既製スタイルガイドの採用 + 差分の明文化が最速で最も守られる。
- CI パイプライン全体（デプロイ・リリースゲート）の設計は → 姉妹スキル cicd-release-design 参照。
- テスト戦略そのもの（何をどこまでテストするか）は → 姉妹スキル test-design 参照。

## Step 2: アーキテクチャテストを導入する

依存方向・レイヤ違反・命名パターンを「テストとして」強制する。

1. **依存ルールを1文で書き出す**。例:「utils から domain を import 禁止」「presentation 層は infrastructure 層に依存しない」
2. **言語に応じてツールを選ぶ**:

   | 言語 | ツール |
   |---|---|
   | Java / Kotlin | ArchUnit |
   | JS / TS | dependency-cruiser、eslint-plugin-boundaries |
   | Python | import-linter |
   | Go | go-arch-lint |

3. **最小ルール1つから始める**。最重要のレイヤ違反1件だけをルール化して CI に組み込み、グリーンを確認してから段階的に追加する。
4. **依存関係図は自動生成する**（dependency-cruiser / madge 等）。手描きの図をドキュメントに置かない。

なぜ: 依存方向のルールをドキュメントにだけ書くと数ヶ月で腐る。CI で落ちるルールだけが生き残る。

## Step 3: CLAUDE.md / AGENTS.md を「最小」に書く

ツールで強制できないものだけを書く。

**書くべき項目:**

- [ ] **明示的禁止条項の箇条書き**——曖昧なベストプラクティスより明示的 NG リストが効く（AI は明示的な禁止条項には従いやすい）。例:「`eslint-disable` 追加禁止（必要なら理由を書いて人間の承認を得る）」「トランザクション内で外部 API を呼ばない」
- [ ] **ドメイン用語集**（ユビキタス言語）——顧客の言葉 = コードの言葉 = 画面の言葉。定義は人間（顧客合意）から受け取る
- [ ] **変更してはいけないファイル・領域**の列挙
- [ ] **検証コマンド**——lint / typecheck / test / build の正確な実行コマンド

**書くべきでない項目:**

- フォーマット規則（インデント・クォート・行長）→ フォーマッタ設定に書く。文書に書くのはトークンの無駄
- リンタで強制済みのルールの再掲 → 二重管理になり、ずれた瞬間に両方が信用を失う
- 一般的なベストプラクティスの長文 → 守られない。禁止条項の形に変換するか削る

**書き方の原則（この節がコンテキストファイル設計の正本）:**

- **薄く保つ**——知識本体は参照先（スキル・ADR・docs・references/）に置き、CLAUDE.md / AGENTS.md はインデックスと不変のルールだけ持つ。
- **コピーよりポインタ**——コードスニペットを貼らず file:line 参照や「→ 参照先」で誘導する。なぜ: 貼ったコードは参照元が変わった瞬間に嘘になるため。
- **二重管理禁止**——ツール非依存の正本を AGENTS.md に置き、CLAUDE.md 等のツール固有ファイルは薄いラッパにする。同じ知識を2箇所に書かない。
- **モノレポはルート + パッケージの二層構成**にする。

なぜ: リンタ・フォーマッタ設定ファイルが規約の正本であり、文書は補足。CLAUDE.md が長いほど1項目あたりの遵守率は下がる。

## Step 4: エージェントフックを設計する

事後レビューではなく「生成中に矯正する」。AI エージェントのフックに決定的チェックを仕込む:

- [ ] **PostToolUse フック**: ファイル編集のたびにフォーマッタ + リンタを自動実行し、違反を即時フィードバックする
- [ ] **Stop フック**: 作業終了時に lint / test / build を回し、失敗していたら完了を宣言させない
- [ ] **disable コメントは理由必須**: `eslint-disable` 等の抑制コメントには理由の記載を必須とし、追加は PR で明示して人間が承認する。無制限許可は規約を骨抜きにする
- [ ] **危険操作の deny**: 本番 DB への書き込み等、取り返しのつかない操作はフックの deny 設定で AI の自動実行から外す

なぜ: 編集直後の機械的フィードバックは、セッション終盤の指摘より修正コストが桁違いに低い。

検証フローの実行手順そのものは → dev-core:verify 参照（6段階検証の正本）。

## Step 5: 命名規約表を1枚に固定する

命名は「原則の議論」ではなく「1枚の表」に落とす。以下をテンプレートとして案件用に埋める:

| 対象 | 規約 | 例 |
|---|---|---|
| ドメイン層の型・クラス | ユビキタス言語の名詞（顧客用語と一致させる） | `PurchaseOrder` |
| ユースケース / サービス | 動詞 + 目的語 | `CancelOrderUseCase` |
| 変数・関数 | 言語標準のケース（camelCase 等）+ 情報を詰めた名前 | `remainingStock` |
| DB テーブル | snake_case・複数形 | `purchase_orders` |
| DB カラム | snake_case | `created_at` |
| ブランチ | 種別プレフィックス + issue 番号 | `feature/123-cancel-order` |
| コミット | Conventional Commits（機械可読） | `feat(order): 注文キャンセルを追加` |

- ドメイン用語は必ずユビキタス言語と一致させる。表の用語列は顧客合意（人間側の担当）を正とする。
- 命名パターンのうち機械判定できるもの（ケース・サフィックス）はリンタ / アーキテクチャテストのルールに翻訳する（Step 0 の分類1）。
- API パス・エンドポイントの命名は外部設計の領域 → 姉妹スキル external-design-deliverables 参照。

なぜ: 案件ごとに規約がバラバラだと、人間の生産性も AI の出力精度も落ちる。1枚の表は AI への指示にもレビュー基準にもそのまま使える。

## Step 6: 構造化ログ規約を設定する

ログ規約も「文書」ではなく、ロガー設定 + 標準フィールド定義として敷く。

1. **構造化ログ（JSON）を必須にする**（pino / zap / slog / structlog / Serilog）。文字列連結ログを禁止する。
   なぜ: フィールド単位の検索・集計・マスキングは構造化されていて初めて可能になる。
2. **標準フィールドを定義する**: `timestamp`, `level`, `trace_id`, `user_id`, `event` + 業務コンテキスト。エラーログには trace_id と主要な業務キー（注文 ID 等）を必須とする。
3. **レベル規律を固定する**: ERROR = 人間の対応が必要 / WARN = 自動回復したが注視 / INFO = 業務イベントの記録 / DEBUG = 本番では原則無効。「ERROR が出たら必ずアラート」が成立するレベル規律を守る（何でも ERROR にするとアラートが狼少年化する）。
4. **PII マスキングは二重防御にする**: ①そもそもログに入れない（オブジェクト丸ごと出力の禁止をリンタ・レビューで強制）を第一防御とし、②フィールド単位マスク + 集約パイプライン（OpenTelemetry Collector の processor 等）で二重に守る。パターンマッチ検出は最終防衛線にすぎない。
   なぜ: リクエストボディを丸ごとログして PII が平文で残ると、インシデント時に「ログが二次漏洩源」になる。
5. **保持期間は規制・契約から逆算して決める**: 例として PCI DSS は監査ログ1年（直近3ヶ月は即時参照可）が目安（2026年時点・案件の規制要件で要確認）。アプリログ 30〜90日 + 監査ログ1年〜が中小案件の現実的な出発点。ログに個人情報が含まれる場合は個人情報保護法上の安全管理措置・削除義務の対象になる点を契約時に確認する。
   これは法的助言ではなく実務の型であり、最終判断は専門家（弁護士・監査人）と顧客の合意に委ねる。保持期間・監査要件の確定は人間側の担当（分担線参照）。

PII の定義・データ保護の全体設計は → compliance-core:privacy-data-compliance 参照。

## 3層ゲートで運用する

規約チェックは3層で構成し、下の層ほど対象を絞る:

1. **第1層: 決定的チェック**（フォーマッタ・リンタ・型・テスト・アーキテクチャテスト）——秒で完了し 100% 再現する。強制できるものは全部ここへ
2. **第2層: LLM 意味レビュー**（命名の質・パターン準拠・規約意図への適合）——リンタが拾えない部分だけを観点リスト化して依頼する。レビュープロセスの設計は → design-core:design-review 参照
3. **第3層: 人間承認**（アーキテクチャ変更・公開 API の変更・disable 追加・ユビキタス言語の変更のみ）——承認フローの設計は → ai-engineering:human-in-the-loop-design 参照

なぜ: 全部を人間レビューに載せると滞留し、全部を AI に任せると規約が漂流する。層ごとに「そこでしか判定できないもの」だけを流すのが持続する形。

## アンチパターン（明示的NGリスト）

- **立派な規約文書だけ書いてツール設定をしない** → 3ヶ月で形骸化する。文書化の前にツール化する
- **`eslint-disable` / `as any` の無制限許可** → 規約が骨抜きになる。理由必須 + 人間承認をルール化する
- **依存方向のルールをドキュメントにだけ書く** → コードで強制しない規約は数ヶ月で腐る（Step 2 へ）
- **案件ごとにバラバラの規約** → 共通スターターキットを整備し案件初日に適用する（Step 1 へ）
- **リクエストボディの丸ごとログ出力** → PII の二次漏洩源になる（Step 6 へ）
- **レベル規律の崩壊（何でも ERROR）** → 本物の障害を見逃す（Step 6 へ）
- **CLAUDE.md へのフォーマット規則の記載** → 守られない上にトークンの無駄（Step 3 へ）

同じ違反が繰り返されたら、その規約が「翻訳漏れ」（分類1なのに文書のまま）でないかを疑う → dev-core:continuous-learning 参照。

## 完了チェックリスト

規約整備を完了と宣言する前に、証拠（実行出力・設定ファイル）で確認する:

- [ ] フォーマッタ・リンタ・型 strict が設定され、CI で PR が落ちることを実際に確認した
- [ ] アーキテクチャテストが最低1ルール動いている
- [ ] CLAUDE.md / AGENTS.md には「ツール化できないもの」だけが書かれている（フォーマット規則の再掲がない）
- [ ] エージェントフック（PostToolUse / Stop）が設定されている
- [ ] 命名規約表とログ規約（標準フィールド + レベル定義 + マスキング対象）がリポジトリに置かれている
- [ ] 人間にしか決められない項目（スタイルガイド選定・ユビキタス言語・保持期間）が承認済みである
