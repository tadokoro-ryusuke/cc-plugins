# Interface Contract Design（機械間境界の契約設計）

**鉄則: 一度公開した契約は破壊しない。加算的変更だけで進化できる形に初期設計する。**

なぜ: API・イベント・エラー形式は内部実装と違いリファクタリングで直せず、破壊は消費者全員の障害になるため。

境界:
- 実装コードのパターン（Repository・サービス層・Result・キャッシュ・トランザクション）→ dev-core:backend-patterns 参照。本スキルは対外契約と互換性戦略のみを扱う。
- 画面・バッチなど基本設計成果物一式 → dev-core:external-design-deliverables 参照。
- 契約テストの設計 → dev-core:test-design 参照。フロントのエラー表示実装 → dev-core:frontend-patterns 参照。

## 分担線: AI がやること / 人間にしか決められないこと

契約確定前に必ずこの表で「人間の決定待ち」を洗い出し、AI が勝手に確定しない。
なぜ: 契約は対外的な約束であり、AI が生成した案の採否そのものが合意事項だから。

| AI がやること（ドラフト・検証） | 人間にしか決められないこと（決定・合意） |
|---|---|
| OpenAPI / AsyncAPI 定義のドラフト生成 | リソース境界の切り方（ドメイン理解の反映） |
| ガイドライン準拠チェック（Spectral 等） | 準拠先ガイドラインの宣言と例外の承認 |
| 破壊的変更の差分検出（oasdiff 等） | 互換性ポリシー・Deprecation/Sunset 期間の決定 |
| SDK・モック・契約テストの生成 | 公開範囲・認証方式・レート制限などセキュリティ方針 |
| Saga 補償アクションの網羅チェック | 整合性境界（どこまで同期で厳密、どこから結果整合か） |
| エラーカタログのドラフト・文言トーン統一 | 補償・返金に関わる文言（法務判断）・SLA・変更通知義務 |

変更通知義務・通知期間は保守契約に明記する（契約条項の確定は自組織の契約・法務プロセスへ。専門家に要確認）。

## Step 1: プロトコルを選定する

**迷ったら REST + OpenAPI 3.1。** GraphQL / gRPC は例外条件を満たすときだけ選ぶ。
なぜ: REST はツール・キャッシュ・人材が成熟しており、外部公開と小規模チームの標準だから。

- [ ] GraphQL の例外条件: クライアントが多様（Web/モバイル/サードパーティ）で画面ごとの取得形が大きく異なり、その代償としてキャッシュ・N+1・認可の複雑さを引き受ける合意があるか
- [ ] gRPC の例外条件: 内部サービス間の高性能通信・型安全が主目的か（ブラウザ直結は不可）
- [ ] Webhook 提供: 受信側のリトライ・署名検証・冪等性を Step 5 のイベント契約と同じ枠組みで設計したか
- [ ] 準拠先ガイドラインを1つ宣言したか（Google AIP / Microsoft REST API Guidelines / Zalando RESTful API Guidelines）
      なぜ: 準拠先宣言で命名・形式の議論時間をゼロにし、自前ルールを最小化できるため
- [ ] スキーマファーストで進めるか（OpenAPI を先に書き、モック・型生成・契約テストへ流す）
      なぜ: コードファーストは実装都合が契約に漏れ、互換性管理が崩れやすいため

## Step 2: 後方互換の規約を最初に文書化する

プロジェクト開始時に以下の規約テンプレを API 設計ガイドライン（1枚）として確定する。
なぜ: 「何が破壊的変更か」の定義がないと、互換性の議論が変更のたびに蒸し返されるため。

```markdown
## 互換性規約（テンプレ）
1. 後方互換（予告なく実施可）= 加算的変更のみ:
   - オプショナルなフィールド / クエリパラメータの追加
   - 新しいエンドポイント / イベントタイプの追加
   - レスポンスへのフィールド追加（クライアントは未知フィールドを無視すること）
2. enum への値追加は「要注意の加算」: 受信側が未知の値で落ちないこと（Tolerant Reader）を
   消費者側の義務として本規約に明記した場合のみ加算的変更とみなす。
3. 破壊的変更（バージョン増設 + 移行期間が必須）:
   - フィールドの削除・改名・型変更・必須化、URL 構造の変更、
   - エラーコードの意味変更、デフォルト値や単位の変更
4. 削除の手順: Deprecation の告知（ヘッダ + ドキュメント）→ Sunset 期日提示 → 移行期間 → 削除。
   期間は消費者との契約に従う（外部公開 API の目安: 6〜12ヶ月。要確認）。
5. 日時は RFC 3339 / UTC 固定。ID は推測不能な形式（ULID / UUIDv7）。
```

- [ ] Tolerant Reader を消費者側の義務として規約に書いたか（未知フィールド・未知 enum 値を無視する）
- [ ] Deprecation → Sunset の手順と期間を契約書レベルの約束として定義したか

## Step 3: バージョニング方式を決める

**URL パス方式（/v1/）を基本とする。** なぜ: 最も単純で誤解がなく、ログ・監視でも判別しやすいため。

- 方針は「破壊的変更を避ける設計」が主、「バージョン増設」が従。v2 は最後の手段。
- 日付バージョン + 互換レイヤ（Stripe 式）は理想だが、少人数では維持コストが高すぎるため選ばない。
- ヘッダ / メディアタイプ方式は消費者のデバッグ難度を上げるので、明確な理由がなければ避ける。

## Step 4: ページネーションと冪等性を規約化する

### ページネーションの使い分け

| 方式 | 向く用途 | 制約 |
|---|---|---|
| オフセット式（page/limit） | 管理画面・任意ページジャンプが要る一覧 | 大規模データでずれ・性能劣化 |
| カーソル式（不透明トークン） | 無限スクロール・大量データ・安定した順序 | 任意ページジャンプ不可 |

なぜ規約化するか: エンドポイントごとに方式が揺れると SDK・画面実装の両方が複雑化するため。

### 冪等性（Idempotency-Key）

決済・注文など再送が事故になる POST は Idempotency-Key ヘッダで冪等化する（Stripe 方式。IETF で標準化ドラフト進行中——2026年時点の目安・要確認）。
なぜ: ネットワーク断・タイムアウト時のクライアント再送は防げない前提で設計するため。

仕様として必ず明記する3点:
- [ ] **再生**: 同一キー + 同一ボディの再送には、初回実行時の保存済みレスポンスをそのまま返す（再実行しない）
- [ ] **不一致は 409**: 同一キー + 異なるボディは 409 Conflict で拒否する
- [ ] **保存期間**: キーとレスポンスの保存期間を仕様に書く（例: 24時間。目安であり業務要件で決める）

## Step 5: イベント契約と配信保証を設計する

まず絞る: 小規模ならモジュラモノリス + 同期呼び出し + ジョブキューで十分。イベント駆動を使う箇所を意図的に限定する。
なぜ: EDA の導入自体が過剰設計になりやすく、消費者が見えにくい分だけ互換性管理が API よりシビアだから。

- [ ] **配信保証は at-least-once + 冪等コンシューマ** を標準とする（イベント ID で重複排除）
      なぜ: exactly-once をインフラに求めるのは限定条件でしか成立せず、受信側設計で吸収するのが実務解のため
- [ ] **Transactional Outbox**: DB 更新とイベント発行を同一トランザクションで outbox テーブルに書き、別プロセスが発行する。受信側は **Inbox** で重複排除を対にする
      なぜ: 「DB は成功したが publish 失敗」の不整合は Outbox 以外で確実には防げないため
- [ ] **DLQ 運用**: リトライ回数、DLQ 落ち後の対応者・手順、滞留アラートを設計に含めたか
      なぜ: 監視なき DLQ は静かにメッセージが溜まり、気づいた時には再処理不能になるため
- [ ] **相関 ID（correlation ID）** を全イベントに貫通させたか
      なぜ: 非同期化すると「この処理はなぜ動いたのか」の追跡が最初の障害調査で必ず問題になるため
- [ ] スキーマ: AsyncAPI 3.0 でイベントカタログ化し、エンベロープは CloudEvents に乗せる。進化は加算的変更のみ。破壊的変更は新イベントタイプ（v2）を並行発行し、購読者の移行完了後に旧を止める
- [ ] 順序保証が必要な処理か判定したか（必要ならパーティションキー / FIFO を明示）
- [ ] ペイロードは「必要最小の事実 + 参照 ID」に絞ったか（全部載せは Event Carried State Transfer を意図的に選んだ場合のみ）

## Step 6: Saga と補償アクションを設計する

分散トランザクションが必要になったら Saga で結果整合を組む。**小規模・少人数運用ではオーケストレーション型を選ぶ**（Step Functions / Temporal 等）。
なぜ: コレオグラフィ型は疎結合だが全体像が見えず、障害の夜にフローを一望できないのは少人数では致命的なため。

補償アクション網羅チェック（AI が網羅を検査し、人間が業務妥当性を承認する）:

- [ ] 全ステップに補償アクション（取消処理）を定義したか。「このステップの補償は?」に全行で答えられるか
- [ ] 補償不能なステップ（メール送信・外部通知など取り消せない副作用）は、フローの最後段に配置したか
- [ ] 補償アクション自体が冪等か（補償の再送でも結果が同じ）
- [ ] 途中失敗時に補償を逆順実行するトリガーと、補償も失敗した場合の人間へのエスカレーション先を決めたか
- [ ] どこまで同期トランザクションで厳密に守り、どこから結果整合を許すかをクライアント / 事業側と合意したか
      なぜ: 「在庫引当は同期で厳密、ポイント付与は非同期で結果整合」のような線引きは業務判断そのもので、外部設計の合意事項だから
- 分離性の欠如への技術対策（Semantic Lock / Commutative Update / Reread Value）・「まず分散させない」判断 → dev-core:resilience-design Step 6 参照。

## Step 7: エラー契約を RFC 9457 で統一する

自前フォーマットを発明せず **RFC 9457 Problem Details**（application/problem+json、RFC 7807 の後継）に乗る。
なぜ: 汎用クライアントと AI エージェントがそのまま解釈でき、消費者ごとの分岐実装を不要にするため。

```json
{
  "type": "https://api.example.com/problems/insufficient-balance",
  "title": "残高不足",
  "status": 422,
  "detail": "注文金額が残高を超えています。",
  "instance": "/orders/12345",
  "code": "PAY-042",
  "errors": [{ "field": "amount", "code": "EXCEEDS_BALANCE", "message": "残高の範囲で指定してください" }],
  "trace_id": "01J..."
}
```

エラーコード体系のルール:

- [ ] 「分類プレフィクス + 連番」の浅い階層にする（例: `AUTH-001`, `PAY-042`）。なぜ: 深い階層はカタログ保守が破綻するため
- [ ] **一度発番したコードは意味を変えない・再利用しない**。なぜ: ログ・サポート記事・顧客の手順書がコードに依存し、コードも互換性の約束事だから
- [ ] コードは「呼び出し側の対処が変わる単位」でだけ分ける（対処が同じエラーは同じコードでよい）
- [ ] HTTP ステータス = 機械的分類（4xx: 呼び出し側起因 / 5xx: サーバ起因、リトライ判断に直結）、エラーコード = 業務的分類、と役割を分ける
- [ ] リトライ可否と待機時間を契約に含める: リトライ可能なエラー（429/503 等）には **Retry-After** ヘッダを返す
- [ ] 機械はコードを、人間は文言を読む——フロントに文言の文字列一致で分岐させない。なぜ: 文言修正が破壊的変更になってしまうため
- [ ] 内部実装（SQL・パス・スタックトレース）をレスポンスに漏らさない。詳細はサーバログへ、レスポンスには相関 ID（trace_id）のみ載せる
- [ ] エラーカタログ（コード・ステータス・文言・対処法・リトライ可否）を単一の YAML / 表で管理し、文言・ドキュメント・型定義をそこから生成する。なぜ: 文言は自由に改善でき、コードと type URI は不変、という層別の互換性ポリシーが成立するため

全部 200 で返して `success: false` は禁止（HTTP セマンティクスを殺し、監視もリトライも壊れる）。バリデーションエラーは全件まとめて返す。

## Step 8: AI エージェント消費者に耐えるスペックにする

API の消費者は人間の開発者だけでなく AI エージェント（MCP 経由含む）になった。**OpenAPI の description・examples・エラー仕様の質が、エージェントのツール呼び出し成功率を直接左右する。**
なぜ: エージェントはドキュメントの行間を読めず、スペックに書かれた情報だけで呼び出しとリトライを判断するため。

- [ ] 全 operation・全パラメータに「何をするか + いつ使うか」の description があるか（空の description をリンタで禁止）
- [ ] 代表的なリクエスト / レスポンスの examples を載せたか（正常系 + 主要エラー）
- [ ] enum 値・単位・フォーマット（通貨、タイムゾーン、ページングの継続方法）を機械可読に明示したか
- [ ] エラーの type URI・エラーコード・Retry-After で、エージェントが自律リトライを正しく判断できるか（Step 7 と連動）
- [ ] スペックだけを渡した別セッションの AI に呼び出しコードを書かせ、誤解なく成功するかを受け入れテストにしたか

## 完了チェックリスト（契約確定前）

- [ ] 準拠先ガイドライン・互換性規約・バージョニング方針が1枚に文書化されている
- [ ] ページネーション方式と Idempotency-Key 仕様（再生・409・保存期間）が規約にある
- [ ] イベントは Outbox+Inbox・DLQ 運用・相関 ID・スキーマ進化ルールまで定義されている
- [ ] Saga の全ステップに補償があり、整合性境界が合意済み
- [ ] エラーは RFC 9457 準拠でカタログ化され、コード不変・Retry-After のルールがある
- [ ] OpenAPI / AsyncAPI が lint（Spectral 等）を通り、破壊的変更検出（oasdiff 等）が CI に入っている
- [ ] 「人間にしか決められないこと」の各項目が承認済み
