# Resilience Design（実行時の信頼性設計）

**鉄則: 「失敗したとき何が起きるか」を仕様として設計する。正常系だけの実装は未完成。**

正本分担: **設計判断・選定フロー = 本スキル**、**実装コード例（Result 型・Cache-Aside・トランザクション API）= dev-core:backend-patterns**。実装に落とす段になったら必ずそちらを参照する。

## Step 0: 適用範囲を確認する

着手前に以下を確認し、必要な Step だけ実行する。

- [ ] 金銭・在庫・予約を扱うか → **Step 4-6 必須**（不整合の事故コストが最も高い領域のため）
- [ ] 外部 API 呼び出し・メール送信があるか → **Step 3・5 必須**（再実行と二重送信の設計が要るため）
- [ ] 失敗しうる業務操作があるか → **Step 1-2 必須**（=ほぼ全案件。異常系が仕様の一部になるため）
- [ ] 性能目的でキャッシュを検討しているか → **Step 7**（ただし導入前チェックを先に通す）

## Step 1: 例外を3分類する

**なぜ**: この3分類を最初に決めると、リトライ・Result 型・通知の設計が全部ここから導ける。

| 分類 | 例 | 性質 | 対応方針 |
|---|---|---|---|
| ① 業務例外 | 在庫切れ・権限なし・重複申請 | 仕様の一部（起きるのが正常） | Result 型で返し、ユーザーに回復手段を提示する |
| ② 一時的技術例外 | ネットワーク断・タイムアウト・一時的な 5xx | 時間が解決しうる | リトライ対象にする（Step 3） |
| ③ 恒久的技術例外 | バグ・設定ミス・不正な状態 | リトライしても直らない | フェイルファストで即座に失敗させ、開発者に通知する |

分類の手順:

1. ユースケースごとに「起こりうる失敗」を全て列挙する（AI に網羅列挙させてよい）。
2. 各失敗を上の3分類に振り分ける。境界が曖昧なもの（「在庫切れは業務例外か」等）は業務判断リスト（後述）へ回す。
3. 分類×対応方針の表を設計書に残す。**なぜ**: 実装者（人間でも AI でも）が catch 節を書くたびに迷わなくなる。

**握りつぶし禁止**:

- `catch (e) { log(e) }` で続行するコードを書かない・許さない。**なぜ**: 静かにデータが壊れ、発覚が最も遅れる失敗モードだから。
- 例外を捕捉してよいのは「その場で意味のある対処ができる層」だけ。対処できない層は素通しする。
- lint（no-empty-catch 等）で決定的に強制する → dev-core:conventions-as-guardrails 参照。

## Step 2: Result 型の適用基準を決める

**なぜ**: Result 型は呼び出し側にハンドリングを型で強制でき、AI が生成するコードでも処理漏れがコンパイルエラーになる。

適用基準（この2行で判定する）:

- **業務例外（分類①）= Result 型で返す**。呼び出し側の負担は増えるが、失敗の見逃しを型で防ぐ。
- **プログラミングエラー（分類③）= 例外を投げてフェイルファスト**。回復不能な状態を Result で包んで伝播させない。起動時の設定検証・事前条件アサーションも同様に即失敗させる。

チェックリスト:

- [ ] 業務例外を例外機構で投げていないか（制御フローに例外を使わない）
- [ ] 回復不能なエラーを Result で握って続行していないか
- [ ] Result の型定義・ヘルパー実装 → dev-core:backend-patterns の Result パターン節を使う

## Step 3: リトライを設計する

**前提条件: リトライ対象の操作は冪等であること。** 冪等キーなしで非冪等操作（決済・メール送信・注文作成）をリトライするのは禁止。**なぜ**: リトライは「同じ操作がもう一度走る」設計であり、冪等でなければ二重実行事故になるから。

初期値テンプレート（Exponential Backoff + Jitter）:

| 項目 | 初期値 | 理由 |
|---|---|---|
| 対象 | 分類②（一時的技術例外）のみ | ①はリトライ不要、③はリトライしても直らない |
| 初期間隔 | 100〜200ms から指数倍 | 早すぎる再試行は障害中の依存先を殴り続けるだけ |
| 上限間隔 | 30〜60秒 | 無限に伸ばすとユーザー体験・キュー滞留が悪化する |
| 最大回数 | 必須（3〜5回を起点に調整） | 上限なしのリトライは障害を長引かせる |
| ジッタ | 間隔に±ランダムを加える | 同時大量リトライ（thundering herd）を散らすため |
| タイムアウト | 実測 p95 の少し上 | 根拠のない長大タイムアウトはスレッド・接続を枯渇させる |

規約:

- [ ] **リトライは1層のみ**。HTTP クライアント・アプリ・キューの多段リトライは障害時にリクエストを指数的に増幅させる。どの層が担当するか1箇所に決めて明記する。
- [ ] 冪等キー（Idempotency-Key）の採番・保存方式を設計する。API 契約としての冪等性は dev-core:interface-contract-design 参照。
- [ ] 連続失敗する依存先にはサーキットブレーカーを置く。**なぜ**: 死んでいる依存先への無駄なリトライが連鎖障害を生むから。実装はライブラリ（resilience4j / Polly 等）を使い、自作しない。

## Step 4: 分離レベルとロックを選択する

まず DBMS のデフォルトを確認する。**なぜ**: デフォルト差を知らないと書き込みスキュー等のアノマリを見逃すから。

- PostgreSQL: Read Committed / MySQL (InnoDB): Repeatable Read。MVCC の実装差があるため、使う DBMS の公式ドキュメントで挙動を確認する。

ロック選択フロー:

1. **その競合、DB の制約で防げないか?** → 二重登録防止は UNIQUE 制約、残数判定は条件付き UPDATE（`UPDATE ... WHERE stock > 0`）を最優先。**なぜ**: 「読み取ってアプリで判定して書き込む」（check-then-act）はトランザクションで囲んでも分離レベル次第で競合するため、判定を DB 側に寄せるのが最も確実。
2. **競合が高頻度・処理が短時間か?**（在庫引当等）→ 悲観ロック（`SELECT ... FOR UPDATE`）。ロック取得順序を固定してデッドロックを防ぐ。
3. **競合が低頻度・ユーザーの編集画面か?**（長い思考時間を挟む）→ 楽観ロック（version カラムで更新時に競合検出）。競合時は「他の人が更新しました」を提示して再編集させる。
4. **どちらも該当しない読み取り中心の処理** → デフォルト分離レベルのまま、競合シナリオ表（Step 5）で問題がないことを確認する。

## Step 5: トランザクション境界を規約化する

境界規約（全案件共通）:

- **トランザクション境界内は DB 操作のみ。短く保つ。**
- **外部 I/O（API 呼び出し・メール送信）は境界の外へ。DB 更新との原子性が必要なら Outbox パターン**（Outbox テーブルに書き、ポーリング/CDC で送信）。**なぜ**: 境界内の外部 I/O はロック長期化を招き、コミット後の送信失敗で「DB は更新済みなのに通知されない」不整合を生むから。
- 「とりあえず transaction で囲む」を書かない。境界はユースケース単位で意図を持って決める。

競合シナリオ表を書く。**なぜ**: 書き込みスキューや更新消失は、シナリオを列挙して初めて気づけることが多いから。同時実行パターンの網羅列挙は AI が得意なので任せてよい。

| シナリオ | 同時操作 | 期待結果（業務判断） | 対策 |
|---|---|---|---|
| 在庫1で2人同時購入 | 購入A / 購入B | 先勝ち・後者は在庫切れ表示 | 条件付き UPDATE or FOR UPDATE |
| 同一フォーム二重送信 | 登録 / 登録 | 1件のみ作成 | 冪等キー + UNIQUE 制約 |
| 編集画面の同時保存 | 更新A / 更新B | 後者に競合を通知 | 楽観ロック（version） |

「期待結果」列は技術では決められない（業務判断リスト参照）。表を顧客・発注者と読み合わせて確定する。

## Step 6: 「まず分散させない」判断と Saga

- **モノリス + 単一 RDB を維持できる限り維持する。分散トランザクションを設計しなくて済むアーキテクチャを選ぶこと自体が最良のトランザクション設計。** なぜ: Saga・結果整合は設計・テスト・運用コストが桁違いに高いから。
- 分散が避けられない場合のみ Saga（ローカルトランザクションの連鎖 + 失敗時の補償トランザクション）を設計する。追跡しやすいオーケストレーション型を起点に検討する。
- **Saga は ACID の I（分離性）を欠く**。対策を明示的に設計する: Semantic Lock（処理中フラグ）・Commutative Update（可換な更新）・Reread Value（更新前に再読して検証）。
- 2PC/XA は運用が重く、最終手段としてのみ検討する。
- 補償アクションの網羅チェックリスト・整合性境界の顧客合意 → dev-core:interface-contract-design Step 6 参照。

## Step 7: キャッシュを設計する

導入前チェック（順に通す。**なぜ**: キャッシュは「意図的に古いデータを許容する設計判断」であり、最後の手段だから）:

- [ ] そのクエリ、インデックスと SQL 改善で足りないか? を先に実測で検証したか
- [ ] 「古いデータが N 秒見えても業務が壊れないか」を顧客に確認したか（TTL は技術値でなく業務値）
- [ ] どの層で解くか決めたか: HTTP/CDN → アプリ内メモリ → 分散キャッシュ (Redis 等) → DB バッファ。多層に同じデータを置くと無効化が地獄になる

導入するなら、キャッシュ設計表を書いてから実装する:

| 対象データ | 戦略 | TTL（許容鮮度=顧客合意値） | 無効化トリガ |
|---|---|---|---|
| 例: 商品マスタ | Cache-Aside | 5分 + ジッタ±10-20% | 商品更新時に delete |

- 戦略の選択: 迷ったら Cache-Aside（最も一般的で制御しやすい）。強い読み取り整合が要る箇所のみ Write-Through、損失許容データ（カウンタ等）のみ Write-Behind。
- 無効化は「書き込み時に delete → 次回読み込みで再生成」を基本形にする。**なぜ**: update 書き戻しは二重書き込みの順序問題で古い値が残留しうるから。
- TTL には ±10-20% のランダムジッタを入れる。**なぜ**: 同時大量 expire がスタンピードを誘発するから。
- キャッシュ全損（再起動）でも DB が耐える容量か、ウォームアップ手順を用意する。
- キー名にスキーマバージョンを含める（デシリアライズ形式変更時の事故防止）。

スタンピード対策4種（人気キーほど必須）:

1. **ロック / singleflight** — 再生成を1リクエストに限定する
2. **確率的早期再生成（XFetch）** — expire 前に確率的に再計算する
3. **バックグラウンド更新** — expire 前にワーカーが更新する
4. **stale-while-revalidate**（RFC 5861）— 古い値を返しつつ裏で更新する（CDN/HTTP 層）

実装コード（Cache-Aside・singleflight 等）→ dev-core:backend-patterns 参照。

## AI がやること / 人間にしか決められないこと

| AI に任せてよい | 人間（+顧客）にしか決められない |
|---|---|
| 失敗モード・競合シナリオの網羅列挙 | 「同時に来たらどちらを勝たせるか」（業務ルール） |
| 3分類マトリクス・設計表のドラフト生成 | 例外3分類の境界判定（「在庫切れは業務例外か」等） |
| Result 型への機械的な書き換え | リトライしてよい操作の認定（冪等性の業務的保証） |
| リトライ / サーキットブレーカー / キャッシュの実装 | 整合性レベルの選択（不整合時の業務被害の見積もり） |
| 無効化漏れの横断チェック（更新箇所×キャッシュ削除） | TTL =「何秒古くてよいか」の顧客合意 |
| デッドロック調査ログの解析 | 本番での分離レベル変更・キャッシュフラッシュの実行承認 |

**なぜ分担するのか**: 信頼性設計の核心は「業務判断（顧客と合意する値）」と「技術判断（定石の適用）」の分離にある。後者は AI + 決定的チェックに委譲できるが、前者を AI が勝手に決めると顧客合意なき仕様が生まれる。

## 業務判断項目リスト（顧客合意値）

設計を確定する前に、以下を顧客・発注者に確認して記録する。合意の進め方は delivery-core:client-alignment 参照。

- [ ] 同時に競合したら**どちらを勝たせるか**（先勝ち/後勝ち/両方エラー）— 競合シナリオ表の「期待結果」列
- [ ] キャッシュ対象ごとに**何秒古くてよいか**（TTL の根拠になる許容鮮度）
- [ ] どの失敗が**業務例外か**（ユーザーに見せて回復させる失敗の範囲）
- [ ] **リトライ・再実行してよい操作**はどれか（二重実行が許されない操作の列挙）
- [ ] 強整合が必要なデータと結果整合で足りるデータの線引き（不整合時の業務被害で判断）
- [ ] 障害時にユーザーへ見せる文言・案内（エラーメッセージの承認）
