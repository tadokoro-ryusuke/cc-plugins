# Security by Design

**鉄則: セキュリティは後付けできない。認証・認可・データ保護は最初の設計レビューで決める。**

後工程での認可モデル作り直しは最悪級の手戻りであり、契約上の責任リスクにも直結するため。

**位置づけ**: 本スキルは**設計・方針の正本**。実行時のチェックは `dev-core:verify` の Stage 5（security）が、コード監査は security-auditor エージェントが、ここで決めた方針を検証する側として担う。

## 全体フロー

```
Step 0 資産の棚卸し → Step 1 軽量STRIDE → Step 2 ASVSレベル選定
→ Step 3 アクセスアーキテクチャ → Step 4 暗号化・シークレット
→ Step 5 脆弱性対応方針 → Step 6 AIエージェント脅威 → 失敗レビュー
```

要件定義〜方式設計と並走させ、実装前に Step 1〜4 を確定させること。実装後に始めると設計手戻りになるため。

## Step 0: 守るべき資産の棚卸し

1. **扱うデータを列挙する**: 個人情報（件数・種類）、認証情報、決済情報、営業秘密。守る対象が不明なままでは統制の強度を決められないため。
2. **法令・規格の該当を確認する**: 個人情報保護法・PCI DSS 等の該当有無（目安であり、最終判断は専門家に確認する）。→ 法令対応の詳細は compliance-core:privacy-data-compliance 参照。
3. **受容リスクをユーザー（顧客）に確認する**: 「全部守る」は設計不能。何を諦めるかはビジネス判断のため。

## Step 1: 軽量 STRIDE 脅威モデリング

フル STRIDE は小規模体制には過剰。**信頼境界をまたぐデータフローだけに絞る**のが現実的な運用形。

1. **DFD を描く**: コンポーネント（ユーザー、フロント、API、DB、外部サービス、AI エージェント）と矢印（データフロー）を Mermaid で列挙する。テキスト管理にするのは Git レビューと AI 読み込みのため。
2. **信頼境界をまたぐ矢印だけ残す**: ユーザー→API、API→DB、API→外部連携、CI→本番など。境界内の矢印まで見ると脅威表が発散して保守されないため。
3. **各矢印に STRIDE 6 分類を当てる**: Spoofing（なりすまし）/ Tampering（改ざん）/ Repudiation（否認）/ Information Disclosure（漏えい）/ DoS / Elevation of Privilege（権限昇格）。
4. **脅威表を作り、対策をマッピングする**:

```markdown
| # | データフロー | 脅威(STRIDE) | シナリオ | 対策 | 状態 |
|---|------------|-------------|---------|------|------|
| 1 | ユーザー→API | S | セッション窃取 | IdP + 短命トークン | 設計済 |
| 2 | API→DB | I | 認可バグで他テナント参照 | テナントIDをクエリ層で強制 | 未対応 |
```

5. **Threat Modeling Manifesto の 4 つの問いで締める**: 「何を作る? 何がまずい? どうする? 十分か?」。網羅性より継続性が価値のため、設計レビューの定例項目にする。

脅威表はリポジトリ内 markdown で維持する。AI エージェントへのコンテキスト供給源を兼ねるため。

## Step 2: ASVS レベル選定と責任スコープ画定

OWASP ASVS（Application Security Verification Standard）5.0（2025年5月リリース、17章・3レベル。目安・2026年時点、最新版を要確認）をセキュリティ要件の語彙として使う。独自チェックリストより標準準拠の宣言が説明責任を軽くするため。

**データ機微度 → レベルの目安**:

| 扱うデータ | レベル目安 | 例 |
|-----------|----------|----|
| 公開情報のみ・個人情報なし | L1 | LP、公開カタログ |
| 一般的な個人情報・ログイン機能あり | L2 | 業務 SaaS、EC、会員制サービス |
| 決済・医療・大量の機微情報・金融 | L3 | 決済基盤、医療系（専門家レビュー併用を推奨） |

1. **レベルをユーザー（顧客）と合意する**: 「全部 L3」は工数・UX を壊すだけで誰も幸せにしないため。
2. **合意したレベルを契約・提案書に明記する**: 「本件は ASVS レベル N 準拠。ペネトレーションテストは別途」のようにスコープを画定する。無限責任の回避と品質宣言を兼ねる最重要の一手のため。契約条項への落とし込みは法務・弁護士に確認する。
3. **API 中心の案件では OWASP API Security Top 10 を併用する**: ASVS だけでは API 固有の落とし穴（BOLA 等）の視点が薄いため。

要件の実装レベルのチェックリスト（OWASP Top 10 対応）は `dev-core:best-practices` の references/security.md 参照。非機能要件としての合意の取り方は delivery-core:requirements-definition 参照。

## Step 3: アクセスアーキテクチャ — ゼロトラストと閉域代替

原則は NIST SP 800-207（目安・2026年時点、要確認）: **ネットワーク位置を信頼せず、すべてのアクセスを認証・認可・暗号化する**。

1. **管理画面・社内ツールは IdP 連携のアクセスプロキシで保護する**: Cloudflare Access / Tailscale / Cloud IAP 等。VPN より鍵の失効・監査ログ・端末条件の統制が容易なため。
2. **「閉域にしたい」と言われたら規程の原文を確認する**: 「なんとなく閉域」は多い。本当の要求が「インターネットから直接触れないこと」なら、IdP プロキシ + IP 制限 + mTLS で代替提案できることが多く、専用線調達（リードタイム数週間〜数ヶ月）と工数増を回避できるため。真の閉域要件（金融・官公庁等）ならスケジュールの最初に回線調達を置く。
3. **サービス間通信も認証する**: mTLS またはクラウド IAM 認証。境界の内側を無条件に信頼しないため。
4. **人間・AI ともに最小権限にする**: ロールは deny-by-default で始め、必要になったら足す。広い権限を後から狭めるのは事実上不可能なため。

## Step 4: 暗号化・シークレット管理のデフォルト

議論の余地をなくすため、以下を**選定済みデフォルト**として扱う。逸脱する場合のみ ADR に理由を残す。

| 項目 | デフォルト | なぜ |
|------|-----------|------|
| 保存時暗号化 | クラウドの KMS 暗号化を**全リソースで有効化** | 個別判断のコストをゼロにし、漏れを構造的に防ぐ |
| 転送時暗号化 | TLS 1.2 以上（新規は 1.3）、内部通信も原則 TLS | ゼロトラスト方針との整合 |
| 鍵管理 | KMS に寄せる。**暗号の自前実装は禁止** | 自前暗号は最頻出の重大事故源 |
| パスワード保存 | Argon2id または bcrypt | 標準アルゴリズム以外を選ぶ理由がない |
| フィールド単位暗号化 | 法令・規格が要求する場合のみ | 過剰適用は検索性・運用を壊す |
| シークレット保管 | AWS Secrets Manager / SSM Parameter Store / GCP Secret Manager。ローカル・小規模は SOPS + KMS | リポジトリと環境変数ファイルから秘密を排除する |
| シークレット検出 | **gitleaks を pre-commit と CI の両方に**（二重化） | 片方だけでは human error がすり抜ける |
| ローテーション | 環境変数注入・起動時取得にし、無停止で差し替え可能に | 漏えい時の初動を数分にする |

**AI 時代の追加鉄則**: AI エージェントが読めるファイル（リポジトリ内・プロンプト・設定 markdown）に秘密を書かない。プロンプト経由の漏えいは gitleaks では防げないため。

**漏えいしたら**: 即ローテーション。削除コミットでは消えない（履歴・フォーク・キャッシュに残る）ため。

## Step 5: 脆弱性トリアージと保守 SLA への接続

1. **検知を自動化する**: 依存関係は Dependabot / Renovate、コンテナ・IaC は Trivy、コードは SAST（CodeQL / Semgrep）。人手の巡回は続かないため。CI への組み込み位置は dev-core:cicd-release-design 参照。
2. **CVSS 単体でトリアージしない**: CVSS は「悪用されたときの深刻度」であり「悪用される確率」ではないため。判定順:
   - **CISA KEV に載っている**（悪用実績あり）→ 最優先で即対応
   - **EPSS が高い**（悪用確率が高い）→ 期限付きで対応
   - **上記以外の Critical/High** → 定期メンテナンスサイクルで対応
   - **Low / 到達不能パス** → 記録して静観（全部対応は疲弊、全部無視は事故のため）
3. **トリアージ基準と対応期限を保守契約の SLA に定義する**: 例「KEV 掲載: N 営業日以内、High: 次回定期リリース」。緊急対応の工数・料金の扱いは自組織の見積・価格判断プロセスで定める。契約に書いていない緊急対応は無償対応かトラブルの二択になるため。
4. **SBOM（CycloneDX / SPDX）生成をビルドに組み込む**: エンタープライズ顧客のサプライチェーン要求に即応できるため。OSS ライセンス面は compliance-core:oss-license-audit 参照。

## Step 6: AI エージェント自体の脅威対策

AI 機能を組み込む案件でも、自分の開発体制（Claude Code / Codex）でも、**AI エージェントは新しい攻撃面**として脅威モデルに含める。参照枠は OWASP LLM アプリケーション Top 10 と CSA MAESTRO（目安・2026年時点、要確認）。

- [ ] **プロンプトインジェクションを Step 1 の DFD に載せる**: 外部入力（Web ページ・ユーザー文書・ツール出力）→ LLM の矢印は信頼境界をまたぐため。
- [ ] **ツール権限を最小化する**: エージェントに渡すツール・API キー・DB 権限はタスクに必要な最小セットに絞る。インジェクション成立時の被害半径が権限で決まるため。
- [ ] **不可逆・破壊的操作に人間の承認ゲートを置く**: 本番適用（`terraform apply` 等）、DNS 変更、削除、送金・送信系。承認フローの設計は ai-engineering:human-in-the-loop-design 参照。
- [ ] **AI 出力（コード・SQL・コマンド）を信頼境界の内側として扱わない**: 生成コードの認可ロジックは人間が最終確認する。AI は「動く」コードを書くが「漏れない」保証はしないため。
- [ ] **AI システム全体の設計は ai-engineering:ai-system-design 参照**、生成 AI の知財・入力データの扱いは compliance-core:genai-ip-clearance 参照。

## よくある失敗レビューリスト

設計レビュー時にこの表で自己点検する。すべて実案件で頻発する事故パターンのため。

- [ ] **認可を後回しにしていないか** — 認証・認可・マルチテナント分離は最初の設計レビューで STRIDE にかける。認可モデルの作り直しは最悪級の手戻りのため。実装パターンは `dev-core:backend-patterns` 参照。
- [ ] **WAF を過信していないか** — WAF は既知パターンの一部にしか効かず、認可バグ（IDOR）は素通しする。認可テストはコードレベルで書く。
- [ ] **シークレットがコミットされ得る構成になっていないか** — gitleaks 二重化（Step 4）を確認。公開リポジトリ化・AI ツール連携で漏えいが顕在化するため。
- [ ] **ASVS レベル（責任スコープ）を契約・提案書に明記したか** — 曖昧なまま事故が起きると賠償交渉で不利になるため。
- [ ] **脆弱性アラートを「全部対応」か「全部無視」にしていないか** — EPSS/KEV トリアージ（Step 5）に落とす。
- [ ] **「閉域」を鵜呑みにしていないか** — 規程の原文を確認し、ゼロトラスト代替（Step 3）を先に検討したか。
- [ ] **脅威表・方針がリポジトリ外にないか** — AI が読めない場所の設計文書は、AI の場当たり実装で境界が壊れる原因になるため。

## AI がやること / 人間にしか決められないこと

| AI がやること | 人間にしか決められないこと |
|--------------|--------------------------|
| DFD からの STRIDE 脅威列挙（網羅性は人間より高い） | 守るべき資産と受容リスクの決定（ビジネス判断） |
| ASVS チェックリストとコード・設計の突合 | ASVS レベルの確定と契約責任スコープの合意 |
| SAST / Trivy / 依存監査結果のトリアージ一次案 | トリアージ最終判断と保守 SLA の条件決定 |
| セキュリティ設計書・脅威表・対策のドラフト | 設計の Accept 判断、逸脱 ADR の承認 |
| gitleaks / SBOM / スキャンの CI 組み込み実装 | インシデント発生時の顧客対応・開示判断 |
| 生成コードへのセキュリティパターン適用 | AI 生成コードの認可ロジック最終確認 |
| 閉域代替案（ゼロトラスト構成）の比較表作成 | 顧客規程の解釈と代替提案の交渉 |

**運用原則**: AI には分析・列挙・ドラフト・検証まで任せ、リスク受容と契約に関わる確定は必ず人間が行う。説明責任は移譲できないため。
