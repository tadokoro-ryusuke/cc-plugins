# CI/CD & Release Design

**鉄則: デプロイ（コードを本番に置く）とリリース（ユーザーに機能を見せる）を分離せよ。**

CI/CD はリポジトリ作成と同時に整備する初期投資であり、以後の全工程の速度と品質の下限を規定する。
一人+AIエージェント体制では CI が「人間の代わりに常時起きている品質監督」になる——エージェントの成果物は CI のゲートを通ることで初めて信頼できる。

設計の良し悪しは DORA Four Keys（デプロイ頻度・変更リードタイム・変更障害率・MTTR）で測る。
なぜ: パイプラインの善し悪しを主観でなく業界標準メトリクスで語れるようにするため。

## 設計時に必ず作る成果物

- [ ] パイプライン定義（GitHub Actions ワークフロー YAML / GitLab CI）
- [ ] 品質ゲート定義（lint / typecheck / test / coverage 閾値 / SAST / 依存監査 / build）
- [ ] ブランチ保護ルール（required checks、レビュー必須、force push 禁止）
- [ ] シークレット管理設計（何をどこに置き、どう注入するか。OIDC 化の範囲）
- [ ] 環境定義（dev / staging / production と昇格条件、Environments の承認設定）
- [ ] リリース手順書（デプロイ戦略・確認項目・ロールバック手順を含む）
- [ ] フィーチャーフラグ台帳（フラグ名・目的・種別・除去期限）
- [ ] DB マイグレーション方針（expand-contract 前提のルール）

## Step 1: 品質ゲートを3段階で設計する

すべてを PR 時に走らせない。段階化が定石。
なぜ: 全チェックを PR に積むと15分超になり開発が滞る。「PR で数分、マージ後に重いもの」で速度と安全を両立する。

| 段階 | 実行するチェック | 目標時間 |
|---|---|---|
| PR 時 | lint + typecheck + unit | 数分以内 |
| マージ時 | integration + build | — |
| リリース前 | E2E + セキュリティスキャン | — |

- 脆弱性は critical/high のみビルド失敗にする等、開発者摩擦と安全のバランスを閾値で調整する。
- カバレッジのラチェット運用（下げない）と flaky テストの隔離ルールは、正本 → 姉妹スキル test-design（Step 7 運用ルール / テスト計画レビュー・チェックリスト）。CI 側はその機械的実装（閾値ゲートの設定・quarantine ラベルと skip 手順）を担う。
- テストの配分（ピラミッド）・技法・観点表の設計 → 姉妹スキル test-design 参照。
- ローカルでの検証実行フロー → dev-core:verify 参照。

## Step 2: シークレットと権限を固める

優先順位を守って選択する。上から順に検討し、下に降りる理由を明文化する。

1. **OIDC キーレス認証**（GitHub Actions → AWS/GCP/Azure へ短命トークンで認証。長期キー保存ゼロ）
2. **GitHub Environments + 承認**（残るシークレットはここに置き、本番用は required reviewers で保護）
3. **HashiCorp Vault / AWS Secrets Manager**（組織要件や既存基盤がある場合）

なぜ: 漏れるシークレットは「存在しないシークレット」に勝てない。長期キーを持たない構成が最強の防御。

必須の追加ハードニング:

- [ ] サードパーティ Action は **SHA ピン留め**する（タグ参照は改ざんに弱い）。
  なぜ: 2025年3月の tj-actions/changed-files 侵害（2.3万リポジトリに影響）はタグ参照経由で広がった。
- [ ] `permissions:` を明示し **GITHUB_TOKEN を最小権限**にする（デフォルトの広い権限で流さない）。
- [ ] シークレットをリポジトリ変数や `.env` コミットに置かない。
  なぜ: 組織の61%が公開リポジトリにシークレットを露出しているという調査がある（目安・要確認）。
- [ ] Dependabot/Renovate による依存自動更新を有効化する。SLSA / SBOM は顧客のセキュリティ要件に応じて追加する。

## Step 3: 標準テンプレを1つ作り、全案件に複製する

案件ごとにパイプラインをゼロから書かない。
なぜ: 一人受託ではテンプレの複製が最大の効率化。差別化にならない CI 基盤に時間を使わない。

- [ ] CI 基盤はマネージド（GitHub Actions / GitLab CI）に全振りする。Jenkins 自前運用は選ばない。
- [ ] **検証コマンドは1箇所に一本化**（package.json scripts / Makefile / justfile / cargo alias / uv+pyproject 等、スタックの標準に従う）し、ローカルと CI で同じコマンドを叩く。複数言語共存（Tauri 等）なら Makefile / justfile で全系統を束ねる。
  なぜ: ローカルで再現できない CI 失敗はデバッグ工数を倍化させる。
- [ ] flaky 隔離の手順（ラベル・skip 方法・復帰条件）をテンプレに含める。
- [ ] テンプレ改善は案件からのフィードバックで継続的に行い、次案件へ還元する。
- CI 失敗の原因調査そのもの → dev-core:debug 参照。

## Step 4: デプロイ戦略を SLA とトラフィック規模で選ぶ

| 戦略 | 仕組み | 強み | 代償・前提 | 向く場面 |
|---|---|---|---|---|
| Blue/Green | 本番同等の2環境を用意し、待機側に新版→検証→切替 | ロールバックは切替を戻すだけで即時 | 環境コスト2倍 | 大きめの変更・即時ロールバック必須 |
| カナリア | 新版をトラフィックの数%に流し、監視しながら段階拡大 | 影響半径（blast radius）最小 | 新旧併存に耐える設計と監視の成熟 | 日次の小リリース |
| ローリング | インスタンスを順次入替（Kubernetes のデフォルト） | コスト効率が良い | 新旧混在期間が長い | k8s 標準構成 |
| マネージドPaaS組込み | Cloud Run のトラフィック分割・Vercel のスキュー保護・Cloudflare Workers の gradual deployments（`wrangler versions upload` → プレビュー検証 → `versions deploy` で%分割 → `rollback`）等 | 追加装備ほぼ不要 | プラットフォーム機能の範囲内 | 小規模案件の多数派 |

**この表はサーバー側デプロイ前提。** デスクトップ/モバイル配布（Tauri・Electron・ストアアプリ）は別の型になる:

- **段階ロールアウトの単位はトラフィック%でなく更新チャネル**（stable / beta）とアップデータの段階配信。
- **コード署名が必須の品質ゲートに加わる**（Windows 証明書 / macOS Developer ID + notarization / モバイルはストア審査）。署名鍵・updater 秘密鍵は CI シークレットで管理し、**updater 署名鍵の喪失 = 既存ユーザーに更新を配れなくなる**ため鍵のバックアップ手順を最初に決める。
- **ロールバックは「切り戻し配信」**: 旧バージョンを新バージョン番号で再配信する手順を用意する（ユーザー環境のバイナリは即時には戻せない）。

- 小規模案件の多数派は「**マネージドPaaS の組込みトラフィック制御 + フィーチャーフラグ + 即時ロールバック手順書**」で十分。Kubernetes + Argo 級の装備は過剰投資。
  なぜ: 安全性はコストと複雑さとのトレードオフ。案件の SLA とトラフィック規模で決める。
- 定石の組合せ: **トランクベース + フィーチャーフラグ + カナリアで日次の小リリース、大きな切替だけ Blue/Green**。
- 金曜夕方デプロイは避ける。なぜ: 障害対応の人的リソースが最も薄い時間帯に賭けをしない。
- staging と本番の乖離を IaC で潰す。なぜ: 検収環境と本番の乖離は検収後トラブルの主因。
- ブランチ運用（GitHub Flow / トランクベース）の選択 → 姉妹スキル issue-driven-dev 参照。

## Step 5: フィーチャーフラグを種別と寿命で管理する

フラグは種別を分け、**作った瞬間に除去期限を決める**（Pete Hodgson「Feature Toggles」の型）。
なぜ: 期限のないフラグは数十個の死にフラグとなり分岐爆発を起こす。

| 種別 | 目的 | 寿命の目安（原典） |
|---|---|---|
| Release toggle | 未完成機能の隠蔽・段階公開 | 1〜2週間で除去 |
| Experiment toggle | A/B テスト | 統計的有意が出るまで（数時間〜数週間） |
| Ops toggle | 負荷遮断等の運用スイッチ | 短命が原則。ただし kill switch は恒久の例外 |
| Permission toggle | プラン・権限による出し分け | 恒久でよい（有料プラン制御などは年単位） |

寿命の目安は Pete Hodgson「Feature Toggles (aka Feature Flags)」（martinfowler.com）に拠る。

- [ ] プロダクト都合で長引く Release toggle も、例外扱いにせず必ず除去期限を切り直す（本スキルの運用ルール）。
- [ ] フラグ台帳（名前・目的・種別・除去期限）を維持する。
- [ ] **月次（最低でも四半期）の棚卸しを固定行事にする**。参照されなくなったフラグは除去 PR を出す。
- ツールは LaunchDarkly / Unleash（OSS）/ OpenFeature（CNCF 標準 API）から選ぶ。
- なぜフラグを使うか: デプロイの技術リスクとリリースのビジネスリスクを分離できるから。

## Step 6: 「戻せるデプロイ」を設計する

### DB マイグレーションは expand-contract で

スキーマ変更は「**追加（expand）→ 新旧両対応 → 旧削除（contract）**」の3段階で行い、常に1世代前と互換にする。
なぜ: スキーマが後方互換でないと、コードだけロールバックしても壊れる。ロールバック可能性は事実上ここで決まる。

3フェーズ手順（Expand / Migrate / Contract）とオンライン DDL の詳細正本 → dev-core:data-design-ops 参照。本スキルはパイプラインへの組み込みとロールバック設計を担当する。

### ロールバック判断基準はデプロイ前に決める

- [ ] 発動基準を事前定義する（例: エラー率 X% 超でロールバック）。「なんとなく大丈夫そう」で全量公開しない。
- [ ] 高リスク変更では、**デプロイ前にロールバックコマンドを書いておく**。
  なぜ: 障害の渦中に手順を考え始めるのが最悪のパターン。
- [ ] ロールバック vs ロールフォワードの使い分け: 即時性が必要ならロールバック、データ変換を伴う場合や hotfix が小さい場合はロールフォワード。

## Step 7: エージェントの権限を設計する

エージェントに CI/CD を触らせる際の権限設計は、それ自体が独立した設計項目である。

- [ ] **本番デプロイの最終トリガは人間の承認に固定する**（GitHub Environments の required reviewers）。
  なぜ: 「自分が寝ている間にエージェントが本番を触らない」が一人会社の安全な既定値。
- [ ] エージェント用トークンは書込先を限定する。
- [ ] **workflow ファイルを CODEOWNERS で保護する**。
  なぜ: CI はエージェントの暴走を止める最後の砦。エージェントがゲート自体を書き換えられてはならない。
- [ ] 書込先が本番系・操作が不可逆・エラーコストがレビューコストを超える操作は、人間承認を必須にする。
- 人間の介在点設計の一般論 → ai-engineering:human-in-the-loop-design（別プラグイン） 参照。

## 分担線: AI がやること / 人間にしか決められないこと

### AI（このスキルを実行するエージェント）がやること

- ワークフロー YAML の生成・保守
- CI 失敗ログの一次解析と修正 PR の作成
- 依存更新 PR のレビュー補助、セキュリティアラートのトリアージ
- リリースノート生成、デプロイ後メトリクスの一次監視
- フラグ棚卸し（未参照フラグの検出と除去 PR）、マイグレーションの互換性チェック

### 人間にしか決められないこと

- **品質ゲートの閾値決定**（何を落第にするか）
- **本番リリースの Go/No-Go、本番環境への昇格承認**
- **ロールバックの発動**、顧客への影響告知
- シークレット/権限設計の最終決定（エージェント自身の権限を含む）

なぜ分担線を引くか: 本番への不可逆操作をエージェントの自律実行から外し human-in-the-loop を必須にするのが、2026年時点の実務コンセンサス。

## レビューチェックリスト（設計レビュー時に確認）

- [ ] 品質ゲートが3段階に分かれ、PR 時のチェックが数分以内に収まるか
- [ ] シークレットは OIDC 優先か。長期キーが残るなら理由が明文化されているか
- [ ] Action は SHA ピン留め、GITHUB_TOKEN は最小権限か
- [ ] ローカルと CI のコマンドが一本化されているか
- [ ] デプロイ戦略が SLA・規模に対して過剰装備/過少装備になっていないか
- [ ] フラグ台帳と棚卸しの運用が定義されているか
- [ ] マイグレーションが expand-contract 準拠で、ロールバック基準が事前定義されているか
- [ ] 本番デプロイの人間承認と workflow ファイルの CODEOWNERS 保護があるか

## 関連スキルとの境界

- テスト配分・技法・観点表・検収テスト → 姉妹スキル test-design
- ローカル6段階検証（build→type→lint→test→security→diff） → dev-core:verify
- TDD・セキュリティ原則・コーディング規約 → dev-core:best-practices
- セキュリティスキャンの選定方針・脆弱性トリアージ（EPSS/KEV）・SBOM 方針 → dev-core:security-by-design（本スキルは組み込み位置とタイミング）
- CI 失敗の根本原因分析 → dev-core:debug
- Issue 運用・ブランチ規約 → 姉妹スキル issue-driven-dev
- 規約を自動ガードレール化する仕組み → 姉妹スキル conventions-as-guardrails
- 人間介在点・承認フローの一般設計 → ai-engineering:human-in-the-loop-design（別プラグイン）
