# Test Design — テスト戦略・テスト設計・検収基準

**境界: 本スキルは「どこに・どの深さで・どの技法でテストを配置するか」の設計を扱う。テストの実行と証拠ベースの完了判定は → dev-core:verify 参照。**

受託開発ではテストは検収（納品物の合否判定）と契約不適合責任に直結する。だからテスト計画は実装後ではなく**見積・契約段階から**始めること。
なぜ: 検収基準が後出しになると「言った言わない」の紛争リスクと手戻りコストを自分が全額負担することになる。

## 分担線: AI がやること / 人間にしか決められないこと

| AI（このスキルを実行するエージェント）がやる | 人間にしか決められない |
|---|---|
| テスト観点表のドラフト生成 | 何をテストしないかの決定（リスク受容） |
| 技法適用の機械的展開（同値クラス・境界値からのケース生成） | 検収基準（受入基準）の確定と顧客合意 |
| 既存コードへのユニットテスト追補 | テストの「質」の最終判定（形だけのテストの棄却） |
| 探索的テストのブラウザエージェント実行 | リスクベース優先順位の承認（どの機能を浅くするか） |
| flaky テストの検出と隔離提案 | テスト戦略全体の承認とスコープ確定 |

なぜ分けるか: AI 生成テストは「量と課題解決率に有意な相関なし」という報告もある（2026年時点の目安・要確認）。AI は**受入基準の正本を人間が握った上での増幅装置**として使う。

## Step 1: 案件タイプからテスト配分を決める

まず配分モデルを1つ選び、テスト計画書に明記する。
なぜ: 配分を決めずに書き始めると、書きやすい場所（手動確認と E2E）にテストが偏る。

1. **テストピラミッド**（既定値）: unit を土台に 7〜8割、integration を中間、E2E を最小限に絞る
   - なぜ: 実行速度・保守コスト・デバッグ信号の経済学で下層が圧倒的に有利
2. **E2E は最重要ユーザージャーニーのハッピーパスのみ**。本数の目安は 5〜15本
   - なぜ: E2E を増やすほど安心に見えるが、flaky 化して CI の信用を壊す方が先に来る
3. **テスティングトロフィー**（Kent C. Dodds）: integration（コンポーネント統合テスト）を最厚にする変形

| 案件タイプ | 推奨モデル | 補足 |
|---|---|---|
| API・バックエンド中心 | ピラミッド | ドメインロジックの unit を最厚に |
| React/Next 等フロントエンド中心 | トロフィー | コンポーネント統合テストが実態に合う |
| 業務システム（状態・権限が複雑） | ピラミッド | デシジョンテーブル・状態遷移技法を厚めに（Step 4） |
| 判断に迷う場合 | ピラミッド | リスクベースの傾斜（Step 2）で調整する |

**アイスクリームコーン型（逆ピラミッド）を禁止する。** 手動テストと E2E に依存する構成は受託の典型的失敗パターン。
なぜ: 修正のたびに回帰工数が膨らみ、瑕疵対応が赤字化する。

## Step 2: リスクベースで深さを傾斜配分する

**全機能を同じ深さでテストする計画を禁止する。**
なぜ: 全機能同深度の計画は、遅延時に全部が中途半端になる。

1. 機能ごとに「障害影響 × 発生確率」で優先度を付ける
2. 優先度に応じて深さを傾斜させる:
   - **高**: 技法適用のケース設計 + 自動テスト + 探索的テスト
   - **中**: 主要な正常系・異常系の自動テスト
   - **低**: ハッピーパスのみ、または「テストしない」と明記してリスク受容
3. 「テストしない」の決定は必ず人間の承認を取り、テスト計画書に残す
   - なぜ: リスク受容は契約上の責任判断であり、AI が勝手に決めてよい領域ではない

## Step 3: テスト観点表を作る

外部設計と並走して、機能 × 観点のマトリクスを作る。
なぜ: 観点表は検収基準の母体になる。ケースを書き始める前に「見る角度」の抜けを潰す方が安い。

テンプレート（観点列は案件特性で増減させる）:

| 機能 | 正常 | 異常 | 境界 | 権限 | 性能 | 互換 |
|---|---|---|---|---|---|---|
| ログイン | ○ | ○（連続失敗ロック） | ○（PW最小/最大長） | − | ○（同時ログイン） | ○（対象ブラウザ） |
| 注文登録 | ○ | ○（在庫切れ・二重送信） | ○（数量0/上限） | ○（ロール別可否） | − | − |
| … | | | | | | |

- 各セルは「○/−」だけでなく、括弧書きで代表観点を1つ添える
- 「−」は「テストしない」の宣言であり、Step 2 のリスク受容として扱う
- 検収前の最終批評として**探索的テスト**（チャーターと時間箱を決めたセッションベース）を1枠確保する
  - なぜ: 一人受託には独立QA部門がないため、スクリプト外の顧客目線チェックはここでしか担保できない

## Step 4: 技法を選んでケースへ展開する

観点表の各セルを、ISTQB/JSTQB 技法でケースに落とす。体系の正本は JSTQB Foundation Level シラバス。

| 技法 | 何をするか | 使いどころ |
|---|---|---|
| 同値分割 | 入力を等価クラスに分け代表値でテスト | すべての入力項目の第一手。ケース数を最小化する |
| 境界値分析 | 境界 ±1 を狙い撃ちする | 数値範囲・文字数・日付。バグは境界に集中する |
| デシジョンテーブル | 条件の組合せを表で網羅する | 割引条件・権限判定など複数条件のビジネスルール |
| 状態遷移テスト | 状態と遷移（有効/無効）を網羅する | 画面遷移・ステータス管理（注文/承認フロー等） |
| ペアワイズ | 2因子間網羅で組合せ爆発を圧縮する | OS×ブラウザ×ロール等の組合せ。定番ツールは Microsoft PICT |

- 技法適用の機械的展開（クラス分け後のケース列挙）は AI に任せてよい。**クラスの切り方と期待結果の正しさは人間がレビューする**
- なぜ: 展開は機械的だが、等価クラスの誤りは全ケースを同時に無意味にする

## Step 5: テスト品質を Khorikov の4本柱で判定する

書かれたテスト（特に AI 生成テスト）は、Vladimir Khorikov『単体テストの考え方/使い方』の4本柱で判定する:

1. **リファクタリング耐性**: 実装詳細ではなく観察可能な振る舞いをテストしているか（内部構造の変更で壊れないか）
2. **退行検出**: このテストは実際のバグを検出できるか（アサーションのない「実行するだけのテスト」ではないか）
3. **迅速なフィードバック**: 実行が速いか（遅いテストは実行されなくなる）
4. **保守性**: 読んで意図がわかるか、変更が容易か

カバレッジ運用のルール:
- カバレッジ閾値（例: 80%）は「下げない」**ラチェット運用**にする
  - なぜ: 数値だけを追うと退行検出力ゼロのテストを量産し、一度下げた閾値は戻らない
- 重要ロジックは「このテストを欺くバグを書けるか」というミューテーションテスト的発想で質を見る

## Step 6: 受託の検収フロー — 受入基準を契約前に合意する

**注意: 本節は法的助言ではなく実務の型。検収条項・契約不適合責任など契約面の最終判断は弁護士等の専門家に委ねること。金額・工数の判断は自組織の見積・価格判断プロセスに従うこと。**

なぜこの順序か: 検収基準を契約前に固定することが、検収紛争の最も安価な予防策になる。

1. **見積段階**: テスト観点表ベースで検収基準のドラフトを作る（対象機能・観点・環境・除外事項）
2. **契約前**: 検収基準を顧客と合意し、契約（個別契約・注文書等）に紐づける
   - 「受入基準のない Issue は実装に入れない」ルールをここから貫く → dev-core:issue-driven-dev 参照
3. **要件定義完了時**: テスト計画書（スコープ・レベル別方針・環境・終了条件・リスクベース優先順位）を確定する
4. **納品前**: 検収テスト仕様書を実行し、結果報告書を添えて納品する

成果物の型:

- **検収テスト仕様書**: 顧客合意済みの受入基準1件ごとに「ID / 対応する受入基準 / 前提条件 / 入力・手順 / 期待結果 / 実施環境」を記載する
- **検収テスト結果報告書**: 「実行日 / 実行者 / 環境 / ケースごとの合否 / 証跡（スクリーンショット・ログ等の実行証拠）/ 不合格項目と対応方針 / 残課題と合意事項」を記載する
  - なぜ証跡が必須か: 検収は契約上の合否判定であり、実行出力のない「たぶん動く」は証拠にならない（この原則の実行面は dev-core:verify の Iron Law と同じ）

## Step 7: 運用ルール（AI エージェント時代）

1. **テスト生成とテストレビューを別エージェント/別セッションに分離する**
   - なぜ: 実装したエージェント自身に自分の実装のテストを書かせると、実装を追認するだけの自己弁護的テストになりがち
2. **受入基準の正本は人間が握る**。AI は観点表・ケースのドラフトと展開を担当し、基準の確定はしない
   - なぜ: 受入基準は「何を作るか」の決定そのものであり、検収の合否線を AI に委ねてはならない
3. **flaky テストは即隔離（quarantine）する**。直すまで CI から外し、隔離 Issue を立てる
   - なぜ: 不安定テストを放置すると CI 不信が広がり、全品質ゲートが形骸化する。CI 側のゲート設計は → dev-core:cicd-release-design 参照
4. AI 生成テストは Step 5 の4本柱でレビューしてからマージする。量は成果ではない
5. E2E のセルフヒーリングや探索的テストのエージェント実行を使う場合も、判定基準（何を不合格とするか）は人間が事前に決める

## テスト計画レビュー・チェックリスト

計画確定前に以下を自己点検し、未達項目は解消してから人間の承認を求める:

- [ ] 配分モデル（ピラミッド/トロフィー）を案件タイプの根拠つきで選定した
- [ ] E2E が最重要ジャーニーのハッピーパスに限定されている（目安 5〜15本）
- [ ] アイスクリームコーン型（手動+E2E依存）になっていない
- [ ] 機能ごとのリスク優先度があり、全機能同深度になっていない
- [ ] 「テストしない」領域が明文化され、人間がリスク受容を承認した
- [ ] テスト観点表（機能×正常/異常/境界/権限/性能/互換）がある
- [ ] 各観点に適用する技法（Step 4）を選定した
- [ ] 検収基準が契約前に顧客合意されている（または合意フローが計画にある）
- [ ] カバレッジ閾値とラチェット運用（下げない）を定義した
- [ ] flaky 隔離ルールとテスト生成/レビューのエージェント分離を運用に組み込んだ
