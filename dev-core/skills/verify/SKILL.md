# Verify — 6段階検証フロー

コードベースの品質を 6 段階で検証する。**各ステップの判定は、確かめた実行出力だけを証拠とする。** 前回の実行を再利用できる条件と、BLOCKED・未実行の扱いは後述の Iron Law に従う。

## Step 0: 検証コマンドの検出（必須・最初に実行）

検証コマンドをハードコードしない。以下の優先順位で検出する:

1. **プロジェクト設定**: `.claude/dev-core.local.md` の `build-command` / `typecheck-command` / `lint-command` / `test-command` / `audit-command`
2. **マニフェストから推定**:
   - `package.json` → `scripts` の `build` / `typecheck` / `lint` / `test`（パッケージマネージャは lockfile から判定: `pnpm-lock.yaml` → pnpm、`yarn.lock` → yarn、`package-lock.json` → npm）
   - `Makefile` → `build` / `lint` / `test` ターゲット
   - `pyproject.toml` → `ruff` / `mypy` / `pytest` 等の設定有無
   - `Cargo.toml` → `cargo build` / `cargo clippy` / `cargo test`
   - `go.mod` → `go build ./...` / `go vet ./...` / `go test ./...`
   - `composer.json` → `scripts` の `lint` / `test`（PHPStan, Pint, PHPUnit 等）
   - `wrangler.toml` / `wrangler.jsonc`（Cloudflare Workers）→ package.json の scripts に加えて `wrangler deploy --dry-run`（ビルド検証）、テストは `@cloudflare/vitest-pool-workers` の有無を確認
3. **複数マニフェストが共存する場合**（例: Tauri = `Cargo.toml` + `package.json`、Python + JS モノレポ）: **検出した全系統を検証する**。片方だけ検証して完了扱いにしない。各 Step は系統ごとに実行し、結果を系統別に報告する。
4. **検出不能な場合**: 推測で実行せず、ユーザーに検証コマンドを確認する

該当ステップのコマンドがプロジェクトに存在しない場合（例: ビルド工程のないスクリプト集）は、そのステップを「⏭ 対象外（理由）」として明示的にスキップする。**黙ってスキップしない。**

## 6つのステップ

| Step | 目的 | 合格条件 |
|------|------|---------|
| 1. Build 🏗️ | ビルド/コンパイルが成功する | exit code 0、エラーなし |
| 2. Type 📝 | 型エラーがない | 型チェッカーがエラー 0 で完了 |
| 3. Lint 🔍 | コーディング規約に準拠 | エラー 0（警告も原則 0 に。`--fix` 指定時は自動修正を先に実行） |
| 4. Test ✅ | 全テストがパスする | 0 failures。新機能にテストが存在すること |
| 5. Security 🔒 | 既知の脆弱性・機密情報がない | 依存監査クリーン（`npm audit` / `pip-audit` / `cargo audit` 等）、ハードコードされた機密情報なし |
| 6. Diff 📊 | 変更が意図通りに収まっている | `git status` / `git diff --stat` で意図しない変更・残骸ファイルがない |

`--skip-test` が指定された場合のみ Step 4 をスキップし、報告に「⏭ スキップ（ユーザー指定）」と明記する。スキップ指定は、プロジェクトや受け入れ条件が必須とするゲートを免除しない。

## 判定の区別

各ステップの判定は次のどれかで書く。

| 判定 | 意味 | 次の対応 |
|------|------|---------|
| ✅ 合格 | コマンドを実行し、成功した | その実行の範囲が主張を支えるかを確かめる |
| ❌ 失敗 | コマンドを実行し、失敗した | 実際の出力を確かめ、スコープ内の原因を直す |
| ⛔ BLOCKED | ツール・依存・環境・権限などの前提が足りない、または信頼できるコマンドがなく実行できない | プロジェクトで使える同等のコマンドを探す。残る穴を報告する |
| ⏭ 対象外 | プロジェクトにそのステップがない | 理由を添える |
| ⏭ スキップ | ユーザーが除外した | 理由を添える |

- 成功として数えるのは ✅ だけ。BLOCKED・スキップ・未実行は成功ではなく、それに依存する受け入れ条件は pending のまま残す
- 対象外は、理由が妥当なら不合格にはしない。ただし、その観点を確かめたことにもならない

## 証拠ベース完了判定（Iron Law）

**実行出力を確かめずに「パス」を宣言することは許されない。**

各ステップの判定には、最終的なコードに関係する実行出力が要る。実行したコマンド、作業ディレクトリ、exit code、実行時刻、revision / diff の識別子、関係する環境、ログなどの成果物の場所を記録する。「通るはず」という推測や、「通った」という要約だけでは証拠にならない。

### 前回の実行を再利用する条件

次のすべてを満たすときだけ、前回の実行結果を証拠として再利用してよい。

1. 生の成果物（ログ・exit code・レポート）が残っていて、今それを確かめられる
2. 関係するソース・テスト・依存・設定・環境が、その実行時と一致している（識別子で確かめられる）
3. プロジェクトの規約が再利用を許している

再利用するときは「前回の実行を今確認した」と明記し、新しい実行と区別する。入力が変わった、一致を確かめられない、未解決の懸念がある、新しい実行が求められている、のいずれかに当たるときは、影響するステップを実行し直す。時刻に依存するチェックや稼働中のシステムの確認には、その時点の観測が要る。

入力の変更も、新しい失敗や懸念もないのに、完了済みのチェックを繰り返さない。

### 最終ゲート

完了の宣言・コミット・PR 作成の前の最終ゲートでは、**最終 diff と同じ入力に対する実行証拠**を必須とする。再利用の条件を満たす前回の実行でもよいが、その実行のあとに関係する編集があれば、影響するステップを実行し直す。報告には、どの入力（revision / diff の識別子、作業ディレクトリ、環境）に対する証拠かを書く。

| 主張 | 必要な証拠 | 証拠にならないもの |
|------|-----------|-------------------|
| 「ビルド成功」 | 最終の入力に対するビルド出力（exit code 0） | 「ビルドに影響する変更はしていない」 |
| 「型エラーなし」 | 最終の入力に対する型チェック出力 | 「型を修正したので大丈夫」 |
| 「lintパス」 | 最終の入力に対する lint 出力 | 入力の一致を確かめていない「前回通った」 |
| 「テスト全パス」 | 最終の入力に対するテスト実行出力（0 failures） | 「変更していないから通る」「should pass」、担当者の要約だけ |
| 「既知の脆弱性なし」 | 最終の入力に対する監査コマンド出力 | 「依存は変更していない」 |

監査の出力は、その入力に対する既知の脆弱性情報だけを示す。「システムに脆弱性がない」とは言い換えない。

**Red Flags**: レポート内に以下があればルール違反:

- 「〜のはず」「おそらく通る」「変更していないので影響なし」
- 再利用のラベルがない過去の結果、入力の一致を確かめていない「前回パスしている」
- 実行出力を伴わない ✅ 判定、担当者の「通った」という要約だけに基づく ✅ 判定
- BLOCKED・スキップ・未実行を ✅ として数えている

## 報告ルール

検証結果の報告は以下に従う。**架空の数値やサンプルの丸写しは禁止。実際の実行結果だけを書く。**

1. ステップごとに「実行したコマンド」「exit code」「結果の要約（実出力からの引用）」を 1 行で報告する。再利用した結果には「前回の実行を今確認した」と添える
2. 実行しなかったステップは ✅ ではなく「⛔ BLOCKED」「⏭ 対象外」「⏭ スキップ」のいずれかとし、理由を添える
3. 失敗・警告があれば、該当する実際の出力（ファイル名・行番号・メッセージ）を抜粋し、修正アクションを提示する
4. カバレッジ等のメトリクスは、計測コマンドを実行した場合のみ実測値を報告する。実行していなければ書かない

## CI/CD 統合

同じ 6 段階を CI でも実行する。検出した検証コマンドをそのまま GitHub Actions 等のステップに並べる（ローカルで通らないものを CI に追加しない）。

CI 上での段階配置（PR時/マージ時/リリース前の3段階）と品質ゲート全体の設計は dev-core:cicd-release-design を正本とする。
