# Verify — 6段階検証フロー

コードベースの品質を 6 段階で検証する。**各ステップの判定は、同一ターン内で実行したコマンドの出力のみを証拠とする**（後述の Iron Law）。

## Step 0: 検証コマンドの検出（必須・最初に実行）

検証コマンドをハードコードしない。以下の優先順位で検出する:

1. **プロジェクト設定**: `.claude/dev-core.local.md` の `build-command` / `typecheck-command` / `lint-command` / `test-command` / `audit-command`
2. **マニフェストから推定**:
   - `package.json` → `scripts` の `build` / `typecheck` / `lint` / `test`（パッケージマネージャは lockfile から判定: `pnpm-lock.yaml` → pnpm、`yarn.lock` → yarn、`package-lock.json` → npm）
   - `Makefile` → `build` / `lint` / `test` ターゲット
   - `pyproject.toml` → `ruff` / `mypy` / `pytest` 等の設定有無
   - `Cargo.toml` → `cargo build` / `cargo clippy` / `cargo test`
   - `go.mod` → `go build ./...` / `go vet ./...` / `go test ./...`
   - `composer.json` → `scripts` の `lint` / `test`（PHPStan, Pint, PHPUnit 等）
   - `wrangler.toml` / `wrangler.jsonc`（Cloudflare Workers）→ package.json の scripts に加えて `wrangler deploy --dry-run`（ビルド検証）、テストは `@cloudflare/vitest-pool-workers` の有無を確認
3. **複数マニフェストが共存する場合**（例: Tauri = `Cargo.toml` + `package.json`、Python + JS モノレポ）: **検出した全系統を検証する**。片方だけ検証して完了扱いにしない。各 Step は系統ごとに実行し、結果を系統別に報告する。
4. **検出不能な場合**: 推測で実行せず、ユーザーに検証コマンドを確認する

該当ステップのコマンドがプロジェクトに存在しない場合（例: ビルド工程のないスクリプト集）は、そのステップを「⏭ 対象外（理由）」として明示的にスキップする。**黙ってスキップしない。**

## 6つのステップ

| Step | 目的 | 合格条件 |
|------|------|---------|
| 1. Build 🏗️ | ビルド/コンパイルが成功する | exit code 0、エラーなし |
| 2. Type 📝 | 型エラーがない | 型チェッカーがエラー 0 で完了 |
| 3. Lint 🔍 | コーディング規約に準拠 | エラー 0（警告も原則 0 に。`--fix` 指定時は自動修正を先に実行） |
| 4. Test ✅ | 全テストがパスする | 0 failures。新機能にテストが存在すること |
| 5. Security 🔒 | 既知の脆弱性・機密情報がない | 依存監査クリーン（`npm audit` / `pip-audit` / `cargo audit` 等）、ハードコードされた機密情報なし |
| 6. Diff 📊 | 変更が意図通りに収まっている | `git status` / `git diff --stat` で意図しない変更・残骸ファイルがない |

`--skip-test` が指定された場合のみ Step 4 をスキップし、報告に「⏭ スキップ（ユーザー指定）」と明記する。

## 証拠ベース完了判定（Iron Law）

**検証コマンドを実行せずに「パス」を宣言することは許されない。**

各ステップの判定には、**同一ターン内で**コマンドを実行した出力が必須。過去の実行結果、キャッシュされた結果、「通るはず」という推測は証拠として認めない。

| 主張 | 必要な証拠 | 証拠にならないもの |
|------|-----------|-------------------|
| 「ビルド成功」 | 同一ターンのビルドコマンド出力（exit code 0） | 「ビルドに影響する変更はしていない」 |
| 「型エラーなし」 | 同一ターンの型チェック出力 | 「型を修正したので大丈夫」 |
| 「lintパス」 | 同一ターンの lint 出力 | 「前回通った」 |
| 「テスト全パス」 | 同一ターンのテスト実行出力（0 failures） | 「変更していないから通る」「should pass」 |
| 「脆弱性なし」 | 同一ターンの監査コマンド出力 | 「依存は変更していない」 |

**Red Flags**: レポート内に以下の表現があればルール違反:

- 「〜のはず」「おそらく通る」「前回パスしている」「変更していないので影響なし」
- 実行出力を伴わない ✅ 判定

## 報告ルール

検証結果の報告は以下に従う。**架空の数値やサンプルの丸写しは禁止。実際の実行結果だけを書く。**

1. ステップごとに「実行したコマンド」「exit code」「結果の要約（実出力からの引用）」を 1 行で報告する
2. 実行しなかったステップは ✅ ではなく「⏭ スキップ」とし、理由（対象外 / ユーザー指定）を添える
3. 失敗・警告があれば、該当する実際の出力（ファイル名・行番号・メッセージ）を抜粋し、修正アクションを提示する
4. カバレッジ等のメトリクスは、計測コマンドを実行した場合のみ実測値を報告する。実行していなければ書かない

## CI/CD 統合

同じ 6 段階を CI でも実行する。検出した検証コマンドをそのまま GitHub Actions 等のステップに並べる（ローカルで通らないものを CI に追加しない）。

CI 上での段階配置（PR時/マージ時/リリース前の3段階）と品質ゲート全体の設計は dev-core:cicd-release-design を正本とする。
