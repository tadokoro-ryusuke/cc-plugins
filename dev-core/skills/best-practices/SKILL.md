## 1. TDD サイクル（t-wada 式）— Red→Green→Refactor→Evidence

1. **Red 🔴**: 単一機能の失敗するテストを1つ作成。実装は存在しないため必ず失敗する
2. **Green 🟢**: テストをパスさせる**最小限のコード**を記述。余分な機能は追加しない
3. **Refactor 🔨**: テストをグリーンに保ちながら品質向上。重複排除、命名改善、複雑さの解消
4. **Evidence ✅**: focused verification を実行して結果を記録。commit はユーザーまたは delivery workflow が明示的に許可した場合だけ、意味のある単位で行う

**Iron Law: 振る舞いを変えるコードは、先に失敗するテストを書いてから実装する。証拠なしに完了を主張しない。**

- Red は省かない。既存のテストがすでに新しい契約を表しているなら、そのテストが今失敗することを確かめて Red とし、同じ内容のテストを重ねて足さない。テストの価値は本数ではなく、検出できる失敗で判断する
- ドキュメントなど実行できる振る舞いを持たない変更は、編集を鏡写しにするテストではなく、内容や構造の検証で確かめる
- 「パス」の宣言には実行出力の確認が要る。前回の実行を再利用する条件と、BLOCKED・未実行の扱いは `verify` スキルの証拠ベース完了判定を参照

## 2. SOLID 原則

- **SRP**: 1モジュール/クラス/関数 = 1つの責任。変更理由は1つだけ
- **OCP**: 拡張に開き、修正に閉じる。新機能は既存コード変更なしで追加
- **LSP**: 派生型は基底型と置換可能
- **ISP**: 使わないメソッドへの依存を強制しない
- **DIP**: 高レベルモジュールは低レベルに依存しない。抽象に依存する

## 3. 普遍のコア規約

リポジトリの既存の規約（フォーマッタ・リンタ・CI の設定）を先に守る。以下はその上で使う既定値で、行数や見た目の重複そのものではなく、具体的なリスクを理由に適用する。

- **ハードコーディング禁止**: 設定値は環境変数/設定ファイル、UI 文字列は既存の定数/言語ファイルの仕組みに置く。ドメイン上の意味を持つ数値や繰り返し使う方針は名前付き定数にする。一度しか使わない自明なリテラルを、具体的な利得なしに抽象化しない
- **DRY**: 安定した共通の意味を持つ知識は1箇所にまとめる。見た目が似ていても、共通化すると無関係な振る舞いが結合するなら重複を許容する
- **早期リターン/ガード節**: 深いネストを避ける
- **イミュータビリティ**: 所有関係が分かりにくくなる共有状態の直接変更を避け、コピーで更新する
- **サイズ**: 行数はレビューのシグナルとして扱う（ファイル 200-400 行が目安、500 行超で分割を検討）。分割は凝集度・テストしやすさ・リポジトリが強制する上限を理由に行い、関数が一定の行数を超えたことだけを欠陥としない

## 4. プロジェクト固有設定

技術スタック・コマンド・閾値（カバレッジ等）はプロジェクトの `.claude/dev-core.local.md` を正とする。このスキルの原則と矛盾する場合はプロジェクト設定が優先。
