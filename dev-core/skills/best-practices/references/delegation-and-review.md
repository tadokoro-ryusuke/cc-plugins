# 委譲とレビュー — 実装の所有・委譲・リスクゲートのレビュー

作業を複数の担当（親と子、実装担当と独立レビュー役）に分けるときの原則。ツールに依存しない形で書く。担当を起動する具体的な方法や設定は、各ツールのワークフローに置く。

用語:

- **親**: ユーザーとの対話、要件・設計の判断、統合、受け入れの判定を持つ主担当
- **子**（実装担当・調査担当など）: 親が範囲を定めて作業を渡す担当
- **独立レビュー役**: 実装の文脈を持たない新しい文脈で、候補を読み取り専用で評価する担当

## 1. 所有者を決めてから委譲する

最初に「誰がこの作業を持つか」を決め、そのあとで委譲の形と設定を選ぶ。

- 既定の実装者は親。逐次的・密結合な実装は、計画が大きくても親が行う
- 曖昧な要件、アーキテクチャ、スコープに関わる判断は親が持つ。子に渡すのは、判断が済んだ範囲の作業に限る
- 委譲するかどうかを振り分ける専用の担当（router）は置かない。判定は親が計画の中で行う
- 親が実装する場合でも、必要な独立レビューは省かない。レビュー役を得るためだけに実装担当を立てる必要はない

なぜ: 役割や設定から逆算すると「役割があるから使う」委譲が増え、引き継ぎ・待ち・統合・再検証のコストが利得を上回る。

## 2. 最小の構成を選ぶ

次の3つから、利得がある範囲で最も小さいものを選ぶ。

| 構成 | 使う場面 |
|---|---|
| 親が実装し、自分でレビューする | リスクゲート（§5）に該当しない変更 |
| 親が実装し、独立レビュー役がレビューする | リスクゲートに該当する変更 |
| 範囲を定めて子に委譲し、親が統合する | §3 の条件に当てはまるとき |

ユーザーが明示的に委譲を指示した場合は、この既定より優先する。ただし、ホストの実際の機能と、書き込み範囲を安全に分けられる範囲の中で行う。

## 3. 委譲の3条件

委譲するのは、次のどれかに当てはまるときだけにする。

1. **独立トラック**: 書き込み範囲・依存・共有リソースが重ならず、並行して進められる
2. **文脈の隔離**: 大量の出力（ビルドログ、E2E の実行ログ、広い調査）を親の文脈から切り離したい
3. **リスクゲートでの独立評価**: §5 のゲートに該当し、実装の文脈を持たない評価が要る

- 「その役割がある」「テストがある」「計画が大きい」だけでは利得にならない
- 委譲したら、計画の判断ログに1行残す（期待する利得、書き込み範囲、担当、親に戻る条件）
- 実装担当を複数並べるのは、書き込み範囲・依存・共有リソースがすべて重ならないときに限る。worktree はファイルを分けるが、DB・ポート・デプロイ先・認証情報は分けない
- 子が作業している間、親は子のファイルを同時に編集しない。重ならない調整や残りの確認は進めてよい

## 4. 決定的な作業はツールで行う

build / type / lint / test / 依存監査 / diff の確認や、Issue・PR の操作のように、結果がコマンドで決まる作業は親がツールで直接実行する。コマンド1つのために担当を立てない。

なぜ: 担当を挟んでも結果は変わらず、親は結局その出力を確かめ直すことになる（§6）。検証の手順は → dev-core:verify

## 5. リスクゲートでのレビュー

独立レビューを行うかどうかは、実装の所有とは別に、リスクで判定する。

### 対象

- セキュリティ・権限・秘密情報の境界
- 永続データ・migration
- 並行処理・冪等性
- 重要な公開契約（API、イベント、公開設定、互換性）
- ユーザーやプロジェクトが明示的に求めたレビュー

モジュールをまたぐ未解決のリスクがあり、新しい文脈での評価に価値があるときも対象にしてよい。行数や計画の大きさだけではゲートにしない。ゲートに当たらない変更は、変更に見合った自己レビューで足りる。レビューした・しなかった理由と根拠を記録する。

### タイミング

- 候補が安定してから（実装と focused な検証が済んでから）、新しい文脈で1回レビューする
- 指摘を直したら、影響する範囲だけを見直す
- レビューした入力が後で変わったら、そのレビュー結果は影響する範囲で無効になる

### 入力

独立レビュー役に渡すもの:

- 元の要件と受け入れ条件、関連する計画の節
- 候補の識別子（revision / diff）と、関連するソース・テスト
- 検証コマンドの生の出力

渡さないもの:

- 期待する結論（「正しく実装されている」など）
- 実装担当の作業中の文脈や、結論を先取りした要約

計画の前提そのものも疑ってよいと伝える。

### 出力

- 指摘は全件を、重大度（P0〜P3）・確度・file:line・具体的な影響付きで返す。未確定な点も書く
- 絞り込みはレビュー役ではなく、後段の親が行う
- 親は指摘を実ファイルと実行出力で確かめてから修正を割り当てる（§6）。P0/P1 は解決し、残りは修正するか開示する。修正後は影響するチェックを再実行する

### 必須レビューを行えないとき

- ゲートに該当するのに独立レビュー役を起動できなければ、別の独立レビュー（別モデルによるレビューなど → dev-core:codex-collab）で代替する
- それもできなければ「独立性は未充足」と明記し、該当する受け入れ条件は pending のまま残す。自己レビューを必須レビューの代わりにしない
- 影響を受けない作業は続けてよい

## 6. Zero Trust Review

実装者（子・自分・別モデル）の報告は主張として扱い、実ファイルと実行出力で確かめてから依拠する。

- 「テスト全パス」→ テストが存在し、変更した振る舞いに意味のあるアサーションを持つかを diff で確かめる。実行の生の出力を見る
- 「lint / typecheck クリア」→ 変更したコードを読み、型の逃げ道・握りつぶした例外・規約からのずれを確かめる
- 「リファクタリングのみで動作変更なし」→ diff を読み、外部の振る舞いが変わっていないかを確かめる
- レビュー役の指摘も主張として扱い、実ファイルで確かめられたものだけを反映する（双方向の Zero Trust）
- モデルの能力の高さは、証拠の代わりにならない

## 7. 証拠の再利用

子や前回の実行が報告した結果は、親が生の成果物（ログ・exit code・レポート）を確かめるまで主張にとどまる。「通った」という要約だけでは証拠にならない。

前回の実行を再利用できる条件（生の成果物がある、入力と環境が一致する、規約が許す）と、そのときのラベル付けは → dev-core:verify の「証拠ベース完了判定（Iron Law）」を正本とする。

## 8. Three Strikes と担当の交代

「同じ修正経路で類似の修正が3回失敗したら、その経路を止める」規則は → dev-core:debug を正本とする。ここには委譲に関わる点だけを書く。

- 担当を替えても試行の履歴は引き継ぐ。担当の交代で回数をリセットしない
- 子が同じ修正経路で3回失敗したら、試行の履歴と失敗の証拠を付けて親に返す

## 9. handoff の契約

### 子に渡すもの

1. 役割と、範囲を定めた1つの成果。関連する計画の節と生の入力ファイル
2. チェックアウト・ブランチと、入力の識別子（revision / diff）。他の作業に属する既存の変更
3. 許可する書き込み範囲、依存、共有リソースの持ち主
4. 受け入れ条件、関連するプロジェクトのコマンド、返してほしい証拠
5. 期待する利得、作業の上限、親に返す条件

### 最小の文脈

必要なインターフェース・決定・証拠だけを渡す。親の全履歴や汎用の手順書を丸ごと渡さない。

なぜ: 余計な文脈はコストを増やし、子の判断を親の結論に寄せてしまう。

### 作業の上限

- 対象とするソースの範囲、時間やツール呼び出しの予算、新しい証拠が出なくなったら止まる条件など、作業に合わせて決める
- 数値は意味があるときだけ書く。ホストが測れない上限を「強制している」と書かない

### 子が返すもの

- 変更したファイル、テスト、実行したコマンドと生の結果、入力と出力の識別子、残る懸念
- 状態は次のいずれか:
  - `completed`: 受け入れ条件を満たした
  - `needs-parent`: 親の判断が要る
  - `blocked`: 前提・権限・環境が足りず進めない

### 前提が崩れたら親に返す

- 計画とコードが食い違う、計画にない公開契約やデータの変更が要る、書き込み範囲が他と重なる、handoff の外にある設計上の問題が見つかった、といったときは推測で進めず、証拠を付けて親に返す
- 親は範囲を定め直してから再び渡す。黙って範囲を広げたり、設定を上げたり、担当を替えて失敗の履歴を消したりしない

### 再帰委譲の禁止

子は、ワークフロー全体を起動し直したり、別の実装・レビューの連鎖を立てたりしない。handoff で許されていない commit・push・公開もしない。

### 上限到達は受け入れではない

- 上限に達したら、残りの作業を記録して返す。予算を使い切ったことは、受け入れ条件を満たしたことを意味しない
- 不要になった割り当ては止め、書き込みが止まったことと途中の結果を確かめてから、次の書き手に所有を移す

## 10. requested と verified の区別

- 委譲の記録（dispatch ledger）は計画に短く残す: 作業、期待する利得、範囲、役割、要求した設定とその出どころ、入力の識別子、状態、返ってきた成果物
- 要求した設定（モデルや推論の設定）と、実際に効いた設定は分けて書く。起動要求が受け付けられたことや、プロンプトに設定を書いたことは要求を示すだけで、実行時の設定を示さない
- ホストが子の実行記録を公開していれば、それで実効設定を確かめて `verified` と記録する。確かめられなければ `requested` として記録する
- 再開時は、この記録と現在のチェックアウトを確かめてから、子や結果を再利用する。後の編集で影響を受けた受け入れの証拠は無効にする

## 11. 無人実行の規律

ユーザーが見ていない実行（ループ、バックグラウンド、自動継続）では、完了を受け入れ条件と証拠で判定する。

- テキストだけの応答で止まったターン（進捗を報告しただけで次の手を打たずに終わったターン）を完了とみなさない
- 受け入れ条件に pending が残っていて、ユーザーの判断待ちがなければ、次の action を実行する
- 実行中のバックグラウンドの担当が残っているうちは完了にしない
- 同じ計画での自動継続は2回までにする。それでも進まなければ、状態・証拠・次の action を計画に残して止める
- 許可済みの作業を、計画や下書きの段階で止めない。受け入れ条件が求める検証と修復まで進める。条件を満たしたら、関係のない再設計や、通った確認の繰り返しに広げない

なぜ: 無人実行では途中の報告が完了に見えやすく、止まったことに誰も気づかない。
