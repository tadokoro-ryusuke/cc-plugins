# テストの書き方

テストを書く・直す・レビューする前に読む。書かれたテストの良し悪しの判定（Khorikov の4本柱、カバレッジ運用）は `dev-core:test-design` の Step 5 が正本で、本書は「どう書くか」を扱う。プロジェクトの既存規約や `.claude/dev-core.local.md` と食い違う場合は、そちらを優先する。

## 1. 構成と名前

- Arrange-Act-Assert（または Given-When-Then）で書く。
- テスト名は、落ちたときに原因の場所が分かる振る舞いの文にする（例: 「期限切れのトークンでは 401 を返す」）。
- 1テスト1振る舞い。操作とアサートを繰り返す長いテストは、最初のアサートまでで区切って分ける。
  - なぜ: 長いテストが落ちると、どの振る舞いが壊れたかの調査が別の仕事になる（Kent Beck, "Decompose run-on tests"）。

## 2. 何が壊れたら落ちるテストか

テスト本体を書く前に、「どの本番コードの変更でこのテストが落ちるか」を名指す。名指せなければ、観察可能な振る舞いを測る形に設計し直す。

- なぜ: 落ちる理由を言えないテストは、退行を検出しない。

## 3. 期待値の出し方

- 期待値は、リテラル・手で確かめた fixture・仕様から独立に導く。本番コードやそのヘルパー・定数を import して期待値を計算しない。
  - なぜ: 期待値を実装から計算すると、実装が誤っていても一致する（実装を写しただけの、トートロジーのアサーション）。
- 意味の読めない数値には、テスト内の名前付き定数か、由来を書いたコメントを添える。
- property-based テストのモデルは、テスト対象のロジックを再実装しない（同じ誤りを共有するため）。

## 4. 変更を検出するだけのテストを避ける

- 定数の値・文言・private な構造だけを固定するテストは書かず、その決定に依存する振る舞いを測る。
- スクリプトや設定は本文を grep せず、実行して出力・副作用・exit code を確かめる。
  - なぜ: 文字列の一致は振る舞いが壊れても通り、無害な書き換えで落ちる。

## 5. テストダブルの優先順位

既定は「本物 > fake > stub > モック」。

- 呼び出しの検証（モックのインタラクションテスト）は、メール送信や決済 API のように、外部から観測できる副作用を持つ、管理外の依存に限る。
- 読み取り専用の依存は、戻り値を使った結果で検証する。モックが呼ばれたこと自体をアサーションの目的にしない（引数・回数・順序が契約の一部である場合を除く）。
- モックの応答は、実データの構造を省略せずに写す。
- モックの準備が肥大化したら、依存の注入（DIP）による設計の見直しか、実コンポーネントでの統合テストを検討する。
- なぜ: 過剰なモックは実際の相互作用を検証しない。実証研究では、コーディングエージェントのコミットは人間のコミットより多くテストにモックを足していた（[arXiv 2602.00409](https://arxiv.org/abs/2602.00409)、2026-01）。

## 6. 自前の DB・ブローカーは実物で integration テストする

- 自前の DB やメッセージブローカーは、既定で実物を使う（Testcontainers、CI の service container、使い捨て DB など）。
- インメモリの代替は、本番との機能差が問題にならないと確かめられるときだけ使う。fake を作るなら、実物と fake の両方に同じテストを流す契約テストを付ける。
- Docker などが使えない実行環境では、モックに差し替えてグリーンにしない。その integration テストは「未実行」と報告し、CI に委ねる（`dev-core:verify` の未実行の扱い）。
- なぜ: インメモリの代替は、制約・トランザクション・方言の違いを再現せず、本番で初めて壊れる。

## 7. テストデータ

- テストデータはファクトリかビルダーでテストごとに作り、共有の可変フィクスチャを避ける。
- テスト間の分離には、トランザクションのロールバック、スキーマ単位の分離、truncate などを使う。対象コードが自前でトランザクションを張る場合や複数の接続を使う場合は、ロールバック方式が効かないことに注意する。
- 本番データを使わないことは → `compliance-core:privacy-data-compliance`（Step 2）。

## 8. Red の確かめ方

- Red では、期待した理由で失敗したことを失敗メッセージで確かめる。setup・import・構文のエラーでの失敗は Red に数えない。
- 後から書いたテストで実装を追認しない（Iron Law は `SKILL.md` の §1）。
- 失敗しているテストを、仕様の変更を根拠にしない改変で通さない（同じく §1）。

## 9. E2E のロケータ

Playwright の推奨に従い、ユーザーから見える属性で要素を探す。

1. `getByRole`（role とアクセシブルな名前）
2. `getByLabel` / `getByPlaceholder` / `getByText` などのユーザーから見える属性
3. `getByTestId`（チームで明示的に合意したテスト用の契約として使う）
4. CSS / XPath（最後の手段）

- なぜ: 役割と名前で探すテストは、画面の見た目の変更に強く、名前の無いボタンのようなアクセシビリティの欠陥にも気づける。
- 待ちは自動で待つアサーション（`await expect(locator).toBeVisible()` など）を使い、固定の sleep を入れない。
