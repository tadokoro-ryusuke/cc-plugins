# Systematic Debugging

**鉄則: NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST**

修正を提案する前に、必ず根本原因を特定すること。

競合する仮説が多く、単独では先入観が心配なときは、複数の仮説を並行で検証する体制を提案してよい（Claude Code では `/dev-core:debug-team` の実行をユーザーに提案する。モデルからは起動できない）。

## Phase 1: 収集 🔍

問題の情報を体系的に収集する:

1. **症状の明確化**: 何が起きているか、何が期待される動作か
2. **再現コマンド**: 症状そのものを判定する再現コマンドを1つ用意する（テスト、curl、CLI と fixture など。できるだけ決定的・高速・無人で実行できる形）
3. **エラーログ**: 完全なエラーメッセージとスタックトレース
4. **最近の変更**: `git log --oneline -10` と `git diff` で直近の変更を確認
5. **影響範囲**: どのファイル/機能に影響するか
6. **発生頻度**: 常に/時々/特定条件で

**Phase 1 の完了条件**: 再現コマンドを1回以上実行し、症状が出る（赤になる）ことを実際の出力で確かめた。満たすまで仮説に進まない。出力に含まれる秘密情報は伏せて示す。

- 断続的に起きる失敗は、繰り返し実行と、時刻・乱数・実行順の固定で再現率を上げる
- 再現コマンドを作れないときは、試したことを列挙して止まる。再現できる環境へのアクセス、伏せ字を施したログや採取物、一時的な計装の許可を求める。推測で仮説に進まない
- 赤くなる再現ができたら、要素を1つずつ削って再実行し、最小の再現にする。良い版と悪い版が分かっている回帰は `git bisect run` で自動化する（作業ツリーがクリーンなとき、または別の作業ツリーで行う）

## Phase 2: 仮説 💭

収集した情報から、症状を説明できる **競合する仮説** を立てる（通常は2〜3つ）。1つだけにするのは、競合する説明が無いと証拠で言えるときだけにし、その根拠を書く。各仮説は「X が原因なら、Y を変えると Z になる」という反証できる予測の形で書く:

```
仮説1: [具体的な原因の推測]
  予測: [Y を変えると Z になる]
  検証方法: [どうすれば確認できるか]
  確認すべきファイル: [関連するコード]

仮説2: [別の原因の推測]
  検証方法: [どうすれば確認できるか]

仮説3: [さらに別の原因の推測]
  検証方法: [どうすれば確認できるか]
```

仮説は互いに独立していること。最も可能性が高い順に並べる。

## Phase 3: 検証 🧪

各仮説を順に検証する:

1. **支持する証拠** を探す
2. **反する証拠** も必ず探す（確証バイアス対策）
3. 証拠が見つかったら記録する
4. 仮説が棄却されたら次の仮説へ
5. 全仮説が棄却された場合は Phase 1 に戻り情報を追加収集

**証拠なしに結論を出さないこと。**

調査のために入れた一時的なログ（計装）には固有のタグを付け、終了前にそのタグを検索して残りがゼロであることを確かめる。

## 3回失敗ルール（Three Strikes Rule）

**同じ修正経路で類似の修正が3回失敗したら、その経路を止める。**

その経路で4回目の修正を試みない。代わりに:

1. **その経路を止める** — 同じアプローチを繰り返しても新しい証拠は出ない。その経路に依存しない、許可済みの独立した作業は続けてよい
2. **問題の理解を疑う** — 同じ経路での3回の失敗は「修正方法」ではなく「問題の理解」やアーキテクチャが間違っている兆候
3. **ユーザーに報告する**: 3回の試行それぞれについて「何を試みたか」「なぜ失敗したか」を列挙し、推測される根本的な問題（アーキテクチャレベルの仮説）と推奨を提示する
4. **判断を委ねる** — 設計変更の是非はユーザーが決定する

数え方:

- 数えるのは、同じ失敗経路に対する類似の修正の失敗。原因が異なる失敗や、TDD の Red で意図したテストの失敗は数えない
- 担当（エージェント・セッション・人）を替えても、試行の履歴は引き継ぐ。担当の交代で回数をリセットしない

報告の推奨として、別モデルの視点に切り替える選択肢を示してよい（Claude Code では codex-collab スキルを参照）。切り替えるのは、ユーザーが同意したときか、計画や依頼で事前に許可されているときだけにする。

## Phase 4: 修正 🔧

根本原因が特定されたら:

1. **原因の報告**: 根本原因、影響範囲、修正方針をユーザーに報告
2. **TDDで修正**: 修正が依頼の範囲内なら、`best-practices` の TDD サイクル（Red から）で自分で修正する。調査だけの依頼なら、根本原因と修正方針を報告して止める（Claude Code では `/dev-core:tdd` での修正をユーザーに提案してよい）
   - まず失敗するテストを書く（バグを再現するテスト。Phase 1 の再現コマンドを元にする）
   - 修正を実装
   - テストがグリーンになることを確認
   - 完了を報告する前に、対象を絞らないテストを1回実行する。再現テストのグリーンを全体のグリーンとみなさず、全体が通らなければ完了にしない（`best-practices` の Iron Law。今の入力に対する結果を再利用できる条件は `dev-core:verify`）
   - 正しい継ぎ目（seam）が無く回帰テストを書けないときは、それ自体を所見として報告する
   - **同じ修正経路で3回失敗したら、上記ルールに従いその経路を止める**
3. **再発防止**: continuous-learning スキルに従い、防止メカニズムを構築

## 報告フォーマット

各フェーズの結論を以下の構成で報告する。**実際に確認した証拠だけを書くこと**:

- 【収集】症状 / 再現コマンドとその実行結果（赤であること）/ 直近の関連する変更
- 【仮説】可能性の高い順に、競合する仮説（予測付き）
- 【検証】各仮説の採否と、その根拠となった実際の証拠（ファイル・行・出力の引用）
- 【根本原因】原因 / 影響範囲 / 修正方針（調査だけの依頼なら、テスト先行での修正を提案する）
