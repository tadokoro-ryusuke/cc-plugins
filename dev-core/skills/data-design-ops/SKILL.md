# Data Design Ops — テーブル物理設計とマイグレーション運用

**鉄則: DDL はスクリプトが正本、性能は EXPLAIN が唯一の証拠。**

手動で本番に DDL を流してはならない。マイグレーション履歴と実 DB が乖離した瞬間、以後の自動化は全部壊れる。
なぜ: 物理設計の失敗は納品後にデータが増えてから顕在化し、保守フェーズの収益性と顧客の信頼を直撃する。

## スコープと境界

このスキルは物理設計（インデックス・パーティション・マイグレーション運用）を扱う。隣接領域は以下へ:

- 概念・論理データモデル（ER・正規化・認可境界）→ dev-core:data-auth-boundary-design 参照
- Repository・トランザクション・キャッシュの実装パターン → dev-core:backend-patterns 参照
- システム移行・データ移行・カットオーバー計画 → dev-core:migration-cutover-planning 参照
- 遅いクエリの原因調査プロセス（仮説→検証）→ dev-core:debug 参照（本スキルは対策側）
- CI/CD パイプラインへの組み込み・デプロイとマイグレーション適用順序 → dev-core:cicd-release-design 参照
- 変更適用後の検証フロー → dev-core:verify 参照
- ルールの決定的強制（hooks・lint への翻訳）→ dev-core:conventions-as-guardrails 参照

## Step 0: 成果物と正本を決める

物理設計に着手したら、まず以下の成果物と「正本はどれか」を確定する:

- [ ] マイグレーションスクリプト一式（**バージョン管理された唯一の変更経路**。テーブル定義書はここから生成する）
- [ ] インデックス設計書（対象クエリ → インデックスの対応表）
- [ ] パーティション・アーカイブ方針（保持期間と削除手順）

なぜ: DDL を正本にしないと、ドキュメントと実 DB が数ヶ月で乖離し、AI にも人間にも信用できる参照点がなくなる。

判断の軸は常に「**読み取り速度 vs 書き込み速度・整合性**」。インデックスは読み取りを速くし書き込みを遅くする。実測した読み書き比と更新競合の激しさで決め、推測で非正規化しないこと。

## Step 1: インデックスを設計する

1. **対象クエリを列挙する** — WHERE / JOIN / ORDER BY に現れる列を分析する。クエリなきインデックスは作らない。
2. **複合インデックスは「等価条件 → 範囲条件」の順に列を並べる。**
   なぜ: 範囲条件の列より後ろの列はインデックスの絞り込みに使えない。
3. **カーディナリティの低い列の単独インデックスは作らない**（性別・ステータスなど）。
   なぜ: 絞り込み効果がなく、書き込みコストだけが残る。
4. **投機的に作らない。** 「オプティマイザに選択肢を」とインデックスを乱造すると書き込み劣化とロック競合を招く。使われないインデックスは pg_stat_user_indexes 等で定期的に棚卸しして削除する。
5. **稼働中の大きなテーブルへの追加は CONCURRENTLY（PostgreSQL）必須。** ロングトランザクションとの共存に注意する。
   なぜ: 通常の CREATE INDEX はテーブルをロックし、本番のサービス停止になる。

### EXPLAIN を証拠とする手順

効果は必ず before/after の実行計画で示す。「速くなったはず」で完了報告しないこと。

1. 対象クエリの `EXPLAIN (ANALYZE)` を実行し、実行計画と実測時間を保存する（before）
2. 本番相当のデータ量を持つ環境でインデックスを作成する
3. 同じクエリを再実行し、スキャン方式の変化と実測時間を保存する（after）
4. before/after の実行計画を並べて報告する

なぜ: EXPLAIN (ANALYZE) が唯一の証拠。少量データの開発環境では実行計画自体が本番と変わるため、証拠にならない。

## Step 2: 特殊インデックスを選択する

B-tree で足りないときだけ、以下の表から選ぶ:

| インデックス | 使いどころ | DBMS |
|---|---|---|
| 部分インデックス | アクティブ行のみ等、条件を満たす行だけを索引化してサイズと更新コストを削減 | PostgreSQL |
| カバリングインデックス | SELECT する列までインデックスに含め、テーブルアクセス自体を消す | PostgreSQL（INCLUDE）/ MySQL |
| GIN | JSONB・全文検索 | PostgreSQL |
| BRIN | 追記型の時系列テーブル。B-tree の 1/4 以下のサイズで済む | PostgreSQL |
| インデックスマージ | 複数の単独インデックスの組み合わせ利用 | MySQL |

なぜ表で選ぶか: 特殊インデックスは適用条件を外すと B-tree より遅くなる。「状況 → 型」の対応を固定して選定の属人化を防ぐ。

## Step 3: マイグレーション運用規約を敷く

プロジェクト初日に以下を規約として固定し、以後の全変更に適用する:

- [ ] **全変更をスクリプト化しバージョン管理する。** マイグレーションが唯一の変更経路。
- [ ] **手動 DDL 禁止。緊急時も必ずスクリプト経由にする。**
  なぜ: 履歴と実 DB が乖離すると、環境再現・差分検出・自動適用が全部壊れる。
- [ ] **環境間で同一手順**（開発 → 検証 → 本番で同じスクリプトを同じ順に適用する）。
- [ ] **ロールバックプランを適用前に書く。** 戻すスクリプトを用意するか、「戻せないので前進修正で対処する」と明記して承認を取るかのどちらかにする。
  なぜ: 失敗してから戻し方を考える時間は本番障害の時間である。
- [ ] インデックス追加は CONCURRENTLY（Step 1 の 5 を規約に含める）。
- [ ] **RLS ポリシーもマイグレーションスクリプトで管理する**（テナント分離設計の正本は dev-core:data-auth-boundary-design Step 8。手動 DDL 禁止の対象に含める）。

ツールは既存スタックに合わせて選ぶ: Flyway / Liquibase（JVM 系）、Prisma Migrate・Drizzle（TS）、Rails / Django migrations、golang-migrate、Atlas、sqldef（宣言的）。

## Step 4: Expand-Contract でゼロダウンタイム変更する

**鉄則: スキーマ変更とそれに依存するコード変更を同一ステップでやらない。**
なぜ: 同時に変えると、デプロイの瞬間に新旧どちらかのコードが必ず壊れ、切り戻しも不可能になる。

カラム名変更・型変更・テーブル分割は、次の3フェーズに分解して**別々に適用**する:

1. **Expand（拡張）**: 追加のみ行う。新カラム・新テーブルを旧構造と併存させる。旧コードは無変更で動き続けることを確認してから次へ。
2. **Migrate（移行）**: 二重書き込みで新旧を同期し、既存データをバックフィルする。新旧の一致を確認してから、読み取りを新構造へ切り替える。
3. **Contract（収縮）**: 旧構造を参照するコードが残っていないことを確認してから、旧カラム・旧テーブルを削除する。

各フェーズを独立したデプロイ+マイグレーションとして適用し、フェーズ間で稼働確認を挟む。急いで1リリースに畳んではならない。

オンライン DDL の支援ツール: pgroll / gh-ost / pt-online-schema-change。
システム全体の移行・カットオーバー規模の話は → dev-core:migration-cutover-planning 参照。

## Step 5: パーティションを判断する

上から順に評価し、最初に該当したものを採用する:

1. **保持期間があり古いデータを定期削除・アーカイブするか?** → **Range**（時系列）。パーティションの DROP で削除が一瞬・低負荷になる。
2. **テナント・地域など離散値でアクセスが分かれるか?** → **List**。
3. **単に巨大で、特定の偏りなく均等分散したいだけか?** → **Hash**。
4. **どれにも該当しない** → パーティションしない。まずインデックスと SQL 改善で戦う。

運用ルール:

- **パーティションキーはアクセスパターンと保持ポリシーに合わせて設計時に決める。**
  なぜ: 後付けの移行はトリガ同期+バッチ移送が必要で高コスト。
- パーティションの作成・削除は pg_partman 等で自動化する。手動運用は必ず作り忘れ・消し忘れが起きる。
- **保持ポリシーは技術判断ではない。** 保持期間は法的保持義務・顧客との契約に結びつく（目安として整理し、確定は顧客・法務等の専門家への確認を経ること・要確認）。

## Step 6: 3年後データ量でレビューする

物理設計レビューは「今のデータ量」ではなく「3年後のデータ量」を仮定して行う。

- [ ] 主要テーブルごとに3年後の行数を見積もったか（増加ペース × 期間で概算する）
- [ ] その行数のデータを検証環境に投入し、主要クエリの EXPLAIN (ANALYZE) を確認したか
- [ ] 読み書き比を実測したか（推測で非正規化・インデックス追加をしていないか）
- [ ] 際限なく成長するテーブルに保持・アーカイブ方針（Step 5)があるか
- [ ] 使われないインデックスを棚卸しする手順が運用に組み込まれているか

なぜ: 開発環境の少量データで性能確認し、本番でデータが増えてから破綻するのが物理設計の最頻死因。遅くなってからの対処はゼロダウンタイム変更(Step 4)を強いられ、数倍高くつく。

## AI がやること / 人間にしか決められないこと

| AI に委譲してよい | 人間にしか決められない |
|---|---|
| DDL・マイグレーションスクリプトの生成 | 破壊的マイグレーション（DROP・型変更）の実行承認 |
| EXPLAIN 結果の解釈と改善案の提示 | パーティション・アーカイブ方針（法的保持期間・契約と結びつく） |
| スロークエリログの分析 | 本番適用のタイミング判断 |
| インデックス棚卸しレポートの作成 | 読み書きトレードオフの最終判断（業務の読み書き比は業務知識） |
| 3年後データ量レビューの起案 | 保持期間の確定（顧客・専門家との合意事項） |

なぜ分担線が要るか: AI はスクリプト生成と分析が得意だが、「消してよいか」「いつ適用するか」は事業・契約側の判断であり、誤ったときの被害が不可逆だから。

## ガードレール: 本番 DB 書き込みを AI の自動実行から外す

**本番 DB への書き込み（DDL・DML とも）は、AI の自動実行対象から必ず除外する。**

- hooks の deny 等の**決定的な仕組み**で強制する。自然言語の指示だけでは確率的にしか守られない。強制の設計は → dev-core:conventions-as-guardrails 参照。
- AI に許可する範囲: スクリプトの生成、開発・検証環境への適用、本番のリードオンリー調査（EXPLAIN・統計ビューの参照）。
- 本番適用は、人間がレビュー・承認したスクリプトを人間または CI/CD パイプラインが実行する。緊急時も同じ経路を通す（Step 3 の手動 DDL 禁止と同じ理由）。

なぜ: 本番 DDL の事故は復旧不能になりうる、このスキルで最も高くつく失敗だから。
