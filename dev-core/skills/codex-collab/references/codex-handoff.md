# Codex への handoff と、結果の受け取り

Claude Code（親）が Codex に仕事を渡すときの文面と、返ってきた結果の扱いを定める。文面を渡せる面（Herdr の端末、`codex exec`、`/codex:rescue`）では、この契約を使う。`/codex:review` は文面を受け取らない組み込みのレビューなので、handoff と dispatch ID は使えない。そのときは、ジョブの ID とレビューした Git の範囲を証拠として記録し、「結果の受け取り方」の指摘の確かめ方だけを使う。返却の形式を指定したいレビューは、`codex exec` で渡す。原則は `dev-core:best-practices` の `references/delegation-and-review.md` §9 にあり、このファイルはそれを Codex 向けに具体化する。

handoff は単独で成立させる。相手の Codex に dev-core のプラグインが入っているとは限らないので、返却の形式・状態・禁止事項・後始末を handoff 自体に書く。

## 渡す前に親が決めること

- 成果を1つに絞る。判断が残っている作業（曖昧な要件、アーキテクチャ、スコープ）は渡さない。
- 書き込みを許す範囲、触ってはいけないもの、共有リソース（DB、ポート、デプロイ先）の持ち主を決める。計画ファイルは親だけが書くものとし、子の書き込み範囲に入れない。
- 受け入れチェック（実行するコマンドと、通ったと言える条件）を決める。
- 役割と設定を `codex-roles.md` から選ぶ。

## dispatch ごとに用意するもの

1回の handoff を dispatch と呼ぶ。dispatch ごとに次を用意する。

- **dispatch ID**: 短い一意の名前（例: `impl-auth-1`、`review-auth-1`）。handoff の本文、端末の名前、返却の先頭、計画の Dispatch Ledger で同じ ID を使う。返ってきた報告がどの handoff のものかを、この ID で突き合わせる。dispatch ID は、端末が閉じるまで変えない。同じ担当に修正を返すときは、ID とは別に試行の番号を付ける（`Attempt: 2`）。
- **dispatch の作業ディレクトリ**: リポジトリの外に、dispatch ごとに作る。ほかの利用者から読めない場所にする。handoff の本文、渡す前の状態、出力ファイルをここに置く。受け入れが済んで、計画に要約を残したら消す。
  - 書き込める sandbox の子は、作業ディレクトリのほかに一時ディレクトリにも書ける（→ `codex-roles.md`）。親のセッションの作業用ディレクトリは、多くの場合この一時ディレクトリの配下にあるので、そこに置いた記録は子から書き換えられる。子は親と同じ利用者として動くので、利用者専用の権限では守れない。
  - そこで、書き込みを伴う dispatch では、渡す前の状態を保存したら、その記録のハッシュを親が自分の応答に書き出しておく。受け取るときに、記録のハッシュが変わっていないことを確かめてから比較に使う。変わっていたら、その記録を使わず、範囲の外の変更を否定できないものとして扱う。
  - 書き手が動いている間に次の handoff を書いたときも、同じに扱う。書いたらハッシュを応答に書き出し、起動の直前に照合する。変わっていたら、書き直す。
  - 計画ファイルも同じに扱う。親が計画を更新するたびに、そのハッシュを応答に書き出す。
  - 子が書けない場所（作業ディレクトリでも一時ディレクトリでもない場所）を利用者が用意しているなら、そこに置いてもよい。
- **渡す前の状態**（書き込みを伴う dispatch）: 対象の各リポジトリについて、HEAD の revision、staged と unstaged の差分、untracked のファイルの一覧を保存する。あとで「子が変えたもの」と「元からあった変更」を分けるための基準になる。`git diff` だけでは staged と untracked が抜ける。git が追跡していないファイルが元からあるなら、範囲の内外を問わず、その内容のハッシュも控える（追跡されていないファイルの書き換えは、差分にも状態の一覧にも出ない）。書き込みを許す範囲にあるものは、内容も退避する。

## handoff はファイルで渡す

handoff の本文は dispatch の作業ディレクトリにファイルとして書き、Codex には「このファイルを読んで、そのとおりに進める」という短い指示だけを渡す。

- 長い文面を端末に貼り付けると、改行や記号が崩れることがある。
- ファイルがあれば、何を渡したかが後から確かめられ、再開のときにも残る。
- リポジトリの中に置くと、差分や commit に混ざる。

計画の節や関連ファイルは、本文を写さずパスで示す。handoff に、秘密情報や、作業に関係しないほかの端末の出力を写さない。

## 実装役のテンプレート

```markdown
# Handoff: <成果を1行で>

Dispatch: <dispatch ID>
Attempt: <試行の番号。最初は 1>

## 役割
実装担当。下の範囲の中で、1つの成果を仕上げる。

## 入力
- リポジトリとブランチ: <path> / <branch>
- 入力の識別子: <revision、または「HEAD + 未コミットの変更」>
- 計画の該当箇所: <計画ファイルのパスと節>
- ほかの作業に属する既存の変更（触らない）: <パス、または「なし」>
- 計画ファイル（読むだけ。書かない）: <パス>

## 書き込みを許す範囲
- <パスやディレクトリ>
- それ以外は読み取りだけにする。共有リソース: <持ち主と扱い>

## 受け入れ条件
- <観測できる条件>
- 実行するコマンド: <コマンド>

## 進め方
- 実行できる振る舞いの変更は、失敗するテストを先に書いてから実装する。
- 既存のテストを通すために、削除・skip・期待値の緩和・入力の特別扱いをしない。必要に見えたら、変えずに止まって報告する。
- 同じマシンでほかの担当も動いている。同時に走らせる build とテストを絞る。
- 終わるときに、自分が始めたバックグラウンドのジョブを止め、自分が作った一時ファイルを消す。

## してはいけないこと
- commit・push・PR の作成・公開・デプロイ、共有のサービスやデータへの書き込み。書き込みを許された範囲にデプロイや公開の設定があっても、実行はしない。これらは親が行う
- 上の範囲に無い、依存の追加や設定の変更
- ほかのエージェントや subagent の起動、ワークフロー全体の起動し直し
- 範囲の外への書き込み、範囲の拡大

## 止まって返す条件
- 計画とコードが食い違う、仕様とテストが矛盾する
- 計画に無い公開契約やデータの変更が要る
- 同じ修正の経路で3回失敗した
- 上の範囲では受け入れ条件を満たせない

## 返却（最後のメッセージをこの形にする）
Dispatch: <dispatch ID>
Attempt: <受け取った試行の番号>
Status: completed | needs-parent | blocked

### 変更したファイル
### 実行したコマンドと結果（exit code と、失敗したものは出力の該当部分）
### 変更・skip・削除した既存のテストと、その根拠（無ければ「なし」）
### 実行しなかったチェックと、その理由（無ければ「なし」）
### 遭遇した問題（エラー、回避したこと、未解決のこと。無ければ「なし」）
### 残る懸念
```

## 読み取り専用の役のテンプレート（レビュー・設計・調査）

```markdown
# Handoff: <レビューや調査の対象を1行で>

Dispatch: <dispatch ID>

## 役割
独立した<レビュー役 | 設計役 | 調査役>。読み取り専用。ファイルの作成・変更・削除、commit・push、ほかのエージェントの起動はしない。

## 入力
- リポジトリとブランチ: <path> / <branch>
- 対象の識別子: <base と head、または対象ファイル>
- 元の要件と受け入れ条件: <計画ファイルのパスと節>
- 検証の生の出力: <ログのパス>

## 見てほしいこと
- <観点。レビューなら、計画の前提そのものを疑ってよいと書く>

## 返却（最後のメッセージをこの形にする）
Dispatch: <dispatch ID>
Status: completed | needs-parent | blocked

### 指摘（レビュー役）
全件を、絞らずに返す。1件ごとに:
- [P0|P1|P2|P3]（確度: high | medium | low）file:line — 問題、具体的な影響、解決する最小の変更

### 案（設計役）
評価軸に沿った案。案ごとに、前提、トレードオフ、捨てた選択肢とその理由

### 調べた結果（調査役）
問いへの答えと、根拠にしたファイルや出力の所在

### 未確定の点（何が分かれば決まるか）
### 確認したこと（読んだファイル、実行したコマンド。確認するつもりでしなかったことと理由）
### 遭遇した問題（無ければ「なし」）
```

役に合わない節は、テンプレートから外して渡す。

読み取り専用の役には、次を渡さない。

- 期待する結論（「正しく実装されている」など）
- 実装の経緯や、実装担当の自己評価
- 設計の独立案を求めるときは、親の案

## 結果の受け取り方

返ってきた報告は主張として扱う。報告に問題が書かれていないことを、問題が無かった証拠にしない。返却の先頭の dispatch ID が渡した handoff と一致しない報告は、その dispatch の結果として使わない。

### 実装役の結果

1. 書き手が止まったことを確かめてから、今の状態（HEAD、staged と unstaged の差分、untracked の一覧とハッシュ）を、渡す前の状態と比べる。許した範囲の外に変更が無いか、元からあった変更が書き換えられていないかを確かめる。計画ファイルは、親が最後に控えたハッシュと一致することを確かめる。一致しなければ、親が書いていない変更（受け入れ条件や範囲の書き換え）が入っているので、その内容を読んでから先に進む。範囲の外の変更は受け入れず、戻すかどうかを親が判断する（ユーザーの変更を上書きしない）。
2. 変更をすべて読む。既存のテストの削除・skip/only 化・期待値の緩和・入力の特別扱いを探し、報告の「なし」と食い違えば、その通過を証拠に数えない。受け入れチェックのコマンドが実行するもの（テストランナーの設定、パッケージのスクリプト、ビルドの設定）が変えられていないかも見る。
3. そのあとで、受け入れチェックのコマンドを親が自分で実行する。Codex の「通った」という報告を証拠にしない。読む前に実行すると、子が変えたスクリプトを親の権限で動かすことになる。
4. 報告の「実行しなかったチェック」「遭遇した問題」を読み、受け入れ条件に影響するものを計画に記録する。
5. 状態が `needs-parent` か `blocked` なら、親が証拠を確かめて範囲を定め直す。黙って範囲を広げたり、設定を上げたり、担当を替えて失敗の履歴を消したりしない。

### 読み取り専用の役の結果

0. 返却の先頭の dispatch ID が、渡した handoff と一致することを確かめる。一致しない結果や、ID の無い結果は、その dispatch の結果として使わない。続けて Status を読む。`completed` でなければ、返ってきた部分は使ってよいが、確認できなかったと書かれた範囲は済んでいないものとして扱い、該当する条件を pending のまま残す。
1. 指摘を1件ずつ実ファイルと実行出力で確かめる。確かめられたものだけを反映する。
2. 確度が低い P0/P1 も捨てない。親が確定か棄却をするまで、該当する受け入れ条件は pending のまま残す。
3. 「確認したこと」を読み、見ていない範囲があれば、そこはレビューされていないものとして扱う。

### 依頼を断られたとき

Codex が依頼の一部や全部を断ったら（例: セキュリティに関わる検証）、言い換えて同じ依頼を通そうとしない。断られたことと範囲を記録し、別の手段（dev-core の `security-auditor`、親による確認）を使うか、ユーザーに報告する。必須のレビューを代わりの手段でも行えなければ、「独立性は未充足」と明記して pending のまま残す。

## 追って渡すとき

- 同じ担当に修正を返すときは、確かめた指摘と、直してほしい範囲だけを渡す。同じ dispatch ID に新しい試行の番号を付け、返却の先頭にその番号を求める。前の試行の報告が画面に残っていても、番号が違えば今回の結果として使わない。
- 修正の経路が同じなら、失敗の回数は担当を替えても引き継ぐ（Three Strikes → `dev-core:debug`）。
- 入力が変わったら、それより前のレビュー結果は影響する範囲で無効になる。
