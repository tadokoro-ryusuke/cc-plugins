# Migration & Cutover Planning

**鉄則: 戻れない移行は計画ではなく賭けである。**

切り戻し手順のない移行計画を書いてはならない。不可逆なデータ変換・旧システムの即時廃止など「失敗したとき戻れない」一手だけは、どれほど工数が浮いても絶対に避けること。
なぜ: 移行は受託で最も事故が起きやすい局面であり、移行失敗は検収遅延・損害賠償に直結する。

## Step 0: 移行を計画するタイミングと成果物を押さえる

リプレース案件では、移行を開発完了後に考え始めてはならない。次のタイミングで着手する:

- **提案段階**: 移行方針（一括か段階か並行か）を提示する
- **要件定義**: 移行要件を確定する（→ delivery-core:requirements-definition 参照）
- **結合テスト以降**: 移行リハーサルを実施する

なぜ: 「移行がうまい」は既存システム置き換え案件を取る強力な差別化であり、逆に後回しにした移行は終盤に手詰まりを起こす。

計画の成果物一式（このスキルの Step 1〜6 で順に作る）:

- [ ] 移行計画書（方針: 一括/段階/並行、体制、スケジュール、リスク）
- [ ] データ移行設計書（マッピング定義、クレンジングルール、検証方法）
- [ ] 並行稼働計画（比較検証方法、差異の裁定ルール、終了判定基準）
- [ ] カットオーバー計画書（当日タイムチャート、Go/No-Go 判定基準、Point of No Return、切り戻し手順）
- [ ] 移行リハーサル計画書と結果報告書（所要時間実測を含む）

## Step 1: 移行方式を選定する（3類型）

まず「業務を何時間止められるか」「失敗したとき戻れるか」「予算はいくらか」の3軸を顧客に確認し、方式を選定する。

| 方式 | 特徴 | 向く条件 |
|------|------|----------|
| 一括（ビッグバン） | 期間最短・コスト最小・リスク最大。失敗時に全損 | 業務停止を許容できる小規模システム、切り戻しが確実に可能な場合のみ |
| 段階（機能・拠点ごと） | リスク小・期間長。新旧接続の開発費がかかる | 業務を止められない基幹系、機能単位で分割できるシステム |
| 並行（Parallel Run） | 最も安全・運用コストは2倍 | 経理・給与など「締め」があり結果を突合できる業務 |

選定基準の考え方:

1. **業務停止許容時間**を最初に聞く。ゼロに近いほど段階・並行へ寄せる。
2. **可逆性**を次に確認する。戻れない要素（片方向のデータ変換、旧環境の廃止契約）があれば、その要素を先に潰す。
3. **予算**で最後に調整する。段階移行の新旧接続コスト・並行稼働の二重運用コストを金額で提示し、リスクとの交換条件として顧客に選ばせる。

なぜ: 移行の3すくみは「リスク・期間・コスト」であり、どれを取るかは顧客の業務判断。受託者が勝手に決めると事故時に責任だけ負う。

方式が決まらないうちに移行見積を確定しないこと。クラウドリフト案件では 7R（Rehost/Replatform/Refactor/Repurchase/Relocate/Retain/Retire）を方針整理の語彙として使う。

## Step 2: Strangler Fig で段階移行を実装する

段階移行を選んだ場合の標準手順。レガシーの前にファサードを挟み、少しずつ置き換える。

1. **ファサード（プロキシ/ルーター）を挟む** — 全トラフィックがファサード経由になるまでは次に進まない。
2. **最初の機能を新システムに実装**し、トラフィックの **1%** を流す。
3. 差異・エラーがなければ **10% → 50% → 100%** と段階的に引き上げる。各段階で監視指標（エラー率・レイテンシ・業務結果の差異）を確認してから進む。
4. 100% 到達後、一定期間問題がなければレガシー側の該当機能を停止する。
5. 全機能で 1〜4 を繰り返し、最後にレガシーを廃止する。

**切り戻しは「設定1つ」にする。** ファサードのルーティング設定を戻すだけで旧系に復帰できる状態を維持すること。
なぜ: 切り戻しが設定1つでできることが Strangler Fig の本質的価値。デプロイやデータ復元を伴う切り戻しは、当日その手順自体が失敗する。

コードベース内部での段階移行には Branch by Abstraction / Feature Flag を使う（システム間なら Strangler Fig、コード内なら抽象層+フラグ）。実装パターンの詳細 → dev-core:backend-patterns 参照。

## Step 3: データ移行を設計する

**データ品質調査を移行見積の前に実施する。** 旧データは汚い（文字コード・全半角・重複・孤児レコード）ことを確実に起きる前提とし、データ移行工数の大半はクレンジングに消えると見込む。
なぜ: 調査なしの固定見積は赤字の典型パターン。金額の付け方自体は自組織の見積・価格判断プロセスに従う。

定石は「**ETL バックフィル + 二重書き込み + 照合ジョブ**」の3点セット:

1. **ETL バックフィル**: 過去データはマッピング定義書（旧項目→新項目、クレンジングルール込み）に基づき ETL で移送する。
2. **二重書き込み（shadow write）**: 移行期間中は新旧両 DB へ書き込み、新系のデータを本番同等に育てる。
3. **照合ジョブ**: 新旧の整合性を継続的に自動検証する。移行は「1回のコピー」ではなくプロセスとして扱う。

さらに以下を顧客業務部門と**事前に**合意する:

- **旧システムの凍結タイミング**（データ変更停止の日時）と、凍結後に発生した差分データの扱い。
  なぜ: ここが曖昧だと「移行後に旧システムで入力し続けた」事故が起きる。
- 旧システムからのデータ抽出手段（エクスポート機能の有無）。開発終盤ではなく計画段階で確認する。

## Step 4: 並行稼働の終了条件を先に決める

並行稼働は同じ入力を新旧両系に流して結果を突合する最高信頼度の検証法だが、運用コストが2倍になる。開始前に必ず次の2つを文書で合意する:

1. **終了判定基準** — 例:「差異ゼロが2締め連続」など、業務サイクル（締め）単位の客観条件で定義する。
   なぜ: 終了条件がないと並行稼働が際限なく続き、二重運用コストが受託側の持ち出しになる。
2. **差異の裁定ルール** — 差異が出たとき「どちらの値を正とするか」「誰が判定するか」「判定期限」を事前に決める。
   なぜ: 裁定ルールなしで差異が出ると「どちらが正か」で顧客と紛糾し、移行全体が止まる。

差異の業務的裁定（どちらの値が業務として正しいか）は顧客の業務判断であり、受託者が代行しない。

## Step 5: カットオーバー計画書を書く

カットオーバー当日は次の3要素を必ず含む計画書に落とす:

1. **分単位のタイムチャート** — 作業項目・担当・開始/終了時刻・完了確認方法を分単位で並べる。所要時間はリハーサルの実測値（Step 6）を使う。机上の見積時間で書かない。
2. **Go/No-Go 判定基準** — 各チェックポイントで「何を確認できたら次へ進むか」を事前に文書化する。当日にその場で考えない。判定材料（データ件数照合・外形監視・業務スモークテスト結果）を列挙しておく。
3. **Point of No Return（回帰不能点）** — 「この時刻までにこの判定を通らなければ切り戻す」という時刻を、**切り戻し所要時間から逆算して**事前に決める。
   なぜ: 業務開始時刻から切り戻し実測時間を引いた時刻が最終判断期限。これを過ぎてからの切り戻しは業務に間に合わない。

判定者（Go/No-Go を宣言する人間）を計画書に名前で書く。連絡網・エスカレーション先・顧客への状況報告タイミングも含める。

## Step 6: リハーサルで実測する

**リハーサルの完了条件は「切り戻し手順まで含めた実測所要時間が取れていること」。** 移行の往路だけ試して成功と呼ばない。

- 本番同等データ・本番同帯・本番体制で実施する。開発環境の小データでの試行はリハーサルと呼ばない。
- 最低1回、基幹系は2〜3回実施する。
- 真の成果物は**実測所要時間**。これがなければ Step 5 のタイムチャートも Point of No Return も机上の空論になる。
- リハーサルで出た差異・手順の詰まりは、すべて解消してから本番に臨む（原因調査 → dev-core:debug 参照)。

移行スクリプト・ETL・照合ジョブの検証は dev-core:verify の6段階フローで証拠ベースに行う。

## よくある事故リスト

計画レビュー時にこのリストを潰したか確認する:

- [ ] 移行を開発完了後に考え始め、旧システムにエクスポート機能がないことが終盤に発覚
- [ ] データ品質調査をせずに固定見積し、クレンジング工数で赤字化
- [ ] 並行稼働の差異裁定ルールがなく「どちらが正か」で顧客と紛糾
- [ ] 切り戻し手順を書いたが一度も試しておらず、切り戻し自体が失敗
- [ ] Point of No Return を決めておらず、当日ずるずると作業を続けて業務開始に間に合わない
- [ ] 旧システムの凍結合意が曖昧で、移行後も旧システムで入力が続く
- [ ] 不可逆なデータ変換を先に実行してしまい、失敗時に戻れない
- [ ] カットオーバー成功後、旧システムの契約解約を忘れて二重コスト

## AI がやること / 人間にしか決められないこと

**本番切替の引き金だけは絶対に AI に引かせない。** 当日の AI の役割は「監視ダッシュボードの異常検知と判定材料の提示」までと、運用設計の段階で線を引いておく。

| AI に任せる | 人間にしか決められない |
|-------------|------------------------|
| 旧システムのコード/スキーマ解読と仕様復元（ドキュメントなきレガシー解析は LLM の得意分野） | 移行方式の選定（顧客の業務停止許容度の交渉） |
| データマッピング表の下書き、ETL・照合スクリプトの生成 | データ差異の業務的裁定（どちらの値が正しいかは業務判断） |
| 移行リハーサルログの差異分析 | カットオーバー当日の Go/No-Go 判断 |
| カットオーバー手順書の整形、タイムチャート下書き | 切り戻しの宣言（Point of No Return の執行） |
| 監視ダッシュボードの異常検知と判定材料の提示 | 本番環境への破壊的操作の承認 |

なぜ: レガシー解析コストの激減で移行案件の実行力は上がったが、業務停止・データ正否・切替可否はすべて事業リスクの引き受けであり、AI には判断できない。
