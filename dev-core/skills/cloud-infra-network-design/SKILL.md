# Cloud Infra & Network Design

**鉄則1: 運用要員がいないなら「壊れにくく・自動で直り・マネージドに任せる」構成を選ぶこと自体が最重要のアーキテクチャ判断。迷ったら常に運用が軽い方に倒す。**

**鉄則2: AI は `plan` まで。`apply` と DNS 切替は必ず人間の承認ゲートを通す。**

インフラ選定は「月額ランニングコスト」と「自分の運用負荷の上限」を同時に決める。両方を成果物として顧客に見せられる状態で設計を終えること。

## 適用範囲と境界

本スキルはインフラ選定・IaC・ネットワーク(VPC/DNS/CDN/TLS/閉域)を扱う。以下は隣接スキルへ送る:

- 方式設計(モノリス/マイクロサービス選定・C4・ADR)→ dev-core:system-architecture-selection
- セキュリティ横断(STRIDE・ASVS・ゼロトラスト・シークレット管理)→ dev-core:security-by-design
- 可用性・DR・SLA の詳細設計 → dev-core:reliability-sla-design
- 運用設計・監視・引き継ぎ → dev-core:ops-design-handover
- 移行計画・カットオーバー(DNS 切替リハーサルの詳細手順)→ dev-core:migration-cutover-planning
- CI/CD パイプラインの設計 → dev-core:cicd-release-design
- 要件ヒアリングの進め方全般 → delivery-core:requirements-definition
- 承認ゲートの設計パターン → ai-engineering:human-in-the-loop-design

## Step 0: 提案段階ヒアリング(見積り前に必ず実施)

**ネットワーク要件、特に閉域接続の後出しは工数を倍にし見積りを崩壊させる。** 提案段階で以下のシートを埋めること:

| # | 質問 | 見積りへの影響 |
|---|------|----------------|
| 1 | システムはインターネット公開か、社内限定か | 公開構成/閉域構成の分岐点 |
| 2 | 接続元 IP 制限の要件はあるか(社内 IP・取引先 IP) | WAF/SG 設計と運用手順が増える |
| 3 | 専用線・閉域接続(インターネット非経由)の要求はあるか | 工数と期間が跳ね上がる分水嶺 |
| 4 | オンプレ・既存システムとの連携はあるか(経路・プロトコル) | VPN/専用線・CIDR 調整が発生 |
| 5 | 顧客の既存ネットワークの CIDR 採番はどうなっているか | 重複すると後から作り直し |
| 6 | 監査・認証要件はあるか(ISMS・ISMAP 等の語が出るか) | Landing Zone 前提に切替(Step 1) |
| 7 | ドメイン・DNS の名義と管理者は誰か | 前業者に権限が残っていると移行が止まる |
| 8 | クラウドの指定・既存契約はあるか | 選定の自由度とアカウント設計を規定 |

「監査」「ISMS」「ISMAP」「閉域」の語が1つでも出たら、Step 1 のエンタープライズ構成で見積もる。

## Step 1: 規模判定 — 二段構えで構成を決める

### 小規模デフォルト構成(まずこれを提案する)

- 実行基盤: **Cloud Run または ECS Fargate** + **マネージド DB**(RDS / Cloud SQL 等)
  - なぜ: ローカル=本番の一致とクラウド間ポータビリティを保ちつつ、運用をマネージドに寄せられる
- ガバナンス要件が薄い案件は Vercel / Cloudflare / Fly.io 等の PaaS も積極的に検討する
  - なぜ: 初速・運用負荷とも最良のことが多く、料金体系ごと分けると見積りが安定する
- Kubernetes(EKS/GKE)は運用人員がいない限り原則選ばない
  - なぜ: 「K8s を選ぶとはプラットフォームチームを雇うこと」— 一人運用では回らない

### エンタープライズ切替条件

- トリガー語: **監査・ISMS・ISMAP・閉域・ログ分離・権限分離**
- 切替内容: Control Tower / **Landing Zone 前提のマルチアカウント構成**で最初から見積もる
  - Transit Gateway でハブ&スポーク、ログは Log Archive アカウントに集中、プライベートホストゾーン共有で単一 DNS 名前空間
  - なぜ: 単一アカウントで提案すると監査要件(ログ分離・権限分離)で必ず手戻りする
- この規模は一人で抱えない。ネットワーク専業パートナーと組む判断も設計のうち
- ISMAP 等の調達要件・規格の最新状況は目安(2026年時点)。案件ごとに原文を要確認し、必要なら専門家(監査・認証コンサル)へエスカレーションする

## Step 2: 実行基盤の選定(コンテナ vs サーバーレス)

| ワークロード特性 | 選択 | なぜ |
|------------------|------|------|
| イベント駆動・スパイク・実行時間短 | Lambda / Cloud Functions | 実行モデルが一致し、待機コストゼロ |
| 常駐 Web アプリ・ランタイム自由度が必要 | Cloud Run / ECS Fargate / App Runner | コンテナで自由度と運用の軽さを両立 |
| 長時間バッチ・常駐処理 | コンテナ(Fargate 等) | FaaS の実行時間制限・コールドスタートと不一致 |

**実行モデルの不一致は選定時に潰す。** なぜ: Lambda に長時間バッチを押し込む失敗はリアーキでしか直らない。

## Step 3: アカウント設計 — 顧客名義+IAM フェデレーションの原則

- 顧客ごと・環境ごとに AWS アカウント / GCP プロジェクトを分離する
- **顧客名義のアカウントで構築し、自分は IAM / フェデレーションで入る**
  - なぜ: 自社名義に顧客資産を置くと、契約終了時の資産譲渡・支払い移管で地獄を見る
- ドメインの名義・DNS 管理権限も必ず顧客側に置く
  - なぜ: 受託者名義は顧客側の事業継続リスクであり、自分の撤退時にも障害になる
- 名義・権限の所在をアカウント設計書に明記する

## Step 4: IaC 標準構成(Terraform / OpenTofu)

**初日から IaC。** なぜ: 手動構築(ClickOps)は再現不能になり、stg 環境が作れなくなる。AI にコンソール操作を説明させるより Terraform を書かせる方が速い。

標準構成チェックリスト:

- [ ] ツールは Terraform または OpenTofu(Terraform 互換・MPL ライセンスで受託には安全な選択。CNCF 入りは2026年時点の目安・要確認)
- [ ] 環境分離は workspace ではなく **ディレクトリ分離(dev/stg/prod)** — なぜ: 適用先の取り違え事故が起きにくい定石
- [ ] State は **リモート(S3+ロック等のクラウド側)** に置く — なぜ: ローカル State は共同作業と災害復旧の両方を壊す
- [ ] CI は **tflint + trivy + `terraform plan` の三点セット** — なぜ: 構文・セキュリティ・差分の3視点を毎 PR で自動化できる
- [ ] plan 結果を PR に貼り、人間が approve して初めて apply が走るパイプラインにする(承認ゲートの標準形)
- [ ] CDK / Pulumi は「顧客側が引き継げるか」で選ぶ — 顧客に開発者がいるなら CDK(TypeScript)も可、いないなら HCL の方が保守業者を探しやすい

## Step 5: ネットワーク設計の定石

### VPC / CIDR 採番

- 基本形: パブリック / プライベート / (DB 用)アイソレートの **3層サブネット × 2〜3 AZ**
- CIDR は最初に採番計画を作り、オンプレ・他システム・将来の VPC ピアリングと **重複させない**
  - なぜ: 後からの変更は事実上の作り直し。拠点接続や統合で発覚してからでは遅い
- Step 0 で聞いた顧客の既存採番と突合してから確定する
- 小規模なら「VPC が要らない構成」(Cloud Run + Cloud SQL のサーバーレス接続等)も積極的に選ぶ
  - なぜ: 管理対象のネットワーク資産そのものを減らすのが最強の運用軽減

### NAT 費用最適化

- NAT Gateway は置くだけで月額固定費+転送課金が発生する(1台あたり月額数十ドル規模、目安・要確認)
  - なぜ: 小規模案件では「気づいたら固定費が想定超過」の筆頭原因
- 小規模では NAT 不要の設計を検討する: パブリックサブネット+SG で絞る、VPC エンドポイント活用

### DNS

- 権威 DNS はクラウド側(Route 53 / Cloud DNS)に寄せ、レジストラと DNS ホスティングを分離する
  - なぜ: 管理責任が明確になり、切替や移行の自由度が上がる
- TTL 設計と切替手順をセットで文書化する。切替の実行計画は dev-core:migration-cutover-planning へ

### CDN

- CloudFront / Cloudflare 等を「入口の標準装備」として扱う(WAF・DDoS 対策・TLS 終端を兼ねる)
- キャッシュキー設計とパージ戦略を最初に決める
  - なぜ: 決めないと「更新が反映されない」系の障害対応に追われ続ける

### TLS / 証明書

- TLS 1.2 以上(新規は 1.3 優先)。内部通信も原則 TLS
- **証明書は ACM / Let's Encrypt で自動更新を必須とする。手動更新運用は設計として不合格**
  - なぜ: 一人運用の手動更新は必ず失効事故を起こす
- 自動更新+有効期限監視(アラート)まで含めて「設計」と呼ぶ
- HSTS、リダイレクト正規化(http→https、apex→www)までテンプレ化する

## Step 6: 閉域接続の使い分け

まず顧客規程の**原文**を確認し、本当に閉域が要求されているか判定する。
なぜ: 「なんとなく閉域」は VPN+IP 制限+ゼロトラスト型アクセスで代替提案できることが多い(→ dev-core:security-by-design)。

| 手段 | 適する場面 | 注意点 |
|------|-----------|--------|
| Direct Connect(専用線) | 帯域・品質保証が必要な基幹連携 | **回線調達リードタイムが数週間〜数ヶ月(目安・要確認)** |
| Site-to-Site VPN | 安価・即納で閉域相当を始めたい | 品質はベストエフォート |
| PrivateLink | 特定サービスだけを VPC 内に公開 | サービス単位。汎用経路にはならない |

- **回線リードタイムはプロジェクト計画の最初に置く** — なぜ: クリティカルパスとしてスケジュール全体を規定する
- 現実的な段階案: VPN で開始し、Direct Connect へ移行する
- 回線種別・冗長構成・責任分界点・帯域を閉域接続設計書に明記する。責任分界点の交渉は人間の仕事(後述)

## Step 7: ランニングコスト概算

- dev/stg/prod 別の月額概算試算表を **提案段階で** 出す
  - なぜ: 試算なしで高額な構成を納品すると必ず揉める。試算表は見積り根拠と説明責任の道具
- 前提(トラフィック・データ量・リージョン)を明記し、AI にドラフトさせて人間が前提を検証する
- コスト最適化の詳細設計は本スキルの Well-Architected「コスト最適化」柱で扱う（NAT・未使用リソースの棚卸し、試算表と実請求の突合）
- 顧客への提示金額・値付けの判断は本スキルの範囲外 — 自組織の見積・価格判断プロセスに従う

## Well-Architected チェックリスト(3クラウド共通・6本柱)

AWS / Google Cloud / Azure のフレームワークは柱の構造がほぼ共通(Azure は5本柱)。
なぜ共通化するか: チェックリストを一度作れば、顧客指定でクラウドが変わっても流用できる。

- [ ] **運用性(Operational Excellence)**: IaC 化率100%か、デプロイは自動化されているか、変更は追跡可能か
- [ ] **セキュリティ**: 最小権限 IAM か、保存時/転送時暗号化は全リソースで有効か、監査ログは残るか → 詳細は dev-core:security-by-design
- [ ] **信頼性**: マルチ AZ か、バックアップは取れて**リストアを検証した**か → 詳細は dev-core:reliability-sla-design
- [ ] **パフォーマンス効率**: マネージドサービスを優先したか、CDN キャッシュは効いているか
- [ ] **コスト最適化**: NAT・未使用リソースの棚卸しをしたか、試算表と実請求を突合する運用があるか
- [ ] **持続可能性**: 過剰プロビジョニングを避けたか(Azure は本柱なし)

納品時に「Well-Architected レビュー実施済み」を品質エビデンスとして添える。各クラウドの無料レビューツールでセルフレビューを構造化できる。

## AI がやること / 人間にしか決められないこと

### AI がやること

- Terraform/OpenTofu モジュールの生成・リファクタ、既存インフラのコード化(import)
- `plan` 差分の説明、Well-Architected チェックリストとの突合
- CIDR 採番案の生成、VPC/DNS/CDN 一式のコード化、構成図の Mermaid 生成
- TLS 設定のベストプラクティス適用、`dig`/`curl` による疎通検証の実行と解釈
- コスト試算ドラフト、DNS 切替手順書ドラフトとリハーサル(dig での事前検証)

### 人間にしか決められないこと

- **`terraform apply` の実行判断**(特に本番・destroy を伴う変更)
- アカウント設計と資産帰属の決定(名義・契約に直結)
- クラウド選定の最終判断(顧客の政治・既存契約が絡む)
- 閉域要件の要否判断と顧客規程の読み込み
- 回線調達・責任分界点の交渉
- **DNS 切替(不可逆・ダウンタイムを伴う)の実行判断と本番レコード変更の承認**

### 承認ゲートの標準形

1. AI が IaC を書き、CI が tflint + trivy + plan を回し、plan 結果を PR に貼る
2. 人間が差分を読み approve する — これが唯一の apply トリガー
3. DNS 変更・ファイアウォール開放は「不可逆/ライブな一手」として AI の自動実行を禁止。手順書とリハーサルは AI、実行は人間
4. ゲートの設計パターンは ai-engineering:human-in-the-loop-design を参照
