# Operations Design & Handover

**鉄則: 一人で守れる約束だけを書け。監視と一次対応を自動化できない運用設計は、夜間の無償労働の設計図である。**

運用設計は「誰が・何を・どう見て・何が起きたらどう動くか」を決める作業であり、保守契約の原価計算そのもの。
基本設計と並行して開始し、リリース前に運用テストで検証し、検収と同時に保守契約へ接続する。
なぜ: 監視とインシデント一次対応を自動化できれば保守は高利益率のストック収益になり、できなければ納品後の無償サポート地獄になる。

## 設計時に必ず作る成果物

- [ ] 運用設計書（運用体制・役割分担・対応時間帯・エスカレーションフロー）
- [ ] 監視設計書（監視項目・閾値・アラート通知先・ダッシュボード）
- [ ] runbook / 障害対応手順書（アラートごとの一次対応手順）
- [ ] インシデント管理ルール（Sev1〜3 定義・対応目標時間・顧客連絡テンプレート）
- [ ] ポストモーテムテンプレート（§Step 5）
- [ ] 運用引き継ぎ書（顧客側作業と受託側作業の責任分界）
- [ ] 保守契約書別紙（SLA・対応範囲・除外事項・月次報告フォーマット）→ 契約条項の設計・法的レビューは自組織の契約・法務プロセスへ（最終判断は弁護士等の専門家）

## Step 1: プロセスの型を最小実装する（ITIL 4 × SRE）

ITIL 4 は34プラクティスあるが、全部はやらない。次の4つだけを最小実装する。
なぜ: この4つが保守契約の骨格（何が起きたら・どう直し・どう変え・何を約束するか）に1対1で対応し、顧客の情シスとの共通言語にもなる。

| プラクティス | 一人受託での最小実装 |
|---|---|
| インシデント管理 | Sev定義+対応目標時間+runbook+連絡テンプレ（§Step 3, 5） |
| 問題管理 | ポストモーテムで根本原因と再発防止を管理（§Step 5） |
| 変更管理 | 本番変更は PR+CI ゲート経由のみ。緊急変更の事後記録ルールを決める |
| サービスレベル管理 | SLO 計測と月次レポートで達成状況を可視化（§Step 6） |

- SRE で補完する: ITIL が「プロセスの型」、SRE が「エンジニアリングの型」で補完関係。SLO とエラーバジェットで信頼性を運転し、toil（手作業）は自動化する。
- SLO 目標値・エラーバジェットポリシー・DR/RTO/RPO の決め方の正本 → dev-core:reliability-sla-design 参照。

## Step 2: 監視は SLO ベースで設計する

原則: **ユーザー影響があるものだけページ（即時通知）、それ以外はチケット。**
なぜ: 監視の網羅性とアラート疲れは両立せず、一人体制では深夜アラートの疲弊がそのまま事業リスクになる。

- [ ] アラートは閾値（CPU 80% 等）でなく **SLO ベース（バーンレート）** で設計する — 「エラーバジェットをこの速度で消費し続けると SLO を破る」ときだけ起こされる構造にする。
  なぜ: リソース閾値アラートはユーザー影響と相関せず、狼少年化して本物を埋もれさせる。
- [ ] SLO は SLA より厳しく設定し、SLA 違反の前に内部警報が鳴る構造にする。
- [ ] 外形監視（synthetic monitoring）を最低1本入れ、稼働率を自動計測する。
  なぜ: 計測できない SLO は合意していないのと同じ。SLA 違反したかどうか誰にも分からない状態が最悪。
- [ ] 計装は **OpenTelemetry**（メトリクス・ログ・トレースの3本柱）で統一する。
  なぜ: OTel は計装の事実上の標準（目安・2026年時点）で、監視 SaaS を乗り換えてもコードを書き直さずに済む。
- [ ] 監視基盤は自前運用せず **SaaS 監視**（Grafana Cloud / Datadog 等）に載せる。
  なぜ: 監視基盤自体の面倒を見る時間は保守の利益を直接削る。可用性は「外注」して自分の責任範囲を絞る。
- [ ] アラートごとに runbook（一次対応手順）を対で用意する。runbook のないアラートは作らない。
  なぜ: 手順のないアラートは「起こされて考える」を強制し、AI 一次対応（§Step 4）にも渡せない。

## Step 3: Severity と対応時間を契約に紐付ける

重要度を定義し、保守契約の対応時間と1対1で紐付ける。
なぜ: Sev 定義は「全部緊急」を防ぐ防波堤であり、対応時間の約束は保守料金の根拠になる。

| Sev | 定義 | 一次応答目標（テンプレ） | 対応時間帯（テンプレ） |
|---|---|---|---|
| Sev1 | 全停止・データ損失・全ユーザー影響 | 即時（例: 1時間以内） | 営業時間内+時間外はベストエフォート |
| Sev2 | 主要機能の一部停止・回避策あり | 例: 営業時間内4時間以内 | 平日 9-18時 |
| Sev3 | 軽微な不具合・問い合わせ | 翌営業日 | 平日 9-18時 |

- [ ] 対応時間は「平日9-18時、Sev1 のみ時間外ベストエフォート」のような **一人で守れる約束** から始める。
  なぜ: 一人受託が 24/365 対応を SLA に書くのは自殺行為。守れない約束は信頼と利益を同時に失う。
- [ ] 24/365 が必要な顧客には、マネージドサービス+自動復旧+AI一次対応（§Step 4）または外部一次受けの組み合わせで提案する。
- SLA条項の4点セット設計（対応時間帯・免責・補償上限・計測方法）と稼働率目標そのものの決め方 → dev-core:reliability-sla-design Step 8 が正本。保守料金の設定 → 自組織の見積・価格判断プロセスへ。

## Step 4: AI 一次対応の線を引く

AI エージェントに本番運用のどこまでを許すかは、運用設計の新しい設計項目である。運用設計書に権限の線を明文化する。
なぜ: AI の一次トリアージは実用域にあり（目安・2026年時点）、一人受託が「疑似24時間運用」を売れる転換点になったが、線を引かずに導入すると本番事故の作り方になる。

| 権限レベル | 許す操作 | 例 |
|---|---|---|
| read-only | ログ・メトリクス・トレースの横断調査、原因仮説の提示、Sev 判定案 | アラート一次トリアージ |
| 承認付き書き込み | 人間の承認を経て実行する変更操作 | スケール変更、設定変更 |
| 自動実行 | runbook 化済み・冪等・影響が限定された定型復旧のみ | 再起動、ジョブ再実行 |

- [ ] **本番環境への破壊的操作の承認は必ず人間が行う**。この一線は動かさない。
- [ ] 自動実行を許す操作は runbook に手順・前提・ロールバックが書かれているものに限定する。
  なぜ: AI に渡せる粒度まで手順を書けていない操作は、人間がやっても事故る操作である。
- 承認ゲート・監査ログの設計の正本 → ai-engineering:human-in-the-loop-design 参照。

## Step 5: インシデント対応とポストモーテム

対応フロー: 検知 → Sev 判定 → 一次対応（runbook）→ 顧客連絡（Sev1〜2）→ 復旧 → ポストモーテム。

- 根本原因の調査手順そのもの → dev-core:debug 参照（4フェーズ根本原因分析）。
- [ ] ポストモーテムは **ブレームレス** で行う — 「誰が悪いか」ではなく「なぜシステムがそのミスを許したか」を問う。
  なぜ: 個人を責める文化では情報が隠れ、根本原因に到達できない。
- [ ] Sev1〜2 の発生後 **24〜72時間以内** に実施する。
  なぜ: 記憶とログが新しいうちでないとタイムラインの精度が落ち、遅い報告は顧客の不信を育てる。
- [ ] テンプレートの構成: **概要 / 影響（誰に・何分・何件）/ タイムライン / 根本原因 / 再発防止アクション（担当・期限付き）**。
- [ ] 顧客向け障害報告書はポストモーテムを整形して共有する。誠実な根本原因分析は信頼を増やし、隠蔽・言い訳は契約を失う。
  なぜ: 障害報告書の品質は保守契約の更新率に直結する。障害対応は最大の営業機会でもある。
- [ ] 再発防止アクションを仕組み（テスト・ガードレール・監視項目）に落とす → dev-core:continuous-learning 参照。

## Step 6: 月次運用レポートを1枚で出す

毎月1枚、以下のフォーマットで報告する。
なぜ: 順調な時期ほど保守の価値が見えず「何もしてないのに払っている」と解約される。「見えない仕事」の可視化が保守契約の生命線。

```markdown
# 運用レポート YYYY年MM月 — <システム名>

## サービスレベル
- 稼働率: 99.9x %（SLO: 99.9 % — 達成 / 未達、エラーバジェット残: ◯分）
- 外形監視の応答時間: p95 ◯ms（先月比 ±◯）

## インシデント
- 件数: ◯件（Sev1: ◯ / Sev2: ◯ / Sev3: ◯）
- 主要インシデントの概要と対応（障害報告書へのリンク）

## 実施した改善・変更
- （例: 依存ライブラリ更新◯件、スロークエリ改善、バックアップリストア訓練）

## ランニングコスト
- 今月実績と前月比（±の主要因を1行で）

## 翌月の予定・推奨事項
- （例: 証明書更新、負荷試験の再実行、改善提案）
```

- 定例報告の運営・顧客コミュニケーション → delivery-core:pm-delivery 参照。

## Step 7: 負荷試験（k6）を運用に組み込む

負荷試験はリリース前の一回きりで終わらせず、保守フェーズの資産にする。

- [ ] 対象は **2点に絞る**: 「最も重い業務」（月末バッチ・締め処理）と「最も多いアクセス」（トップ/検索）。
  なぜ: 全画面の負荷試験は一人受託では過剰投資。事故が起きるのはほぼこの2点である。
- [ ] k6 スクリプトを納品物に含め、**再実行可能** な状態で引き継ぐ。
  なぜ: 構成変更・データ増加・ライブラリ更新のたびに同じ物差しで回帰確認でき、保守フェーズの資産になる。
- [ ] CI に組み込むか、月次・四半期の定期実行を運用設計書に載せる → パイプラインへの組み込みは dev-core:cicd-release-design 参照。
- [ ] **本番環境への負荷試験の実行承認は必ず人間が行う**。
  なぜ: 課金・障害リスクがあり、AI の自動実行に含めてはならない操作の典型。

## Step 8: 運用引き継ぎと保守フェーズ移行

- [ ] 引き継ぎ完了条件は「**顧客側担当者が手順書だけでリストア/再起動を実演できること**」に設定する。
  なぜ: 手順書が「書いた本人しか分からない」のが引き継ぎの典型失敗。実演がドキュメント品質の唯一の証明になる。
- [ ] 無償保証（契約不適合対応）と有償保守の境界を、**検収時に文書で合意** する。
  なぜ: ここが曖昧だと納品後の全問い合わせが無償化する。境界の条項化は自組織の契約・法務プロセスへ（最終判断は弁護士等の専門家。目安・2026年時点の実務、要確認）。
- [ ] 責任分界（顧客側作業/受託側作業/クラウド事業者責任）を運用引き継ぎ書に明記する。経産省「情報システム・モデル取引・契約書」の保守運用フェーズが出発点として使える（目安・2026年時点、最新版を要確認）。
- [ ] バックアップの引き継ぎは「リストア成功の証跡」をもって完了とする。
  なぜ: 取っているだけのバックアップは、いざという時に復元できないことが最頻出の失敗。
- 移行・カットオーバー計画（新旧切替そのもの）→ dev-core:migration-cutover-planning 参照。
- 検収・完了合意の進め方 → delivery-core:client-alignment 参照。

## AI がやること / 人間にしか決められないこと

| AI に任せてよい | 人間にしか決められない |
|---|---|
| アラートの一次トリアージ（ログ・メトリクス横断調査と原因仮説の提示） | Sev1 の顧客コミュニケーション（謝罪と説明は人間の仕事） |
| runbook の生成と、承認範囲内での実行（§Step 4 の線の内側） | 本番環境への破壊的操作・負荷試験実行の承認 |
| 監視設定・ダッシュボード・SLI 計測クエリのコード生成 | SLO 目標値と SLA 条項の決定（＝事業リスクの引き受け） |
| ポストモーテムのタイムライン起こし・報告書草案 | 再発防止策の投資判断と、顧客への説明 |
| 月次運用レポートの草案生成 | SLA・保守料金の改定交渉（→ 自組織の見積・価格判断プロセスへ） |
| k6 シナリオ生成と試験結果の一次分析 | AI に許す操作範囲（§Step 4 の線）の決定そのもの |

なぜこの分担か: AI は「調査・生成・一次分析」を担えるが、約束（SLA）を守れるかは受託者本人の稼働体制の問題であり、リスクの引き受けと顧客への謝罪は代行できない。

## よくある失敗チェック

- [ ] 手順書が書いた本人しか分からない → 完了条件を「顧客が実演できる」にしたか（§Step 8）
- [ ] 無償保証と有償保守の境界が曖昧 → 検収時に文書合意したか（§Step 8）
- [ ] 月次報告がなく順調な時期に解約される → 1枚レポートを毎月出しているか（§Step 6）
- [ ] アラートが多すぎて本物を見逃す → ページ対象を「ユーザー影響のあるもの」に絞ったか（§Step 2）
- [ ] SLA を謳いながら SLI 計測がない → 外形監視で稼働率を自動計測しているか（§Step 2）
- [ ] runbook のないアラートがある → アラートと一次対応手順が1対1か（§Step 2）
- [ ] ポストモーテムが犯人捜しになっている → 「なぜシステムが許したか」を問うたか（§Step 5）

## 境界（このスキルが正本でないもの）

- SLO/SLA 目標値・エラーバジェット・DR/RTO/RPO 設計 → dev-core:reliability-sla-design
- デプロイ戦略・ロールバック・リリース手順 → dev-core:cicd-release-design
- 障害の根本原因調査の手順 → dev-core:debug
- 再発防止の学習メカニズム → dev-core:continuous-learning

- 移行・カットオーバー・切り戻し → dev-core:migration-cutover-planning
- 保守契約の条項設計・法的レビュー → 自組織の契約・法務プロセスへ（最終判断は弁護士等の専門家）
- 顧客への定例報告・合意形成の運営 → delivery-core:pm-delivery / delivery-core:client-alignment
