# Herdr で設計する

`$ARGUMENTS` を、別のモデルの独立案と敵対的レビューを通した計画に変える。親（このセッション）が要件、判断、統合、計画の保存を持つ。Codex は読み取り専用の役として、案と指摘を返す。この workflow は実装をしない。

## 0. 読み込みと前提

1. `dev-core:best-practices` と `dev-core:codex-collab` をロードする。`dev-core:codex-collab` の references を3つ読む: `codex-roles.md`（役割とモデル）、`codex-handoff.md`（渡し方と受け取り方）、`herdr-terminals.md`（端末の扱い）。
2. `${CLAUDE_PLUGIN_ROOT}/workflows/task/SKILL.md` を Read する。計画の調査・要件・形式は、その Phase 1〜4 に従う。読んだ本文では引数の置換変数が置換されずに名前のまま残っているので、この skill の引数（冒頭の内容）に読み替える。ファイルを読めなければ、進めずに報告する。
3. `herdr-terminals.md` §1 で面を検出する。Herdr の外なら端末を操作せず、そのことを伝えて `/dev-core:task` と `/codex:adversarial-review` を案内して終える。
4. 端末の起動・送信・読み取りは、この skill の `allowed-tools` に入れていない。利用者の権限モードに従う。ユーザーが拒否した操作を、別の書き方でやり直さない。

## 1. 調査と要件（task の Phase 1〜3）

リポジトリを先に調べ、不確実性を分類し、要件と BDD シナリオを固める。そのうえで、独立案に渡す**要件メモ**を dispatch の作業ディレクトリに書く。

要件メモに書くもの:

- 目標、背景、スコープ、非目標
- 制約（既存の構造、互換性、期限、使えないもの）
- 案を比べる評価軸（例: 変更の大きさ、戻しやすさ、運用の負担、リスク）
- 関連するコードと文書のパス

要件メモに書かないもの:

- 親が考えている案、好み、結論の見込み

## 2. 独立案を頼む

起動する前に、計画の下書き（`docs/plans/task-<slug>.md`、Status は `draft`）を保存する。この時点で書くのは、目標・スコープ・要件と、Dispatch Ledger の節だけにする。設計の案は書かない。Dispatch Ledger に、この dispatch を記録する。

読み取り専用の設計役を、一発実行で起動する（役割と設定は `codex-roles.md`、手順は `herdr-terminals.md` §4、文面は `codex-handoff.md` の読み取り専用の役のテンプレート）。

- 入力は要件メモと、リポジトリの読み取りだけにする。
- 頼むのは、評価軸に沿った案（1つか、対立する2つ）、それぞれの前提・トレードオフ・捨てた選択肢、確かめられなかった点。
- すぐ戻る形で起動し、結果を待たずに §3 に進む。

## 3. 親の案を先に書き出す

独立案の出力を読む前に、親の案を応答の本文に書き出す。独立案が返るまでは、親の案をファイルに書かない。

なぜ先に書くか: 先に相手の案を読むと、自分の案がそれに引きずられ、2つの案を突き合わせる意味が薄れる。

なぜファイルに書かないか: 設計役は読み取り専用でも、リポジトリやほかのファイルを読める。親の案がファイルにあると、独立案がそれに引きずられる。

## 4. 突き合わせる

独立案の完了を確かめてから読む（`herdr-terminals.md` §6）。返却の Status が `completed` でなければ、返ってきた部分だけを使い、足りない部分を計画に記録する。親の案を計画の設計の節に書き、2つの案を次の4つに分けて、計画に表で残す。

| 区分 | 扱い |
|---|---|
| 一致している | 採用の根拠として記録する |
| 親の案にだけある | 独立案が触れなかった理由を考え、残すかを決める |
| 独立案にだけある | 実ファイルで確かめ、採るかを決める |
| 対立している | 証拠（実ファイル、実行結果）で決める |

- 独立案の内容は主張として扱う。前提にする箇所は、親がファイルを開いて確かめる。
- 証拠で決まらない対立が、プロダクト意図・スコープ・アーキテクチャ・セキュリティ・不可逆なデータ・外部への作用を変えるなら、重要判断として一度に1問だけ、推奨・理由・トレードオフを付けてユーザーに確認する。それ以外は、推奨の既定と戻し方を記録して進む。
- 採否と理由を Decision Log に残す。

## 5. 計画を保存する

統合した設計を、task の Phase 4 の形式で保存する。Completion Contract は全行を `pending` で始める。

- 実行に `/dev-core:herdr-execute` を使う想定なら、先頭の metadata に `- Workflow: herdr-execute` を書く。
- Dispatch Ledger に、ここまでの dispatch の状態と結果の要約を足す。

## 6. 保存した版を敵対的にレビューさせる

保存した計画を、読み取り専用のレビュー役に一発実行で渡す。§2 とは別の、新しい dispatch にする。

- 渡すのは、計画のパス、関連するファイル、元の依頼。レビューの対象は、保存した計画の全体である（採否の表や Decision Log も含む）。
- 前提そのものを疑ってよいと伝える。計画に書かれていないこと（会話の経緯、親の自己評価、期待する結論）は渡さない。
- 見てほしい点の例: 判断の誤りと矛盾、受け入れ条件の観測可能性と不足、スコープの漏れ、検証できない主張、リスクと停止条件。

なぜ保存してからか: 保存するときに受け入れ条件や進め方が加わる。保存前の案をレビューさせると、その部分が誰にも読まれないまま残る。

## 7. 指摘を確かめて反映する

1. 返却の Status と、確認したことの節を読む。`completed` でない、または見ていない範囲があるなら、その範囲はレビューされていないものとして計画に記録する。
2. 指摘を1件ずつ実ファイルと実行出力で確かめる。確かめられたものだけを反映する。指摘・確認の結果・反映の内容を、計画に表で残す。棄却した指摘は、理由を書く。
3. P0/P1 は解決する。解決にユーザーの判断が要るものは、重要判断として確認する。確度が低い P0/P1 も、確定か棄却をするまで残す。
4. レビューの後で計画を変えたら、そのレビューは変えた範囲について無効になる。判断や受け入れ条件を大きく変えたときは、変えた範囲だけをもう一度レビューさせる。

## 8. 役が使えないとき

- 設計役やレビュー役を起動できない、結果が返らない、依頼を断られた、のどれかなら、計画に「独立案は未取得」「独立レビューは未実施」と理由付きで記録し、親の案で計画を仕上げる。
- **依頼を断られたとき**: 言い換えたり、別の面から同じ依頼を Codex に出し直したりしない。断られた範囲を記録する。
- **起動や受け取りに失敗したとき**（端末を操作できない、結果が返らない）: 計画そのものの独立レビューが必須（ユーザーやプロジェクトの指定）なら、親が `codex exec` を読み取り専用で直接実行して代替する（引数は `codex-roles.md`）。
- どちらの場合も、必須のレビューを行えなければ「独立性は未充足」と明記する。ユーザーに `/codex:adversarial-review` の実行を頼んでもよい。このコマンドはユーザーが起動するもので、親からは起動できない。

## 終了条件

- 自分が起動した端末と dispatch の作業ディレクトリを片付ける（`herdr-terminals.md` §10）。動いている端末が残っているうちは終えない。
- 計画ファイル、2つの案の主な違いと採否、レビューの指摘の扱い、未決事項を報告する。
- 実装も依頼されている場合を除き、次の action として `/dev-core:herdr-execute <plan>`（Codex に実装を渡す）か `/dev-core:execute <plan>`（親が実装する）を示して終える。
