# Systematic Debugging

**鉄則: NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST**

修正を提案する前に、必ず根本原因を特定すること。

**複雑な問題で複数の視点が必要な場合は `/dev-core:debug-team` を使用してください。**

## Phase 1: 収集 🔍

問題の情報を体系的に収集する:

1. **症状の明確化**: 何が起きているか、何が期待される動作か
2. **再現手順**: どうすれば再現するか（必ず再現を確認）
3. **エラーログ**: 完全なエラーメッセージとスタックトレース
4. **最近の変更**: `git log --oneline -10` と `git diff` で直近の変更を確認
5. **影響範囲**: どのファイル/機能に影響するか
6. **発生頻度**: 常に/時々/特定条件で

## Phase 2: 仮説 💭

収集した情報から **3つの独立した仮説** を立てる:

```
仮説1: [具体的な原因の推測]
  検証方法: [どうすれば確認できるか]
  確認すべきファイル: [関連するコード]

仮説2: [別の原因の推測]
  検証方法: [どうすれば確認できるか]

仮説3: [さらに別の原因の推測]
  検証方法: [どうすれば確認できるか]
```

仮説は互いに独立していること。最も可能性が高い順に並べる。

## Phase 3: 検証 🧪

各仮説を順に検証する:

1. **支持する証拠** を探す
2. **反する証拠** も必ず探す（確証バイアス対策）
3. 証拠が見つかったら記録する
4. 仮説が棄却されたら次の仮説へ
5. 全仮説が棄却された場合は Phase 1 に戻り情報を追加収集

**証拠なしに結論を出さないこと。**

## 3回失敗ルール（Three Strikes Rule）

**修正の試行が3回連続で失敗したら、STOP。**

4回目の修正を試みてはならない。代わりに:

1. **立ち止まる** — 同じアプローチの繰り返しは時間の浪費
2. **アーキテクチャを疑う** — 3回失敗は「修正方法が間違っている」のではなく「問題の理解が間違っている」兆候
3. **ユーザーに報告する**:
   ```
   ⚠️ 3回修正を試みましたが解決できません。
   
   試行1: [何を試みたか] → [なぜ失敗したか]
   試行2: [何を試みたか] → [なぜ失敗したか]
   試行3: [何を試みたか] → [なぜ失敗したか]
   
   推測される根本的な問題:
   - [アーキテクチャレベルの問題仮説]
   
   推奨: 設計レベルの見直しが必要です。
   ```
4. **判断を委ねる** — 設計変更の是非はユーザーが決定する

## Phase 4: 修正 🔧

根本原因が特定されたら:

1. **原因の報告**: 根本原因、影響範囲、修正方針をユーザーに報告
2. **TDDで修正**: `/dev-core:tdd` へハンドオフ
   - まず失敗するテストを書く（バグを再現するテスト）
   - 修正を実装
   - テストがグリーンになることを確認
   - **3回失敗したら上記ルールに従い STOP**
3. **再発防止**: continuous-learning スキルに従い、防止メカニズムを構築

## 出力形式

```
【Phase 1: 収集】
症状: [症状の説明]
再現手順: [手順]
直近の変更: [関連する変更]

【Phase 2: 仮説】
1. [仮説1] — 可能性: HIGH
2. [仮説2] — 可能性: MEDIUM
3. [仮説3] — 可能性: LOW

【Phase 3: 検証】
仮説1: ❌ 棄却（[反する証拠]）
仮説2: ✅ 確認（[支持する証拠]）

【Phase 4: 根本原因】
原因: [根本原因の説明]
影響範囲: [影響するファイル/機能]
修正方針: [修正アプローチ]

→ /dev-core:tdd で修正を実装しますか？
```
