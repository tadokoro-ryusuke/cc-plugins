# Org Change Enablement — 導入を「使われる」まで運ぶ

**鉄則: 稼働開始は導入の終わりではなく定着の始まり。「配布して終わり」を作らない。**

導入失敗の主因は技術ではなく人と組織にある(BCG の 10-20-70 原則: アルゴリズム10%・技術とデータ20%・人と業務プロセス70%。AI変革研究由来だがシステム導入一般に通じる)。
予算・工数・計画の重心を「人と業務プロセス」側に置くこと。
なぜ: ツールが動いても業務が移らなければ、投資は「導入したのに使われない」棚卸資産になるだけだから。

- 技術面のカットオーバー(データ移行・切替方式・ロールバック) → dev-core:migration-cutover-planning
- 発注者・顧客との合意形成やキックオフ運営 → delivery-core:client-alignment
- 導入プロジェクト自体のPM運営・変更管理 → delivery-core:pm-delivery

## 分担線: AIがやること / 人間にしか決められないこと

着手前にこの線を確認し、右列の判断を勝手に代行しないこと。
なぜ: チェンジマネジメントは本質的に信頼のビジネスであり、AIは文書量産と分析で支える側に回るのが正しい配置だから。

| AI(このスキルの実行者)がやること | 人間にしか決められないこと |
|---|---|
| ステークホルダー別コミュニケーション文面の生成(経営向け/管理職向け/現場向けの翻訳) | 抵抗の裏にある政治的事情の察知、キーパーソンとの1on1 |
| 想定反対意見と返し方のFAQ(抵抗対応プレイブック)の網羅的ドラフト | 「この部門は今は触らない」という撤退・順序の判断 |
| アンケート自由記述の分類・ADKAR段階への仕分け | 診断結果を踏まえた施策の優先順位と重み付けの合意形成 |
| 研修教材・演習課題・SOP・マニュアルのドラフト生成と差分更新 | チャンピオンの人選、評価制度への組み込みの決定 |
| 利用率・業務指標の集計、未利用部門の検出、定着レポート生成 | 経営層への耳の痛い進言、旧システム停止の最終判断 |
| 事例共有記事・社内報のドラフト | 現場との信頼構築、抵抗者との対話そのもの |

## Step 0: 変革の骨格を敷く — Kotter で全体戦略、ADKAR で個人診断

2つのフレームワークを役割固定で併用すること(実務の定番)。
なぜ: Kotter は組織レベルのロードマップ、ADKAR は個人レベルの詰まり診断で、守備範囲が違うから。

- **Kotter の8段階** = 全体戦略・計画書の骨格に使う: 危機感の醸成 → 変革推進チーム → ビジョン → 周知 → 障害除去 → 短期成果 → 加速 → 定着。
  - 第6段階「短期成果(Quick Win)」を計画に明示的に置く。なぜ: 小さな成功の実績が本命施策の予算と協力を引き出すから。
- **ADKAR** = 個人の詰まり診断に使う: Awareness(なぜ変わるか) → Desire(変わりたい) → Knowledge(やり方を知る) → Ability(できる) → Reinforcement(定着)。
  - 「研修したのに使われない」は Knowledge ではなく Desire の問題、と段階で切り分ける。なぜ: 詰まっている段階が違えば打ち手が全く違うから(Desire 不足に追加研修は効かない)。

| 症状 | 詰まり段階 | 打ち手 |
|---|---|---|
| 「なぜ変えるのか聞いていない」 | Awareness | 変革ストーリーの発信、経営層の口から語る |
| 「自分には関係ない/損だ」 | Desire | WIIFM(本人のメリット)への翻訳、抵抗対処(Step 1) |
| 「やり方が分からない」 | Knowledge | 研修・SOP(Step 2, 3) |
| 「研修は受けたが実務でできない」 | Ability | 実践課題・伴走・練習会(Step 2) |
| 「一度使ったが元に戻った」 | Reinforcement | 定着測定・チャンピオン・表彰(Step 4, 5) |

- 顧客支援の場合、顧客側に**変革オーナー**を必ず立てさせること。オーナー不在の導入定着案件は受けない。
  なぜ: 外部支援者は設計とコーチングはできるが、組織内の決定と号令は内部の人間にしかできないから。

## Step 1: ステークホルダーマップを作り、抵抗に対処する

### 1-1. 影響度×賛否の4象限マップ

全ステークホルダーを「影響度(高/低)×賛否(賛成/反対)」でマッピングし、キーパーソンを特定する。

| 象限 | 方針 |
|---|---|
| 影響大×賛成 | 変革推進チーム・スポンサーに引き込み、その口から語らせる |
| 影響大×反対 | 最優先で個別対応。懸念を聞き取り、業務再設計に反映する |
| 影響小×賛成 | チャンピオン候補(Step 4)。事例の初期供給源にする |
| 影響小×反対 | 初期リソースを使わない。マジョリティが動けば追従する |

- 人選と初期投資はアーリーアダプター層に寄せ、ラガード(最後発層)の説得に序盤の時間を使わないこと(ロジャーズの普及理論)。
  なぜ: 普及は層の順に伝播するもので、最も硬い層から攻めるのは資源配分として最悪だから。

### 1-2. 中間管理職を最初に味方にする

現場より先に、中間管理職との合意セッションを入れること。順序を守る。
なぜ: 現場は上司の顔色で行動する——管理職が「新システムで部下の工数が浮くと自部門の人員が削られる」と考えた瞬間、全てが止まるから。

1. 管理職だけを集め、業務がどう変わるかを先に開示する
2. 「浮いた工数で何をやるか」を管理職自身に決めさせ、文書で合意する
3. 部下への説明は管理職の口から行わせる(伝達物は用意してよい)

### 1-3. 抵抗の3類型と対処

抵抗を「遅れた人の感情」と扱わないこと。**抵抗は情報である**——業務理解が深い人ほど具体的な懸念を持つ。
なぜ: 抵抗者を敵に回すと、最も価値ある業務知識の持ち主を失うから。

| 類型 | 中身 | 対処 |
|---|---|---|
| 雇用不安 | 「自動化・新システムに仕事を奪われる」 | 「なくなるのはタスクであり職ではない」を具体的な業務再設計(浮いた時間の使い道)で示す |
| スキル不安 | 「使いこなせない自分を晒したくない」 | 心理的安全性のある少人数練習会、失敗共有の場を公式に設ける |
| 品質不信 | 「新システムの出力・結果は信用できない」 | 人間の確認を残す業務フローを明示し「最終判断は人間」を制度化する。並行稼働・段階移行で実績を見せる |

- AIを含むシステムで人間の確認点を業務フローに設計する場合 → ai-engineering:human-in-the-loop-design
- 全ての伝達物は **WIIFM**(What's In It For Me)で書く。「会社の生産性向上」ではなく「あなたの残業が減る」に翻訳する。
  なぜ: 人は組織の目標ではなく自分の損得で動くから。
- 展開方針は**ハイブリッド**にする: 利用環境と安全なデフォルトはトップダウンで整備し、活用方法の発見はボトムアップで表彰する。
  なぜ: 強制(全員必須・KPI化)だけでは面従腹背を生み、自発だけでは一部しか使わないから。
  ただし**利用が裁量的なツール**(補助的な生産性ツール等)では、使わない選択肢が常に残るため Desire と体験価値の設計に重心を置く。
  **利用必須の基幹システム**(業務がそこでしか回らないもの)では利用自体は強制で入るぶん、重心は Desire 対策(納得と WIIFM)と**例外時SOP**(Step 3)へ移る。
  なぜ: 後者で定着を壊すのは「使うかどうか」ではなく、例外に遭遇したときの旧手順回帰と不満の蓄積だから。

## Step 2: 教育を「イベント」ではなく「プログラム」にする

単発研修で終わらせないこと。効果は2週間程度で消える(目安)。必ず4点セットで設計する。
なぜ: 学習の大半は座学ではなく実務経験と他者からの学びで起きるから(70:20:10 モデル — 実務70%・他者20%・座学10%)。

1. **研修** — 階層別に分ける(経営層: 短時間で判断材料 / 管理職: 業務再設計と部下の評価 / 実務者: ハンズオン)。全員に同じ研修は最頻の失敗。
   実務者研修は必ず**受講者自身の実業務データ・実画面**で演習する。なぜ: 汎用例題は翌日忘れられるから。
2. **実践課題** — 研修後2週間、実業務での適用課題を出す。なぜ: 70% の学びはここで起きるから。
3. **フォローアップ会** — 課題のつまずきを回収し、個別に解消する。なぜ: Ability の詰まりはここでしか見えないから。
4. **事例共有会** — 成功事例を本人の口から共有させ、表彰する。なぜ: ピア(同僚)経由の普及はトップダウン研修より定着率が高い(約2倍とされる・目安)から。

- 効果測定は**研修前に**仕込む: 受講前に利用頻度・自己効力感のアンケートを取る。なぜ: ベースラインがないと効果を示せないから。
- 測定指標は「研修満足度」ではなく「4週間後の利用率・業務での適用数」にする(Step 5)。

## Step 3: SOP・マニュアルを役割別・例外込みで整備する

### 型(構成の指針)

- **役割別に分冊する**: 一般利用者 / 承認者・管理職 / システム管理者 / 例外対応担当。なぜ: 全員向けの分厚い1冊は誰も読まないから。
- **1手順1トピック**で書く: 目的1行 → 前提 → 手順 → よくあるつまずき → 例外時の連絡先。
- **例外・異常系を必ず含める**: システム停止時の代替手順(手作業フォールバック)、差し戻し・修正のフロー、移行期間中の新旧併用ルール。
  なぜ: 現場が旧手順に回帰するのは、例外に遭遇してマニュアルが答えをくれなかった瞬間だから。
- 具体例は**自組織の実業務・実データ**で書く。雛形の汎用例のままでは判断に使えない。
- 禁止・制限事項は「ツール名」ではなく「用途・情報の種類」で書く(例: 社外秘情報の入力可否は、製品名ではなく情報区分で規定する)。なぜ: ツールで書くと新ツールのたびに改訂が要るから。
- 文書のレイアウト・可読性の設計 → design-core:business-doc-design

### 鮮度維持の仕組み

作って配布して終わりが最頻の死因。文書と同時に更新の仕組みを作ること。

- [ ] 文書ごとに**オーナー1名**を明記する(組織名でなく役割・氏名)
- [ ] **次回見直し日を文書自体に書き込む**(半年ごとが目安)。なぜ: 期日が文書の外にあると誰も思い出さないから
- [ ] システムの変更管理と連動させる: リリース・設定変更のたびに SOP 差分更新をチェック項目に入れる
- [ ] 問い合わせログ・FAQ を改訂の入力にする。なぜ: 質問が多い箇所 = 文書が答えられていない箇所だから
- [ ] 旧版は撤去する(アーカイブへ移動)。新旧が並ぶと旧が使われ続ける

## Step 4: チャンピオン制度を設計する

各部門のアーリーアダプターを「同僚への伝道者」として公式化する。Train-the-Trainer(期間限定の講師養成)ではなく、**継続的な実践コミュニティ**として設計すること。

- **選定**: 公募+上長推薦の併用。基準は役職ではなく「新しいやり方を試し、人に教えるのが好きか」。
- **公式な時間確保**: 業務時間の10〜15%を公式に割り当て、評価に組み込む(目安)。
  なぜ: 任命だけして時間を確保しないと通常業務に埋没する——制度の死因第1位だから。
- **定例**: 月次のチャンピオン会(横のつながり・事例交換)+ 四半期の経営報告(成果の可視化)。
  なぜ: 横のつながりがないと孤立し、経営層が成果を見に来ないと士気が続かないから。

チャンピオン制度の死因チェック:

- [ ] 活動時間が公式に確保されているか(任命だけになっていないか)
- [ ] チャンピオン同士が定期的に会う場があるか
- [ ] 経営層が四半期に一度、成果を直接聞く場があるか

## Step 5: 定着を測る — 満足度ではなく利用率と業務指標

「研修満足度が高い」「稼働した」は定着の証拠にならない。**4週間後に測る**こと。
なぜ: 直後の数字は新規性効果で膨らみ、元に戻るかどうかは数週間経たないと分からないから。

3層で測り、経営報告は業務指標を主役にする:

| 層 | 指標例 | 用途 |
|---|---|---|
| 利用指標 | 週次アクティブ率、**4週間後利用率**、部門別利用率 | 定着の早期警報。未利用部門の特定 |
| 業務指標 | 処理件数、リードタイム、エラー率・手戻り率 | 経営報告の主役。導入前ベースラインとの比較 |
| 財務指標 | コスト削減・売上影響 | 参考値に留める |

- 「削減時間×時給」の換算は過大評価になりやすい。なぜ: 削減された時間が価値ある業務に再配分される保証がないから。使うなら前提を明示する。
- ベースライン(導入前の業務指標)は**移行前に**取得しておく(Step 6 チェックリスト)。
- 定着(Reinforcement)工程を最初から予算化すること。なぜ: 予算がないと3ヶ月で元に戻る——最も多い失敗だから。
- 利用率が低い部門を見つけたら、ADKAR 診断(Step 0)に戻って詰まり段階を特定してから打ち手を選ぶ。

## Step 6: カットオーバー前後の業務移行チェックリスト

技術面(データ移行・切替方式・リハーサル・ロールバック)→ dev-core:migration-cutover-planning。ここでは**業務・人の側**の移行を扱う。

### カットオーバー前

- [ ] 新旧業務フロー対比表を作成した(どの業務がどう変わるか・消える業務・新たに増える業務)
- [ ] 役割別 SOP を配布し、対象者の研修完了率を確認した
- [ ] 例外時・障害時の代替手順(手作業フォールバック)を現場と合意した
- [ ] 問い合わせ窓口・FAQ・チャンピオン体制が初日から稼働する状態にした
- [ ] 並行稼働または旧システム参照期間の**終了日**を決めて周知した。なぜ: 終了日のない併用は永遠に続くから
- [ ] 定着KPIのベースライン(移行前の業務指標)を取得した
- [ ] 初日のトラブルを想定した現場向けアナウンス文面を準備した

### 直後〜2週間(ハイパーケア)

- [ ] 問い合わせに即応する体制を敷き、つまずきを日次で収集・分類している
- [ ] 利用率を日次/週次でモニタし、未利用者・未利用部門を特定している
- [ ] 旧手順への回帰(表計算での並行管理・旧システムの残存利用等)を検出し、原因を聞き取っている。なぜ: 回帰は怠慢ではなく、新フローの欠陥を教えてくれる情報だから
- [ ] 収集したつまずきを SOP・FAQ に日次で反映している

### 4週間後

- [ ] 4週間後利用率・業務指標をベースラインと比較し、報告した
- [ ] 低定着の部門・個人を ADKAR で診断し、追加施策(練習会・業務再設計・SOP改訂)を打った
- [ ] 事例共有会を開催し、成功事例を横展開した
- [ ] 旧システム停止の判断材料を揃えて提示した(停止の最終判断は人間が行う)

## アンチパターン早見表

| アンチパターン | なぜ失敗するか | 対応する Step |
|---|---|---|
| キックオフだけ盛大で後続コミュニケーションがない | 変革は一度の号令では伝播しない | Step 0, 1 |
| 抵抗者を「遅れた人」と扱い敵に回す | 業務知識の深い懸念という情報を失う | Step 1 |
| 全員に同じ単発研修 | 階層で必要な内容が違い、単発は2週間で消える | Step 2 |
| マニュアルが汎用例のみ・例外なし | 例外に遭遇した瞬間、現場は旧手順に戻る | Step 3 |
| チャンピオンを任命だけして時間を渡さない | 通常業務に埋没して制度が形骸化する | Step 4 |
| 満足度アンケートで定着を宣言 | 使われているかは利用率と業務指標でしか分からない | Step 5 |
| 定着工程を予算化しない | 3ヶ月で元に戻る | Step 5 |
| 旧システム併用の終了日を決めない | 併用が永続し、移行が完了しない | Step 6 |
