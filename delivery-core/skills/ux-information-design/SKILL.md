# UX設計と情報アーキテクチャ

**鉄則: 検証(テスト)を削るくらいなら生成(ドキュメント)を削る。**

このスキルの目的は、**利用者個人がプロダクトをどう体験するか**(UX)と
**ユーザーが情報を見つけ、理解できる構造**(IA)を設計・検証すること。
受託では要件定義〜外部設計の間に位置し、「発注者が満足したのにエンドユーザーが使えないシステム」
という受託最大の失敗パターンをここで防ぐ。
国際規格上の裏付けは ISO 9241-210(人間中心設計プロセス)。公共系案件では準拠を求められることもある(2026年時点の目安・要確認)。

境界(重複させない):

- 業務フロー・サービスブループリント・システム化範囲の線引き → `delivery-core:business-service-design` 参照
- 要件定義プロセスそのもの → `delivery-core:requirements-definition` 参照
- ワイヤーフレーム・画面仕様・APIの具体化 → `dev-core:external-design-deliverables` 参照
- ビジュアルデザインの評価 → `design-core:design-review` 参照
- ユビキタス言語の用語集・コンテキスト境界(正本) → `delivery-core:domain-modeling-strategic` 参照
- DDD の戦術的設計・実装パターン → `dev-core:best-practices` 参照

## 全体フロー

1. **ダブルダイヤモンドで工程を切る** — 問題発見と解決策開発を分離し、契約フェーズに対応付ける
2. **ペルソナ / CJM** — 誰の・どの体験を設計するかを固定する
3. **ユーザビリティテスト** — プロトタイプ段階で実ユーザーに検証する
4. **IA設計** — 組織化・ラベリング・ナビゲーションの3要素で構造を決める
5. **カードソート → 設計 → ツリーテスト** — 構造を生成し、構造を評価する
6. **OOUX + 用語対訳表** — UI構造とドメインモデルを同期させる

## Step 1: ダブルダイヤモンドで工程と契約を対応付ける

英国 Design Council のプロセスモデル。4段階を2つのひし形(発散→収束)として扱う:

| 段階 | ダイヤモンド | やること |
|---|---|---|
| Discover(発見) | 第1: 正しい問題を見つける | ユーザーリサーチ・インタビューで発散 |
| Define(定義) | 第1: 正しい問題を見つける | 問題定義・ペルソナ・CJMに収束 |
| Develop(展開) | 第2: 正しい解を作る | アイデア・プロトタイプで発散 |
| Deliver(提供) | 第2: 正しい解を作る | テストと改善で収束 |

- **見積・契約の切れ目はダイヤモンドの間(Define後)に置く**(→ なぜ: 問題定義まで=準委任、解決策開発=請負、という契約設計に対応させやすい。契約形態の最終判断は弁護士・法務に確認する)
- 第1ダイヤモンドを飛ばして Develop から始めない(→ なぜ: 間違った問題の正しい解は無価値)

### デザインスプリントを使う場合

5日間で「マップ→スケッチ→決定→プロトタイプ→ユーザーテスト」を回す短期集中手法(GV / Jake Knapp)。新規プロダクトの方向性検証に使う。

- 少人数の受託では5日フル拘束は重い。**3日圧縮版**か「スプリント設計+ファシリテーションのみ受注」が現実的
- **最終日のユーザーテストを省略しない**(→ なぜ: テストのないスプリントは単なるアイデア出しワークショップで、意味がない)

## Step 2: ペルソナを作る

1. **一次データを集める** — ユーザーインタビュー・アクセスログ・問い合わせ記録(→ なぜ: 実在データに基づくことがペルソナの生命線)
2. **1〜3体に絞り、プライマリ1体を明確にする**(→ なぜ: 全員向けの設計は誰向けでもなくなる)
3. **データなしで作った場合は必ず「仮説ペルソナ」と明記する** — シートの目立つ位置に「仮説(未検証)」と検証予定を書き、検証済みペルソナと扱いを分ける。これは省略不可のルール
4. 意思決定で主語に使う — 「田中さんはこれを使うか?」と問える状態にする(→ なぜ: 参照されないペルソナは作らないのと同じ)

- [ ] AIで生成したペルソナ草案は実データで裏取りしたか(→ なぜ: バイアスの再生産リスクがある)

## Step 3: カスタマージャーニーマップ(CJM)を作る

1. プライマリペルソナ1体を選ぶ
2. **行動・思考・感情・タッチポイント・課題**を時系列で1枚化する
3. 感情曲線を描き、**谷を改善機会として番号付きで抽出する**
4. As-Is体験版(現状)と To-Be体験版(導入後)を分けて描く

- 使い分け: 顧客の感情と体験の理解が目的なら CJM、裏側の業務・システムまで設計するならサービスブループリント → `delivery-core:business-service-design` 参照
- [ ] この CJM はどの意思決定で参照されるか答えられるか(→ なぜ: 壁に貼って終わりの成果物は工数の損失)

## Step 4: ユーザビリティテストを計画・実施する

**発注者担当者の意見をユーザーの声として扱わない。** テストは実ユーザーで行う。

### 計画テンプレート

| 項目 | 内容 |
|---|---|
| 目的 | 定性的な問題発見(統計的検証ではない — クライアントに事前説明する) |
| 被験者 | **5人 × 複数回**(→ なぜ: Nielsen の「5人で問題の85%が見つかる」が実務根拠。少人数×反復が正解) |
| リクルーティング | クライアント側の顧客接点(営業・CS)経由で確保。**段取りを契約時に握る**(→ なぜ: 被験者確保が最大のボトルネック) |
| タスクシナリオ | **5〜7個**。操作指示ではなく「状況+目的」で書く(例:「来月の出張の経費を申請してください」) |
| 実施方法 | 思考発話法 — 考えていることを声に出しながら操作してもらう |
| タイミング | ペーパープロトタイプ / Figma 段階で最低1回(→ なぜ: 作り終わってからでは直せない) |

### 課題の深刻度3分類

発見した課題は必ず3段階に分類し、**全部直そうとしない**:

1. **タスク完遂不能** — ユーザーが目的を達成できない。必ず直す
2. **迷い** — 達成はできるが時間がかかる・誤操作する。優先度を付けて直す
3. **違和感** — 完遂に影響しない引っかかり。直さない判断も記録する

### 合成ユーザーテストの位置づけ

LLMエージェントに操作させる合成ユーザーテストは、**実テスト前のスクリーニング限定**で使う。

- 明白なラベル問題・導線切れを事前に潰し、貴重な実ユーザーテストを本質的な問題に集中させる
- **実ユーザーテストの代替にしない**(→ なぜ: 合成ユーザーと実ユーザーの相関は未証明、が研究・実務の共通見解。2026年時点の目安・要確認)

## 予算・納期が足りないときの優先順位

リサーチの深さと予算が両立しないときは、この順で削る:

**実ユーザーテスト1回 > ペルソナの精緻化 > CJMの網羅性**

- 最後まで残すのは実ユーザーテスト1回(→ なぜ: 検証だけが仮説を事実に変える。生成物はAIで安く再作成できるが、検証の欠落は本番障害として返ってくる)
- ペルソナ・CJMはドラフト品質で止めてよい。テストを削ってドキュメントを磨くのは本末転倒

## Step 5: IAの3要素で構造を設計する

Rosenfeld & Morville『情報アーキテクチャ』(シロクマ本)の骨格をレビューチェックリストとして使う。
業務システムではメニュー構造・帳票の項目配置・マスタの分類体系が IA の対象になる。

### 組織化システム(分類の軸)

- [ ] 分類軸は **LATCH** のどれかを意識して選んだか — Location(位置) / Alphabet(五十音・アルファベット) / Time(時系列) / Category(カテゴリ) / Hierarchy(連続量・重要度)。組織化の軸はこの5つしかない
- [ ] 迷ったら「どの軸がユーザーのメンタルモデルに合うか」から決めたか
- [ ] 同一階層に分類軸が混在していないか(→ なぜ: 対象別と業務別が同じメニューに同居すると、ユーザーはどちらを辿るべきか毎回迷う)
- [ ] 利用頻度データで「よく使う2割を一等地に、残りは検索と整然とした階層に」と分けたか(→ なぜ: すべてを均等に整理すると主要ユースケースが埋もれる)

### ラベリングシステム(命名)

- [ ] ラベルはユーザーの語彙か — 検索ログ・問い合わせ文言が語彙の一次情報
- [ ] 組織図・社内用語をそのままラベルにしていないか(→ なぜ: ユーザーは部署を知らない)
- [ ] 同じ概念に画面ごとに違う名前が付いていないか → Step 8 の用語対訳表で防ぐ

### ナビゲーション/検索システム(移動手段)

- [ ] グローバル / ローカル / パンくず / 検索の方針を設計書に明文化したか
- [ ] 階層は「広く浅く」が原則になっているか(→ なぜ: 3クリック規則そのものは神話だが、迷いの少なさが正義)
- [ ] ユーザーが常に「今どこにいるか」を判別できるか

## Step 6: カードソート → 設計 → ツリーテスト

**生成と評価を分ける。** カードソートは構造を生成する手法、ツリーテストは構造を評価する手法。対にして使うのが定石。

1. **コンテンツインベントリ** — 既存コンテンツ・機能を棚卸しし、カードの元データを作る(既存システムのクロールはAIに任せる)
2. **カードソート** — コンテンツ名のカードをユーザーに分類してもらう。**5〜15人で十分な示唆が得られる**
   - **オープン**: 分類名もユーザーが作る — 新規構造の探索に使う
   - **クローズド**: 分類は所与、カードの振り分けだけ — 既存構造への追加時に使う
   - **ハイブリッド**: 所与の分類+ユーザーが分類を追加可 — 折衷
3. **構造設計** — ソート結果のクラスタからサイトストラクチャ図(業務システムならメニュー体系図)を作る
4. **ツリーテスト** — 提案した階層構造だけ(見た目なし)を提示し、「○○を探してください」タスクで**到達率・迷走率**を測る。リモートツールで実施可能
   - 合否判断基準(例: 到達率の下限)は実施前に人間が決めておく(→ なぜ: 結果を見てから基準を動かすと評価にならない)

## Step 7: OOUXでオブジェクトを抽出し、ドメインモデルと同期する

OOUX(Object-Oriented UX / Sophia Prater)は、画面やフローより先に「オブジェクト(名詞)」を抽出する方法論。
**DDDのエンティティ抽出とほぼ同型**であり、UI構造とドメインモデルを直結できる。エンジニアが IA を設計するとき最も相性が良い。

1. 要件・業務ヒアリング記録・CJMから**名詞(オブジェクト)を抽出する**(例: 案件、見積、請求、顧客)
2. 各オブジェクトの**属性・関係・アクション**を整理する
3. 画面はオブジェクトの表現として組み立てる — 一覧 / 詳細 / 作成・編集がオブジェクトごとに揃っているか確認する
4. **ドメインモデルと突き合わせる** — UIのオブジェクトとドメインのエンティティで名前・関係が食い違ったら、どちらかを直してから先に進む(→ なぜ: ズレを放置すると画面とコードで別の概念体系が育ち、保守で崩壊する)。突き合わせ先のドメインモデル・用語集・コンテキスト境界は `delivery-core:domain-modeling-strategic` が正本、エンティティ・集約などの実装パターンは `dev-core:best-practices` 参照

## Step 8: 用語対訳表を作り、運用する

同じ概念が「業務の呼び名・画面ラベル・コード名」で食い違うのを防ぐ台帳。**業務システムでは必ず作る。**

| 業務用語 | 画面ラベル | コード名(enum・カラム) | 備考 |
|---|---|---|---|
| 得意先 | 顧客 | customer | 営業部の呼称は「得意先」 |

運用ルール:

- **正本は `delivery-core:domain-modeling-strategic` のユビキタス言語用語集**。この対訳表は、正本に「画面ラベル」列を加えた**拡張ビュー**として同期させる(→ なぜ: 用語台帳を2つ持つと必ず片方が腐り、どちらが正しいかで揉めるため)
- **CIでの用語逸脱検出は `domain-modeling-strategic` Step 2 の仕組みに相乗りする**。同種の検出を二重に作らない
- **新しい概念の命名は、対訳表(と正本の用語集)に追加してから実装する** — 開発者が実装時に即興で命名することを禁じる(→ なぜ: 即興命名が「同じ概念に画面ごとに違う名前」の根本原因)
- コードレビューで対訳表からの逸脱を検出する。対訳表とコード(enum・カラム名)の突合はAIに任せる
- 画面ラベル側の語彙はユーザーの言葉に合わせ、コード名側はドメイン用語に合わせる。両者の橋渡しがこの表の役割

## AIがやること / 人間にしか決められないこと

| AIに任せてよい | 人間にしか決められない |
|---|---|
| インタビュー記録の書き起こし・発言のタグ付け・親和図の草案 | 実ユーザーテストの実施と結果の解釈(感情・文脈のニュアンス読解) |
| ペルソナ / CJM / タスクシナリオのドラフト生成 | 仮説ペルソナを「検証済み」に昇格させる判断(実データでの裏取り) |
| テストセッション録画のハイライト抽出 | **どの課題を直さないか**の判断 |
| 合成ユーザーによる実テスト前スクリーニング | 実ユーザーテストそのもの(合成で代替しない) |
| コンテンツインベントリの自動生成・既存システムのリバースIA | 分類軸の最終決定(何を目立たせたいかはビジネス戦略・ステークホルダーの意思) |
| カードソート結果のクラスタ分析 | 社内政治が絡むラベルの判断(部門名を出す/出さない) |
| ラベル案の複数生成・語彙一貫性チェック・対訳表とコードの突合 | ツリーテストの合否判断基準の設定 |

## 完了チェックリスト

作業を完了と宣言する前に確認する:

- [ ] プライマリペルソナが1体に定まり、未検証のものには「仮説」と明記されている
- [ ] プロトタイプ段階で実ユーザーテストを最低1回実施した(合成ユーザーのみで済ませていない)
- [ ] 発見課題が深刻度3分類で記録され、「直さない」判断も明文化されている
- [ ] IAの3要素(組織化・ラベリング・ナビゲーション)のチェックリストを通過した
- [ ] 新規構造ならカードソートの示唆とツリーテストの到達率・迷走率が記録されている
- [ ] 用語対訳表が存在し、画面ラベル・コード名と同期している
- [ ] 各成果物が「どの意思決定で参照されるか」に答えられる
