# Requirements Definition（要件定義）

**鉄則: 合意なき要件で実装に入らない。曖昧さは後工程の全トラブル（手戻り・追加費用・検収紛争）の根源である。**

要件定義とは「何を作るか・なぜ作るか・**何を作らないか**」を、発注者と受注者が同じ絵で合意する作業。
受託では見積と契約の前提そのものであり、工程遅延の最大要因は一貫して要件定義の不備である（IPA調査）。

## 分担線: AIがやること / 人間にしか決められないこと

このスキルを実行するエージェントは、着手前にこの線を確認し、人間側の判断を先回りして確定させないこと。

**AI（このスキルを実行するエージェント）がやること**:

- 議事録・インタビュー録・チャットログからの要求候補の抽出と構造化
- ユーザーストーリーのドラフト生成と INVEST 準拠チェック
- 要求文の曖昧語検出（EARS / ISO 29148 準拠の校閲）
- RDRAモデルのレイヤー間整合性（トレーサビリティ）の機械的検証
- 要件定義書・受入基準・スコープ定義書のドラフト作成と体裁統一
- 要件と実装のトレーサビリティ検証

**人間にしか決められないこと**:

- ステークホルダー間の利害調整と「本当の問題は何か」の見立て
- スコープを削る決断、顧客への「作らない提案」
- 要件の承認（顧客側の承認責任者による承認が必須。AIの整合性チェック通過は承認ではない）
- 契約形態・金額の決定（→ 自組織の見積・価格判断プロセスへ）
- ヒアリングの場で相手の表情・組織力学を読む部分

## Step 0: 進め方を合意する（2段階契約と不確実性コーン）

要件定義に着手する前に、要件定義そのものの契約的な位置づけを顧客と合意する。

1. **2段階契約を定石として提案する**: 要件定義だけを準委任で先行契約し、その成果物を根拠に開発フェーズの請負見積を出す。
   なぜ: 要件が固まる前の確定見積は受注者が不確実性を全額かぶる構造であり、外れれば赤字、当てにいけば過剰バッファで失注する。
2. **不確実性コーンで説明する**: 企画時点の見積は4倍〜1/4倍ブレ、要件定義後は1.5倍〜1/1.5倍に収束する（Steve McConnell の経験則）。
   「今の段階で確定金額は出せない。要件定義後なら責任ある見積が出せる」の根拠として顧客に提示する。
3. **顧客側の承認責任者を1人立てさせる**: 「全員合意」は誰も責任を取らない。要件の承認者（Accountable）を契約前に1名確定する。
4. 具体的な金額・単価の決定はこのスキルの範囲外。自組織の見積・価格判断プロセスに従う。

> 注: 契約形態（請負/準委任）の話は法的助言ではなく実務の型である。契約条項の最終判断は弁護士等の専門家に委ねる。

## Step 1: 要求を引き出す（ヒアリング）

1. **解決策ではなく問題まで一段掘る**: 顧客の「こういう画面が欲しい」は解決策の提案であり要求ではない。「その画面がないと何に困るのか」まで掘る。
   なぜ: 解決策をそのまま要件化すると、より安く同じ問題を解ける選択肢（既存機能・運用回避・SaaS）が検討から消える。
2. **顧客の発言をそのまま要件化しない**: 通常フローの裏にある業務の例外系（返品・キャンセル・締め後修正・権限の例外）を必ず質問する。
   なぜ: 要件漏れの典型は正常系ではなく例外系で起きる。
3. **議事録・録音から要求候補をAIで抽出する**: 打合せ後、会話ログから「新規要求・変更要求・宿題」を抽出し、要求候補一覧として構造化する（抽出運用の正本 → delivery-core:client-alignment Step 8）。
4. 議事録の型・24時間以内送付・サイレント確認の運用 → delivery-core:client-alignment 参照。

## Step 2: RDRA 2.0 で構造化する

要求候補を RDRA 2.0 の4レイヤーに配置し、レイヤー間を関連（リレーション）でつなぐ。
なぜ: 図の連鎖で「この機能は誰のどの業務のためか」を常にトレースでき、少ないダイアグラムで整合性を機械的に検証できる。

| レイヤー | 問い | 主なダイアグラム |
|---------|------|----------------|
| システム価値 | 誰のために・なぜ作るか | システムコンテキスト図・要求モデル |
| システム外部環境 | どの業務の中で使われるか | ビジネスユースケース・業務フロー |
| システム境界 | 人とシステムの接点は何か | ユースケース・画面・イベント |
| システム | 中で何を扱うか | 情報モデル・状態モデル・機能 |

**レイヤー間トレーサビリティのAI検証**（モデル更新のたびに実行する）:

- [ ] どの要求にもつながらないユースケースはないか（= 作る理由のない機能）
- [ ] どのユースケースからも参照されない情報・画面はないか（= 使われないデータ）
- [ ] どの業務フローにも登場しないアクターはないか（= 架空の利用者）
- [ ] 逆方向: 実現手段（ユースケース）を1つも持たない要求はないか（= 宙に浮いた要求）
- [ ] 用語が情報モデルと業務フローで同じ意味で使われているか（用語集と突き合わせる）

検証で見つけた孤立要素は、削除ではなくまず顧客への質問リストに載せる。
なぜ: 孤立は「不要」ではなく「ヒアリング漏れ」のシグナルであることが多い。

業務フロー・ドメインモデル自体の設計 → delivery-core:business-service-design 参照。

## Step 3: ユーザーストーリーマッピングでスコープを切る

1. **バックボーンを作る**: ユーザーの行動の流れ（時間軸）を左から右へ並べる。RDRAの業務フローがそのまま元ネタになる。
2. **バックボーンの下にストーリーを吊るす**: 各行動を実現する具体的なストーリーを、優先度順に縦に並べる。
3. **リリーススライスでMVPを切り出す**: 水平線を引き、1本目の線の上を「行動の流れが左から右まで一気通貫でつながる最小セット」にする。
   なぜ: 機能単位でなく体験単位で切ることで、「半分作ったが誰も使えない」リリースを防ぐ。
4. ストーリーは「会話の約束」であり仕様書ではない。詳細は受入基準（Step 4）と実装直前の会話で確定する。
5. 顧客とのワークショップ1〜2回（オンラインならホワイトボードツール）で全体像とフェーズ分けを合意する。

## Step 4: 受入基準を書く（Gherkin / INVEST）

**受入基準は三役を兼ねる: ①ストーリーの完了条件 ②検収条件 ③AI実装エージェントへの実装指示。**
なぜ: 受託では受入基準が検収条件に直結し契約上の意味を持つ。同時に、Gherkin で書いた受入基準はそのまま E2E テストのシナリオと実装エージェントへの指示になり、書く手間が三重に回収される。

1. **Gherkin（Given-When-Then）で書く**:

   ```gherkin
   シナリオ: 在庫切れ商品の注文
     Given 商品「A」の在庫が 0 である
     When 顧客が商品「A」を注文する
     Then 注文は受け付けられず、在庫切れの旨が表示される
   ```

2. **具体例で語る**: 「適切にエラー処理する」ではなく、代表値・境界値・例外の具体例をシナリオにする（Specification by Example）。
3. **INVEST でストーリー品質を判定する**: Independent（独立）/ Negotiable（交渉可能）/ Valuable（価値がある） / Estimable（見積可能）/ Small（小さい）/ Testable（テスト可能）。
   Testable でないストーリーは受入基準が書けていない証拠。
4. **受入基準のないストーリーをバックログに入れない**。検収時紛争の典型は受入基準の欠如である。
5. 受入基準からのテストケース展開・テスト設計 → dev-core:test-design 参照。バックログのIssue化 → dev-core:issue-driven-dev 参照。

## Step 5: 曖昧語を検出する（ISO 29148 / EARS）

要求文を確定する前に、必ず曖昧語チェックを通す。AIによる機械的校閲が最も効く工程。
なぜ: 「〜等」「柔軟に」の1語が、検収時に「言った/言わない」の紛争コストに化ける。

**EARS のテンプレ文型に当てはめて書き直す**:

| 型 | 文型 | 用途 |
|----|------|------|
| Ubiquitous | システムは常に〜する | 常時成立する性質 |
| Event-driven | When〈イベント〉のとき、システムは〜する | トリガー起点の動作 |
| State-driven | While〈状態〉の間、システムは〜する | 状態依存の動作 |
| Unwanted | If〈望まない状況〉ならば、システムは〜する | 異常系・防御 |
| Optional | Where〈機能がある場合〉、システムは〜する | 構成依存 |

**曖昧語検出チェックリスト**（検出したら具体化するか削除する）:

- [ ] 「〜等」「など」「その他」 → 列挙を確定するか「本リストに限る」と明記
- [ ] 「適切に」「柔軟に」「必要に応じて」 → 条件と動作を EARS 文型で特定
- [ ] 「原則として」 → 例外の条件と例外時の動作を明記
- [ ] 「可能な限り」「最大限」「なるべく」 → 検証可能な基準値に置換
- [ ] 「高速に」「使いやすい」「わかりやすい」 → 測定可能な指標に置換（詳細な非機能要件化は本スキルの範囲外。IPA非機能要求グレードを使う）
- [ ] 「想定される」「一般的な」 → 想定の中身を列挙して顧客に確認
- [ ] 1文に要求が2つ以上（「AしBする」） → 単一性: 1文1要求に分割
- [ ] 検証方法を書けない要求 → 検証可能性: 受入基準（Step 4）が書けるまで具体化

## Step 6: スコープを定義し、凍結境界を引く

1. **「やらないことリスト（Out of Scope）」を第1級成果物にする**: In リストと同じ粒度・同じ見た目で文書化し、顧客の承認対象に含める。
   なぜ: スコープ紛争の大半は Out of Scope の記載欠如に起因する。「書いていない = やらない」は顧客には通じない。
2. Out of Scope には「議論して外したもの」を優先的に載せる（例: 多言語対応、既存システムからのデータ移行、管理画面の権限細分化）。
   なぜ: 一度話題に出たものほど「やってくれると思っていた」が起きやすい。
3. **2層凍結を適用する**:
   - **凍結する層**: 業務要件・データモデル（情報モデル）。変更する場合は必ず変更管理プロセスを通す。
   - **凍結しない層**: 画面の詳細（レイアウト・文言・入力順）。スプリント内で顧客と確定する。
   なぜ: 全凍結は手戻りの温床、全可変は請負契約の破綻。変更コストが高い層（業務・データ）だけ凍結するのが実務解。
4. どの層に属するかの判定基準を要件定義書に明記する（「この変更は無償か有償か」の判定を後で揉めないため）。
5. 凍結後の変更管理（CR・影響分析・変更台帳） → delivery-core:pm-delivery 参照。

## Step 7: レビューして承認を取る

1. **IPA『ユーザのための要件定義ガイド 第2版』を二役で使う**:
   - 自分のレビューチェックリストの元ネタとして（収録された勘どころ集から案件に効く項目を抽出）
   - 顧客教育の副読本として（発注者視点で書かれた無料公式ガイドなので、そのまま顧客に渡せる）
2. **IPA『機能要件の合意形成ガイド』をレビュー観点集として使う**: 画面・帳票・バッチ等の分野別に「言ったのに伝わらない」を防ぐ観点が整理されている。要件定義書の分野別セルフレビューに適用する。
3. **図とモデル中心でレビューする**: 長文の要件定義書は読まれず、レビューが儀式化する。RDRAモデル図・ストーリーマップ・受入基準を直接レビュー対象にする。
4. **承認は Step 0 で決めた承認責任者から取る**: 議事録による決定記録・期限付き異議申し立ての運用 → delivery-core:client-alignment 参照。

## 成果物チェックリスト

要件定義フェーズの完了時に、以下が揃っていることを確認する。

- [ ] 要件定義書（業務要件・機能要件・非機能要件。非機能の詳細化は本スキル範囲外）
- [ ] RDRAモデル図一式（トレーサビリティのAI検証済み）
- [ ] ユーザーストーリーマップ（バックボーン + リリーススライス）
- [ ] 受入基準付きプロダクトバックログ（全ストーリー INVEST・Gherkin 準拠）
- [ ] スコープ定義書（In / Out。Out of Scope が顧客承認済み）
- [ ] 凍結境界の定義（業務要件・データモデル凍結、画面詳細はスプリント内確定）
- [ ] 用語集（→ ドメインモデリングの詳細は delivery-core:business-service-design 参照）
- [ ] 承認責任者による承認の記録
