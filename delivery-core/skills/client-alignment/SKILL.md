# Client Alignment（顧客合意形成・ステークホルダー管理）

**鉄則: 合意は口頭ではなく記録で成立させる。すべての口頭合意は24時間以内に書面化する。**

受託の失敗の多くは技術ではなく「聞いていた人と決める人が違った」「決めたはずのことが覆った」という合意形成の失敗である。本スキルはそれを構造的に予防する。

## Step 1: ステークホルダーを特定する（権力×関心グリッド）

キックオフ前に30分で初版を作る。なぜ: 反対勢力（現行業務の担当者など）の早期特定が炎上予防になるため。

1. 顧客側の登場人物を列挙する: 「金を出す人」「使う人」「決める人」「反対しうる人」
2. **影響力（権力）× 関心度**の2軸・4象限に配置し、関与方針を決める:

| 象限 | 関与方針 |
|------|---------|
| 影響力 高 × 関心 高 | 密に管理（定例・マイルストーンレビューに巻き込む） |
| 影響力 高 × 関心 低 | 満足させる（要点だけ短く報告し、不意打ちを作らない） |
| 影響力 低 × 関心 高 | 情報提供（詳細を共有し、味方にする） |
| 影響力 低 × 関心 低 | 監視（変化がないか見ておく） |

3. 結果はステークホルダー登録簿（役割/関心/影響力/コミュニケーション方針）として**内部資料**に残す。なぜ: 顧客に見せる前提で書くと本音の分析（反対勢力の特定など）ができないため。

## Step 2: RACI で承認者を確定する

各作業・各決定について Responsible（実行）/ Accountable（説明責任）/ Consulted（相談）/ Informed（報告）を割り当てる。

- **Accountable は常に1名**。「全員合意」は誰も責任を取らない状態と同義。
- 顧客側の承認責任者（要件・検収の Accountable）を**契約前に**確定させる。なぜ: 後から決めようとすると誰も引き受けず、検収時に紛争化するため。
- 大きめの個別決定（技術選定・スコープ変更）には DACI（Driver/Approver/Contributor/Informed）で都度「承認者は誰か」を明示してもよい。

**⚠️ 警戒シグナル: Accountable が決まらない顧客**

「A を1名決めてください」に対して曖昧な回答が続く顧客は、後工程で「決めたことが覆る」「検収者が現れない」リスクが高い。以下を実施する:

1. キックオフ資料に「承認責任者: ___」の空欄を作り、埋まるまでキックオフを完了扱いにしない
2. それでも決まらない場合は、リスクとして記録し、進め方（承認フロー・契約形態）の見直しをユーザー（人間）に提案する

## Step 3: キックオフを設計する（標準アジェンダ）

キックオフで決めるべき最重要事項は機能ではなく**「決め方」**である。なぜ: 顧客のレスポンス遅延は一人受託の最大の生産性キラーであり、プロセスで予防するしかないため。

標準アジェンダ（インセプションデッキをベースにテーラリング）:

1. **目的の確認** — 「我々はなぜここにいるのか」を発注側の言葉で語ってもらう
2. **スコープと「やらないことリスト」** — In だけでなく Out を明文化し、その場で承認者に読み上げて確認する。なぜ: スコープ紛争の大半は Out of Scope の記載欠如に起因するため（リストの中身の作り方 → delivery-core:requirements-definition 参照）
3. **トレードオフスライダー** — 品質/スコープ/期限/予算の優先順位を顧客に順位付けしてもらう。なぜ: 後で「全部最優先」と言われたときに立ち返る基準になるため
4. **体制と RACI** — Step 2 の結果を提示し、承認責任者を確定する
5. **決め方の合意**（最重要）:
   - 誰が承認するか（承認者の氏名）
   - 返答期限は何営業日か
   - 期限超過時の扱い（例: 「3営業日回答なしは現案承認とみなす」の事前合意）
   - ※期限超過ルールを契約条項に落とす場合は法的論点を含む。実務の型であり法的助言ではないため、最終判断は弁護士等の専門家に確認する
6. **コミュニケーション計画** — 定例頻度・使用ツール・エスカレーション経路
7. **発注者がやるべきこと一覧の手渡し** — Step 6（実質PM）参照

**決裁者（金を出す人・最終承認者）を必ずキックオフに同席させる。** なぜ: 窓口担当者とだけ合意すると、その上司・経営者の意向が後から降ってきて検収時に爆発するため。

## Step 4: 定例を運営する

- **報告は事前送付し、会議は意思決定と課題解消だけに使う。** なぜ: 定例が進捗報告の朗読会になると、決裁者が出席する価値を失い来なくなるため（週次報告の書き方 → delivery-core:pm-delivery 参照）
- アジェンダは「前回宿題の確認 → 要決定事項 → 課題解消 → リスク見直し5分」で固定する
- 決定は「決定権者1人+期限付きの異議申し立て」方式（consent-based）で進める。なぜ: 全員の合意を待つと進まず、独断で進めると覆るため
- 会議で出た「ついでにこれも」は必ずスコープ変更候補として記録する（変更要求の影響分析・変更管理台帳 → delivery-core:pm-delivery 参照）

## Step 5: 議事録を書く

**議事録は必ず自分側が書く。** なぜ: 相手の議事録は相手に有利に書かれるため。議事録は記録ではなく合意形成の装置である。

議事録の型（この順で書く）:

```
1. 決定事項        ← 冒頭に置く。受託では簡易的な契約変更履歴として機能する
2. 宿題            ← 全項目に「担当者 + 期限」を必ず付ける。担当なき宿題は消滅する
3. 議論メモ        ← 経緯。後から「なぜそう決めたか」を辿る材料
4. 次回予定        ← 日時・アジェンダ候補・持ち越し事項
```

運用ルール:

- **24時間以内に送付する**。なぜ: 記憶が新しいうちの異議は安価で、1週間後の異議は蒸し返しになるため
- **サイレント確認**を使う: 送付時に「◯月◯日までに異議なければ確定します」と期限を切る。なぜ: 承認会議を待つより速く、証跡も残るため
- 電話・立ち話・チャットでの口頭合意も、24時間以内に「先ほどの件、以下で認識しています」とメールで書面化する

## Step 6: Decision Log / ADR を運用する

すべての決定を1つの台帳（Decision Log）に集約する。なぜ: 顧客側の担当者交代は頻発イベントであり、台帳がないと新担当者が過去の決定を蒸し返すため。

- 1決定 = 1行〜1ページで記録する: **決定内容 / 日付 / 決定者 / 背景 / 却下した代替案**
- 「却下した代替案」を必ず書く。なぜ: 蒸し返しの大半は「別の案は検討したのか」であり、検討済みの証跡が最速の回答になるため
- 使い分け: **業務決定は Decision Log、技術決定は ADR**（Architecture Decision Record）。ADR の技術的な中身のレビュー → design-core:design-review 参照
- 議事録の「決定事項」欄から Decision Log への転記を運用に組み込む（AI に委任可。Step 8 参照）
- 顧客の担当者交代時は、Decision Log の主要決定を新担当者へのオンボーディング資料として使う

## Step 7: 実質PMとして立ち回る（顧客側PM不在への対処）

一人受託では顧客側にPM経験者がいないことが常態である。受注者でありながら顧客側のPM機能（会議設計・宿題管理・決裁の段取り）まで代行するのが標準の立ち回りであり、これは差別化要素でもある（PM込みの価値の値付けは自組織の見積・価格判断プロセスへ）。

実施事項:

1. **「発注者がやるべきこと一覧」を文書で渡す** — キックオフで手渡し、合意を取る:
   - 素材・データの提供（内容と期限）
   - 仕様質問への回答（返答期限のルール）
   - テストへの協力（受入テストの実施者と期間）
   - 意思決定（各マイルストーンで何を決めてもらうか）
   - 環境・アカウントの手配
2. **顧客タスクを自分の WBS に載せて進捗管理する**。なぜ: 「顧客待ちで遅延」の証跡が自分を守り、顧客も自分のボールを認識できるため（WBS・進捗管理の本体 → delivery-core:pm-delivery 参照）
3. **決裁者をマイルストーンレビューに同席させる**。キックオフだけでなく、以後の節目にも出てもらう約束を最初に取り付ける。なぜ: 決裁者が現物を定期的に見ていれば、最終検収での「聞いていない」が構造的に起きないため
4. 顧客教育には IPA『ユーザのための要件定義ガイド』（無料公開）を副読本としてそのまま渡せる
5. 同じ顧客で仕様前提が3回覆ったら、個別対応をやめて進め方（承認フロー）自体を見直す。なぜ: 3回の繰り返しはプロセス欠陥のシグナルであるため（Three Strikes の考え方の正本 → dev-core:debug 参照）

## Step 8: AI を活用する（文字起こしからの自動抽出）

打合せを文字起こしし、エージェントに以下を抽出させる運用を標準にする。なぜ: LLM は「会話の中に埋もれたスコープ変更」の検出器として極めて優秀であり、変更管理の取りこぼしを実質自動化できるため。

会議後に文字起こしから抽出するもの:

1. **決定事項** — 決定内容・決定者を議事録ドラフトの冒頭へ
2. **宿題** — 担当者・期限を補完し、欠けていれば「担当/期限未定」として明示
3. **スコープ変更候補** — 「これはスコープ変更では?」という新規要求・変更要求の指摘（影響分析と値札付けは → delivery-core:pm-delivery 参照）
4. **要決定事項の持ち越し** — 決まらなかった論点を次回アジェンダへ

その他 AI に委任できる定型運用:

- 議事録ドラフト生成（Step 5 の型に整形）
- Decision Log への自動追記
- 宿題の期限リマインド
- 定例アジェンダの自動生成（前回宿題 + 今週の進捗 + 要決定事項）
- ステークホルダーごとの説明資料の粒度調整（経営者向け1枚 / 現場向け詳細。資料の設計 → design-core:business-doc-design 参照）

## 分担線: AI がやること / 人間にしか決められないこと

このスキルを実行するエージェントは、以下の線を越えて勝手に判断しない。

**AI（このスキルを実行するエージェント）がやること:**

- 権力×関心グリッド・RACI・キックオフ資料・議事録・Decision Log の各ドラフト作成
- 文字起こしからの決定・宿題・スコープ変更候補の抽出と分類
- 宿題の期限管理・リマインド文面の作成、アジェンダの自動生成
- 「Accountable 未確定」「返答期限超過」「仕様前提の反転が3回目」などの警戒シグナルの検出と報告

**人間（ユーザー）にしか決められないこと:**

- 議事録・キックオフ資料・催促文面の**送付の実行**（対外送信は必ず人間が最終確認する）
- 決裁者との信頼関係の構築、組織内政治・抵抗勢力を読むこと、対立の調停
- 悪い知らせを伝えるタイミングと言い方
- 変更を受けるか否か・金額を付けるかの判断（金額は自組織の見積・価格判断プロセスへ）
- 承認フロー・契約形態の変更、案件を降りる判断

## 他スキルとの境界

- 週次報告・WBS・変更管理台帳・進捗の可視化 → delivery-core:pm-delivery
- やらないことリストの中身・スコープ定義・要求の引き出し → delivery-core:requirements-definition
- ADR の技術的内容のレビュー → design-core:design-review
- 顧客向け資料のドキュメント設計 → design-core:business-doc-design
- 検証・完了判定の証拠主義 → dev-core:verify
- 契約条項への落とし込み（返答期限・検収・変更管理条項）は法的論点を含む。本スキルは実務の型であり法的助言ではない。最終判断は弁護士等の専門家に委ねる
