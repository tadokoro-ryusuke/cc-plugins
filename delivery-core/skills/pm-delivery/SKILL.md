# PM Delivery — 受託案件のPM運営

**鉄則: 記録ゼロの変更を作らない。進捗をパーセントで語らない。**

PM・要件定義は受託の「利益とリスクの制御装置」である。要件の曖昧さと変更の無統制は、
見積の外れ・スコープクリープ・検収紛争として直接キャッシュフローを毀損する。
品質問題より先に経営問題になる——だから軽量でも**証跡が残るプロセス**を必ず敷く。

> 契約形態の選択・条項設計には法的論点が絡む。本スキルは法的助言ではなく実務の型であり、
> 最終判断は専門家（弁護士等）に委ねること。

## 分担線: AIがやること / 人間にしか決められないこと

このスキルを実行するエージェントは、着手前にこの線を確認し、右列の判断を勝手に代行しないこと。
なぜ: PM業務の定型作業は自動化できるが、約束（コミットメント）と交渉は発注者との信頼関係そのものだから。

| AI（このスキルの実行者）がやること | 人間にしか決められないこと |
|---|---|
| プロジェクト計画書のドラフト生成（キックオフ資料 → delivery-core:client-alignment） | 契約形態×開発方式の組み合わせの最終決定 |
| リスク登録簿の初版生成・プレモーテム（失敗を仮定した原因列挙） | リスクの受容判断（= 経営判断） |
| 議事録・チャットログからの変更要求候補の自動検出 | 変更を受けるか否か・値札を付けるかの判断 |
| CR影響分析のドラフト（コード規模・依存関係からの工数試算） | 顧客決裁者への説明と交渉 |
| 週次報告・SteCo資料の自動ドラフト、EVM指標の自動集計 | RAGステータスの最終判定（Amberを付ける勇気は判断そのもの） |
| 課題の期限超過アラート、遅延予兆の検出 | 悪い知らせを伝えるタイミングと言い方、リカバリープランの選択 |
| バックログ整理・チケット起票・定例アジェンダ生成 | 「この顧客にこの手法が回るか」という相手の成熟度評価 |

## Step 1: 開発方式を決める（契約形態 → 方式の順）

**契約形態を先に確認し、方式を後から選ぶこと。** 逆順は事故のもと。
なぜ: 請負で純アジャイルをやるとスコープ紛争になり、準委任で純ウォーターフォールをやると顧客が「成果が見えない」と不安になる。

### 決定マトリクス

| 契約形態 | 要件の安定度 | 推奨方式 |
|---|---|---|
| 請負（固定スコープ） | 高い（検収基準を先に固めたい） | ウォーターフォール。工程末レビューゲート、成果物定義を契約に直結させる |
| 請負 | 中程度 | **ハイブリッド（デフォルト解）**: 外枠（マイルストーン・検収物）を固定し、内側をスプリント/カンバンで回す |
| 準委任（継続開発） | 変化する | スクラム縮退運用: デイリーは省き、スプリントレビュー（= 顧客デモ）とレトロだけ残す |
| 準委任（保守・運用、複数案件並行） | 流動的 | カンバン: WIP制限とフローの可視化。全案件横断ボードとして運用する |

- 顧客の「アジャイルでお願いします」を鵜呑みにしないこと。請負契約のまま受けると無限変更の入口になる。
- 方式を選んだらセレモニーは**減らす方向に**テーラリングする。残すのは「顧客が動くものを見る場（レビュー）」と「決定を記録する場（定例）」の2つだけで十分。
- 全案件で進め方をバラバラにしない。なぜ: プロセスをテンプレ資産として育てることが小規模受託の競争力になる。

### 案件規模3段階のテーラリング

規模は期間・関係者数で判定する（金額の判断は自組織の見積・価格判断プロセスへ）。

| 規模 | 目安 | 敷くプロセス |
|---|---|---|
| S | 〜1ヶ月・窓口1名 | 計画書1ページ + カンバン + 週次報告のみ。CRは2段階制（Step 4）だけ守る |
| M | 1〜3ヶ月 | 計画書1〜3ページ + ハイブリッド + リスク登録簿・課題管理表 + 週次報告 |
| L | 3ヶ月超・関係部署が複数 | M に加えて SteCo 設置 + 簡易EVM + マイルストーントレンドチャート |

## Step 2: プロジェクト計画とバッファを設計する

1. **計画書は1〜3ページで書く**: 目的・スコープ・体制・マイルストーン・前提条件・除外事項。
   なぜ: 長文の計画書は誰も読まず、レビューが儀式化する。
2. **「やらないことリスト」（Out of Scope）を第1級市民にする**。
   なぜ: スコープ紛争の大半は Out of Scope の記載欠如に起因する。
3. **変更管理プロセスと承認者を計画書に定義する**（誰が・いつ・どう承認するか。Step 4 参照）。
4. 要件定義の進め方・成果物 → delivery-core:requirements-definition 参照。
5. キックオフの設計・決裁者の巻き込み → delivery-core:client-alignment 参照。

### CCPM流バッファ管理

1. **各タスクの見積を50%確率値（成功率五分五分の楽観値）まで削る**。
2. 削った安全余裕を**プロジェクトバッファとして末尾に集約**し、計画書・見積根拠書に
   「実装 X週 + リスク予備 Y週」と**明示**する。
   なぜ: タスクごとに埋めたサバはパーキンソンの法則（与えた時間を使い切る）と学生症候群（締切直前まで着手しない）で必ず消費される。明示バッファなら消化状況を顧客と共有でき、信頼も得られる。
3. **バッファ消費率を進捗率と併せて毎週監視する**。
4. **バッファ消費率が50%を超えたら顧客へ早期警報を出す**（週次報告の RAG を Amber に落とし、打ち手と依頼をセットで提示する）。
   なぜ: 手遅れになってからの Red が最も信頼を毀損する。
5. 工数から金額への換算・価格提示は本スキルの範囲外。自組織の見積・価格判断プロセスへ送ること。

## Step 3: リスクと課題を分けて管理する

**リスク（まだ起きていない）・課題（起きた）・変更（約束の変更）を1つの表に混ぜないこと。**
なぜ: 混在した表は全部塩漬けになる。3つは統制プロセスが異なる。

### リスク登録簿

- 列: リスク / 発生確率 / 影響度 / 対応策（回避・転嫁・軽減・受容）/ オーナー / **トリガー（発動条件）**。
- キックオフ前に30分で初版を作り、定例アジェンダに「リスク見直し5分」を固定で入れて月1回見直す。
  なぜ: 作って終わりが典型的失敗。トリガーを書いておかないと発動に気づけない。
- 「転嫁」は契約条項（責任上限・免責）と保険で実装する。条項の中身は専門家と自組織の契約実務へ。

### 課題管理表（顧客と共有する単一の表）

- **全課題に「ボール保持者」と「期限」を必ず付ける**。どちらか欠けた課題は登録しない。
- **顧客側のタスク（素材提供・仕様回答・環境手配・テスト協力）も必ず載せる**。
  なぜ: 「顧客待ちで遅延」の証跡が自分を守る。顧客タスクを載せない進捗表は遅延責任を曖昧にする。
- 期限超過はエージェントに自動検出させ、定例前にアラートを出させる。
- 同種の問題が同じ顧客で3回起きたら、個別対応をやめてプロセス自体（承認フロー・進め方）を見直す
  （Three Strikes の考え方。調査手順の正本は → dev-core:debug 参照）。

## Step 4: 変更管理 — 断らず、値札を付ける

**変更要求への返し方の型: 「できます。ただし影響はこうです」。**
なぜ: 「NO」は関係を壊し、無言の「YES」は自分の利益を壊す。判断を顧客に返すことで敵対せずスコープを守れる。

1. **ベースラインを固定する**: 合意済みスコープ（要件定義書 + Out of Scope リスト）を変更判定の基準にする。
2. **CR（変更要求書）の様式**: 内容 / 理由 / 影響分析（スコープ・工数・費用・納期）/ 承認欄。
   承認者（顧客側の決裁者）は**最初に固定**しておく。
   なぜ: 窓口担当者と現場合意した変更が決裁者に伝わっておらず、検収時に爆発するのが定番の事故。
3. **2段階制で運用する**:
   - 軽微な変更（目安: 2時間以内）→ 都度CRは切らず、**月次でまとめて記録・報告**する。
   - それ以上 → 都度CRを起票し、承認を得てから着手する。
   - **記録ゼロの変更は絶対に作らない**。無償対応も「無償と決めた」という決定として台帳に残す。
   なぜ: 全変更に書面CRを要求すると小規模顧客には窮屈すぎ、運用が崩壊する。2段階制が統制と軽快さの実務解。
4. **口頭・電話・チャットでの合意は24時間以内に書面化する**（後追いメールで「この理解で進めます」）。
   なぜ: 「言った言わない」は書面化の遅れから生まれる。
5. **返し方の定型**: 「対応できます。影響は +X工数 / 納期 +Y週です。代わりに機能Zを外せば現行の枠内に収まります」
   と、**選択肢 + 影響**で返す。金額の算定・提示は自組織の見積・価格判断プロセスに送り、勝手に値付けしない。
6. 打合せ記録からの新規要求・変更要求・宿題の抽出（抽出運用の正本 → delivery-core:client-alignment Step 8）。
   なぜ: スコープクリープの主犯は「会話に埋もれた小さな変更の無償対応の積み重ね」であり、記録に残さない限り防げない。

## Step 5: 進捗管理 — 2値管理と簡易EVM

1. **タスクは1〜3日粒度に分解し、完了/未完了の2値でしか報告しない。パーセント報告は禁止**。
   なぜ: 「進捗90%が2週続く」事故はパーセント報告が生む。2値なら誤魔化しようがない。
2. **完了の定義は「検証済み・デモ可能」に固定する**。デモできない進捗は進捗と数えない。
   証拠ベースの完了判定の正本 → dev-core:verify 参照。
3. **簡易EVMを回す**（L規模。M規模でも遅延の兆候があれば導入）:
   - EV = 完了タスクの見積工数合計、PV = 計画上の完了予定工数、AC = 実投入工数。
   - SPI = EV/PV（スケジュール効率）、CPI = EV/AC（コスト効率）。
   - **CPI < 0.9 が2週連続したら赤字警報**。原因分析と打ち手を週次報告に載せる。
   なぜ: フルEVMは計測負荷が重い。「完了タスクの見積工数 = EV」の簡易版で精度の8割は出る。
4. 顧客向けのチャートは**バーンアップ**を優先する（バーンダウンよりスコープ増加が見える）。
   なぜ: 「要望追加で線が上がった」を視覚で説明でき、CRの影響説明に直結する。
5. **90%完成症候群への対策**: 結合・例外系・環境差異・データ移行を「最後の仕上げ」にせず、
   最初からWBSに独立タスクとして計上する。
   なぜ: 最後の10%に工数の半分が潜む。タスク化されていない作業は見積にも進捗にも現れない。
6. テスト計画・受入テストの設計 → dev-core:test-design 参照。リリース手順 → dev-core:cicd-release-design 参照。

## Step 6: 報告 — 週次報告とSteCo

### 週次報告（全案件共通・1ページ固定）

```
1. 全体ステータス: RAG（Green / Amber / Red）+ バッファ消費率
2. 今週やったこと（完了タスクのみ。着手中は書かない）
3. 来週やること
4. 課題・リスク（事実 → 解釈 → 打ち手 → 依頼 の順で書く）
5. 顧客への依頼事項（期限付き）
```

- **「事実→解釈→打ち手→依頼」の順を崩さない**。
  例: 「2週遅れ（事実）。原因は仕様回答待ち（解釈）。並行して画面Bに着手済み（打ち手）。◯◯の回答を金曜までに（依頼）」。
  なぜ: 「遅れています」で終わる報告は無価値。依頼まで書いて初めて顧客が動ける。
- **Amber を恐れず早めに使う**。いきなり Red が最悪。順調な時こそ省略せず淡々と定期報告する。
  なぜ: 問題が起きてから急に報告が密になるパターンが最も不信を生む。
- 報告ドラフトはエージェントに自動生成させる: コミット履歴・チケット・作業ログから
  1〜5 を組み立てさせ、**人間は RAG 判定と打ち手の決定だけを行う**。
  なぜ: 報告資料作りに週の半日を使うのは本業の圧迫。自動化で報告品質と頻度を両立する。

### ステアリングコミッティ（SteCo）

- 3ヶ月超・関係部署が複数の案件では、小規模でも月次〜隔月のSteCo設置を提案する。
  なぜ: 決裁者を定期的に拘束する仕組みそのものに価値がある（決裁遅延の予防）。
- SteCo は進捗報告の朗読会にしない。**「要決定事項の決裁」の場**として設計する。資料の型:

```
1. 全体サマリ（RAG + マイルストーン達成状況）
2. マイルストーントレンドチャート（予測日の推移。後退の早期開示）
3. バッファ消費・予算消化状況
4. 要決定事項（選択肢 + 各選択肢の影響 + 推奨案 + 決めてほしい期限）
```

- 資料は事前送付し、会議は意思決定と課題解消だけに使う。議事録・Decision Log の運用 → delivery-core:client-alignment 参照。

## 実質PMの立ち回り（発注側PM不在の案件）

発注側に PM 経験者がいないことは受託では常態である。受注者でありながら顧客側のPM機能まで
代行する「実質PM」を、負担ではなく差別化要素として設計的にやること。

1. **「発注者がやるべきこと一覧」を文書にしてキックオフで渡す**: 素材提供・仕様回答・環境手配・
   テスト協力・意思決定の期限。なぜ: 顧客は自分の作業が納期の前提だと知らないことが多い。
2. **顧客側のタスクも自分のWBS・課題管理表に載せて進捗管理する**（Step 3 参照）。
3. **キックオフで決めるべき最重要事項は機能ではなく「決め方」**: 承認責任者を1人に固定する
   （「全員合意」は誰も責任を取らない）、返答期限（例: 3営業日）、期限超過時の扱い
   （例: 回答なしは現案承認とみなす、の事前合意）。
   なぜ: 顧客のレスポンス遅延は小規模受託の最大の生産性キラーであり、契約とプロセスの両方で予防する。
4. 顧客教育には IPA『ユーザのための要件定義ガイド』等の公式無料ガイドを副読本としてそのまま渡す。
5. 会議設計・議事録・サイレント確認・Decision Log の詳細 → delivery-core:client-alignment 参照。

## 他スキルとの境界（重複させない）

| 話題 | 送り先 |
|---|---|
| 要件定義の手法・成果物（RDRA・ストーリーマッピング・受入基準） | delivery-core:requirements-definition |
| キックオフ・議事録・Decision Log・ステークホルダー管理 | delivery-core:client-alignment |
| 業務設計・サービス設計・システム化範囲の線引き | delivery-core:business-service-design |
| テスト計画・テスト設計 | dev-core:test-design |
| CI/CD・リリース設計 | dev-core:cicd-release-design |
| Issue駆動の開発運営 | dev-core:issue-driven-dev |
| 実装の完了判定・検証（Iron Law） | dev-core:verify |
| 開発原則・TDD・設計 | dev-core:best-practices |
| 障害・バグの原因調査 | dev-core:debug |
| 工数の金額換算・価格提示・値引き対応 | 自組織の見積・価格判断プロセス |
| 契約条項の設計・レビュー | 専門家（弁護士等）+ 自組織の契約実務 |
