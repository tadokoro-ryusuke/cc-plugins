# Domain Modeling — Strategic Design（ドメイン設計・戦略的DDD）

**鉄則: 境界を決めてから中身を作る。コンテキスト境界はモジュール構成・チーム分割・マイクロサービス分割すべての親であり、上流で最も後戻りコストが高い判断である。**

ドメイン設計とは、業務とサービスの理解を**ソフトウェアの構造に写し取れる概念モデル**へ変換する作業。
要件定義後半〜基本設計の入口で行い、「どこに境界を引くか」「何を作り込み、何を汎用品で済ませるか」を決める。

- 戦術的設計（エンティティ・集約・リポジトリ等の実装パターン）→ dev-core:best-practices 参照（正本）
- 要件定義プロセスそのもの → delivery-core:requirements-definition 参照
- サービス設計・事業仮説（何を作るべきかの手前）→ delivery-core:business-service-design 参照
- 情報設計・OOUX（UI構造との接続）→ delivery-core:ux-information-design 参照
- アーキテクチャスタイルの選定（境界を決めた後のデプロイ単位の議論）→ dev-core:system-architecture-selection 参照

## 分担線: AIがやること / 人間にしか決められないこと

このスキルを実行するエージェントは、着手前にこの線を確認し、人間側の判断を先回りして確定させないこと。

**AI（このスキルを実行するエージェント）がやること**:

- ヒアリング記録・議事録・既存ドキュメントからのドメインイベント候補・用語集ドラフトの抽出
- イベントストーミング成果（Miroエクスポート等）の構造化と集約候補の整理
- コンテキスト境界案の複数生成と、根拠（用語の意味変化・データ所有・変更理由の違い）の比較表作成
- Bounded Context Canvas・コンテキストマップのドラフト作成と成果物間の整合チェック
- コードとユビキタス言語の乖離検出（命名逸脱のCIチェック設計・実行）
- ドメイン設計成果物の AGENTS.md / CLAUDE.md への変換（Step 6）

**人間にしか決められないこと**:

- **何がコアドメインか（= 事業の競争優位はどこか）の判断** — 技術判断ではなく経営判断であり、クライアント経営層との対話でしか決まらない
- ホットスポット（部門間で定義が食い違う概念）の政治的解決
- 組織の境界・チーム編成に踏み込む境界変更の意思決定（コンウェイの法則により組織変更を伴う）
- Buy vs Build の最終決定と、それに伴う予算・保守体制の判断（→ 自組織の見積・価格判断プロセスへ）

## Step 0: 適用レベルを決める

案件規模に応じて装備を選ぶ。**DDDフル装備は要件ではない**。

1. **小規模案件でも必ず作る最小セット**: サブドメイン分類表（Step 3）+ ユビキタス言語用語集（Step 2）。
   なぜ: この2つだけで「どこに投資するか」「同じ言葉を使えているか」が担保され、費用対効果が最も高い。
2. 複数部門・複数システム・既存レガシーが絡む案件では、イベントストーミング（Step 1）とコンテキストマップ（Step 5）まで実施する。
   なぜ: 境界の引き間違いによる後戻りコストが、ワークショップ工数を大きく上回るため。
3. **マイクロサービスにするかどうかは、この時点では議論しない**。まず境界を見つける。
   なぜ: デプロイ単位の議論は境界が見えてからで遅くない（Step 5 の失敗集参照）。

## Step 1: イベントストーミングで全体像を得る

イベントストーミング（Alberto Brandolini）は、業務フロー・ユビキタス言語・コンテキスト境界の候補を**1回のワークショップで同時に得られる**上流ヒアリングの主兵器。3レベルを段階的に実施する。

### 実施手順（3レベル）

1. **Big Picture（全体像、2〜4時間）**:
   - 壁または Miro にドメインイベント（**オレンジ付箋・過去形**。例:「注文が確定した」）を時系列に貼り出す
   - 発注側の業務キーパーソンを必ず巻き込む。なぜ: 開発者だけでやると想像のモデルになる
   - 定義が食い違う・議論が紛糾する箇所は**ホットスポット**として印を付けて先へ進む。なぜ: その場で解決しようとすると全体像に到達できない。ホットスポットこそ境界候補と政治的論点の一覧になる
2. **Process Modeling**: 重要プロセスを選び、イベントの間にコマンド（誰が何をした結果か）・アクター・ポリシー・外部システムを重ねる
3. **Software Design**: 集約候補（コマンドとイベントが集まる名詞）を特定し、コンテキスト境界の仮説を線で引く

### 成果物

- ドメインイベント時系列、集約候補、ホットスポット一覧
- ここで得た用語→ Step 2 の用語集へ、境界仮説→ Step 4/5 へ接続する

### リモート版の段取り（目安・要確認）

- ツールは Miro 等の無限キャンバス。付箋の色凡例（イベント=オレンジ、コマンド=青、アクター=黄、外部システム=ピンク、ホットスポット=赤系）を**事前にボードへ用意**しておく
- 対面の半日を、90〜120分 × 2〜3セッションに分割する（目安）。なぜ: リモートは疲労が早く、休憩なしでは後半の発言が止まる
- ファシリテーターとは別に、付箋の整列・重複整理を行うボード係を置くと進行が安定する（目安）
- セッション間に AI で中間整理（イベントの重複統合・時系列の穴の質問リスト生成）を回すと、次セッションの立ち上がりが速い

## Step 2: ユビキタス言語の用語集を作り、腐らせない

ユビキタス言語は「コードと会話と図で同じ言葉を使う」ことが本体で、用語集はその副産物。
**用語の意味が変わる場所がコンテキスト境界**という発見的な使い方が実務の要（例: 営業の「顧客」と請求の「顧客」は属性も振る舞いも違う）。

### 用語集テンプレート

| 用語 | 英語名(コード上の名前) | 定義 | コンテキスト | 同義語(許容) | 禁止語 |
|---|---|---|---|---|---|
| 受注 | Order | 顧客の購入意思が確定した取引単位 | 販売 | 注文 | オーダー、案件 |

- 1行1概念。同じ語が別コンテキストで別の意味を持つなら**行を分ける**。なぜ: 「全社で1つの統一モデル」を目指さないのが戦略的DDDの中核的な割り切り
- 英語名の列を必ず埋める。なぜ: コードとの乖離検出（下記）はこの列が基準になる

### コードとの乖離をCIで検出する運用

用語集は初回納品後に更新されず腐るのが最頻の失敗。**コードレビューと CI で用語逸脱を検出する運用まで含めて設計する**。

1. 用語集を機械可読な場所に置く（例: `docs/glossary.md` の表、または YAML）。正本は1箇所
2. 禁止語リストから検出スクリプトを生成し、CI に組み込む（例: 新規差分の識別子・クラス名に禁止語が含まれたら fail）。なぜ: 人間のレビューだけでは同じ概念に画面ごとに違う名前が付くのを防げない
3. PR テンプレートに「新しいドメイン用語を導入したか? したなら用語集を更新したか?」のチェック項目を入れる
4. 用語集の変更はドメインエキスパート（顧客側キーパーソン）の確認を経る。なぜ: 開発側だけで用語を進化させると会話との同期が切れる

実装後の検証フロー全体 → dev-core:verify 参照。

## Step 3: サブドメインを分類し、投資方針に直結させる

**分担**: 提案前アセスメント段階の粗い分類（Buy vs Build の一次判断）→ delivery-core:business-service-design（Step 6）が担当。
本スキルは**要件定義後の検証・詳細化と Bounded Context Canvas（Step 4）への接続**を担当し、**判定質問と投資方針表の正本は本スキル**とする。
なぜ: 同じ分類を2回やるのではなく、粗い線引きで提案を成立させ、境界設計の段階で根拠を検証して確定させる二段構えにするため。

サブドメイン分類は**そのまま Buy vs Build 判断の入力になる**。分類せずに見積・提案に入らない。

### 判定質問（上から順に問う）

1. 「この能力が競合より優れていると、顧客のビジネスは選ばれるようになるか?」— Yes → **コアドメイン**
2. 「無いと業務が回らないが、優れていても差別化にはならないか?」— Yes → **支援サブドメイン**
3. 「市販の SaaS / OSS でそのまま代替できるか?（認証・決済・通知・会計等）」— Yes → **汎用サブドメイン**
4. 迷ったら「これを丸ごと買ってきたら競争力は落ちるか?」— 落ちないなら、コアではない

### 投資方針への直結

| 分類 | 投資方針 | なぜ |
|---|---|---|
| コア | 作り込む（Build）。最良のリソースを投入 | 競争優位の源泉。ここが痩せるとプロジェクトの存在意義が消える |
| 支援 | 最小限の Build またはローコード | 必要だが差別化しない。凝るほど損 |
| 汎用 | 買ってくる（SaaS / OSS） | 認証・決済・メール送信等をスクラッチする提案は原則として職務怠慢 |

- 分類の最終決定は人間（経営判断）。AI は候補分類と根拠の提示まで（分担線参照）
- ここでの分類は Bounded Context Canvas（Step 4）の Strategic Classification 欄にそのまま記入する

## Step 4: Bounded Context Canvas で境界を定義する

境界づけられたコンテキストごとに、ddd-crew の **Bounded Context Canvas**（GitHub で無料公開）を1枚ずつ埋める。境界内の一貫性だけを守るのが目的で、境界の「合意された定義書」として機能する。

埋める主な欄（テンプレート準拠）:

1. **Name / Description**: コンテキスト名と存在目的を1〜2文で
2. **Strategic Classification**: コア/支援/汎用（Step 3 の結果を転記）
3. **Ubiquitous Language**: このコンテキスト内の主要用語（Step 2 の用語集から該当行を抜粋）
4. **Business Decisions**: このコンテキストが所有する業務ルール・ポリシー
5. **Inbound / Outbound Communication**: 誰から何を受け、誰へ何を渡すか（→ Step 5 のコンテキストマップの素材になる)
6. **Open Questions**: 未解決のホットスポットを残す。なぜ: 未解決を「決まったこと」に見せない誠実さが後の紛争を防ぐ

書けない欄があるコンテキストは境界の理解が浅いシグナル。イベントストーミングの該当範囲に戻る。

## Step 5: コンテキストマップを描く — 現状を先に、理想を後に

### 順序の原則

1. **現状マップを先に描く**: 組織・既存システムの実態としての境界と力関係をそのまま写す
2. **理想マップを後に描く**: 現状とのギャップを移行課題として列挙する
3. なぜ: **コンウェイの法則により、組織の境界を無視したコンテキスト境界は維持できない**。理想を先に描くと願望ベースの絵になり、実装時に組織の力学へ引き戻される。境界とチーム境界の整合は Team Topologies との統合が実務トレンド（2024年以降）

### 関係パターンの選択基準

コンテキスト間の線には必ず関係パターンを書く。なぜ: 線の意味（力関係と変換責任）を曖昧にすると、実装時に無自覚な結合が生まれる。

| パターン | 選ぶ場面 |
|---|---|
| Partnership | 両チームが対等で、同時にリリースを揃えられる密な協働関係にあるとき |
| Shared Kernel | モデルの一部を意図的に共有し、変更調整コストを両者が払う合意があるとき（**無自覚な DB 共有は該当しない**。失敗集参照） |
| Customer/Supplier | 上流が下流の要求を計画に入れてくれる交渉力があるとき |
| Conformist | 上流に交渉力がなく、変換コストも払えないとき（上流モデルをそのまま受け入れる） |
| **Anticorruption Layer (ACL)** | **クライアントの既存レガシー・外部 SaaS との境界には必ず検討する**（下記） |
| Open Host Service / Published Language | 多数の下流に同じ形で公開するとき（API 公開側の定石） |
| Separate Ways | 統合コスト > 統合価値のとき。つながないのも設計判断 |

### ACL を置く判断（受託で最重要）

- レガシー / 外部 SaaS のモデルを**自分の設計に汚染させない防波堤**として、境界面に変換層を置く
- 判断基準: 相手のモデルが自分のユビキタス言語と食い違い、かつ相手を変えられないなら ACL。なぜ: モデルの純粋さと既存システムの現実が両立しないときは、**境界の内側の純粋さを守り、妥協を境界面（変換層）に局所化する**のが定石。「どこでも少しずつ妥協」が最悪手
- 境界面の API・契約の具体設計 → dev-core:interface-contract-design 参照

## よくある失敗（着手前チェックリスト）

- [ ] **最初からマイクロサービス分割の議論をしていないか** — モジュラモノリスで境界だけ守るのが先。デプロイ単位の議論は dev-core:system-architecture-selection へ
- [ ] **DB スキーマ共有のまま境界を引いたつもりになっていないか** — Shared Kernel の無自覚な乱用。データを共有した瞬間、境界は絵に描いた線になる
- [ ] **汎用サブドメイン（認証等）を作り込んで、コアドメインが痩せていないか** — 工数の配分表をサブドメイン分類表と突き合わせて検証する
- [ ] **用語集が初回納品後に更新されず腐る前提になっていないか** — CI 検出と PR チェック（Step 2）まで含めて初めて設計と言える
- [ ] **開発者だけでイベントストーミングをやっていないか** — 業務キーパーソン不在の成果は想像のモデル
- [ ] **理想マップを現状より先に描いていないか** — コンウェイの法則に引き戻される（Step 5）

## Step 6: 成果物を AI エージェントのコンテキスト素材へ変換する

AI エージェントに実装を任せる時代ほど、境界とユビキタス言語の明文化は「AI へのコンテキスト供給」として価値が上がる。ドメイン設計成果物はそのまま AGENTS.md / CLAUDE.md の素材になる。

1. **用語集**: 正本ファイル（Step 2）をリポジトリに置き、AGENTS.md から参照させる。「コード上の命名はこの用語集に従う。禁止語を使わない」と明記する
2. **コンテキスト境界**: 境界とディレクトリ/モジュール構成の対応表を書く（例: `contexts/sales/` = 販売コンテキスト）。「コンテキストをまたぐ参照は公開インターフェース経由のみ」を規約化する
3. **サブドメイン分類**: モジュールごとの品質バー・変更方針として書く（コア = テスト厚め・レビュー必須、汎用 = 既製品優先・独自実装を提案しない）
4. **ACL の位置**: 「この外部システムのモデル・命名をコアに持ち込まない。変換は `adapters/` で行う」と禁止事項として書く
5. **ホットスポット・未決事項**: 「未決。勝手に確定させず人間に確認する」と明記する。なぜ: エージェントは空欄を埋めたがるため、未決の明示がない設計書は勝手に補完される
6. 変換後、AGENTS.md / CLAUDE.md と成果物正本の**二重管理をしない**。知識本体は成果物側に置き、エージェント設定はポインタと規約のみ持つ
